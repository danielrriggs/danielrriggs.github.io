 Welcome back, and in this lesson I want to talk about one of the newer logging services available within AWS, and that's AWS X-Ray. Now, X-Ray is a distributed tracing application. What that means is that it's designed to track sessions through an application. Now, an application might be a traditional monolithic application, but it could be a serverless or distributed application, which might include things like API Gateway, Lambda, Elastic Beanstalk, load balancers, and even downstream services such as DynamoDB. Now, X-Ray takes data from all of these separate services and gives you one single overview of session flow throughout your application. This is what distributed tracing does, and that's the service provided by AWS X-Ray. Now, I want to start by covering the fundamental concepts of the product before showing you... the architecture visually. So, when a user first connects to an application which has been configured for X-Ray, a tracing ID is generated and inserted into a tracing header. It's using this header that the request is tracked through all of the supported services that form part of your application. Supported services send data into the X-Ray service using what are known as segments. Now, these segments you can think of as... one single block of data sent into X-Ray. They detail the hostname, IP, or alias. They detail info about the request, the method, the client address, the path, and the user agent, so which browser is being used to connect. They detail the response, so the work done, including the start and end times and any issues. So all of this data is grouped together in one segment, and that data is sent into X-Ray, and X-Ray collates all of the individual segments to provide an end-to-end flow for a specific request. Now, segments can contain sub-segments if that level of granularity is required. So one operation could show details of various HTTP endpoints which are called, or calls to different database services that are part of that one single component of the application. Now, X-Ray uses all of the data that your application needs, and all of the data that your application sends into the service to generate what's known as a service graph. So this is an overall structure of how your application components fit together. So each AWS resource that sends data into the X-Ray service is logged as a service within the graph, and then connections between those services are built up to show how those components work together to service requests. The X-Ray console uses this service graph to show how those components work together to service requests. The X-Ray console uses this service graph and the data that it collects to generate a service map, which is a visual representation of this graph. Now, let's look at what this might look like for the CataGram serverless application. So let's say that we have a serverless version of the CataGram application which we've enabled for X-Ray. So our users connect to an API gateway stage, and the first thing which happens, because this is the first stage, a tracing header is generated. Which identifies that one specific request. And a segment is generated, which remember is this unit of data, which details this interaction. And this allows X-Ray to show the average latency of this part of the application, together with the frequency that this particular component is being accessed. So we have this tracing header, and each time this tracing header is logged as flowing through one of the components of the application, it's known to be part of the application. And it's known to be part of this same specific request. And so we can trace the flow throughout our application. So because the tracing header is unique, each of the flows through our application can also be tracked in a unique way. So through each supported component, in this case Lambda and DynamoDB, and for each of these components of the application, because we have this tracing header, we're able to track the performance of this particular session throughout the application. So the service map shows the flow through a distributed application. This includes response time, requests, and any particular errors or issues. Now remember, while this might seem simple, it's worth keeping in mind that this distributed application consists of many different and separate products. And so the value that the X-Ray service brings is to allow this distributed tracing. So we can get access to the information for what we see as the X-Ray service. And of course, that means that we can target one particular application even though it is built from lots of separate components. Now the way that X-Ray is provided with this data is done in a number of different ways. So if your application uses any EC2 resources, then there is an X-Ray agent installed on those EC2 instances. If you use the elastic container service, then an agent is installed as part of any tasks running within that service. For Lambda, you just need to enable X-Ray daisy collection within a Lambda function, for Beanstalk the agent is pre-installed, for API Gateway then X-Ray data collection is enabled on a per stage basis and you can also configure services such as SNS or SQS to send data into X-Ray. Now the thing about all of these different services is that as normal with any AWS services which interact with other services on your behalf, you need to provide permissions to allow them to do this and X-Ray is no different. You need to grant permissions using IAM. So in many cases for example with Lambda this is using an IAM role so you need to ensure that the Lambda execution role is provided with the permissions required to send data into the X-Ray service.
