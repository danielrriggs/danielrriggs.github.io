So let's jump in and get started. Now I've covered AWS IoT elsewhere in the course. It's a set of services designed to allow IoT devices to interact with AWS. AWS Greengrass is an extension of those services which move those services closer to the edge. Instead of IoT devices running at the edge and interacting with AWS services over slow and unreliable connections, Greengrass allows some services including compute, messaging, data management, sync, and even some machine learning capabilities. To run from edge devices. So devices with the Greengrass core software can locally run Lambda functions or containers, which means compute can run against data and other events without leaving the local network. Greengrass provides local device shadows which are synced back to AWS, again improving performance and the ability for local communications to occur, even if there's an unreliable connection back to AWS. Greengrass provides local messaging using MQTT, and it even allows Lambda functions to access hardware connected at remote and industrial locations. The idea is that remote locations can provide IoT capability locally without excessive communications from those remote locations to AWS. Communication links can be unreliable and intermittent, and so Greengrass allows for a degree of localization. This is a very important aspect of the Greengrass operation. Now visually, this is how it looks. Now the problem is that these wind farms are remote, and so suffer from bad quality and intermittent connections. But luckily for us, the operating company has decided to deploy Greengrass on local devices. The local devices can use Greengrass and the associated local functionality, including device shadows and local Lambda functions. Greengrass offers a lot of features which can run locally, but local services can also communicate with AWS, assuming that they have the permissions to do so. Now this offers an interesting architecture, because it means that device reactions can occur in real time, without issues with latency caused by the communication links. And if a link fails, then industrial operations can continue, even though they don't have direct connectivity with AWS. Messaging works between Greengrass and AWS, and so other AWS services can be used using IoT rules, or called directly. In this particular case, we can use an IoT rule to pass data into Lambda, and then Lambda can utilize SOS, S3, and DynamoDB. The overall aim with Greengrass is to improve local processing and capability for IoT devices, by extending the effective edge of the AWS network, right up to the industrial space where many IoT devices run from.
