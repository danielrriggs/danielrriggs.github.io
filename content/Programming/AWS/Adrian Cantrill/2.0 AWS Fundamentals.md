## VPC
VPC is the service used to create private services in AWS which other private services will run from.

VPC is also the service used to connect AWS private network to on prem networks when creating a hybrid environment.

Or, it lets you connect to other cloud platforms when creating a multi-cloud deployment.

A VPC is within 1 account & 1 region. VPCs are **regional** services, meaning they're regionally **resilient**.

VPCs operate from multiple AZs within a region.

VPCs are private and isolated.

Two types of VPCs are available within a region - **Default VPC** and **Custom VPCs**.
You can only have 1 default VPC per region, but you can have many Custom VPCs.

VPCs are isolated (they can't communicate to other VPCs) unless configured.

Understanding how VPCs are regionally resilient - 

Every VPC has a range of ip addresses (the VPC CIDR). This defines the start and end range of ip addresses that the VPC can use. If anything needs to communicate with the VPC, it needs to communicate with that VPC CIDR.

Custom VPCs can have multiple CIDR ranges, but the default VPC only gets one & it's always the same - 172.31.0.0/16. This is one of the strengths of the default VPC - it's always configured the same way.

A region has multiple AZ's, which is isolated infrastructure. VPCs provide resilience by dividing into subnets. Each subnet is located in one AZ. This is set on creation and can never be changed. With a default VPC, it's always configured the same way - it's configured to have one subnet in every AZ in that region. Each subnet uses part of the VPC's range of IP addresses (its CIDR range). These can't be the same as other subnets in the VPC & they can't overlap with any of the subnets inside the VPC. The IP ranges the subnets are given define the start and end ranges for services within. If a an AZ fails, the subnet within that AZ will fail.

There can only be one default VPC per region. This can be deleted and recreated. So, in theory, a region can have 0 default VPCs.

Some services within AWS assume that the default VPC will be present, so I do tend to leave the default VPCs active in my regions, but I don't tend to use them for anything production related because they're too inflexible.

The number of IP addresses available to the default VPC is fairly large because it uses a /16 CIDR. Inside every default VPC, a smaller /20 subnet is created in every AZ in that region (the # of AZs in a region can vary). The higher the CIDR range is, the smaller the network is. /17 is half the size of a /16. That means 16 /20 subnets can fit into the /16 that the VPC uses. There's enough for 16 AZs.

The default VPC includes a few things preconfigured:
- Internet Gateway (IGW) - allows the VPC to communicate with the internet & vice versa.
- A default VPC security group & network ACL (NACL) - these are security features to limit incoming and outgoing data transfer.
- Subnets assign public IPv4 addresses.

If you delete the default VPC, it will delete all of the network configurations, which includes:
- The Internet Gateway
- The Default Security Group
- The Network ACL
- The VPC itself

## High-Availability vs Fault-Tolerance vs Disaster Recovery
**High Availability** - aims to **ensure** an agreed level of operational **performance**, usually **uptime**, for a **higher than normal period**.
	*Most people assume that HA means ensuring that the system never fails, or that the user of a system never experiences any outages. This isn't true. HA isn't aiming to stop failure, and it doesn't mean customers won't experience outages. A HA system is designed to be online & providing services as often as possible. It's designed so that when it fails, its components can be replaced or fixed as quickly as possible, often using automation to bring systems back into service. HA is not about the user experience. If a system fails & a component is replaced & this disrupts service for a few seconds, it's still highly available. HA is about maximizing a system's online time, and that's it.*

System availability is generally expressed in a % of uptime.
99.9 (3 9's) - means we can only have 8.7 hours of downtime per year.
99.999 (5 9's) allows for 5.26 minutes per year of downtime.

HA can have user experience interruptions -while not ideal, HA is just about minimizing outages.

Example: HA is like driving with a spare tire on the back of the car. You can change the tire & get back on the road. There's some down time, but it prevents you from being dead in the wild & having to call for help.

HA has some cost, requires some decisions ahead of time, and requires some automation.

Sometimes HA needs redundant servers or infra in place to be ready to switch customers over to.

Fault Tolerance vs HA
When most people think of HA, they're mixing it up with fault tolerance. Fault tolerance is similar.

**Fault Tolerance** - the property that enables a system to **continue operating properly** in the event of a **failure of some** (one or more faults within) of its **components**.

Most people think HA means operating through failure. This is incorrect. HA just means maximizing uptime. Fault Tolerance means operating through failure. FT can be expensive because it's more complex to implement.
HA can be implemented by having spare equipment - stand by, physical, or virtual components.

A plane is Fault Tolerant - it has extra engines (4), duplicate electrical and hydraulic systems.

Disaster Recovery (DR) - a set of policies, tools and procedures to **enable the recovery** or **continuation** of **vital** technology infrastructure and systems **following a natural or human-induced disaster**.
Store backups offsite.
DR planning isn't only about tech. It's about staff & knowledge. Make sure knowledge of all your processes are available. All logins to key systems for key systems are available for staff to access at a standby site. Do this in advance & it won't be chaotic when a disaster happens. Ideally, you run periodic DR testing to ensure you have everything you need.

If HA is a 4x4 car & FT is an airplane w/ resilient systems, DR processes are like an ejection system. DR is designed to keep the crucial & non replaceable parts of your system safe.

Summary
DR - **Minimize** any **outages** (max availability.
FT - Operate **through faults**. More complex & expensive. Takes more time to implement & manage.
DR - used when **DR & FT** don't work.

## Route 53 Fundamentals
Provides 2 main services
1) Allows you to register domains
2) It can host zone files for you on managed nameservers which it provides
- S3 operates as a global service w/ a single database (you don't need to pick a region)
	- It's globally resilient. Route 53's data is replicated between regions. Can tolerate the failure of 1 or more regions.

It's one of the most important AWS products. It needs to scale, remain performant while remaining reliable, & continue working through failure.

Route 53 has relationships with all the main domain registries. These are the companies that manage the top level domains. They've been granted this ability by **IANA**, who manage the **root zone** for DNS. One manages the .com zone, one the .net zone, another the .io zone, and so on.

There are 13 DNS root servers which are managed by 12 large organizations. IANA manages the root zone for DNS.

An organization called PIR manages .org domains.
When a domain is registered, S3 checks the top level domain to see if it's available (let's assume it's available for this example). Then Route 53 creates a zone file for the domain being registered. A zone file is a database which contains the DNS info for a particular domain.
As well as creating the zone file, route 53 allocates name servers for this zone. There are generally 4 for one individual zone. This is called a hosted zone in route 53 terminology. It takes the zone file & puts it on these four managed name servers.
As part of registering the domain, it communicates with the registry (PIR, in this example), and liaising with the registry, it adds the name server records into the zone file for the top org level domain. It does this using name server records. These name server records are how PIR delegate the admin of the domain tools. By adding the name server records to the org zone, they indicate that our four name servers are authoritative for the domain.

Summary:
- Create Zone File. Create # of managed named servers. Put Zone file on named servers. Liaison with registry for top level domain. Get name server records added to top level domain zone which point back at these servers.
Remember, DNS is just a system of delegation.

Route 53 provides DNS zones as well as hosting for those zones. It's basically DNS as a service. It lets you create & manage zone files (hosted zones - because they're hosted on AWS managed name servers).

- A hosted zone can be **public**, which means the data is accessible on the public internet. The name servers for a public zone live in the AWS public zone. This is accessible anywhere with a public internet connection; so, they're part of the public DNS system.
- A hosted zone can also be **private**, which means it's linked to one or more VPSs and is only accessible from within those VPCs. You might use this type of zone if you want to host sensitive DNS records that you don't want to be publicly accessible.
- Stores records (recordsets)

**DEMO**
Every time you create a **hosted zone**, route 53 will allocate four different name servers to host that zone.

Transfer lock is a security feature. It means the domain can't be transferred away from route 53 without you disabling this lock.

If you delete and re-create a hosted zone, you'll be given 4 brand new name servers. To stop DNS problems, you'll have to take these new name servers & update the items within the registered domains area of the console. Otherwise, if you don't delete anything, everything will be done end to end by R53.

## DNS Record Types
- Nameserver (NS) record.
	- The record types which allow delegation to occur in DNS.
The .com zone (managed by Versign) has multiple nameserver records for amazon.com These nameserver records are how the .com delegation happens for amazon.com. They point at servers managed by the amazon.com team and the servers host the amazon.com zone. Inside this zone are DNS records, such as www, which is how you can access those records as part of DNS.

The same is true on the other side. The root zone has delegated management of .com by having name servers in the root zone point at name servers inside the .com zone.
(servers from root zone) > point to  > (servers in the amazon.com zone)

Nameserver records are how delegation works within DNS. Nameservers are hugely important.

A records or AAAA **records**. They do the same thing. Given a DNS zone (google.com), these type of records map host names to IP address. The difference is the type of IP address.
An A record maps the host to an ipv4 address.
An AAAA record maps the host to an ipv6 address.

Generally, you'll create two records - one will be an A record & one will be an AAAA record. The client software can choose the correct address it wants.

Next is the CNAME (canonical) record type. The CNAME record type lets you create the equivalent of DNS shortcuts. So, host to host records. Let's say we have an A record called server, which points to an ipv4 address. It's common for a server to provide multiple tasks. Suppose this server provides ftp, mail, and web services. Creating 3 CNAMEs and pointing them to them all at the A server record means they will all resolve the same ipv4 address.
CNAMEs are used to reduce admin overhead. In this case, if the ipv4 address changes, we only have to update one A record (because the 3 CNAMEs reference that one record).

CNAMEs cannot point to ip addresses - only to other names. Expect this trick question on the test.

- MX Records
	- Important for how the internet works (specifically, for how email works).
Suppose you want to send an email to hi@google.com. Your email server needs to know which server to pass the email onto.
	We start in the google.com zone. We have an A record with the name, 'mail' (the name is arbitrary; it could be called rabbit or apple, etc), and this is pointing at an IP address.

In the google.com zone, there are a collection of MX records.
MX Records have 2 main parts:
- A priority
- A value

2 example mx records:
MX 10 mail
MX 20 mail.other.domain. (note the dot on the right)


The value can be just a host (ex: MX 10 mail) - there's no .com on the right; it's assumed to be part of the same zone that it's in.
So if our zone is google.com, mail means mail.google.com.
It's the mail host inside the google.com zone.

If you include a dot on the right, this means it's a fully qualified domain name. It can either point to a host inside the same zone, or something outside that zone.

Lower values for the priority field are higher priority. If there's a tie, any of them could be selected.

Whenever you send an email, it's using DNS to do an MX lookup to locate the mail server to use.

**TXT Records** - a text record. Allows you to add arbitrary text to a domain. It's a way for the DNS system to provide additional functionality. One common usage for a txt record type is to **prove domain ownership**.

Let's say we want to add animails4life.org to an email system (google mail or office 3365 or amazon WorkMail). Whatever system we use to host our email might ask us to add a text record to the domain containing a certain piece of text data.
Ex: Prove you own animals4life.org - add 'cats are the best'.
The sys admin would add a TXT cats are the best record in our domain.
The external party, (say, the google email system), would query that text data, ensure that it matches the value they're expecting, and if it does, that proves that we own that we own that domain & we can manage it.

Other uses for TXT records - fighting spam.

**DNS TTL value** - Time To Live. A TTL value is something that can be set on DNS records. It's a numeric value in seconds.

A client wants to connect to amazon.com.
Client queries Resolver hosted @ ISP.
That resolver server points to the DNS root, which points to the .com registry of authoritative servers.
So, the resolver queries the .com servers. Those authoritative servers for .com provide the nameservers at the amazon.com zone. That server hosts and is authoritative for the amazon.com zone, which has a record for www.
It uses this record to get the ip address & connect to the server. This process takes time (walking the tree process) is a lengthy process. Getting a result from the authoritative source - the source that is trusted by DNS, is known as an **authoritative answer**. You get an authoritative answer by talking to a nameserver that is authoritative for a particular domain.
If I query the nameserver for amazon.com, and I'm querying for the www record in amazon.com, then I get back what's called an authoritative answer. That's always going to be preferred because it's always going to be accurate. It's the single source of truth. Using TTL values, the administrator of amazon.com can indicate how long records can be cached for.

Summary
Client > Resolver
Resolver > Root
Resolver > .com
Resolver > amazon.com

TTL 3600 means the results of the query are stored at the resolver server for 3600 seconds (1 hour). If another client queries the resolver for the same thing (which is likely for amazon.com), they will get back a **non-authoritative answer**. That answer will be retrieved immediately, because it's hosted (probably) at our ISP, so it's faster.

Usuaully, non-authoritative answers are the same (because DNS usually doesn't change much). TTL is important for when things change. If you migrate your email service and you have a high TTL value for your MX record, when you change to a provider with a different ip address then email delivery might be delayed because old ip addresses for those mx records will be cached an they will be used. TTLs are a balance - low values mean more queries against your nameservers. High values mean less queries, but also less control if you need to change records. You can change TTL values before projects and upgrades or you can leave them permanently low. Also, keep in mind that a resolver should obey TTL values (but that's not always the case - it can ignore them). That configuration can be changed locally by the admin at the resolver server.
DNS is often the cause of project failures because of TTL values.

If you're doing any work that involves changing any DNS records, it's recommended to lower the TTL value well in advance of the work (sometimes days or weeks) to make sure you have less caching issues when you do change those records.
