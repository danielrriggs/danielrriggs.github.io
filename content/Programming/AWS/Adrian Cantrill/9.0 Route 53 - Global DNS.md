## R53 Public Hosted Zones
2 types of DNS zones in Route53 - public & private.

- A **R53 Hosted Zone** is a DNS DB for a domain e.g. animals41ife.org (for a given section of the global DNS database).
- **Globally resilient** (multiple DNS Servers)
- Created with domain registration via R53 - can be created separately
	- Monthly fee for hosted zone.
	- Fee for the queries made against that hosted zone.
- A zone, whether public or private, hosts **DNS Records** (e.g. A, AAAA, MX, NS, TXT ...). Hosted zones are databases which are referenced via delegation using name server records.
- Hosted Zones are what the DNS system references - **Authoritative** for a domain e.g. Animals41ife.org
	- When you register a domain, name server records for that domain are entered into the top-level domain zone, and these point at your name servers, and they're the ones that are used to register your domain. Then your name servers and the zone that they host become authoritative for that domain.
- A public hosted zone is a DNS database (**zone file**) hosted by R53 (on **Public Name Servers**)
- Accessible from the **public internet** & **VPCs** (via the R53 resolver)
- When you create a public hosted zone, R53 allocates **4** public Name Servers (**NS**) specific for the zone.
	- It's on those Name Servers that the zone file is hosted.
	- Use "**NS records**" to point at these **NS** (connect to global DNS)
- Inside a public hosted zone, you create Resources Records (**RR**) within the Hosted Zone
	- These are actual items of data which DNS uses.
- Externally registered domains can point at R53 Public Zone

So for example, you can use Hover or GoDaddy to register a domain. You can create the public hosted zone in Route 53. Get the four name servers which are allocated to that hosted zone. And then via the Hover or GoDaddy interface, you can add those name servers into the DNS system for your domain.

![[R53 Public Hosted Zones.png]]

We start by creating a public hosted zone. Creating this allocates four Route 53 name servers for this zone.  Those name servers are all accessible from the public internet. They're also accessible from AWS VPCs using the Route 53 resolver, which assuming DNS is enabled for the VPC, is directly accessible from an internal IP address of that VPC.

Inside this hosted zone, we can create some resource records. In this case, a www record, two MX records for email, and a text record. Within the VPC, the access method is direct. The VPC resolver using the VPC plus two address. This is accessible from any instances inside the VPC which use this as their DNS resolver. They can query the hosted zone as they can any public DNS zone using the Route 53 resolver.

From a public DNS perspective, the architecture is the same in that the same zone file is used. But the mechanics are slightly different. DNS starts with the DNS root servers. These are the first servers queried by our users resolver server. Bob is using a laptop. He's using a laptop. Talking to his ISP DNS resolver server, which queries the root servers. The root servers have information on the .org top level domain. And so the ISP resolver server can then query the .org servers. These servers host the .org zone file. And this zone file has an entry for animalsforlife.org, which has four name servers. And these all point at the Route 53 public nameserver. For the public hosted zone for animals for life. This process is called **walking the tree**. And this is how any public internet host can access the records inside a public hosted zone using DNS.

That's how public hosted zones work. They're just a zone file which is hosted on four name servers provided by Route 53. This public hosted zone can be accessed from the public internet. Or any VPCs which are configured to allow DNS resolution. There's a monthly cost for hosting this public hosted zone. And a tiny charge for any queries made against it. Almost nothing in the grand scheme of things. But for larger volume sites, it's something to keep in mind.

## R53 Private Hosted Zones
- Operates just like a Public Hosted Zone, except it isn't public.
- Associated with **VPCs**
	- **only accessible** in those **VPCs**
	- Using **different accounts** is supported via **CLI/API**
		- Everything else is the same. You can use them to create resource records. And these are resolvable within VPCs.
- Split-view (overlapping **public** & **private** ) for **PUBLIC** and **INTERNAL** use with the same zone name
	- Meaning that you can have a different variant of a zone for private users versus public.

![[R53 Private Hosted Zones.png]]

We start with a private hosted zone, and as with public zones, we can create records within this zone. from the public intranet, our users can do normal DNS queries, so for things like netflix.com and catagram.io, but the private hosted zone is inaccessible from the public internet. It can be made accessible, though, from VPCs. Let's assume all three of these VPCs have services inside them and use the Route 53 resolver, so the VPC plus 2. Any VPCs which we associate with the private hosted zone will be able to access that zone via the resolver. Any VPCs which aren't associated will face the same problem as the user on the public internet on the left - access isn't available.

So private hosted zones are great when you need to provide records using DNS, but maybe they're sensitive and need to be accessible only from internal VPCs. Just remember, to be able to **access** a private hosted zone, the **service** needs to be running inside a VPC, and that **VPC** needs to be **associated** with the **private hosted zone**.

**Split View or Split Horizon DNS**

![[R53 Split View Hosted Zones.png]]

The private hosted zone is associated with VPC1 on the right.
	Meaning the workspace could use the Route 53 resolver to access the private hosted zone. For example, to access the accounting records stored within the private hosted zone. Now the private hosted zone is not accessible from the public internet.
	
What split view allows us to do is to create a public hosted zone with the same name. This public hosted zone might only have a subset of records that the private hosted zone has. From the public internet, access to the public hosted zone would work in the same way as you would expect.

## CNAME vs R53 Alias
- In DNS, an "A" record maps a **NAME** to an **IP Address**
	- catagram.io => 1.3.3.7
- **CNAME** maps a **NAME** to another **NAME**
	- www.catagram.io => catagram.io
- CNAME is **invalid for naked/apex** (catagram.io)
	- So, you couldn't have a CName record for catagram.io pointing at something else. It just isn't supported within the DNS standard.
- Many AWS services use a DNS Name (ELBs) (not an IP address to use).
- With just **CNAME** - **catagram.io => ELB would be invalid**
	- You could point www.catagram.io at an ELB, because using a CNAME for a normal DNS record is fine, but you can't use it for the domain apex (a.k.a the naked domain). This is a problem which alias records fix

- **ALIAS** records map a **NAME** to an **AWS resource**
- Can be used both for **naked**/**apex** and **normal** records
- For non apex/naked - functions like **CNAME**
- There is no charge for **ALIAS** requests pointing at **AWS resources**
- For **AWS Services** - **default** to picking **ALIAS**
- Should be the same "Type" as what the record is pointing at
- You have to create an A record alias if you want to point at ... API Gateway, CloudFront, Elastic Beanstalk, ELB, Global Accelerator & S3

The alias is a type of record that's been implemented by the AWS services and it's outside the DNS standard. It's something you can only use if R53 is hosting your domains.

## Weighted Routing
Weighted routing can be used when you're looking for a **simple form of load balancing**, or when you want to test new versions of software. weighted routing is really useful when you have a group of records with the **same name**, and want to **control** the **distribution** of returned responses.

Specify a weight for each record, and this is called the record weight. Each record then gets returned based on its weighting versus the total weight.

![[Route53 Weighted Routing.png]]

## Latency Routing
Latency-based routing should be used when you're trying to optimize for performance and user experience for global applications by directing traffic towards infrastructure with the best latency. It's worth noting though, that the database (of infrastructure latency) which AWS maintain isn't real-time.

In addition to record name (www) and type ("A"), you can specify a record region (US East 1, US West 1, AP Southeast 2). Latency-based routing supports one record with the same name for each AWS region.

Latency-based routing can also be combined with health checks. If a record is unhealthy, If a record is unhealthy, If a record is unhealthy, then the next lowest latency is returned to the client making the resolution request.

![[Route53 Latency-Based Routing.png]]

## Geolocation Routing
Geolocation routing is similar to latency. Only, instead of latency, the **location** of **customers** and the location of **resources** are used to influence resolution decisions.

This type of routing policy does not return the closest record, it only returns any which are applicable or the default; or no answer. You will not get a Canadian record returned if you're based in the UK and no closer records exist. The smallest type of record is a subdivision, which is a US state. Then you have country, then you have continent, and finally, optionally, a default record.

Geolocation **isn't** about **proximity**. It's about **location**.

![[Route53 Geolocation Routing.png]]

## Geoproximity
GeoProximity aims to provide records which are as close to your customers as possible.

Latency-based routing provides the record which has the lowest estimated latency between your customer and the region that the record is in. GeoProximity aims to calculate the distance between a customer and a record and answer with the lowest distance.

When using GeoProximity, you define **rules**:
- You tag the Location
	- **latitude** and **longitude** coordinates for external resources.
	- You define the **region**, if it's an AWS resource, you define the region the resource is created in.
- You also define a **bias** - rather than just using the actual physical distance, we can adjust how Route 53 handles the calculation.

## R53 Interoperability
Route 53 interoperability - using Route 53 to register domains or to host zone files, when the other part of that is not with Route 53.
	Generally both of these things are performed together by Route 53, but it's possible for Route 53 just to do one or the other.

- R53 normally has 2 jobs - **Domain registrar** and **Domain Hosting**
- R53 can do **BOTH**, either **Domain Registrar** or **Domain Hosting**
- R53 Accepts your money (**domain registration fee**)
- R53 allocates 4 Name Servers (NS) (**domain hosting**)
- R53 Creates a zone file (**domain hosting**) on the above NS
- R53 communicates with the registry of the TLD (**Domain Registrar**) (they have a relationship with the registry - the company or entity responsible for the specific top level domain).
	- sets the NS records for the domain to point at the 4 NS above

**R53 - Both Roles**

![[Route 53 - Both Roles.png]]

Step one is to register a domain within Route 53 (pay the 1 or 3 year fee).
The Route 53 **registrar** **liaises** with the Route 53 DNS hosting entity. It creates a public hosted zone which allocates **four** Route 53 **name servers** to host that zone which are then returned to the registrar.

The **registrar** and the **hosting** are separate functions of Route 53.

Once the registrar has these four name servers. It passes all of this along through to the .org top level domain registry. The registry is the manager of the top level domain zone file. It's via this entity that records are created in the top level domain zone (for the animalsforlife.org domain). So, entries are added for our domain which point at the four name servers which are created and managed by Route 53. That's how the domain becomes active on the public DNS system.

At this point, we've paid once for the domain registration. To the registrar which is Route 53. And we also have to pay a monthly fee to host the domain. So the hosted zone. And with this architecture, this is also paid to Route 53. 

**R53 - Registrar Only**
![[Route 53 - Registrar Only.png]]
This time, Route 53 is acting as a registrar only. The registrar and the DNS hosting entity are separate.

As the DNS admin, you would need to create a hosted zone.
The third party provider would generally charge a monthly fee to host that zone on name servers that they manage. You would need to get the details of those servers once it's been created and pass those details on to Route 53. Route 53 would then liaise with the .org top level domain registry and set those name server records within the domain to point at the name servers managed (in this case by Hover).

We don't see this architecture often in the wild. Probably because: the domain registrar functionality that Route 53 provides is nothing special. You're not actually using Route 53 for domain hosting. And domain hosting is the part of Route 53 which adds most of the value. If anything, this is the worst way to manage domains.

**R53 - Hosting Only**
This architecture is more popular. You might see this either when a business has registered with another provider, but you want to get the benefit that Route 53 DNS hosting provides.

![[Route 53 - Hosting Only.png]]

The domain is registered via a third party domain registrar (hover).
To host the domain, we have to create a public hosted zone within Route 53. This creates the zone and the name servers to host the zone (for a monthly fee). Once this has been created, we pass those details through to the registrar who liaise with the registry for the top level domain. Then those name server records are added to the top level domain. Meaning the hosted zone is now active on the public internet.

Review of the basics:
Route 53 offers a component which:
1) **registers** the domain (this is the registrar)
2) **hosts** the zone files and provides managed DNS name servers.

I think Route 53 is one of the better DNS providers on the market. And so generally for my own domains, I will use Route 53 for both the registrar and the domain hosting components.

## DNSSEC using Route53
This is how Route 53 works normally:
A query against the animalsforlife.org domain would start with our laptop:
- go to a DNS **resolver**,
- then to the **root servers** looking for details of the .org top-level domain,
- then it would go to the .org **top-level domain name servers** looking for **animalsforlife.org**,
- then it would proceed to the four **name servers** which are hosting the **animalsforlife.org zone** using Route 53.
	- we have an AWS VPC using the plus-two address which is the Route 53 resolver, and those instances can query the animalsforlife.org domain from inside the VPC.

![[Implementing DNSSEC with Route53.png]]

Enabling DNSSEC starts with KMS.
This part can either be done separately or as part of enabling DNSSEC signing for the hosted zone. In either case, an asymmetric key pair (there's a public & a private part) is created within KMS.

You can think of these conceptually as the key signing keys or KSKs, but in actual fact, the KSK is created from these keys. These aren't the actual keys, but this is a nuance which isn't required at this level. So these keys are used to create the public and private key signing keys which Route 53 uses. And these keys need to be in the US East 1 region. That's really important. Both the creation and the management of the zone signing keys is handled internally within Route 53. KMS isn't involved.

Next, R53 adds tke KSK and the ZSK public part into a DNS key record within the hosted zone. This tells any DNSSEC resolvers which public keys to use to verify the signatures on any other records in this zone.

Next, the private KSK is used to sign those DNS key records and create the RRSIG DNS Key record. And these signatures mean that any DNSSEC resolver can verify that the DNS key records are valid and unchanged. At this point, that's signing within the zone configured, which is step one.

Next, Route 53 has to establish the chain of trust with the parent zone. The parent zone needs to add a delegated signer record (DS record), which is a hash of the public part of the KSK for this zone.
	How we do this depends on if the domain is registered via R53. If so, the registered domain's area of the R53 console or the equivalent CLI command can be used to make this change. R53 will liaise with the appropriate top level domain and add the DS record.
	If we didn't register the domain using R53 and instead are just using it to host the zone, then we'll need to perform this step manually.
	
Once done, the top level domain (in this case, .org) will trust this domain via the DS record (which is a hash of the domain's KSK). The domain zone will sign all records within it, either using the KSK or ZSK.

As part of enabling this, you should also make sure to configure CloudWatch alarms, specifically create alarms for DNSSEClnternalFailure and DNSSECKeySigningKeysNeedingAction. Both of these indicate a DNSSEC issue with the zone which needs to be resolved urgently, either an issue with the KSK or a problem interacting with KMS.

Lastly, you might want to consider enabling DNSSEC validation for VPCs. This means for any DNSSEC-enabled zone, if any records fail validation due to a mismatched signature or otherwise not being trusted, they won't be returned. This doesn't impact non-DNSSEC-enabled zones, which will always return results.
