![[Private Lambda-NewWay.png]]
- There used to be disadvantages to running Lambda in a VPC because of the networking architecture that Lambda used. Lambda functions don't actually run within your VPC - they work similar to Fargate. Historically, each lambda invocation would create an ENI within the customer VPC. Configuring these ENIs takes time & delays code execution. Also, it doesn't scale well because concurrent lambda executions would require additional ENIs (1Lambda Invocation : 1 ENI).
- New way - instead of 1 ENI per invocation, AWS analyzes all of the functions running in a region in an account and build up a set of **unique combinations** of **SGs** and **subnets**.
	- It **scales** better.
		- For every unique one of those, one ENI is required in the VPC. So if all your functions used a collection of subnets but the same SGs, then one network interface would be required per subnet. If they all used the same subnet and all used the same SG, then all of your Lambda functions could use a single ENI. 
	- When you create the function or update the networking configuration, this networking configuration is created or updated - which could take **90 seconds**. It isn't done per invocation.

## AWS Lambda - PART3
There are three different methods for invoking a lambda function: **Synchronous** invocation, **Asynchronous** invocation, & **Event Source mappings**

**Lambda Synchronous Invocation**
![[Lambda Synchronous Invocation.png]]
- **Synchronous** invocation
	- Generally used when it's a human directly or indirectly invoking a lambda function
	- Synchronous invocation happens if: invoked via CLI/API, or indirectly via the API gateway
	- Result returned during the request
	- Errors or retries must be handled by client

**Lambda Asynchronous Invocation**
![[Lambda Asynchronous Invocation.png]]
- **Asynchronous** invocation
	- Typically used when invoked via AWS services
	- Can retry 0-2 times (configurable)
	- The function must be [[idempotent]]
	- **Failed** reprocessing events can be sent to a **Dead Letter Queue** (DLQ)
	- Events can be delivered to **destinations** like **SQS, SNS, Lambda, & EventBridge**

**Lambda Event Source Mappings**
![[Lambda Event Source Mappings.png]]
- **Event Source mappings**
	- Typically used on streams or queues which don't generate event to directly invoke lambda
		- (things like Kinesis streams, DynamoDB streams, SQS queues, Amazon managed streaming for Apache Kafka).
		- Ex: some kind of polling is required.
	- Polls **Source Batches** (batches of source data) - Source Batches are broken up into **Event Batches** (based on batch size).
	- Event Batches are sent to lambda
		- Lambda could receive hundreds of events in a batch
		- Remember, Lambda has a 15 minute timeout; so, you need to control the batch size to ensure the lambda function doesn't terminate before completing the batch
	- The event source mapping uses permissions from the Lambda **execution role** to access the source service
		- So, even though a lambda function may not use a service (s3, kinesis, etc), its execution needs permission because the Event Source Mapping uses it on its behalf to retrieve data.
	- Batches which consistently fail can be sent to a DLQ for further processing or analysis

**Versions**
- Lambda functions have **versions** - VI, v2, v3
- A version is the **code** + the **configuration** of the lambda function
- Its **immutable** - it never changes once published & has its own In **Amazon Resource Name**
- **$Latest** points at the latest version (so, not immutable)
- **Aliases** (DEV, STAGE, PROD) point at a version - **can be changed**

**Startup Times**
When a lambda function is invoked, an execution context needs to be created and configured. This takes time. The environment itself is created (this involves physical hardware). Any runtimes are downloaded & installed (eg. Python 3.8). The deployment package is downloaded & installed. This process is known as a **cold start**. Can take >100ms.

**Warm start** - Execution context is reused.
If too much time passes between invocations, the context can be deleted, resulting in a cold start, again.

1 function invocation runs at a time per context. If you need 20 invocations to run at a time, it will result in 20 cold starts.

**Provisioned concurrency** can prepare execution contexts in advance. You might use these when:
- You have periods of higher load on a serverless application
- You're preparing for a new production release of a serverless application
- Incurs overhead **costs** that may not be warranted during periods when the function experiences minimal to zero invocations.

Other things to improve **performance**:
- Use the **temp** space to pre-**download** things within an execution context
	- For example, maybe you're using some animal images as part of your processing, if **another** function uses the same execution context then it too will have access to those same animal images without having to download them a second time.
		- Never assume the presence of anything.
	- Code can do things **outside** the lambda **function handler** which will be made available for any future function invocations.
		- Things which are potentially reused - like database connections.
			- But again, your function should be fine with recreating everything. Reusing common aspects which persist is for efficiency.
- Enable **Lambda SnapStart**
	- Initializes functions as new versions are published.
	- Lambda then takes a Firecracker microVM snapshot of the memory and disk state of the initialized execution environment, encrypts the snapshot, and caches it for low-latency access.

**Misc**
- **response streaming**
	- progressively stream response payloads back to clients
		- [Introducing AWS Lambda response streaming | AWS Compute Blog](https://aws.amazon.com/blogs/compute/introducing-aws-lambda-response-streaming/)

- SUCCEED & FAIL
- WAIT - For a certain period of time OR until a specific date and time
	- It's provided with this information as an input and it holds or pauses the processing of the state machine work.

	- Ex: a list of orders.

## Simple Queue Service
SQS provides managed message queues.

- Public, Fully Managed, Highly-Available Queues - **Standard** or **FIFO**
	- Replication & resiliency happens within a region by default
	- FIFO guarantee an order
	- Standard is best efforts
- Messages up to 256KB in size - link to large data
	- If you need to deal with larger data, you can store it on something like S3 and link to that object inside the message.
	- Architecturally, you want to keep messages small because they're easier to process and manage at scale.
- Received messages are **hidden** (**VisibilityTimeout**).
	- When a client polls and receives messages, those messages aren't actually deleted from the queue. They're actually hidden for a period of time.
	- **VisibilityTimeout** - the amount of time a client can take to process a message in some way.
- Messages either reappear (retry) or are explicitly deleted
	- When a client finishes processing whatever workload that that message represents, then it can explicitly delete that message from the queue. Then it's gone forever.
	- If a client doesn't explicitly delete that message, the message will reappear in the queue.
	- Architecturally, this is a good way to ensure fault tolerance.
		- If a client fails when it's processing a job, or maybe even fails completely, then the queue handles the default action to put the message back in the queue, which makes that message available for processing by a different client.
- **Dead-Letter queues** can be used for problem messages
	- For example, if a message is received five or more times, goes to DLQ.

Queues decouple app components. 1 Component adds to queue; another reads from queue. Neither component need to worry about each other. Queues are also great for scaling. ASGs can scale based on queue length. Lambdas can be invoked when messages appear on a queue. This allows you to build complex worker pool style architectures.

**Conceptual worker pool style Architecture**

**SNS and SQS Fanout**
![[SNS and SQS Fanout.png]]
- Standard = **at-least-once**, FIFO = exactly-once. Also guarantees order.
	- With standard queues, you can get the same message delivered twice in two different polls. Order can be different.
- FIFO (Performance) **3,000 messages per second** with batching, or up to **300 messages per second without**
- Billed based on 'requests'
	- A request isn't a message
- 1 request can return 1-10 messages up to 64KB total
	- SQS is less efficient the more frequently you make requests. Requests can return 0 messages. The more frequently you poll, the less cost effective the service is.
- **Short** (immediate) vs **Long** (**waitTimeSeconds**) Polling
	- Short polling uses one request and it can receive zero or more messages.
		- If the queue has zero messages, then it still consumes a request
		- If you only use short polling, keeping a queue close to zero length would require an almost constant stream of short polls
	- Long polling - you specify a time (up to 20s). If messages are available on the queue when you lodge the request, then they will be received. Otherwise, it will sit and **wait** for messages to arrive.
		- Up to 10 messages and 64 kilobytes will be counted as a single request
		- **Long polling is how you should poll SQS** because it uses fewer requests
	- Encryption at rest (**KMS**) & in-transit
		- Messages can sit in the product for up to 14 days
		- Data is encrypted by default between SQS and any clients.
		- KMS is used for server side encryption at rest (on disk)
	- **Access** to a queue is based on **identity policies** or you can use a **Queue policy**
		- Identity policies or queue policies can be used to control access to a queue from the same account, but queue policies only can allow access from external accounts
		- A queue policy is just a resource policy (like resource policies used on S3 buckets or SNS topics)

## SQS Delay Queues
Delay queues at a high level allow you to postpone the delivery of messages to consumers.

![[SQS Delay Queues.png]]

We send a message to a queue. We poll for a message using receive message. While the message is being processed, visibility timeout takes effect. During this time, any further receive message calls will return no results. During this processing period, either the process will complete and the message will be explicitly deleted or not. If not, this suggests a failure in processing and the message will reappear on the queue.

The critical thing to understand about visibility timeout is that messages need to appear on the queue and be received before this visibility timeout occurs. This is used to allow automatic reprocessing. So you receive messages from a queue and you begin processing. If that processing fails and the application doing it crashes, it might not be in a position where it can tell the queue that processing has failed. Visibility timeout means that after a certain configurable duration, that message will reappear in the queue and can be processed again. It's generally used for error correction and automatic reprocessing.

A delay queue is significantly different.
Delay queues in a way are similar to visibility timeouts because both features make messages unavailable to consumers for a specific period of time. But the difference between the two is that for delay queues, a message is hidden automatically when it's **first added** to the queue. Using visibility timeouts, a message is initially visible and it's only hidden after it's consumed from the queue and automatically reappears if that message isn't deleted.

Delay queues are generally used when you need to build in a delay in processing into your application. Visibility timeouts are used to support automatic reprocessing of problematic messages.

## Kinesis Data Streams
A lot of people confuse Kinesis with SQS. There are exam questions to test your ability to select between the two. Kinesis is a scalable streaming service. It's designed to ingest lots of data from lots of devices or applications.

- Kinesis is a **scalable streaming** service
- Producers **send** data into a kinesis **stream**
- Streams can scale from low to near infinite data rates
- Public service & highly available (in a region) by design
- Streams store a **24-hour** moving window of data
	- as a product it includes storage for that amount of data
	- can be increased to a maximum of **365 days** (additional cost)
- Multiple consumers access data from that moving window
	- Different levels of granularity. Ex: 1ce/minute, 1ce/hour.
	- Good for things like analytics, dashboards.

**Kinesis Architecture**
![[Kinesis Architecture.png]]
Kinesis scales using a shard architecture. A stream starts with 1 shard. As additional scale is required, a shard is added to the stream. Each shard provides its own capacity - 1MB/s ingestion, 2MB/s consumption. More shards = more expensive, better performance.
The **data window** (length Kinesis stores data) also impacts the price. Default data window is 24 hours. This can be increased to 365 days.
The way that the data is stored on a stream is via Kinesis **data records**. These have a maximum size of 1 MB. Kinesis data records are stored across shards. Meaning the performance scales in a linear way based on the number of shards.
**Kinesis data fire hose** connects to a Kinesis stream and can move the data which arrives onto a stream en masse into another AWS service (ex: S3).

**SQS vs Kinesis**
(**exam**): Is the question about the ingestion of data? Or is it about worker pools, decoupling? Or does it mention asynchronous communications?
If it's about **ingestion** of data - it's about **Kinesis**; if it's about any of the **others** then assume it's **SQS** first and only change your mind if you have strong reasons to do so.
- SQS
	- 1 production group, 1 consumption group
		- SQS generally has one thing or one group of things sending messages to the queue; ex: Web Tier ASG. Generally, you won't have 100,000's of sensors sending data to an SQS queue. It isn't designed for that.
	- **Decoupling** and **Asynchronous** communications.
	- **No persistence** of messages, **no window**
- Kinesis
	- designed for **huge scale ingestion**
		- and **multiple consumers**,  **rolling window**
	- Data **ingestion**, **Analytics**, **Monitoring**, **App Clicks**, mobile click streams

## Kinesis Data Firehose
The end result of Firehose is to deliver incoming data through to a number of supported destinations: HTTP endpoints, splunk, redshift, ElasticSearch, S3.

- **Fully managed** service to load data for **data lakes**, **data stores** and **analytics services**
- **Automatic scaling** ... fully **serverless** , **resilient**
- (**exam**) - **Near Real Time** delivery (-60 seconds)
- Supports **transformation** of data on the fly (**lambda**)
- **Billing** - volume **through** firehose

**Kinesis Data Firehose**
![[Kinesis Data Firehose.png]]

Firehose can directly accept data from producers a Kinesis Data Stream.
Firehose **receives** data in real time, but it doesn't **deliver** data in real time. Received data is **buffered** for delivery. Minimum buffers: 1 MB of **or** 60 seconds (adjustable).
Firehose can **transform** data passing through using **Lambda**. Functions can be created from **blueprints**. Transformations add latency. You can optionally store the unmodified data (**source records**) in a backup bucket which you define.

Kinesis Firehose is not real time. You trade the fact that you don't have to build this yourself, but you lose the real time nature of Kinesis. If you need a solution which handles data in real time, then you need to stick to Kinesis and use something like a Lambda function to handle what to do with that data - say delivering it in real time.

## Kinesis Data Analytics
Kinesis Data Analytics is a service which provides real-time processing of data which flows through it using SQL.

- **Real time processing** of data
	- Uses **SQL**
- Ingests from **Kinesis Data Streams** or **Firehose**
	- can optionally pull in static reference data from S3
- Destinations
	- **Firehose** (S3, Redshift, Elasticsearch & Splunk)
		- If you're using Firehose, keep in mind the data becomes near real time rather than real time.
	- AWS **Lambda**
	- Kinesis **Data Streams**

Conceptually the product fits between two streams of data - input streams and output streams. It allows you in real-time to use SQL queries to adjust the data from the input to the output.

![[Kinesis Data Analytics.png]]

Kinesis data analytics doesn't actually modify the sources in any way. Inside the analytics application you define **sources** and **destinations** known as **inputs** and **outputs**.

**In-application input streams**
For the input side, objects called **In-application input streams** are created based on the inputs - it's like a continuously updating table upon which you can perform SQL operations.
// [Amazon Kinesis Data Analytics for SQL Applications: How It Works - Amazon Kinesis Data Analytics for SQL Applications Developer Guide](https://docs.aws.amazon.com/kinesisanalytics/latest/dev/how-it-works.html)

**Reference Table**
The **reference table** matches data contained in an S3 bucket. It can be used to store static data which can enrich the data coming in over the streams. Ex: a game is streaming only game activity data. The reference table can have **meta** / **additional** data which can be used to enrich the incoming stream - stuff like player names, item info, etc.\

**Application Code**
The core to the Kinesis analytics application is the **application code**. This is coded using SQL. It processes inputs and it produces outputs.

(input) So, in this case, it operates on data in the in-application input stream table and the reference table.

(output) Any output from the SQL statement is added to **in-application output streams**. Again, think of these like tables which exist within the Kinesis Analytics Application - only these tables map onto real external streams. Any data that's outputted into those tables by the Kinesis analytics application is entered onto the Kinesis stream or Kinesis firehose. These will feed into any consumers of the stream or destinations of the firehose.

(errors) Any errors generated by the SQL query can be added to an in-application error stream.

(summary) All of this happens in real time - Data is captured from the source streams via the in-application input stream (virtual tables), it's manipulated by the analytics application using SQL, then stored into the in-application output streams which put that data into either the external Kinesis stream or external Kinesis firehose.

If the output data is delivered into a Kinesis stream, then it stays real time.
If the output data is delivered into a Kinesis firehose, then it becomes **near** real time (delivering to all of those supported destinations).

You only **pay** for the **data processed** by the application, but it is **not cheap**, so you should only use it for scenarios which really fit this type of need.

**Kinesis Data Analytics - When and Where**
- Streaming data needing **real-time SQL processing**
- Time-series analytics .. **elections** / **e-sports**
- Real-time dashboards - **leaderboards** for games
- Real-time metrics - **Security** & **Response** teams

Data firehose can also support transformation of data using Lambda. But remember, the key differentiator is that data firehose is not a real-time product. And using Lambda, you're restricted. It's relatively simple manipulations of data. Using Kinesis data analytics, you can create complex SQL queries. And use those queries to manipulate input data into whatever format you want for the output data. So it has a lot more in terms of features than data firehose. So if you're dealing with any exam questions which need really **complex manipulation** of data in **real-time**, then Kinesis data analytics is the product to choose.

## Amazon Cognito - User and Identity Pools
This is going to be one of the most important non-graphical screens of information in the entire course.

- Cognito has terrible naming
- **Authentication**, **Authorization**, and **user management** for web/mobile apps (user management = creation & management of a serverless user database)
- There are two parts to Cognito, and the **naming** is **terrible** - User Pools, and Identity Pools
- **USER POOLS** - **Sign-in** and get a JSON Web Token (**JWT**)
	- // This JWT can be used for authentication with applications, certain AWS products such as API Gateway, but **most AWS services cannot use JWTs**. To access most AWS services, you need actual AWS credentials. User pools do not grant access to AWS services. Their job is to control sign-in and deliver a JWT. They do things like sign-up and sign-in services. The important thing to understand is this is about offering a joined-up user management experience. At no point can a user pool be used to directly access most AWS resources. When you think of user pools, imagine a database of users, which can include external identities.
- User directory management and profiles, sign-up & sign-in (customizable web Ul), MFA, and other security features
	- // Security features: check for compromised credentials; account takeover protection; phone and email verification
- // You can also implement customized **workflows** and user migration by using **Lambda triggers**
- // User pools, as well as allowing **sign-in** from built-in users, they also allow **social sign-in** using identities provided by Facebook, Google, Amazon, Apple, as well as offering sign-in services using other identity types such as **SAML** identity providers.
- **IDENTITY POOLS** - Allow you to offer exchange a type of external identity for a set of **Temporary AWS Credentials**
	- **Unauthenticated Identities** - Guest Users
	- **Federated Identities** - SWAP - Google, Facebook, Twitter, SAML2.0 & User Pool for short term AWS Credentials to access AWS Resources.
	- // Identity pools are about swapping either an unauthenticated or authenticated identity for AWS credentials. One possible type of identity is actually a user pool identity.

**Identity pools** work by assuming an **IAM role** on behalf of the identity. That assumption generates **temporary credentials** and they're provided back in return - in most cases to a mobile or web application. These IAM roles are configured within identity pools.

**Amazon Cognito - User Pools**
A **user pool** is a **collection** of **identities** of users used to allow sign up and sign in both for internal users and social sign in. The **tokens** which are generated as a result can be used for self-managed systems & API Gateway (but not AWS resources; that requires AWS credentials - which are handed out by identity pools).

**Amazon Cognito - Identity Pools**
![[Amazon Cognito - Identity Pools.png]]
A 3rd party IdP **authenticates** a user & gives us a **token**. Our application takes this token and passes it to an **identity pool** that we've configured. If we want to support five external IdPs, we need five different configurations - five different types of token to be supported. Cognito is configured with **roles** - at least one for authenticated identities and one for unauthenticated or guest identities. In this example, google is our **Authenticated role**. Cognito assumes a role and generates **temporary AWS credentials** which are then passed back to the application. The application can then use these credentials to access AWS resources. Once they **expire** the application **renews** them again using Cognito and the process continues. The permissions the application has are based on the **roles permissions**. At no point does the application store any credentials within code or any credentials permanently.

With this configuration your application has to be able to deal with many different ID tokens from many different external providers. One option is that we could use user pools to handle the many different types of identity and then we can use identity pools to swap the Cognito user pool token for AWS credentials. Now the swapping of any external ID provider token for AWS credentials is known as web identity **federation**. Federation is the process of identity pools swapping external identity tokens for AWS credentials.

**Cognito - User & Identity Pools**
![[Cognito - User & Identity Pools.png]]
By using a **user pool** we've **abstracted** away from all of the configuration of many different external IdPs. We have conceptually one user store to manage one set of user profiles all provided via a Cognito user pool. The user pool simplifies the management of identity tokens. The application can pass this user pool token into an identity pool and this assumes an IAM role defined in the identity pool which generates temporary AWS credentials and these temporary credentials are returned to the application. The benefit to this approach is that the identity pool need only be configured with a single external identity provider the user pool.

## AWS Glue 101
- Serverless ETL (Extract, Transform, & Load)
	- vs **datapipeline** (which can do ETL) and uses servers (**EMR** clusters)
- Moves and transform / enrich data between **source** and **destination**
	- databases, streams, or other sources, such as S3

- Data **Source**: **Stores**: S3, RDS, JDBC Compatible, & DynamoDB
- Data **Source**: **Streams**: Kinesis Data Stream & Apache Kafka
- Data **Targets**: S3, RDS, Databases

A data catalog is a collection of metadata combined with data management and search tools.
- **Persistent metadata** about data sources in region
- **One catalog** per region per account
- **Avoids data silos**
	- Makes this metadata, the data structure, available to be browsed and then brought into other systems using the ETL features of Glue. Improves the visibility & accessibility of data across an organization.
- Amazon Athena, Redshift Spectrum, EMR & AWS Lake Formation all use **Data Catalog**
	- configure **crawlers** for data sources

**AWS Glue**
![[AWS Glue.png]]
Data Catalog publicizes data from across an organization.
Glue jobs are ETL jobs.
Glue is serverless. AWS maintain a pool of resources to perform the transform tasks when required. Only billed for resources consumed.
Can be started manually or invoked in an event-driven (EventBridge).

Historically, the ETL part of this has been done using data pipeline. In exam questions, look for keywords such as serverless, ad hoc, or cost effective. And if you see these, you should pick Glue rather than data pipeline.

Data pipeline does offer some additional functionality versus Glue, but over time, it's my expectation that the Glue product will replace the functionality offered by data pipeline.
