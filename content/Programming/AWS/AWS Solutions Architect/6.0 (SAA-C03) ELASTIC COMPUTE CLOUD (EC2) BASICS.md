EC2 provides virtualization as a service. It's an IaaS product.

Virtualization is the process of running more than one OS on a piece of hardware, a server.
**Virtualization 101 - no virtualization**
![[Virtualization 101 - no virtualization.png]]
Without Virtualization:
**OS Kernel** runs in **Privileged Mode** which can interact directly with the hardware. **Apps** run in **User Mode** which makes system calls to the Kernel. If an App tries to a Privileged call (tries to interact with the hardware directly), the system will detect it and cause a system wide error, generally crashing the whole system. Or at minimum, the application.

**Virtualization 101 - virtualization**
![[Virtualization 101 - virtualization.png]]
With Virtualization - a single piece of hardware running multiple OS's.
A CPU can only have one thing running in privileged mode.

 Initially, virtualization was really inefficient, because the hardware wasn't aware of it. It had to be done in software, and it was done in one of two ways:
 1) Emulated Virtualization
 2) Software Virtualization

A host operating system still ran on the hardware, and it included additional capability known as a **hypervisor**. The software ran in privileged mode, and so it had full access to the hardware on the host server. Now around the multiple other operating systems, which we'll now refer to as **guest operating systems**, were wrapped a container of sorts called a **virtual machine**. Each virtual machine was an unmodified operating system, such as Windows or Linux, with a virtual allocation of resources such as CPU, memory, and local disk space.
	Virtual machines also had devices mapped into them, such as network cards, graphics cards, and other local devices, such as storage. The guest operating systems believed these to be real, they had drivers installed just like physical devices, but they weren't real hardware. They were all emulated, fake information provided by the hypervisor to make the guest operating systems **believe** that they were **real**. The crucial thing to understand about emulated virtualization is that the guest operating systems still believed that they were running on real hardware, and so they still **attempt to make privileged calls**.
		They try to take control of the CPU, they try to directly read and read, to what they think of as their memory and their disk, which are actually not real, they're just areas of physical memory and disk that have been allocated to them by the hypervisor. Without special arrangements, the system would at best crash, and at worst all of the guests would be overwriting each other's memory and disk areas.

The hypervisor, it performs a process known as **binary translation**. Any privileged operations which the guests attempt to make, they're **intercepted** and **translated** on the fly in software by the hypervisor. Now the binary translation in software is the key part of this. It means that the guest operating systems need no modification, but it's **really, really slow**. It could actually half the speed of the guest operating systems or even worse. Emulated virtualization was a cool set of features for its time, but it never achieved widespread **adoption** for demanding workloads because of this **performance**.

**Emulated Virtualization**
![[Emulated Virtualization.png]]
Another approach: **para-virtualization**.

Instead of the slow binary translation which is done by the hypervisor, para-virtualization only works on a small subset of Operating Systems - ones which can be modified.

With para-virtualization, there are areas of the guest operating systems which attempt to make privileged calls, and these are modified. They're modified to make them user calls, but instead of directly calling on the hardware, they're calls to the hypervisor called **hypercalls**.

**Para-Virtualization**
![[Para-Virtualization.png]]
Areas of the operating systems which would traditionally make privileged calls directly to the hardware, they're actually modified, so the source code of the operating system is modified to call the hypervisor rather than the hardware. So the operating systems now need to be modified (vendor specific) specifically for the particular hypervisor that's in use. It's no longer just generic virtualization.
	By modifying the operating system in this way and using para-virtual drivers in the operating system for network cards and storage, it means that the OS became almost virtualization aware - this massively improves performance. But it was still a set of software processes designed to trick the OS and/or the hardware into believing that nothing had changed.

**Hardware Assisted Virtualization**
![[Hardware Assisted Virtualization.png]]
The major improvement in virtualization came when the hardware became virtualization aware - this allows for **hardware virtualization**, also known as **hardware assisted virtualization**. The CPU contains specific instructions and capabilities so that the hypervisor can directly control and configure this support. The CPU knows that virtualization exists.
	What this means is that when guest operating systems attempt to run any privileged instructions, they're trapped by the CPU, which knows to expect them from these guest operating systems. So the system as a whole doesn't halt. But these instructions can't be executed as is because the guest operating system still thinks that it's running directly on the hardware. And so they're redirected to the hypervisor by the hardware. The hypervisor handles how these are executed. And this means very little performance degradation over running the operating system directly on the hardware.

The problem, though, is while this method does help a lot, what actually matters about a virtual machine tends to be the input-output operation. So network transfer and disk I.O. The virtual machines, they have what they think is physical hardware. For example, a network card. But these cards are just logical devices using a driver which actually connect back to a single physical device. So if you have a single piece of hardware which sits in the host, the hardware, everything is running on. Unless you have a physical network card per virtual machine, there's always going to be some level of software getting in the way. And when you're performing highly transactional activities such as network I.O. or disk I.O., this really impacts performance. And it consumes a lot of CPU cycles on the host. 

**SR-IOV**
![[SR-IOV.png]]
The final iteration is SR-IOV (single root IO Virtualization), where the hardware devices themselves become virtualized. It's a complex & feature rich set of standards. At a high level, it allows a network card, or any other add on card, to present itself - not as one single card - but almost as several mini cards. Because this is supported in hardware, these are fully unique cards as far as the hardware is concerned. These are directly presented to the OS as real cards, dedicated for its use. This means no translation has to happen by the hypervisor. The guest operating system can directly use its card whenever it wants. The physical card which supports SR-IOV handles this process end to end. It makes sure that when the guest operating systems use their logical mini network cards, they have physical access to the physical network when required.

In EC2, this feature is called **Enhanced Networking**, and it means network performance is massively improved. Faster speeds, lower latency, and more importantly, it means consistently lower latency even at high loads. And it means less CPU usage for the host CPU - Even when all of the guest operating systems are consuming high amounts of consistent I/O.

AWS do have their own hypervisor stack now called Nitro. This enables a lot of the higher end EC2 features.

SRIOV is used for enhanced networking right now, it can also help hardware manufacturers design cards which can be split up into logical cards that can be presented to guest operating systems. It essentially makes any hardware virtualization aware.

## EC2 Architecture and Resilience
- EC2 Instances are **virtual machines** (OS+Resources)
	- An operating system plus an allocation of resources such as virtual CPU, memory, potentially some local storage, maybe some network storage, and access to other hardware such as networking and GPUs.
- EC2 Instances run on **EC2 Hosts**
- **Shared** Hosts or **Dedicated** Hosts
	- **Shared** hosts are shared across different AWS customers. You don't get any ownership over the hardware and you pay based on for the individual instances based on how long you run them for and what resources they have allocated.
		- It's important to understand, though, that every customer, when using shared hosts, are isolated from each other, so there's no visibility of it being shared. Shared hosts are the default.
	- With **dedicated** hosts, you're paying for the entire host, not the instances which run on it. It's yours. It's dedicated to your account, and you don't have to share it with any other customers. So if you pay for a dedicated host, you pay for that entire host, you don't pay for any instances running on it, and you don't share it with other AWS customers.
- **EC2 is an AZ resilient service**
	- The reason is that hosts themselves run inside an AZ.
	- **Hosts = 1 AZ** - AZ Fails, Host Fails, Instances Fail

**EC2 Architecture1**
![[EC2 Architecture1.png]]
EC2 hosts have some local hardware, logically CPU and memory, which you should be aware of, but also they have some local storage called the **instance store**. The instance store is temporary. If an instance is running on a particular host, depending on the type of the instance, it might be able to utilize this instance store. But if the instance moves off this host to another one, that storage is lost.

They also have two types of networking, storage networking and data networking.

When instances are provisioned into a specific subnet within a VPC, what's actually happening is that a primary **ENI** is provisioned in a subnet, which maps to the physical hardware on the EC2 host.

Remember, **subnets** are also in **one** specific AZ.

Instances can have multiple network interfaces, even in different subnets, as long as they're in the same AZ.
	Everything about EC2 is focused around this architecture, the fact that it runs in one specific AZ.

EC2 can make use of **remote storage**, so an EC2 host can connect to the **Elastic Block Store (EBS)**.
	The Elastic Block Store service also runs, inside a specific availability zone. The EBS service running in AZ A is different than the EBS service running in AZ B and you can't access them cross zone.
EBS lets you allocate **volumes**, and volumes are portions of **persistent storage**, and these can be allocated to instances in the **same AZ**.

 The host is in an availability zone.
 The network is per availability zone.
 The persistent storage is per availability zone.

Now an instance runs on a specific host, and if you **restart** the instance, it will **stay** on that host.
Instances stay on a host until one of two things happen - 
1) The host fails or is taken down for maintenance for some reason by AWS
2) If an instance is **stopped** and then **started** - that's different than just **restarting**
If either of those things happen, then an instance will be relocated to another host, but that host will also be in the same AZ. Instances can't natively move between AZs - there are ways to do a **migration**, which means taking a copy of an instance and creating a brand **new** one in a different AZ - this will be covered when we discuss **snapshots** & **AMIs**.

What you **can never** do is connect network interfaces or EBS storage (volumes) located in one AZ to an EC2 instance located in another AZ. EC2 and EBS are both AZ services. They're **isolated**.

Instances running on an EC2 host share the resources of that host. Instances of different sizes can share a host. But, generally, instances of the same type and generation will occupy the same host. When you think about an EC2 host, think that it's from a certain year and includes a certain class of processor and a certain type of memory and a certain type and configuration of storage. And instances are also created with different generations, different versions that utilize specific types of CPU memory and storage.

What's EC2 Good For?
- Traditional **OS + Application** Compute
- **Long-Running** Compute
- **Server** style applications  ..
- .. either **burst** or **steady-state** load
- **Monolithic** application stacks
- **Migrated** application workloads or **Disaster Recovery**

As a starting point, pick EC2 as the default, and only move away if you have a specific requirement.

Remember that EC2 is tied down to **One AZ**. Problem blast radius will always be limited to an AZ.

## Storage Refresher
- **Direct** (local, physical) attached Storage - Storage on the EC2 Host
	- In EC2, this is called the **instance store**
	- Fast
	- If disk / hardware fails, storage can be lost
	- If an EC2 instance moves between hosts, the storage can be lost
- **Network** attached Storage - Volumes delivered over the network (EBS)
	- In on-premises environments, this uses protocols such as iSCSI or Fiber Channel. In AWS
- **Ephemeral** Storage - Temporary Storage
	- Ex: the instance store
- **Persistent** Storage - Permanent storage - lives on past the lifetime of the instance
	- Ex: EBS
![[Block Storage.png]]
- **Block** Storage - **Volumes** presented to the **OS** as a collection of blocks. No structure provided. **Mountable**. **Bootable**.
	- Has a number of addressable blocks. There's **no structure** beyond that. Presented logically as a volume or as a bank HDD.
	- Generally, on top of raw block storage, an **operating system** would **create a file system** on top of this - for example, NTFS, EXT3, or other. Then, it **mounts** that - either as the C drive in Windows, or the root volume in Linux.
	- Comes in the form of physical HDDs / SSDs (physical media) or a logical volume that's backed by different types of physical storage.
	- Network attached storage systems, or storage area network systems, provide block storage over the network.
	- In AWS, you can mount a block storage volume (EBS), and you can boot off an EBS volume.
		- Most EC2 instances use an EBS volume as their boot volume - that's what stores their OS.
- **File** storage - Presented as a file share. **Has Structure**. **Mountable**. **Not Bootable**.
	- Example use case: If you want to share a file system across multiple different servers or clients.
- **Object** Storage - Collection of objects, flat. **Not mountable**. **Not bootable**.
	- A very abstract system. No structure. You store objects.
	- To retrieve an object, you generally provide a key
	- Objects can be anything - binary, images, movies, etc - the key thing to remember is that they're just **flat** storage.
	- Benefits of object storage: it's very scalable.

**Storage Performance**
- IO, or **block** size
	- The size of the blocks of data that you're writing to disk. Expressed in kilobytes or megabytes.
	- Can range from pretty small sizes to pretty large sizes (16K, 64K, 1MB)
	- If your storage block size is 16 kilobytes, and you write 64 kilobytes of data, it will use four blocks.
- IOPS - input output operations per second
- Throughput - amount of data that can be transferred in a given second; generally expressed in megabytes per second.

These things cannot exist in isolation. An analogy as an example:
- IOPS - the speed at which the engine of a race car runs at (revolutions per second).
- IO (block size) - the size of the wheels of the race car.
- Throughput - the end speed of the race car.
In theory, in isolation, if you increase the size of the wheels or increase the revolutions of the engine, you would go faster.

**Throughput = IO x IOPS**
Example: 16KB block size x 100 IOPS = 1.6MB/s.

A physical storage device isn't the only thing involved in that chain of storage.
	Reading or writing data starts with the application, then the operating system, then the storage subsystem, then the transport mechanism to get the data to the disk, the network, or the local storage bus, such as SATA, and then the storage interface on the drive, the drive itself, and the technology that the drive uses. They are all components of that chain. Any point in that chain can be a limiting factor, and it's the lowest common denominator of that entire chain that controls the final performance.

Certain media types are better at delivering high IOPS versus other media types, and certain media types are better at delivering high throughput versus other media types. If you use network storage versus local storage, the network can also impact how many IOPS can be delivered. High latency between a device that uses network storage and the storage itself can massively impact how many operations you can do in a given second.

If you want to maximize your throughput, you need to use the right block size, and then maximize the IOPS.
 A system might have a throughput cap.
 As you increase the block size, the IOPS that you can achieve might decrease.

You might face exam questions where you need to answer what type of storage you will pick for a given level of performance demands. Certain types of AWS storage can achieve different levels of IOPS or throughput. You might need to know these numbers so that you can know when to use a certain type of storage.

## Elastic Block Store (EBS) Service Architecture
- EBS provides **Block** storage - raw disk allocations (volume) - Can be **encrypted** using **KMS**.
	- Instances see **block device** and create **file system** on this device (ext3/4, xfs)
		- The important thing to grasp is that EBS volumes appear just like any other storage device to an EC2 instance.
- Storage is provisioned in **ONE AZ** (Resilient **in that AZ**). **EBS IS AN AZ SERVICE!**
	- Even though EBS is an availability zone-based service, you can create a backup of a volume into S3 in the form of a **snapshot**. Snapshots in s3 are now regionally resilient.
- Attached to one EC2 instance (or some other service) over a storage network
	- With some storage types, you can use a feature called multi-attach which lets you attach it to multiple EC2 instances at the same time. This is used for clusters. But if you do this, the cluster application has to manage it -so you don't overwrite data and cause data corruption by multiple writes at the same time. By default, think of EBS volumes as attached to one thing at a time.
	- **detached** and **reattached**, not lifecycle linked to one instance .. **persistent**.
		- If an instance moves between different EC2 hosts, then the EBS volume follows it.
		- If an instance stops and starts or restarts, the volume is maintained.
		- An EBS volume is created, it has data added to it, and it's persistent until you delete that volume.
- **Snapshot** (backup) into **S3**. Create volume from snapshot (migrate **between AZs**).
- Different physical storage **types**, different **sizes**, different **performance profiles**.
- Billed based on **GB-month** (and in some cases **performance**).
	- The price of one gig for one month would be the same as two gig for half a month, and the same as half a gig for two months.
	- There are some extras for certain types of volumes; for certain enhanced performance characteristics.

## EBS Volume Types - General Purpose
- GP2 is the default general-purpose SSD-based storage provided
- GP3 is newer

**EBS - General Purpose SSD - GP2**
![[EBS - General Purpose SSD - GP2.png]]
- Volumes can be as small as 1 GB, or as large as 16TB

- When you create a volume, it is created with an IO credit allocation. An IO credit is a 16KB chunk of data. An IOP is 16KB in one second. Transferring a 160KB file would be 10 IO blocks of data. If you do that in 1 second, that's 10 credits in one second. 10 IOPS.
- IO 'Credit' Bucket Capacity start with an initial **5.4** million IO Credits & fill at rate of **Baseline Performance**.
- Bucket Fills with min 100 IO Credits per second **Regardless of volume size**.
- Buckets replenish **3** IO credits per second **per GB** of volume size
	- This means that a 100 GB volume gets 300 IO credits per second, refilling the bucket.
	- Anything below 33.33 recurring GB gets this 100 IO minimum. Anything above 33.33 recurring gets three times the size of the volume as a baseline performance rate.
	- You aren't limited to only consuming at this baseline rate. By default, GP2 can **burst** up to **3,000 IOPS** by **depleting** the bucket.
		- The credit bucket, which starts full at 5.4 million IO credits, could run at 3,000 IOPS, so 3,000 IO per second, for a full 30 minutes.
			- And that assumes that your bucket isn't filling up with new credits, which it always is.
- Volumes which are up to one TB in size will use this IO credit architecture.

- But for volumes larger than one TB, they will have a baseline equal to, or exceeding, the burst rate of 3,000. And so they will always achieve their baseline performance as standard. They don't use this credit system.
- The maximum IO per second for GP2 is currently 16,000. So any volumes above 5.33 recurring TB in size achieves this maximum rate constantly.

- At the time of creating this, GP2 is the default. But I expect that to change over time to GP3 (as it's actually cheaper, in most cases).
- GP2 is great for boot volumes, for low latency interactive applications, or for dev and test environments. Anything where you don't have a reason to pick something else.
- You can also use the elastic volume feature to change the storage type between GP2 and all of the others.

**EBS - General Purpose SSD - GP3**
![[EBS - General Purpose SSD - GP3.png]]
- GP3 is SSD based, but it removes the credit bucket system for something simpler.
- Every GP3 volume starts with the standard 3000 IOPS (3016 KB operations per second) and it can transfer 125 MB per second.
	- This is standard regardless of volume size.
- Volumes can range from 1 GB through to 16 TB.
- Currently, the base price for GP3 is 20% cheaper than GP2.
	- If you only intend to use up to 3000 IOPS, then it's a no-brainer. Choose GP3 over GP2.
	- If you need more performance, then you can pay for up to 16,000 IOPS and up to 1,000 MB per second of throughput. And even with those extras, generally it works out to be more economical than GP2.
	- GP3 offers a higher max throughput as well, so you can get up to 1,000 MB per second versus the 250 MB per second maximum of GP2.
- Usage scenarios for GP3 are also much the same as GP2
	- virtual desktops, medium-sized databases, low latency applications, dev and test environments, and boot volumes
- You can safely swap GP3 to GP2 to GP3 at any point.
- Be aware that for anything above 3,000 IOPS, the performance doesn't get added automatically like with GP2, which scales on size.
	- With GP3, you would need to add these extra IOPS, which come at an extra cost, and that's the same with any additional throughput. Beyond the 125 MB per second standard, it's an additional extra. But still, even including those extras, for most things, this storage type is more economical than GP2.

## EBS Volume Types - Provisioned IOPS
- Provisioned IOPS SSD - IO1 and IO2.
- There are now three types of provisioned IOPS SSD: IO1, IO2, IO2 Block Express (in preview)
	- They all offer slightly different performance characteristics and different prices, but the common factors is that IOPS are configurable independent of the size of the volume and they're designed for super high performance situations, where low latency and consistency of that low latency are both important characteristics.

**EBS - Provisioned IOPS SSD (iol1, io2)**
![[EBS - Provisioned IOPS SSD (iol1, io2).png]]
- With IO1 and IO2 you can achieve a maximum of 64,000 IOPS per volume.
	- That's four times the maximum for GP2 and GP3.
- With IO1 and IO2 you can achieve 1,000 MB per second of throughput.
	- This is the same as GP3 and significantly more than GP2.
- With IO Block Express you can achieve 256,000 IOPS per volume and 4,000 MB per second of throughput per volume.
- Volume sizes you can use with provisioned IOPS SSDs:
	- With IO1 and IO2: 4 GB to 16 TB
	- With IO2 Block Express: up to 64 TB volumes
- You can allocate IOPS performance values independently of the size of the volume.
	- This is useful for when you need extreme performance for smaller volumes or when you just need extreme performance in general. But there is a maximum of the size to performance ratio.
		- For IO1 it's 50 IOPS per GB of size.
			- This is more than the 3 IOPS per GB for GP2.
		- For IO2 this increases to 500 IOPS per GB of volume size.
		- For Block Express this is 1,000 IOPS per GB of volume size.
		- These are all maximums. With these types of volumes you pay for both the size and the provisioned IOPS that you need.
- There is also another restriction that you need to be aware of - the **per instance** performance maximum (between the EBS service and a single EC2 instance). This is influenced by a few things:
	- The type of volumes.
	- The type of the EC2.
	- The size of the instance.
	- Only the most modern and largest instances support the highest levels of performance. These **per instance maximums** will also be **more than one volume** can provide on its own. And so you're going to need multiple volumes to saturate this per instance performance level. Think of this as a performance cap for an individual EC2 instance.
		- With **IO1** volumes you can achieve a maximum of 260,000 IOPS per GB. And a throughput of 7,500 MB per second.
			- It means you'll need just over four volumes of performance operating at maximum to achieve this per instance limit.
		- **IO2** is slightly less at 160,000 IOPS for an entire instance. And 4,750 MB per second.
		- **IO2 Block Express** can achieve 260,000 IOPS and 7,500 MB per second for an instance maximum.
	- These are the maximums for the volume types; you also need to take into consideration any maximums for the **type** and **size** of the instance. All of these things need to align in order to achieve maximum performance.

Keep these figures locked in your mind. It's not so much about the exact numbers. But having a good idea about the levels of performance that you can achieve with GP2 or GP3. And then IO1, IO2 and IO2 Block Express. Will really help you in real-world situations and in the exam. Instance store volumes can achieve higher performance, but they aren't persistent.

As a comparison, the per instance maximums for GP2 and GP3. Is 260,000 IOPS and 7,000 MB per second per instance.
	Don't focus too much on the exact numbers. But you need to have a feel for the ranges these different types of storage volumes occupy versus each other and versus instance store.

- Now you'll be using provisioned IOPS SSD. For anything which needs really **low latency**. Or sub millisecond latency. **Consistent** latency. And higher levels of performance. 
	- One common use case is when you have smaller volumes but need super high performance. That's only achievable with IO1, IO2 and IO2 Block Express.

## EBS Volume Types - HDD-Based
**ST1** - Throughput optimized HDD
- Designed for data which is sequentially accessed. Not great at random access (because it's HDD based)
- ST1 volumes range from 125 GB to 16 TB in size
- 500 IOPS (1MB blocks) - so, 500MB/s

HDD-based storage works in a similar way to how GP2 volumes work with a credit bucket, only with HDD-based volumes, it's done around MB per second rather than IOPS.

- With ST1, you have a baseline performance of **40 MB** per second for every **1 TB** of volume size
- Burst to a maximum of **250 MB** per second for every **TB** of volume size
	- Up to the maximum of 500 IOPS and 500 MB per second

**ST1** is designed for throughput intensive, sequential workloads (when data is sequentially accessed). Big data, data warehousing, log processing.

**SC1** - cold HDD

**SC1**, on the other hand is designed for infrequent workloads. It's geared towards maximum economy when you just want to store lots of data and don't care about performance.
- Max 250 IOPS (1MB)
- Max 250 MB/s of throughput.
- 12MB/s/TB Base
- 80MB/s/TB Burst

This offers significantly **less performance** than ST1, but is cheaper.

- Volumes range from 125 GB to 16 TB in size.

This storage type is the **lowest cost** EBS storage available.

It's designed for less frequently accessed workloads.

## Instance Store Volumes - Architecture
Understand the pros and cons.
It can save money, improve performance, or it can cause headaches.

**Instance Store Volumes**
- Provide **Block Storage** Devices
- Physically connected to **one EC2 Host**
- Instances **on that host** can access them
- Highest storage performance in AWS
- Included in instance price. Use it or lose it.
- (**exam**) **ATTACHED AT LAUNCH** - store volumes can't be added later. Only at launch.

Think of instance store as ephemeral.
If an instance store moves between hosts, any data on its store will be lost.
If an instance is stopped & started again, this causes a migration between hosts. Data will be lost.

You can achieve much **higher** levels of **throughput**, and more **IOPS** by using instance store volumes **versus EBS**.

D3 is storage optimized.
- D3 = 4.6 GB/s throughput
i3's have NVMe's
- 13 = 16 GB/second of sequential throughput

- Instance store volumes are local to an **EC2 host**.
- Add at **launch only**
- Lost on instance **move**, **resize**, or **hardware failure**
- High performance
- You pay for it anyway - included in instance price
- **TEMPORARY**

## Choosing between the EC2 Instance Store and EBS
(**exam**) Considerations to choose between EC2 Instance Store and EBS:
- If you need **persistent** storage - **EBS**.
- **Resilience** - **EBS**.
	- If hardware fails, instance store can be lost.
- Storage **isolated** from instance **lifecycle** - **EBS**.
- **Resilience** w/ app **in-built replication** - it **depends**
	- You can use lots of instance store volumes on lots of volumes, so you get the performance benefits but without the negative risks.
- High performance needs - it **depends**
- Super high performance needs - **Instance Store**
- **Cost** - **Instance Store** (it's often included)

**Remember all of these figures** - these are some of the few numbers you need to know for the exam.
- Cheap - ST1 or SC1
	- If you see questions on the exam which focus purely on cost efficacy, you should use ST1 or SC1 because they're cheaper - they HDDs, so they're cheaper than SSDs.
	- If the question mentions **Throughput** or **streaming**, you should default to **ST1**.
	- Unless the question mentions **Boot Volumes** - **not ST1 or SC1**.
- **GP2/3** - can deliver up to 16,000 IOPS per volume
	- With GP2, this is based on volume size. With GP3, you can pay for additional performance. But, for both, the max performance is 16,000 IOPS.
- IO1/2 - up to 64,000 IOPS (*256,000 - OP2 Block Express - these numbers must be paired with the largest EC2 instances to deliver those performance levels).
- **RAID0** (with **EBS** volumes) up to **260,000** IOPS (io1/2-BE/GP2/3)
	- Need a large size of instance, and enough EBS enough volumes to saturate.
- More than 260,000 IOPS - **Instance Store**
	- But, you need to be able to tolerate lack of **persistence**.

## Snapshots, Restore & Fast Snapshot Restore (FSR)
- Efficient way to backup EBS volumes to S3
- Protect the data on those volumes against **availability zone** issues or local storage system failure in that availability zone
- Can also be used to **migrate** the data that's on **EBS volumes** between **availability zones** using S3 as an intermediary

- Snapshots are incremental volume copies to S3
	- S3 is **region** resilient
- The first is a full copy of '**data**' on the volume
- Future snaps are **incremental**
	- They only store the difference between the previous snapshot and the state of the volume when the snapshot is taken
	- Even if you accidently delete one of the incremental snapshots, can be thought of as self-sufficient (EBS is smart enough) - that is, the restore will still work even if you accidently delete one of the incremental snaps.
- Volumes can be created (restored) from snapshots. This can be done in a **different AZ**.
- Snapshots can be copied to another **region**
	- So, you can use snapshots for global DR processes

![[EBS Snapshot Architecture.png]]

- New EBS volume = **full performance immediately**
- **Snaps restore lazily** - fetched gradually
- Requested blocks are fetched immediately
	- Force a read of all data immediately
		- Used with OS tools such as dd in linux.
	- This is generally something you would do after doing a restore before moving that volume into production to ensure performance. Historically this was the only way to do a rapid restoration of a volume, but now there's a feature called ...
- Fast Snapshot Restore (**FSR**) - Immediate restore
	- You can create 50 per region. When you enable it on a snapshot, you set **Snap & AZ**'s you want to do restores to. Each combination of that Snap + that AZ = 1 FSR.
		- 1 Snap configured to restored to 4 AZs represent 4/50 of the FSRs for that region.
	- FSR costs extra. It can get expensive, especially if you have lots. You can always achieve the same result by forcing a read of every block manually by using `dd` or another tool in the operating system.

**Storage Consumption and Billing**
- Cost per Gigabyte-month
- Snapshots are billed for data that's **Used** on the volumes, NOT allocated data
- Incremental
	- Because they're incremental, you can perform them regularly. Only the data that's changed is stored. Snapping more frequently won't necessarily cost more.

**End of Demo Notes**
- EBS Volumes are created within 1 AZ
- EBS volumes can be mounted to instances in that AZ only & can be moved between instances while retaining their data.
- You can created a snapshot from an EBS volume (stored in S3) - that data is replicated within the region; then you can use snapshots to create volumes in different AZs.
- Snapshots can be copied to other AWS regions - as data migration or DR
- EBS is persistent (not ephemeral like instance store)
- Instance Store volumes
	- If an instance moves hosts (STOP & START, or hardware failure), then data on the instance store volume will be lost.

## EBS Encryption
EBS volumes are block storage devices presented over the network. They're HA to an AZ. By default, no encryption is applied.

**EBS Encryption**
![[EBS Encryption.png]]

- When you create an encrypted EBS volume initially, EBS uses KMS and a KMS key to generate a DEK (using the GenerateDataKeyWithoutPIaintext API call)
	- Which can either be the EBS default (aws/ebs)
	- Or it can be a customer managed KMS key that you create and manage
The DEK is stored with the volume on the raw storage. It can only be decrypted using KMS, and the entity doing needs permissions to decrypt the DEK using the corresponding KMS key.

On disk, data is ciphertext. Data only exists in an unencrypted form inside the memory of the EC2 host.

**EBS Encryption2**
![[EBS Encryption2.png]]
 When the EC2 instance moves from this host to another, the decrypted key is discarded, leaving only the encrypted version with the disk. For that instance to use the volume again, the encrypted data encryption key needs to be decrypted and loaded into another EC2 host. If a snapshot is made of an encrypted volume, the same data encryption key is used for that snapshot. Meaning the snapshot is also encrypted. Any volumes created from that snapshot are themselves also encrypted using the same data encryption key. And so they're also encrypted.

EBS encryption doesn't cost anything to use, so it's one of those things which you should really use by default.

**Remember** these **hints** because the exam asks curveball questions around encryption:
- Accounts can be set to **encrypt by default** - **default KMS Key**.
- Otherwise **choose a KMS Key** to use.
- Each volume uses 1 unique DEK.
	- (The KMS key isn't used to directly encrypt or decrypt EBS volumes; instead it's used to generate a per volume DEK).
		
- **Snapshots** & **future volumes** use the **same DEK**
	- If you do make snapshots or create new volumes from those snapshots, then the same data encryption key is used.
	- But for every single time you create a brand new volume from **scratch**, it uses a **unique** DEK.
- Can't change a volume to **NOT** be encrypted
	- There are ways that you can manually work around this by cloning the actual data from inside an operating system to an unencrypted volume, but this isn't something that's offered from the AWS console, the CLI, or the APIs
- OS isn't aware of the encryption ... **no performance loss**
	- There's something else called *software disk encryption* in which the OS encrypts things (& the OS holds the keys rather than EC2, EBS, and KMS). To do this, you'll need to configure volume encryption within the operating system itself. you can use software disk encryption within the operating system and EBS encryption at the same time, but it doesn't really make sense for most use cases.

EBS encryption is really efficient though, you don't need to worry about keys, it doesn't cost anything, and there's no performance loss for using it.

## Network Interfaces, Instance IPs and DNS
Every EC2 instance has **at least one ENI** (elastic network interface) (the primary interface or primary ENI). Optionally, you can attach one or more secondary ENIs, which can be in separate subnets, but everything needs to be within the same AZ.
	Remember, EC2 is isolated in one AZ. An instance can have different network interfaces in separate subnets, but all of those subnets need to be in the same AZ.

![[EC2 Network & DNS Architecture.png]]

 Security Groups are attached to ENIs, not directly to instances.
 Network interfaces have things attached to them:
 - MAC address - hardware address of the interface. Visible in the OS. So, it can be used for things like software licensing.
 - Primary IPv4 Private IP
	 - that's from the range of the subnet that the interface is created in.
	 - When you select a VPC and a subnet for an EC2 instance, what you're actually doing is picking the VPC and the subnet for the primary network interface
- 0 or more secondary (private) IPs
- 0 or 1 Public IPv4 Address
- 1 elastic IP per private IPv4 address
	- With elastic IP addresses, you can have one public elastic IP address per private IP address on this interface. With normal public IPv4 addresses, you have 1 per interface.
- 0 or more IPv6 addresses
	- Remember, these are by default publicly routable; there's no public / private distinction; they're all public.
- Security Groups
	- Applied to Network Interfaces.
- Source/Destination Check
	- If traffic is on the interface, it's going to be discarded if it's not **from** one of the IP addresses on the interface as a **source**, or **destined** to one of the IP addresses on the interface as a **destination**. If this is enabled, traffic is discarded if it doesn't match one of those conditions.

The **capabilities** of the **secondary** interfaces are the **same** as the primary, except that you can **detach** secondary interfaces and move them to other EC2 instances.

![[EC2 Network & DNS Architecture2.png]]

The instance is also given a DNS name that's associated with this private address.
Logical Format: ip-x-x-x-x.ec2.internal
You can use this private DNS name for internal communications only inside the VPC.

Assuming that the instance is either manually set, to receive a public IPv4 address, or that it's launched with the default settings into a subnet, which is configured to automatically allocate IPv4 public addresses, then it will get one. But this is a dynamic IP. If you stop an instance, its public IPv4 address is deallocated. When you start it, it's allocated a brand new IPv4 address. Restarting the instance won't change the IP address. Anything that would cause an instance to change hosts will cause an IP address change.

EC2 instances are also allocated a **public DNS name**.
Format: ec2-x-x-x-x.compute-1.amazonaws.com.
What's special about this public DNS name is that inside of this format, inside the VPC it will resolve to the primary private IPv4 address of the instance, so the primary network interface.
	Remember how VPC works, this public IP version 4 IP address is not directly attached to the instance or any of the interfaces. It's associated with it, and the internet gateway handles that translation. So, in order to allow instances in a VPC to use the same DNS name and to make sure they're always using the private addresses inside the VPC, it always resolves to the private address. Outside of the VPC, the DNS will resolve to the public IP version 4 address of that instance

**Elastic IP addresses**
- Allocated to your AWS account
- When you **allocate** an elastic IP you can associate the elastic IP with a private IP - either on the primary interface or a secondary interface.
	- If you do associate it with the **primary** interface, then as soon as you do that the normal (the non-elastic IPv4) address that the instance had is removed and the elastic IP becomes the instance's new public IPv4 address. If you remove that elastic IP address, it will gain a new public IP version 4 address.
		- **This question comes up on the exam all the time.**
			- An instance has a non-elastic public IP, and you assign an elastic IP and then remove it; is there any way to get that original IP back? And the answer is no, there's not.

**Exam Tips**
- Secondary ENI + MAC = Licensing
	- Lots of legacy software is licensed using MAC addresses (a MAC address is viewed as something that can't change). But, because EC2 is a virtualized environment, then we can swap and change ENIs. If you provision a secondary ENI on an instance and use that secondary network interface as MAC address for licensing, you can detach that secondary interface and attach it to a new interface. 
- Multi-homed (subnets) Management & Data
	- An instance with an ENI in two different subnets
	- You might use multiple interfaces rather than just multiple IPs. Why?
		- Security groups are attached to interfaces
		- Per interface you can also enable or disable the source and destination check.
- Different Security Groups - **multiple interfaces**
	- If you need different rules, so different security groups, for different IPs or different rules for different types of access based on IPs your instance has, then you need multiple ENIs with different SGs on each.
		- When you interact with an instance and apply security groups, if you're doing it on an instance level, you're generally interacting with the primary ENI. In many ways, **you can almost think of the primary interface as the instance in a way**, but they are separate things.
- OS - DOESN'T see public IPv4
	- This is provided by a process called NAT, which is performed by the IGW.
	- As far as the operating system is concerned, you always configure the private IPv4 address on the interface, always. The OS never has visibility of the networking configuration of the public IPv4 address. You will never be in a situation where you need to configure Windows or Linux with the IP version 4 public address. IPv6 is different, because they're all public.  for the exam, just remember this: **you never configure a network interface inside an operating system with a public IPv4 address** inside AWS. 
- IPv4 Public IPs are **Dynamic**. Stop & Start (or migrating hosts) = Change
- Public DNS = **private IP in VPC**, public IP everywhere else
	- This is done so that communication between two EC2 instances using the public DNS will stay inside the VPC. It doesn't have to go to the IGW & then back.

## Amazon Machine Images (AMI)
AMIs are one way that you can create a template of an instance configuration, and then use that template to create many instances from that configuration.

- AMI's can be used to **launch EC2** instance
- **AWS** or **Community** Provided
- Marketplace (can include **commercial software**)
- **Regional** .. **unique ID** e.g. ami-Oa887e40106549351
- Permissions (Public, Your Account, Specific Accounts)

You can create an AMI from an existing EC2 instance to capture the current configuration of that instance.

When you make an AMI, any EBS volumes which are attached to that EC2 instance will have EBS snapshots created from those volumes. Those snapshots are referenced inside the AMI using block device mapping. Block device mapping is a table of data - it links the snapshot IDs & device ID the original volumes had. This means that when this AMI is used to create a new instance, this instance will have the same EBS volume configuration as the original.

AMIs are a regional construct. Snapshots are stored in S3 (already regional). AMIs can be used to deploy instances into the same AZ as the source instance, or other AZs in that region.

![[AMI Lifecycle.png]]

**AMI Exam Tips**
- AMI = **One Region**, only works in that one region
- **AMI Baking** .. creating an AMI from a configured instance + application
- An AMI **can't be edited** .. launch instance, update configuration and make a new AMI
- Can be copied **between regions** (includes its snapshots)
- Remember permissions **default = your account**

Billing for AMIs:
AMI does contain EBS snapshots, and so you are going to be billed for the **capacity** used by those **snapshots** (remember that that snapshots only store the data used in EBS volumes).

## EC2 Purchase Options
For all projects, start with On-Demand as your choice and choose another purchase option if you can justify it.

![[EC2 Purchase Options - On Demand.png]]

- No capacity reservation
	- If AWS has a major failure and capacity is limited, the reserved purchase option receives highest provisioning priority on whatever capacity remains.
	- If something is critical to your business, then you should consider an alternative rather than using on-demand.
- On-demand offers predictable pricing. It's defined upfront. You pay a constant price, but there are no specific discounts.
	- Pricing applies to the duration that you use instances.
		- So, on-demand is suitable for short-term workloads: provision - workload - terminate.

If you're unsure about the duration or the type of workload, then on-demand is ideal.
If you have short-term or unknown workloads, which definitely can't tolerate any interruption, then on-demand is the perfect purchase option.

###### Spot
![[EC2 Purchase Options - Spot.png]]

Spot Pricing:
A customer elects a spot price. That's their maximum willingness to pay for spot instances.
Amazon sets the spot price (based on demand). If Amazon raises the spot price above your willingness to pay, your instances are terminated.

###### Reserved
On-demand is generally used for unknown or short-term usage which can't tolerate interruption, reserved is for long-term consistent usage of EC2.

You need to be sure that you plan reservations appropriately because it's possible to purchase them and not use them. **Once you commit, you pay.**

![[EC2 Purchase Options - Reserved.png]]

- Reservations can be purchased for a particular **type** of **instance** and locked to an **AZ** specifically or to a **region**.
	- If you purchase a reservation to an **AZ**, it reserves **capacity** AND you get better price.
	- If you purchase reservation for a region, it doesn't reserve capacity, but it can benefit instances which are launched to any AZ in that region.

Choices in how you pay for reservations:
- Term length - 1 year or 3 year.
	- 3 Year commitment saves more $ (greater discount), but you bear greater risk from longer term commitment (likelihood of changing requirements).
- Payment schedule
	- Upfront - ALL - cheapest
	- Upfront - Partial - middleground
	- Upfront - None - no per/s Fee savings.

Reserved instances are ideal for components of your infrastructure, which have known usage, require consistent access to compute, and you require this on a long term basis.
There are some other elements to reservations that I want to talk about, such as **capacity** reservations, **conversion** and **scheduled** reservations, but I'll be doing that in a dedicated lesson.

###### Dedicated Hosts

![[EC2 Purchase Options - Dedicated Hosts.png]]
You pay for a host which is designed for a specific family of instances (A, C, R, etc ...). You pay for the host; any instances which run on that host have **no per second charge**.

Why might you use a dedicated host?
You might have software which is licensed based on sockets or cores in a physical machine. This type of licensing still exists (applies to physical machine - not to resources allocated to virtual machines).

Dedicated hosts have a feature called host affinity, linking instances to certain EC2 hosts. This can have licensing implications.

###### Dedicated Instances
![[EC2 Purchase Options - Dedicated Instances.png]]

- First, you pay a one-off hourly fee for any regions where you're using dedicated instances.
	- This is regardless of how many you're utilizing.
	- There's a fee for the dedicated instances themselves.

Dedicated instances are common in sectors of the industry with strict requirements which prohibit sharing infrastructure.

The **default** or **shared** model is used for on-demand, for spot, and for reserved instances.
**Dedicated hosts** are generally used when you have strict licensing requirements.
**Dedicated instances** are used when you have requirements not to share hardware.

## Instance Status Checks & Auto Recovery
![[Instance Status Checks.png]]

- The first status check is the system status.
	- Could fail due to:
		- loss of system power
		- loss of network connectivity
		- software or hardware issues with the EC2 **host**
- The second is the instance status

2) EC2 auto recovery (Actions > Create Status Check Alarm)

	3) Alarm Action: Recover
		1) Remember, EC2 is an AZ-based service. So, this won't protect you against an entire AZ failure.
		2) This feature relies on having spare EC2 host capacity.

		4) Won't work if you're using instance store volumes (it will only work on instances which solely have EBS volumes attached)

To add another layer of protection against accidently terminating an EC2 instance, you can R click > Instance Settings > Turn on Termination Protection.

## Horizontal & Vertical Scaling
**Vertical Scaling**
- Each resize requires a reboot - **disruption**
- Larger instances often carry a **$ premium**
- There is an upper cap on performance - **instance size**
- **No application modification** required
- Works for ALL applications - **even Monoliths**

**Horizontal Scaling**
Many copies of your app running on many servers. All need to take their share of incoming load. And this generally means some form of load balancer.
- **Sessions**
	- When you think about horizontal scaling, **sessions** are everything. The state of your interaction with that application is called a session. With a single application running on a single server, the sessions of all customers are generally stored on that server. With horizontal scaling, this won't work.
 - Requires application support OR **off-host sessions** (your session data is stored in another place, like an external database)
	 - This means that the servers are **stateless** (just dumb instances of your app - they have no session data).
 - **No disruption** when scaling
 - **No real limits** to scaling
 - Often less expensive - **no large instance premium**
 - More granular
