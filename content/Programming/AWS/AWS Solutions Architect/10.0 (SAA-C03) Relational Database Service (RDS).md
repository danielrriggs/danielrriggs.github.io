## Database Refresher - Part 1
- Relational; SQL
- Structure in & between tables of data - Rigid Schema.
	- Relationships between tables
- NoSQL isn't one thing - different models
	- Generally more relaxed schema
	- Relationships handled differently

RDBMS
- Records have a PK
- A Join Table = a composite key. (A composite key in its entirety must be unique).

Because the schema is fixed and must be declared in advance, it's difficult to store any data which has rapidly changing relationships.

**NoSql**
- Key-Value
	- No Schema. No Structure. Scalable. Really fast.
	- Only the key matters. You write and read values to keys. Only the key matters to the database.

(**exam**) Key-Value stores are generally used for **in memory caching**.

**Wide Column Store**
A variation on Key-Value.
	Each row has 1 or more keys. 1 is called the partition keys. Optionally, you can have additional keys as well as the partition key. In DynamoDb (an AWS example of this type), this secondary key is called the **sort** or the **range** key.
Every item in a table has to have the same key layout. So that's one key or more keys, and they just need to be unique to that table.

![[Wide Column Store.png]]

Wide column stores offer groupings of items called **tables**, but they're still not the same type of tables as in relational databases. They're just **groupings of data**.

Every item in a table can also have attributes. But, and this is really important, they **don't have to be the same** between items. This is different than an RDBMS. The only rule for placing data into a table using wide column stores is that every item in a table has to use the same key structure, and it has to have a unique key - whether it's a single partition key, or a composite key (combination of the values must be unique).

Wide column stores are fast & scalable. As long as you don't need to run relational operations such as SQL commands on the database, it often makes the perfect database product to take advantage of, which is one of the reasons why DynamoDB features so heavily amongst many web-scale or large-scale projects.

**Document Database**
You can think of a document database almost like an extension of a key value store, where each document is interacted with via an ID that's unique to that document. But the value, the document contents, are exposed to the database, allowing you to interact with it. Each document has a unique ID, and the database has access to the structure inside the document.

![[Document Database.png]]

- Generally formatted using a structure such as JSON or XML
	- The structure can be different between documents in the same database

Document Dbs are good for the following use cases:
- Situations where you generally interact with the data as a document
	- Ex: order databasess, collections, contact-style databases
- When you need to interact with deep attributes (nested data items within a document structure)
- catalogs, user profiles, CMS's
	- where each document is unique, but it changes over time
	- it might have different versions
	- documents might be linked together in hierarchical structures (different pieces of content for a CMS)

Document databases provide flexible indexing, so you can run really powerful queries against the data that could be nested deep inside a document.

**Column-based databases**
Limitations of row-based databses:
Rows are stored on disk together. If you needed to read the price of one order from the database, you read the whole row from disk.

![[Column Database.png]]

If you don't have indexes or shortcuts, you'll have to find that row first, and that could mean scanning through rows and rows of data before you reach the one that you want to query. Now if you want to do a query which operates over lots of rows, for example, you wanted to query all of the sizes of every order, then you need to go through all of the rows, finding the size of each.

**Row-based** databases are ideal when you operate on rows, creating a row, updating a row, or deleting rows. Row-based databases are often called **OLTP**, or online transaction processing databases, and they are ideal, as the name suggests, for systems which are performing transactions. Things like order databases, contact databases, stock databases. Where these rows and items are constantly accessed, modified, and removed.

Column-based databases handle things very differently. Instead of **storing** data in rows **on disk**, they store it **based on columns**. The data is the same, but it's grouped together on disk based on column. 
This means two things:
- It makes sense to store data in columns, because it makes it very very **inefficient** for **transaction**-style processing (which is generally operating on whole rows at a time).
- Good for **reporting**.
	- If your queries relate to just one particular column, because that whole column is stored on disk grouped together, then that's really efficient.
- Example column-based database in AWS: Redshift, a data warehousing product.
	- Generally, what you'll do is take the data from an OLTP database, a row-based database, and you'll shift that into a column-based database when you're wanting to perform reporting or analytics.

**Graph-style databases**
Relationships between things are stored in the db along with the data. They aren't calculated every time you run a query. This is good for relationship driven data, like social media or HR systems.

![[Graph Database.png]]

Nodes (objects) can have properties which are simple key-value pairs of data.
With graph databases, there are also relationships between the nodes, which are known as **edges**. Edges have a name and a direction.

A query to pull up details on all employees of XYZCorp would run much quicker than on a standard SQL database because that data of those relationships is just being pulled out of the database, just like the actual data. With a relational-style database, you'd have to retrieve the data, and the relationships between the tables is computed when you execute the query. So it's a really inefficient process with relational database systems. These relationships are fixed and computed each and every time a query is run. With a graph-based database, those relationships are fluid, dynamic.

## ACID vs BASE
- **ACID** and **BASE** are DB transaction models
- [[CAP Theorem]]
- [[ACID]] = Consistency
	- (**exam**) - Generally, if you see ACID mentioned, generally, it's referring to any of the RDS databases. These are generally ACID based.
	- ACID limits the ability of a database to scale.
- [[BASE]] = Availability
	- Advantages: **performance**, because they don't need to worry about things like consistency within the database. They offload that to the applications.

(**exam**) Tips:
- If you see the term BASE mentioned, you can safely assume it means a NoSQL-style database.
- If you see the term ACID, you can safely assume it means an RDS database.
- But, if you see NoSQL or DynamoDB mentioned together with ACID, then it might be referring to DynamoDB transactions.

## Databases on EC2
It's always a bad idea to manually run databases on EC2. Let's discuss arguments around whether the benefits to you or your business outweigh the fact that it is a bad idea.

![[Databases on EC2.png]]

Generally, when people think about running databases, they picture one of two architectures in the picture above.

When you split up the components into separate instances, you've introduced a dependency into the architecture. The dependency you've introduced is that there needs to be reliable communication between the instance running the application and the database instance. If not, the application won't work.

If you do decide to split these instances across multiple availability zones, then you should also be aware that there is a cost for data when it's transiting between different availability zones in the same region. It's small, but it does exist. That's in contrast to where communications between instances using private IPs in the database, in the same availability zone, is free.

Reasons why you **might want** to run databases on EC2 in your own environment:
- Access to the DB Instance **OS**
	- There aren't many situations where **OS-level access** is really a requirement. You should really **question / challenge** this requirement.
- **Advanced DB Option tuning**... (DBROOT)
	- There are some database tuning things which can only be done with root-level access, and because you don't have this level of access with managed database products, then these values, or these configuration options, won't be tunable.
	- In many cases AWS allows control for a lot of these parameters that historically you would need root access for.
		- This is one of those situations where you need to **question / challenge** any situation where it's presented to you that you need **database root access**
- DB or DB Version AWS don't provide..
	- Niche use cases for Db which isn't supported by AWS. This is often one justified reason to run Dbs on EC2.
- Specific **OS/DB Combination** AWS don't provide
- Architecture AWS don't provide (replication/resilience)
- Decision makers who '**just want it**'

Why you shouldn't really run databases on EC2:
- **Admin overhead** - managing EC2 and DBHost
	- Don't underestimate the effort required to keep an EC2 instance patched or keep a database host running at a certain compatible level with your application.
- **Backup** / DR Management
	- Running DBs on EC2 adds alot of additional complexity.
- EC2 is **single AZ**
	- You need to worry about taking EBS snapshots inside the database server and putting those on storage somewhere, maybe S3. This is more admin overhead and risk for the business.
- **Features** - some of AWS DB products are amazing
- EC2 is **ON** or **OFF** - no serverless, no easy scaling
- **Replication** - skills, setup time, monitoring & effectiveness
- **Performance** - AWS invest time into optimization & features

## Relational Database Service (RDS) Architecture
- Database as a Service (**DBaaS**) is incorrect
- Database **Server** as a Service (**DBSaaS**) is correct
- Multiple databases on one DB Server (instance)
- Choice of DB Engines (MySQL, MariaDB, PostgreSQL, Oracle, Microsoft SQL Server)
	- Licensing implications
- Amazon Aurora* is a different product

RDS isn't a public service. It runs within (subnets within) a VPC (in a specific AWS region).

You can think of an **RDS subnet group** as a list of subnets which RDS can use for a given database.

**RDS Architecture**
![[RDS Architecture.png]]
When launching an RDS instance you pick to have it highly available or not. You need to pick a DB subnet group to use. It would pick one subnet for the primary instance, and another for the standby. It picks at random unless you indicate a specific preference (it will put the primary and standby within different AZs).

Now because these database instances are within private subnets, it means that they would be accessible from inside the VPC or from any connected networks, such as on-premises networks connected using VPNs or Direct Connect, or any other VPCs which appeared with this one.

Making RDS instances in public subnets publicly accessible by giving them public addressing is really frowned upon from a security perspective. But it's something that you need to know is an option when deploying RDS instances into public subnets.

You can use a single DB subnet group for multiple instances, but then you're limited to using the same defined subnets. Generally as a best practice, I like to have **one DB subnet group** for **one RDS deployment**.

- RDS instances can have multiple databases on them
- Every RDS instance has its **own dedicated storage** provided by **EBS**
	- If you have a multi-AZ pair (primary and standby), each has their own dedicated storage
	- This is different than how Amazon Aurora handles storage.

If you choose to use **multi-AZ** then the primary instances **replicate** to the standbys using **synchronous** replication.
You can also have **read replicas** (RRs), which use **asynchronous** replication. They can be in the same region or other AWS regions.
Lastly, we also have **backups** of RDS. Backups occur to S3. The data is replicated across multi-az's. If you have an AZ failure, backups will ensure your data is safe. If you use multi-AZ mode, backups occur from the standby instance, which means no negative performance impact.

**Costs**
You're billed for resource allocation.
- Cost #1 - Instance Size & Type
- Cost #2 - Multi AZ or not
- Cost #3 -Storage type & amount
	- Per GB monthly fee.
	- Certain types of storage, such as provisioned IOPS, cost more.
		- This is in line with how EBS works (because the storage is based on EBS).
- Cost #4 - Data transferred
	- Cost per GB of data transferred in and out of your Db instance from or to the internet and other AWS regions.
- Cost #4 - Backups & Snapshots
	- You get the **amount of storage** that you pay for for the database instance **in snapshot storage** for free
		- So if you have 2 TB of storage, then that means 2 TB of snapshots for free. Beyond that, there is a cost, and the **cost** is gig per month of storage.
- Cost #5 - Licensing* (if applicable)

## Relational Database Service (RDS) MultiAZ - Instance and Cluster
Historically, only method of providing high availability which RDS had was Multi-AZ. This is now called **Multi-AZ instance** deployment.

**RDS - Multi AZ - Instance**
![[RDS - Multi AZ - Instance.png]]
With this architecture, RDS has a **primary** database instance containing any databases that you create. And when you enable Multi-AZ mode, this primary instance is configured to **replicate** its data **synchronously** to a **standby replica**, which is running in another instance. This means that this standby also has a copy of your databases. In Multi-AZ instance mode, this replication is at the storage level. This is actually less efficient than the cluster Multi-AZ architecture.

The method RDS uses depends on the database engine you pick. MariaDB, MySQL, Oracle, and PostgreSQL use Amazon failover technology. Microsoft SQL instances use SQL server database mirroring or always-on availability groups. This is abstracted away. All you need to understand is that it's a **synchronous replica**.

All accesses to the databases are via the database CNAME. This is a DNS name which by default points at the primary database instance. With Multi-AZ instance architecture, **you always access the primary** database instance. There's **no access to the standby**, even for things like reads. Its job is to simply sit there until you have a failure scenario with the primary instance. Other things though, such as **backups**, can occur from the standby. Data is moved into S3 and then replicated across multiple availability zones in that region. This places no extra load on the primary because it's occurring from the standby.

In the event that anything happens to the primary instance, this will be detected by RDS and a failover will occur. This can be done manually if you're testing or if you need to perform maintenance, but generally this will be an automatic process. In this scenario, the database CNAME changes. Instead of pointing at the primary, it points at the standby.

Because this is a DNS change, it generally takes between 60 to 120 seconds for this to occur. So there can be brief outages. This can be reduced by removing any DNS caching in your application for this specific DNS name.

**Summary**
- Data => Primary AND Replicated to StandBy = **Committed** (Synchronous)
- Not free tier ... extra cost for replica
- ONE StandBy replica ONLY
	- Which can't be used for reads or writes
- 60-120 seconds failover
- Same region only ... different AZs in the same region
- **Backups** taken from **standby** to **improve performance**
- AZ Outage, Primary Failure, Manual failover, Instance type change and software patching

**Multi-AZ Cluster**
![[Multi-AZ Cluster.png]]
With this mode RDS is capable of having one writer replicate to two reader instances.
This is a key difference between this and Aurora. With this mode of RDS Multi-AZ you can have two readers only. These are in different AZs than the writer instance but there will only be two. Whereas with Aurora you can have more.

Your application needs to understand that it can't use the same instance for reads and writes. But it means that you can use this Multi-AZ mode to scale your read workloads.

Data is sent to the writer and it's viewed as being **committed** when at least one of the readers confirms that it's been written. At that point, it's resilient across multiple AZs within that region.
In RDS Multi-AZ mode each instance still has its own local storage. This is different than Aurora.

You access the cluster using a few **endpoint types** (same as Aurora).
1) For example, the database CNAME points at the **writer** and can be used for reads and writes and administration functions.
2) There's a **reader endpoint** and this points at any available reader within the cluster. In some cases this does include the writer instance. In general operation though this reader endpoint will be pointing at the dedicated reader instances. This is how reads scale.
3) Finally there are instance endpoints - each instance in the cluster gets one of these. Generally it's not recommended to use them directly. You generally only use these for testing and fault finding.

**Summary**
- 1 Writer and 2 Reader DB instances (different AZs)
	- This gives you a higher level of availability compared to instance mode, because you have the 2 readers instead of the 1 standby instance.
	- Much faster hardware, Graviton + local NVME SSD Storage
	- Fast writes to local storage => flushed to EBS
	- Readers can be used for reads ... allowing some read scaling
- Replication is via transaction logs ... more efficient
	- Also allows for faster failover. Instead of 60-120 seconds. Can occur in as little as 35 seconds.
- Writes are "**committed**" when 1 reader has confirmed

## RDS Automatic Backup, RDS Snapshots and Restore
Within RDS there are two types of backup-like functionality: **automated** backups, and **snapshots**.
	(**exam**) Both use AWS managed buckets (which are invisible to you). You can see backups in the RDS console, but you can't move to S3 and see any form of RDS bucket, which exists for backups.

**RDS Backups - General**
![[RDS Backups - General 1.png]]
S3 is regionally resilient. Data's replicated across multiple AZs within that region.

RDS backups, when they do occur, are taken, in most cases, from the standby instance if you have Multi-AZ enabled. While they do cause an I/O pause, this occurs from the standby instance, and so there won't be any application performance issues. If you don't use Multi-AZ, for example with test and development instances, then the backups are taken from the only available instance, so you may have pauses in performance.

**RDS Backups - General**
![[RDS Backups - General 2.png]]
Snapshots aren't automatic. They're things that you run explicitly, or via a script or custom application. Run against an RDS database instance. They're stored in S3 (managed by AWS). They function like the EBS snapshots. Snapshots and automated backups are taken of the instance, which means all the databases within it, rather than just a single database. The **first** snapshot is a **full copy** of the data stored within the instance, and **from then on**, snapshots **only** store **data which has changed** since the last snapshot.

When any snapshot occurs, there is a brief interruption to the flow of data between the compute resource and the storage. If you're using Single-AZ, this can impact your application. If you're using Multi-AZ, this occurs on the standby, and so won't have any noticeable effect.

(**exam**) **Snapshots don't expire**. You have to clear them up yourself. They live on past when you delete the RDS instance. They're only deleted when **you delete them manually**.

One way that lower recovery point objectives can be met is by taking more frequent snapshots.

**Automated Backups**
There is another part to RDS backups, and that's **automated backups**. These occur once per day, but the architecture is the same. The first one is a full, and any ones which follow only store changed data. So far, you can think of them as though they're automated snapshots. If you're using single AZ, you should make sure that this happens during periods of little to no use, as again, there will be an I/O pause. If you're using multi-AZ, this isn't a concern, as the backup occurs from the standby. In addition to this automated snapshot, every five minutes, database transaction logs (which store the operations which change the data) are also written to S3. Together with the snapshots created from the automated backups, this means a database can be restored to a point in time with a five-minute granularity. In theory, this means a five-minute recovery point objective can be reached.

Automated backups aren't retained indefinitely. They're **automatically cleared up** by AWS, and for a given RDS instance, you can set a retention period from **zero to 35 days**. Zero means automated backups are disabled. 35 days means you can restore to any point in time over that 35-day period using the snapshots and transaction logs. But it means that any data older than 35 days is automatically removed.

- RDS can replicate backups to another region
	- both snapshots and transaction logs
- Charges apply for the cross-region data copy
	- and the storage in the destination region
- **NOT DEFAULT** ... configured within automated backups

**Restores**
RDS restores creates a **new RDS instance** when you restore an automated backup or a manual snapshot. Why this matters is that you will need to **update applications to use the new database endpoint** address because it will be different than the existing one.
- Snapshots = single point in time, creation time
	- which means it influences the RPO. Unless you created a snapshot right before a failure, then chances are the RPO is going to be suboptimal.
- Automated = any 5 minute point in time
	- backups are restored from the closest snapshot, and then transaction logs are "replayed" to bring DB to desired point in time (**GOOD RPO**).
- Restores **aren't fast** - Think about **[[RTO]]** (**RR's**)
	- Think about this from a DR & business continuity perspective.

## RDS Read-Replicas
Benefits of read replicas:
- Performance benefits for read operations
- Cross-region failover capability
- They provide a way for RDS to meet really low [[RTO]]s

**RDS - Read Replicas**
![[RDS - Read Replicas.png]]
Read replicas aren't part of the main database instance in any way. They just exist off to the side. There's no automatic failover. They have their own database endpoint address, and so applications need to be adjusted to use them.

They're kept in sync using **asynchronous** replication.
	Remember MultiAZ uses **synchronous** replication and that means that when data is written to the primary instance, at the same time as storing that data on disk on the primary, it's replicated to the standby. Conceptually, this is like a single write operation to both the primary and the secondary.
	With asynchronous replication, there can be a small lag between when data is committed to the primary & replicated to the secondary.

Read replicas can be created in the same region as the primary database instance, or they can be created in other AWS regions known as cross region read replicas. AWS handle all of the networking between regions and it's fully encrypted in transit.

- 5x direct read-replicas per DB instance
- Each providing an additional instance of read performance
- Read-Replicas can have read-replicas - but lag starts to be a problem
- Global performance improvements
- Snapshots & Backups Improve RPO
- RTO's are a problem
	- Because restoring snapshots takes a long time
- RRs offer near 0 RPO
	- Because the data on the RR is synced from the main instance, so there's little potential for data loss.
- RRs can be **promoted quickly** - Iow RTO
	- Failure only - watch for data corruption
- Read only - until promoted
- Global availability improvements ... global resilience

## RDS Data Security
- Authentication - how users can log into RDS
- Authorization - how access is controlled
- Encryption in transit between clients and RDS
	- **SSL/TLS** (**in transit**) is available for RDS
		- can be **mandatory** on a per user basis
- Encryption at rest
	- RDS supports **EBS volume** encryption - **KMS**
	- Handled by the **RDS Host** & the underlying **EBS** based storage
		- As far as the RDS database engine knows, it's just writing unencrypted data to storage
	- AWS or Customer Managed CMK generates **DEKs**.
		- DEKs used for **encryption operations**
	- Storage, Logs, Snapshots & replicas are encrypted (using the same customer master key)
		- **encryption can't be removed** once it's added
	- RDS **MSSQL** and RDS **Oracle** Support **TDE**
		- Transparent Data Encryption
		- Encryption handled within the DB engine
	- RDS Oracle supports integration with **CloudHSM**
		- Much stronger key controls (even from AWS)
			- Because Cloud HSM is managed by you with no key exposure to AWS, it means that you can implement encryption where there is no trust chain which involves AWS. For many demanding regulatory situations, this is valuable.

**IAM authentication for RDS**
![[Amazon RDS IAM Authentication.png]]
Normally, logins to RDS are controlled using local database users (usernames & passwords) - outside of the control of AWS.

## Aurora Architecture
Technically, Aurora is part of RDS, but the features and architecture are so radically different that I treat it as its own product.

- Uses a "**Cluster**"
- A single **primary** instance + **0** or more **replicas**
	- Replicas can be used for reads (unlike the standby replicas in RDS; provide the benefits of both RDS multi-AZ and RDS read replicas (RR))
		- That alone would be worth the move to Aurora, since you don't have to choose between read scaling and availability
- No local storage - uses **cluster volume**
	- Faster provisioning & improved availability & performance

A typical Aurora cluster functions across multiple AZs. Inside the cluster is a primary instance, and optionally, a number of replicas. By default, the primary instance is the only instance able to write to the storage. The replicas function as failover options, but they can also be used during normal functioning of the cluster for read operations from applications.

When data is written to the primary DB instance, Aurora synchronously replicates that data across these 6 storage zones, spread across the AZs in the cluster. All instances inside your cluster have access to all of these storage nodes. Replication happens at the storage level, so no extra resources are consumed on the instances or the replicas during this replication process.

**Aurora Storage Architecture**
![[Aurora Storage Architecture.png]]
- The shared storage is SSD based. Max Size: 128 TiB, 6 replicas, ::AZs (// 3??).
- // (5/24/25) TutorialsDojo practice test says max 15 replicas.
	- All SSD Based - high IOPS, low latency
		- No magnetic storage option.
	- The **storage** subsystem inside Aurora is much more **resilient** than that which is used by the normal RDS database engines.
		- Aurora maintains multiple copies of your data in three AZs. Aurora automatically detects failures in the disk volumes. When a disk fails, Aurora automatically repairs the disk & recreates that data using the other storage nodes.
	- Another powerful difference between Aurora and the normal RDS database engines is that with Aurora you can have up to **15 replicas**, and any of them can be the **failover target** for a failover operation (rather than the one primary instance)
		- That failover operation will be much quicker because it doesn't have to make any storage modifications.
	- Billing is based on **what's used**
		- Storage for the cluster isn't allocated.
		- **High water mark** - billed for the most used
			- If you consume 50 GB, then free up 10 GB, you're still billed for 50 GB
				- This high watermark architecture is being changed by AWS - this no longer is applicable for the more recent versions of Aurora
	- Replicas can be added and removed without requiring storage provisioning.
	- Access method - uses endpoints
		- DNS addresses which are used to connect to the cluster
		- Unlike RDS, Aurora clusters have multiple endpoints that are available for an application.
			- Cluster endpoint - always points at the primary instance. Can be used for read and write operations.
			- Reader endpoint - also points at the primary instance, but load balances across all available replicas.
				- Aurora is easier to manage read scaling than RDS (because as you add more replicas, the reader endpoint is automatically updated)
			- You can create Custom endpoints
			- Each instance have their own unique endpoint

- Cost
	- No free tier
		- Because Aurora doesn't support micro instances
	- Beyond RDS singleAZ (micro) Aurora offers better value
	- Compute - hourly charge, per second, 10 minute minimum
	- Storage - GB-Month consumed, IO cost per request
	- 100% DB Size in backups are included
		- For most situations, unless you have high data turnover or long retention, the backup costs are often included in the charge that you pay for the database cluster itself.

- Backups in Aurora work in the same way as RDS
- Restores create a **new cluster**
- **Backtrack** can be used which allow in-place rewinds to a previous point in time.
	- Alternative to restoring to a new database. No need to reconfigure your applications. Data is just rolled back.
	- Need to enable on a per cluster basis. Can adjust window.
- Fast clones make a new database MUCH faster than copying all the data - **copy-on-write**.
	- Doesn't make a 1:1 copy of the data. It references the original storage and only stores differences. So, cloned databases don't take much space.
		- Differences could be: you update data in the cloned database OR the original database.

- If not using a Replica or Aurora Serverless, Aurora will attempt to create a new DB Instance in the **same Availability Zone** as the original instance.

## Aurora Serverless
Aurora Serverless is to Aurora what Fargate is to ECS.

You don't need to statically provision database instances of a certain size or worry about managing those database instances. A step closer to a DBaaS product. Removes admin overhead (of managing individual db instances).

- Scalable - **ACU** - Aurora Capacity Units
	- Allocated from a warm pool, managed by AWS, to a cluster.
	- ACUs are stateless.
	- They're shared across AWS customers.
	- They have no local storage.
		- Once allocated to an Aurora Serverless Cluster, they have access to the cluster storage in the same way that a provisioned Aurora instance would have access to the storage in a provisioned Aurora Cluster.
	- Each ACU includes about 2 gibibytes (GiB) of memory, along with the necessary CPU and networking.
- Aurora Serverless cluster has a **MIN & MAX ACU**
- Cluster adjusts based on load
- Can go to **0** and be **paused**
- Consumption billing per-second basis
- Same resilience as Aurora (6 copies across AZs)

Benefits of Aurora Serverless: simpler, removes db management, easier to scale (scales compute & capacity in the form of ACUs w/o disruption to clients), cost effective (only pay for db resources consumed per second - unlike Aurora Provisioned).

**Aurora Serverless Architecture**
![[Aurora Serverless Architecture.png]]
- When a user interacts with an Aurora Serverless Cluster, it actually goes through a shared **proxy fleet** (managed by AWS; transparent to you) which brokers a connection between the application and the cluster. Because the client never connects directly to the resource that provides the ACU, it means the scaling can be fluid.
- Types of apps that suit Aurora Serverless:
	- **Infrequently** used applications
	- **New** applications (where you're unsure of the load to be placed on the app)
	- **Variable** workloads
	- **Unpredictable** workloads
	- **Development** and **test** databases
		- Because it can pause itself during periods of no load.
	- **Multi-tenant** applications
		- Where the scaling is fairly aligned between infrastructure size and incoming revenue.

**Aurora Failover**
- If you are running Aurora Serverless and the DB instance or AZ becomes unavailable, Aurora will automatically recreate the DB instance in a **different AZ**.

## Aurora Global Database
This subject may not immediately feature heavily on the exam.

Global Databases allow you to create global-level replication using Aurora from a master region to up to five secondary AWS regions.

**Aurora Global Database**
![[Aurora Global Database.png]]
One read/write instance & up to 15 replicas in that cluster.
Global databases introduce the concept of secondary regions (right in the image above). These replicas are read only. Replicates one way from the primary region to all secondary regions.

When would you use this?
- Cross-Region **Disaster Recovery** and **Business Continuity**
	- 1 second replication ensures the RPO & RTO will be low if you do perform a cross region failover
- Global Read Scaling - Iow latency performance improvements
	- For international customers. Create lots of secondary regions replicated from the primary region
- Replication has **no impact** on DB performance since it occurs at the storage layer
- Secondary regions can have 16 replicas
	- Any of these can be promoted to R/W
	- Currently MAX 5 secondary regions (this is likely to change)

## Multi-master writes
This subject may not immediately feature heavily on the exam.

- Default Aurora mode is **Single-Master**
	- **One R/W** & **0+ Read Only** Replicas
- Cluster Endpoint is used to write, read endpoint is used for load balanced reads
- Failover takes time - replica promoted to R/W
- In Multi-Master mode **all instances are R/W**

**Aurora Multi-Master**
![[Aurora Multi-Master.png]]
In Multi-Master mode, there is no cluster endpoint to use. Applications are responsible for connecting to instances within the cluster. There's no load balancing across instances.

When one of the read-write nodes inside a Multi-Master cluster receives a **write** request from the application, it immediately **proposes** that data be committed to all of the storage nodes in that cluster. Each node either confirms or rejects the proposed change. 

The writing instance is looking for is a quorum of nodes to agree, at which point it can commit the change to the shared storage.

The quorum **rejects** the write proposal if it conflicts with something that's already in flight. It cancels the change & generates an error.

If the quorum **agrees** to a write, that write is committed to storage and it's replicated across every storage node in the cluster. Since instances cache data, it also updates their in-memory **caches** in addition to committing it to disk.

Single master failover situation vs Multi master failover:
Single Master:
Client app connects to Aurora via cluster endpoint. This always points at the primary instance. When the primary **fails**, then access to the cluster is **interrupted**. So, this application **can't be fault tolerant**. The cluster will change the cluster endpoint to point at the replica which becomes the new primary instance. But, this process takes time.

Multi Master failover:
**Aurora Single-Master**
![[Aurora Single-Master.png]]
With multi master, both instances are able to write to the shared storage. Applications could maintain connections to both writers and be ready to act if one of them fails. When a writer fails, apps could send 100% of any future data operations to the a working writer. If the application is designed in this way, it's designed to operate through this failure. It could be **fault tolerant**.
- Better and much faster availability
- Failover events can be performed inside the application
- Failover events don't need to disrupt traffic between the application and the database
- Can be used to implement **fault tolerance**, but the application logic needs to manually load balance across the instances (it's not handled by the cluster)

## Relational Database Service (RDS) - RDS Proxy
Why use RDS Proxy?

- **Opening** and **Closing** Connections **consume resources** - takes **time**. Increases **latency**.
	- For small DB operations, overhead of establishing connection is significant.
- With serverless .. **every lambda** opens and closes?
- Handling **failure** of Database instances is **hard**
	- What should your application do while waiting?
	- When should it consider it a failure?
	- How should it react? 
	- How should it handle the failover to the standby instance in the case of RDS?
	- doing it within your application **adds risks**
- DB **Proxies** help ... **managing** them is not trivial (**scaling/resilience**)
- Application(s) => Proxy (connection pooling) => Database
	- Connections stay open long term
	- Can multiplex (maintain a smaller number of connections to the DB) requests over the connection pool between the proxy and the DB.

![[RDS Proxy Architecture.png]]

When should you use RDS Proxy?
- **Too many connections** errors (because proxy reduces # of connections to DB).
	- Especially important if you're using smaller databases instances. Ex: **T2/T3**. **Smaller/burst instances**.
- Useful when using **AWS Lambda** .. **time saved**/connection **reuse** & **IAM Auth**.
	- No per invocation DB conn setup, usage, & termination.
- Long running connections (SAAS apps) - low latency
- Where **resilience** to database failure is a priority
	- RDS proxy can **reduce the time for failover**
	- and make it **transparent to the application** (apps don't have to wait for DB CNAME to move from the primary to the standby)

RDS Proxy Key Facts
- **Fully Managed** DB **Proxy** **RDS/Aurora**
	- **auto scaling**, **highly available** by default
		- Lower overhead vs managing a DB proxy yourself
- Provides **connection pooling** - reduces DB Load
	- 1) No constant **opening** & **closing** DB connections - unnecessary load on DB.
	- 2) Can **multiplex** to use a lower # of connections between the proxy and the DB relative to the # of connections between the clients and the proxy.
- ONLY **accessible** from **a VPC**
- Accessed via **Proxy Endpoint** - no app changes
- Can enforce **SSL/TLS**
- Can **reduce failover time** by **over 60%**
- **Abstracts failure** away from your applications

## Database Migration Service (DMS)
Normally if we exclude the vendor tooling which is available, database migrations are a manual process end to end which involves setting up replication, taking a point in time backup, and restoring this to the destination database.

But how do you handle changes which occur between taking that backup and when the new database is live? This is where DMS is useful.

DMS
- A managed database migration service
- Runs using a **replication instance**
- Source and Destination **Endpoints** point at Source and Target **Databases**
- One endpoint MUST be on AWS
	- Can't use this product for 2 on prem DBs

**Database Migration Service (DMS)**
![[Database Migration Service (DMS).png]]

**Replication tasks** define all of the options relating to the migration. Two of the most important things are the **source** and **destination** **endpoints**.

Jobs can be one of three types:
- **Full Load** - used to migrate existing data
	- If you can afford an outage long enough to copy your existing data then this is a good one to choose.
	- Migrates data from your source database to your target database & creates tables as required.
- **Full Load + CDC** (change capture data) - migrates existing data & replicates any ongoing changes.
	- Performs a full load migration & at the same time, captures any changes occurring on the source. After the full load migration is complete, captured changes are applied to the target. Eventually, the application of changes reaches a steady state. At this point, you can shut down your applications, let the remaining changes flow through to the target, then restart your applications and point them at the new target database.
- **CDC Only** - Replicates only data changes.
	- In some situations it might be more efficient to copy existing data using a method other than AWS DMS (ex., Oracle has its own export/import tools). You can use those tools to do your initial bulk load, then use DMS to replicate the changes starting at the point when you do that initial bulk load.

DMS doesn't natively support any form of schema conversion, but AWS does have a dedicated tool for that - **SCT**. Schema Conversion Tool. Performs schema modifications between different database versions or different database engines.

For any database migration scenarios on the **exam** - generally, DMS is a safe default option.
You can default to DMS...:
- As long as **one** of the databases is **within AWS**
- As long as there are no weird databases involved which aren't **supported** by the product
If the question talks about a **no downtime migration**, then you absolutely **should** default to DMS.

**SCT** (Schema Conversion Tool)
- SCT is used when converting **one database** engine to **another**.
	- Can be used when the engines being migrated from and to aren't compatible.
	- Including **DB** -> **S3** (Migrations using DMS)
		- Can be used for larger migrations - When you need to have an alternative way of moving data between on premises and AWS - Rather than using a data link.
- SCT is **not used** when migrating between DB's **of the same type** (between **compatible** DB engines)
	- For example, on prem MySQL -> RDS MySQL
		- The engines are the same. Even though the products are different. SCT is NOT used.
- Works with **OLTP** DB Types (MySQL, MSSQL, Oracle)
- And **OLAP** (Teradata, Oracle, Vertica, Greenplum..)
- Examples of where SCT would be used:
	- On-Premises **MSSQL** -> RDS **MySQL**
	- On-premises **ORACLE** -> **Aurora**

**DMS & Snowball**
DMS normally will transfer the data over the network (over Direct Connect or a VPN or a VPC peer), but if the data volumes that you're migrating are bigger than you can practically transfer over your network link, you can order a Snowball & use DMS together with SCT to make the transfer faster & more effective.

- Larger migrations might be multi-TB in size
	- Moving data over networks takes time and consumes capacity (which could impact normal business operations)
- DMS can utilize snowball
- Step 1: Use SCT to extract data locally and move to a snowball device
- Step 2 : Ship the device back to AWS. They load onto an S3 bucket.
- Step 3: DMS migrates from S3 into the target store
- Step 4 : Change Data Capture (CDC) can capture changes, and via S3 intermediary they are also written to the target database

The rule to remember for the exam is that SCT is only used for migrations when the engine is changing. SCT is used here because you're actually migrating a database into a **generic file format** (for transfer to AWS) which can be moved using Snowballs. So this doesn't break the rule.
