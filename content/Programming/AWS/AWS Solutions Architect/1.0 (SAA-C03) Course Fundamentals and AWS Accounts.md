## AWS Accounts - The basics
![[AWS Accounts.png]]
The Identity and Access Management (IAM) Service is dedicated to an account.
- IAM Users
- IAM Groups
- IAM Roles

IAM identities managed by the IAM service start off with no permissions. You have to give them permissions.
The management account and the general account are the same thing.

When **creating new accounts**, configure the following on the root account:
- **MFA** - in addition to username & password.
- A **Budget** - to protect against unintended costs.
- IAM Identities (an **IAM user**) called Admin. This is to prevent using the root account.
- **Role Access** to billing
	- // Root user must first enable "IAM User and Role Access to Billing Information" and then attach appropriate IAM policies to the users or roles.
- (optional) Add account contacts
When you create AWS accounts, view them as disposable.

You can use Gmail aliases for multiple accounts.
Example:
catguy@gmail.com
catguy+AWSAccount1@gmail.com
catguy+AWSAccount2@gmail.com
etc...

## Identity and Access Management (IAM) Basics
Account root user is created with an account and **can't be restricted in any way**.

Giver **least privilege** permissions for users, groups, etc.

IAM is a **globally resilient** service. All data is secure across all AWS regions.

IAM as a service can do as much as the account root user. Your IAM service is fully trusted by your AWS account.

- IAM can create 3 **identities**:
	- IAM **Users** - **humans** or **applications** that need access to your AWS account.
	- IAM **Groups** - **Collection** of **related users**.
	- IAM **Roles** - Can be used by **AWS Services** or for granting **external access** to your account
		- // Ex: Give EC2 instances access to S3. Create a role grainting access to (S3), & allow the EC2 instances to use that role.
		- // Generally use roles when you want to grant services to your account for an **uncertain # of entities**. Or to give **external access** to your account.

**Policies** **allow** or **deny** access to AWS services WHEN they're **attached** to identities (users, groups, & roles). Only work when attached.

- IAM has 3 main jobs
	- **Manages** Identities - an ID Provider (**IDP**)
	- **Authenticate** - (prove **who** you claim to be - generally w/ username & password)
	- **Authorize** - allow or deny **access** to resources

IAM Basics
- No cost
- Global service / Global resilience
- ALLOW or DENY its identities on its AWS account
- No **direct** control on external accounts or users
- **Identity federation** and **MFA**


## IAM Access Keys
Auth on the command line is done with access keys, not username & password.
**Access keys** are **long term credentials** (there are more). All long term credentials are used with IAM users.

- An IAM User has **1** username and **1** password
- An IAM User can have **two access keys**
	- // Two, so you can rotate them. If you lose it, you have to delete it and create a new one. No way to re-gain access to it after it's generated if it's lost.
- Access keys can be **created**, **deleted**, made active, or made **inactive**.

You can have **machine identities** that don't use username + password.
An **access key** is composed of: **Access Key ID** + **Secret Access Key**.
IAM Users are the only identity that use long term access keys.
IAM Roles don't use access keys.
