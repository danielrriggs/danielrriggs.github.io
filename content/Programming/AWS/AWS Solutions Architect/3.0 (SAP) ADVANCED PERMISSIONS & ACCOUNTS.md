## Security Token Service STS
Underpins many of the identity processes within AWS.

**Security Token Service (STS)** - Temporary Credentials
- (**exam**) Generates temporary credentials (**sts:AssumeRoIe**)
	- When you assume an IAM role, you use the STS assume role call
	- When you **role switch** in the console UI, you're assuming a role in another AWS Account; you're using STS to gain access to these temporary credentials. This happens behind the scenes.
- Similar to access keys
	- (**exam**) .. they **expire** and don't **belong** to the identity
		- An IAM user, for example, owns its own credentials. It has an allocated access key ID and a secret access key - long-term credentials.
- Limited Access
	- By default, the authorization is based on the permissions policy of the role, but a **subset** of that can be granted to the temporary credentials.
- Used to access AWS resources
- (**exam**) Requested by an Identity (AWS or EXTERNAL)
	- Either an AWS Identity - IAM user via an IAM role
	- Or an external identity - Google login, Facebook, or Twitter, which is known as Web Identity Federation.
**Security Token Service (STS)**
![[Security Token Service (STS).png]]
Around a role, you have a **trust policy** - it's like a wall. It controls who can assume that role.

Assume role calls are made via the **STS** service. STS checks the **role's trust policy**. If the identity is allowed, then it reads the **permissions policy**, which is also attached to the role. The permissions policy controls what is allowed or denied inside AWS. The permissions policy, associated with a role, controls what permissions are granted when anyone assumes the role.

STS uses the permissions policy in order to generate **temporary credentials**. The temporary credentials are **linked** to the **permissions policy** on the **role**, which was assumed in order to generate the temporary credentials. If the permissions policy changes, the permissions that the credentials have access to also change.

The following actions in AWS use STS:
- Assume a role
- Role switch between accounts (via console UI)
- Perform cross account access using a role
- Various different types of identity federation

## Revoking IAM Role Temporary Security Credentials
- Roles can be assumed by **many identities**
- Who all get the **same permissions**
	- Not granular
- Temporary credentials **can't be cancelled**
- All assumptions = **the ROLES permissions policy**
- Credentials can last hours - **what if leaked ?**
	- // Remember, they can't be canceled.
- Delete Role, change permissions impact ALL assumers
**Revoking Temporary Credentials**
![[Revoking Temporary Credentials.png]]
Credential Leak Scenario: Changes to the trust policy would have no effect in this scenario. We could change the permissions policy attached to the role, but that would impact everyone (all credentials gained from assuming a role would immediately change to use these new permissions).

One potential action: revoke all of the existing sessions. Apply a new inline policy to the role - explicit deny to all operations on all AWS resources **conditional** on NOW. Our legitimate users can assume the role again (to update NOW).

Remember, you cannot manually invalidate temporary credentials. They only expired when they expire. We revoke Role Sessions by adding a conditional deny policy to an existing role's permissions policy.

## AWS Resource Access Manager (RAM)
Before Resource Access Manager was introduced, AWS accounts provided full isolation. A virtual private cloud, or VPC, that was created within one AWS account wasn't visible within any other account. The only way that services in one account could access network resources contained in another was to create a VPC and configure VPC peering between the two VPCs to provide network connectivity. Now, Resource Access Manager adjusts the available architectures that we're able to use as Solutions Architects.

**Resource Access Manager (RAM)**
- Share AWS resources **between AWS Accounts**
- Products need to support RAM
- Shared with **Principals** (**Accounts**, **OU's**, or **ORG**)
- Shared resources can be accessed **natively**
	- So, for example, if you share a VPC subnet with another account, it can be viewed and interacted with as though it were in that account (UI, CLI).
- **No charge** for using RAM - only the service cost
- **Substantial changes** to traditional AWS architectures
	- Traditional AWS architectures were structured around accounts with networks within them, often connected using transit gateways, or VPC peers. RAM allows you to create shared services between accounts, so it can influence architectures pretty extensively.

Availability Zone ID (AZ IDs)
![[Availability Zone ID (AZ IDs).png]]
- My us-east-1a might not be your us-east-1a.
	- Consequences: a failure with physical infrastructure might show as a different account versus mine. This presents a challenge in multiple account project situations.
- So, AWS implemented another designation for their infrastructure called **availability zone IDs** - these are **consistent**. They may be used for coordinating infrastructure deployments across many different accounts. Useful when using Resource Access Manager.

**Resource Access Manager (RAM)**
- Owner account **creates a share** provides a name
- Owner **retains full ownership**
- Defines the **principal** with **whom to share**
- If participant is inside an ORG with sharing enabled its **accepted automatically**
- For non ORG accounts, or sharing with AWS Organizations is not enabled - you need to **accept an invite**

A **shared services VPC** is one which provides infrastructure which can be consumed by other VPCs. Examples: application services, domain controllers, APIs, shared storage.
In AWS, this has been traditionally architected using separate networks connected using peering or transit gateways. With RAM and AWS Organizations, you can create something which is much more effective.

## AWS Service Quotas
Every AWS account is impacted by service quotas - A quota defines how much of a thing that you can use inside an AWS account.
- Ex: The # of EC2 instances of a certain type you can have running in the US East 1 region at any one time.
- Ex: The number of IAM users that you can create, in a single AWS account

- (**exam**) Each service has a **default per-region** quota
- (**exam**) (some services can be per account) (e.g. global services)
- **Most** service quotas **can be increased** as needed
- (**exam**) Some can't ... learn these, architecture impacts
	- Ex: Number of IAM users which can be created inside an AWS account - hard 5,000 limit.
- Higher increases = more **process** & **time** needed
