## AWS Public vs Private Services
![[Public vs Private Services.png]]
**Public** & **private** services refer to **networking** only; public services aren't things that are available to everyone.

A public service is something that's accessed using public **endpoints** (like s3) - s3 can be accessed anywhere that you have internet access.

A **private** service is something that is accessed **within** a **VPC**. Only things within or connected to the VPC can access the service.

For both of these, **permissions** & **networking** are two different considerations when talking about access to a service.

**"Public Internet" Zone** - connect over public internet.
**"AWS Public Zone"** - in between Public Internet & the AWS Private Zone network. It's a network that's connected to the public internet. This is where services with public endpoints (such as s3) operate.
**"AWS Private" Zone** - connect through VPC (like your home wifi - only people connected can use).

VPC's can't communicate unless you allow it.
You can place services inside Private Zones. The services can only access the internet & vice versa if you configure it.

On Prem can access VPCs only if configured via **VPN** or **DX**.

You can attach an **IGW** to an AWS Private Zone. This allows Private Zone resources to access the **public internet** as long as the services within the Private Zone have an allocated **IP Address**. The IGW also allows access to AWS Public Zone services (such as s3). This data doesn't touch the public internet at any point. It communicates with the public service using the AWS Public Zone.

AWS Region, Edge Location, Availability Zone
Service **Resilience**:
- **Global** Resilient
- **Region** Resilient
- **AZ** Resilient

AWS can't have a region everywhere, so they provide **edge locations**. They only have **CDNs** & some **edge computing**. They're useful for companies like Netflix who need to store media closer to users.

## Availability Zones
Inside every region, AWS provides multiple AZ's. An AZ is isolated infrastructure (compute, storage, networking, power, & facilities) within a region.

AZ's are a logical thing within AWS. It isn't a data center. AWS doesn't give you visibility into AZ's - it could be one Data Center (DC), or multiple. AZ's are isolated from other AZ's and connected with redundant, high speed, networking.

## VPC
Virtual Private Network
VPC is the service used to create & run **private services** in AWS.
Used to connect AWS **private network** to **on prem** networks when creating a **hybrid environment**.
Lets you connect to **other cloud** platforms when creating a **multi-cloud** deployment.

- A VPC is within **1 account** & **1 region**.
	- // VPCs are **regional** services, meaning they're regionally **resilient**.
	- // VPCs operate from **multiple AZs** within a region.
- VPCs are private and isolated unless you decide otherwise
	- They can't communicate to other VPCs unless configured.
- Two types - **Default VPC** and **Custom VPCs**.
	- You can only have 1 default VPC per region, but you can have many Custom VPCs.
- **VPC CIDR** - start and end range of IP addresses that the VPC can use
	- Communication must use that VPC CIDR.
- How VPCs are regionally **resilient** - divide the CIDR across multiple **subnets** & **AZ**s
	- Each subnet is located in one AZ at time of creation & can't be changed.
	- The CIDR range per subnet **can't overlap** with the others.
	- // the Default VPC is preconfigured to have 1 subnet in every AZ in that region
	- // if AZ fails, subnet fails

**Default VPC**
- **One** per region - can be removed & recreated
	- // Some services assume the Default VPC will be present, so I tend to leave it active, but just not use it for anything production related because they're too inflexible.
- Default VPC CIDR is always **172.31.0.0/16**
	- // Custom VPCs can have multiple CIDR ranges, but the **Default VPC** only gets one & it's always the same - always **172.31.0.0/16**
	- // One of the strengths of the Default VPC is it's always configured the same way.
- **/20** **Subnet** in each AZ in the region
	- // The # of AZs in a region can vary.
	- The higher the CIDR range is, the smaller the network is
		- Ex: /17 is half the size of a /16.
	- The Default VPC uses a /16 CIDR, which is fairly large.
		- That means 16 /20 subnets can fit into the /16 that the VPC uses. There's enough for 16 AZs.
- Includes a few things preconfigured:
	- IGW - allows the VPC to communicate with the internet & vice versa.
	- Security Group (**SG**) & Network ACL (**NACL**)
		- Limit incoming and outgoing data transfer.
		- SG - like a mini firewall.
- Subnets assign public IPv4 addresses
	- // By default, anything placed in the Default VPC subnets is assigned an IPv4 address.
		- // Some private services can be made public by projecting parts of themselves into the AWS public zone.

If you delete the default VPC, it will delete all of the network configurations, which includes:
- The Internet Gateway
- The Default SG
- The NACL
- The VPC itself

Consider S3 your default solution for storage requirements unless it won't work for your requirements

- **Global** Storage Platform - **regional** **based**/**resilient**
	- Global: Runs from all of the AWS regions.
	- Regional Based: at rest, your data is stored in a specific region. Data never leaves unless you explicitly configure it to.
	- Regionally **resilient** - Data is replicated across AZs in that region.
		- Can tolerate AZ failure

	- Global namespace (for navigation), but buckets are regional
- **Public** service, unlimited data, & multi-user
- Economical & accessed via UI/CLI/API/HTTP.
- **Objects** & **Buckets**
	- Buckets are containers for objects.
	- Objects - conceptually, like files (they're interchangeable)
	- Object parts:
		- **Key** = name (like a file name)
		- **Value** - data (content being stored)
			- (**exam** - **MEMORIZE**) **0 bytes up to 5 terabytes**
			- You can have empty objects
		- Access object w/ `object key + bucket`
			- Need **permissions** configured. By **default**, for public services, **no access** is allowed except for the root user.
	- Other parts of an object:
		- Version ID
		- Metadata
		- Access Control
		- Subresources
- Buckets
	- Created in a specific AWS **region**.
		- Has a primary home region. Data never leaves unless configured.
		- S3 blast radius = region
	- Names are **globally unique
		- // Most AWS things are region/account unique. Buckets are different.
	- Names 3-63 characters, all lower case, no underscores
	- Start with lowercase letter or a number
	- Can't be IP formatted eg 1.1.1.1
	- Aren't limited in # of objects in a bucket.
	- Can be made completely public
		- // Disabling `block all public access` when creating an s3 bucket **doesn't** make it public. It just means that you can grant it public access.
- **No hierarchy**. **Flat structure**. NOT like a file system (w/ files within folders). Everything stored at root level. No concept of file type (based on file name).
- Folders represented with object name. Folders are prefixes (prefix object names). Ex:

- S3 - **Object** store - not **file** or **block**.
	- S3 Candidate Use Case:
		- Where you access the whole of an entity (entire image, entire audio file, etc)
	- // ex file store - windows server that needs to access a network file system.

	- For some types of metric collection (like collecting data **outside** AWS - **on prem** or **other cloud**; also monitoring some things inside products that **aren't exposed** to AWS - such as what **processes** are running on an EC2 instance, or the memory **utilization** of those processes), you need to install the **CloudWatch agent**.

	- Ex: AWS/**service** .. i.e. AWS/**EC2**

## High-Availability vs Fault-Tolerance vs Disaster Recovery
**High Availability** - aims to **ensure** an agreed level of operational **performance**, usually **uptime**, for a **higher than normal period**.

*Most people assume that HA means ensuring that the system **never fails**, or that the user of a system never experiences any **outages**. This isn't true. HA isn't aiming to stop failure, and it doesn't mean customers won't experience outages. A HA system is designed to be **online** & providing services as **often as possible**. It's designed so that when it fails, its components can be **replaced** or **fixed** as **quickly** as possible, often using automation to bring systems back into service. HA is **not** about the **user experience**. If a system fails & a component is replaced & this disrupts service for a few seconds, it's still highly available. HA is about **maximizing** a system's **online** time, and that's it.*

System availability is generally expressed in a % of uptime.
**99.9%** (3 9's) - means we can only have 8.7 hours of downtime per year.
**99.999%** (5 9's) allows for 5.26 minutes per year of downtime.

HA can have user experience interruptions - while not ideal, HA is just about **minimizing outages**.
![[High Availability Example.png]]
HA is like driving with a spare tire on the back of the car. You can change the tire & get back on the road. There's some down time, but it prevents you from being dead in the wild & having to call for help.

HA has some **cost**, requires some **decisions** ahead of time, and requires some **automation**.
Sometimes HA needs **redundant** servers or infra in place to be ready to switch customers over to.

**Fault Tolerance vs HA**
**Fault Tolerance** - the property that enables a system to **continue operating properly** in the event of a **failure of some** (one or more faults within) of its **components**.

Most people think HA means operating through failure. This is incorrect. HA just means maximizing uptime. Fault Tolerance means **operating through failure**. FT can be **expensive** because it's more **complex** to implement.
HA can be implemented by having **spare** equipment - **stand by**, physical, or virtual components.

![[Fault Tolerance Example.png]]
A plane is Fault Tolerant - it has extra engines (4), duplicate electrical and hydraulic systems.

**Disaster Recovery (DR)** - a set of policies, tools and procedures to **enable the recovery** or **continuation** of **vital** technology infrastructure and systems **following a natural or human-induced disaster**.
Store backups offsite.
DR planning isn't only about tech. It's about **staff** & **knowledge**. Make sure knowledge of all your **processes** are **available**. All logins for key systems are available for staff to accessible at a standby site. Do this in advance & it won't be chaotic when a disaster happens. Ideally, you run **periodic DR testing** to ensure you have everything you need.

If HA is a 4x4 car & FT is an airplane w/ resilient systems, DR processes are like an ejection system. DR is designed to keep the crucial & non replaceable parts of your system safe.

Summary
DR - **Minimize** any **outages** (max availability.
FT - Operate **through faults**. More complex & expensive. Takes more time to implement & manage.
DR - used when **DR & FT** don't work.

## Route 53 Fundamentals
R53 provides **DNS zones** & **hosting** for those zones. It's basically **DNS as a service**. It lets you **create** & **manage** **zone files** (**hosted zones** - because they're **hosted** on **AWS managed name servers**).

Provides 2 main services
1) Allows you to **register domains**
2) It can **host zone files** for you on **managed nameservers** which it provides
- Global service ... single database
	- R53's data is replicated between regions. Can tolerate the failure of 1 or more regions.
It's one of the most important AWS products. It needs to scale, remain performant while remaining reliable, & continue working through failure.
![[Register Domains.png]]
DNS is just a system of delegation. **IANA** manages the root zone for DNS.

There are 13 DNS root servers which are managed by 12 large organizations. 

R53 has **relationships** with all the main **domain registries** companies that manage the **top level domains**. They've been granted this ability by **IANA**, who manage the **root zone** for DNS.
One manages the **.com** zone, one the **.net** zone, another the **.io** zone, and so on. **PIR** (an organization) manages **.org** domains.

0) When a domain is **registered**, R53 checks the **top level** domain to see if it's **available** (let's assume it's available for this example).
1) R53 creates a **zone file** for the domain being registered.
	1) A zone file is a **database** which contains the **DNS info** for a particular domain.
2) R53 **allocates name servers** for this zone & puts the **zone file** on them. There are generally **4** for one individual zone.
	2) These zone files are called **hosted zones** in Route 53 terminology because they're hosted on AWS managed name servers.
3) R53 **liaises** with the **registry** (PIR, in this example) & adds the **name server records** into the **zone file** for the **top** org **level domain**.
	3) These **name server records** are how **PIR** **delegate** the admin of the domain tools. By adding the name server records to the org zone, they indicate that our four name servers are authoritative for the domain.

Summary:
1) **Create Zone File**.
2) Create # of **managed named servers**. Put **Zone file** on **named servers**. 
3) **Liaison** with TLD registry. Get **name server records added** to **TLD zone** which point back at the managed named servers.

- Can be **public**
	- // Which means the data is accessible on the public internet. The name servers for a public zone live in the AWS public zone. This is accessible anywhere with a public internet connection; so, they're part of the public DNS system.
- .. or **private** .. linked to **VPCs**
	- // A hosted zone can also be private, which means it's linked to one or more VPCs and is only accessible from within those VPCs. You might use this type of zone if you want to **host sensitive DNS** records that you don't want to be publicly accessible.
- Stores records (**recordsets**)

## DNS Record Types
- **Nameserver** (NS) record.
	- The record types which allow **delegation** to occur in DNS.
**Nameserver (NS)**
![[Nameserver (NS).png]]
The .com **zone** (managed by Versign) has multiple **nameserver records** for amazon.com. These nameserver records are how the .com **delegation** happens for amazon.com. They **point** at **servers** managed by the amazon.com team and the servers host the **amazon.com zone**. Inside this zone are **DNS records**, such as **www**, which is how you can access those records as part of DNS.

The same is true on the other side. The **root zone** has delegated management of .com by having **name servers** in the **root zone** **point** at name servers inside the **.com zone**.
(servers from root zone) > point to  > (servers in the amazon.com zone).
**A and AAAA Records**
![[A and AAAA Records.png]]
**A** records or **AAAA** records do the same thing. Given a **DNS zone** (google.com), these type of records **map host names to IP address**. The difference is the type of IP address.
An **A** record **maps** the **host** to an **IPv4** address.
An **AAAA** record **maps** the **host** to an **IPv6** address.
Generally, you'll create two records - one will be an A record & one will be an AAAA record. The client software can choose the correct address it wants.
**CNAME Records**
![[CNAME Records.png]]
The **CNAME** (canonical) record type lets you create the equivalent of **DNS shortcuts**. So, host to host records.
Let's say we have an **A record** called server, which points to an IPv4 address. It's common for a server to provide multiple **tasks**. Suppose this server provides **ftp**, **mail**, and **web** services. Creating **3 CNAMEs** and **pointing** them to them all at the A **server record** means they will all **resolve** the same **IPv4 address**.
CNAMEs are used to **reduce admin overhead**. In this case, if the IPv4 address **changes**, we only have to **update one** A record (because the 3 CNAMEs **reference** that one record).
(**exam**) CNAMEs **cannot point to ip addresses** - **only to other names**. Expect this trick question on the test.

**MX Records** (Mail eXchanger records) - DNS records that specify which mail servers are responsible for receiving email on behalf of a domain, ensuring emails are routed to the correct destination.
![[MX Records.png]]
Example: sending an email to hi@google.com.
In the google.com zone, we have an **A record** with the **name**, 'mail' (the name is arbitrary; it could be called rabbit or apple, etc) **pointing** at an **IP address**.

In the google.com zone, there are a collection of MX records.
MX Records have 2 main parts:
- A **priority**
	- Lower values for the priority field are higher priority. If there's a tie, any of them could be selected.
- A **value**

- 2 example mx records:
	- MX 10 mail
	- MX 20 mail.other.domain. (note the dot on the right)
The value can be **just a host** (ex: MX 10 mail) - there's no .com on the right; it's **assumed** to be part of the **same zone** that it's in. (So, if our zone is google.com, mail means mail.google.com. It's the **mail host** inside the google.com zone.).

If you include a **dot on the right**, this means it's a **fully qualified domain name**. It can either point to a host **inside** the same zone, or something **outside** that zone.

Whenever you send an email, it's using **DNS** to do an **MX lookup** to locate the mail server to use.

**TXT Records** - a text record. Allows you to add arbitrary text to a domain. It's a way for the DNS system to provide additional functionality. One common usage for a txt record type is to **prove domain ownership**.
![[TXT Records.png]]
Let's say we want to add animails4life.org to an email system (google mail or office 365 or amazon WorkMail). Whatever system we use to host our email might ask us to add a text record to the domain containing a certain piece of text data.
Ex: Prove you own animals4life.org - add 'cats are the best'.
The sys admin would add a TXT cats are the best record in our domain.
The external party, (say, the google email system), would query that text data, ensure that it matches the value they're expecting, and if it does, that proves that we own that we own that domain & we can manage it.

Other uses for TXT records - fighting spam.

**DNS TTL value** - Time To Live. A TTL value is something that can be set on DNS records. It's a numeric value in seconds.
![[TTL - Time To Live.png]]
Scenario: A client wants to connect to amazon.com.
The Client queries **Resolver** hosted **@ ISP**. That **resolver** server points to the **DNS root**, which **points** to the **.com registry** of authoritative servers.
So, the resolver **queries** the **.com** servers. Those authoritative servers for .com **provide** the **nameservers** at the **amazon.com zone**. That server hosts and is authoritative for the amazon.com zone, which has a **record** for **www**.
It uses this record to get the **IP address** & connect to the server. This process (walking the tree process) is lengthy.

Getting a result from the authoritative source - the source that is **trusted** by DNS, is known as an **authoritative answer**. You get an authoritative answer by talking to a **nameserver** that is **authoritative** for a particular **domain**.
If I query the **nameserver** for amazon.com, and I'm querying for the **www** record in **amazon.com**, then I get back what's called an authoritative answer. That's always going to be preferred because it's always going to be accurate. It's the single source of truth.

Using **TTL** values, the administrator of amazon.com can indicate how long records can be **cached** for.

**Summary**
Client > Resolver
Resolver > Root
Resolver > .com
Resolver > amazon.com

**TTL 3600** means the results of the query are **stored** at the **resolver** server for 3600 seconds (1 hour). If another client queries the resolver for the same thing (which is likely for amazon.com), they will get back a **non-authoritative answer**. That answer will be retrieved immediately, because it's hosted (probably) at our ISP, so it's faster.

Usually, non-authoritative answers are the same (because DNS usually doesn't change much). **TTL** is **important** for when things **change**. If you **migrate** your email service and you have a **high TTL** value for your **MX record**, when you **change** to a **provider** with a **different IP** address then email delivery might be delayed because old IP addresses for those MX records will be cached an they will be used.

- TTLs are a **balance** - **low** values mean **more queries** against your nameservers. **High** values mean **less queries**, but also **less control** if you need to change records.
	- You can change TTL values before projects and upgrades or you can leave them permanently low. Also, keep in mind that a **resolver** should obey TTL values (but that's not always the case - it **can ignore them**). That configuration can be changed locally by the admin at the resolver server.

DNS is often the cause of project failures because of TTL values.

If you're doing any **work** that involves **changing** any **DNS** records, it's recommended to **lower** the **TTL** value well in **advance** of the work (sometimes days or weeks) to make sure you have less caching issues when you do change those records.
