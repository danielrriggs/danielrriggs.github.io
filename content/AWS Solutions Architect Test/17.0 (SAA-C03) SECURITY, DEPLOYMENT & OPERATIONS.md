## Application Layer (L7) Firewall
OSI model.
Let's refresh our knowledge of Layer 3, 4, and 5.
![[Normal Firewalls Layer 3-4-5.png]]
Because this is Layer 3 and 4, the firewall sees **packets** and **segments**, **IP addresses**, and **ports**. It sees two flows of communications. **Request**. From the laptop to the server. And then **responses** from the server back to the laptop. Because this firewall is limited to Layer 3 and 4 only, these are viewed as separate and unrelated. You need to think of these as different streams of data - request and response (even though they're part of the same communication from a human perspective).

 If we enhance the firewall, this time adding **session capability**, then the same communication between the laptop and server can be viewed as one. The firewall understands that the **request** and the **response** are part of the **same session**. This small difference both reduces the admin overhead (one rule instead of two), but this also lets you implement more **contextual security** - where you can think of response traffic in the context that it's response to an original request, and treat that differently than traffic in the same direction which is not a response.

In both cases, these firewalls don't understand anything above the layer at which they operate. The top firewall operates at Layer 3 and 4, so it understands Layers 1, 2, 3 and 4. The bottom firewall does this, plus Layer 5. Both of them can see IP addresses, ports, flags, and the bottom one can do all of this, and additionally, it can understand sessions. Neither of them, though, can understand the data which flows over the top of this. They have no visibility into Layer 7, for example, HTTP (so they can't see L7 things like headers). Malware can travel via L7. L7 exposes the things we're protecting to a wide range of attacks. This is a significant limitation. Layer 7 firewalls fix many of these limitations.

![[Application (Layer 7) Firewalls.png]]
Layer 7 firewalls understand various Layer 7 protocols. This example is stepping through HTTP. They understand how that protocol transfers data, its architecture, headers, data, hosts, all of the things which happen at Layer 7 or below. It can identify normal or abnormal elements of a Layer 7 connection, which means it can protect against various **protocol-specific attacks** or weaknesses.

In this example, so a HTTPS connection to the Categram server, the **HTTPS connection** would be **terminated** on the Layer 7 firewall. So while the client thinks that it's connecting to the server, the **HTTPS** tunnel would be **stripped away**, leaving just **HTTP**, which IT could **analyze** as it transits through the firewall. A new HTTPS connection would be created between the Layer 7 firewall and the backend server. From the server and client perspective, this process is occurring transparently.

Data at Layer 7 can be inspected, blocked, replaced, or tagged, and this might be protecting against adult content, spam, off-topic content, or even malware. Because you can see and understand one or more application protocols, you can be very granular in how you allow or block content. You can even replace content - replacing adult images with a nice kitten picture. You can block specific applications such as Facebook and block the flow of business data leaving the organization onto services such as Dropbox.

The key thing to understand is that a Layer 7 firewall keeps all of the Layer 3, 4, and 5 features, but can react to Layer 7 elements. This includes things like DNS names which are used, the rate of flow (how many connections per sec). Some Layer 7 firewalls only understand HTTP, some understand SMTP (email). The limit is only based on what the firewall software supports.

## Web Application Firewall (WAF), WEBACLs, Rule Groups and Rules
AWS's implementation of a Layer 7 or application layer firewall.

**Web Application Firewall (WAF)**
![[Web Application Firewall (WAF).png]]
WAF protects products it supports - (global service): CloudFront; (regional services): ALBs, AppSync and API Gateway.
WAF is the product. Web Access Control List (**Web ACL**) is the unit of configuration. The Web ACL is used by WAF and also **associated** with the various supported services.

When you create the Web ACL, you need to configure it in either a region or globally (for CloudFront).

Within a Web ACL you have **rule groups** and **rules**. This might be things like AWS managed rules or simple allow or deny lists. It might cover things like SQL injections, XSS attacks, HTTP floods, or might relate to things like IP reputation and even protect against known botnets. These rule groups and rules which control how the WAF product reacts to incoming traffic. Allowing connections from valid users while hopefully blocking those from bots and other attackers against your web resources. When we combine this with other AWS products and architectures it can be even more useful. You can obviously update the Web ACLs manually based on human identified security events or risks. But you could also do simple automated things such as using EventBridge and scheduled rules to pass various publicly maintained IP lists to block known bad actors.

WAF does **output logs** and logging can be **directed** at S3 directly, at CloudWatch logs or Kinesis Firehose. Importantly if you want to react to logs quickly you shouldn't directly use S3. As these are delivered directly approximately every 5 minutes. Firehose can be configured to put the logging data into any of its supported destinations, including S3.

All of these **destinations** can be integrated with an **event driven security response architecture** - Using a combination of products such as S3 events, lambda, Athena, and EventBridge, you can extract and identify intelligence to act on, and then use this intelligence to update web ACLs to update the platform in a way that doesn't require humans. This type of architecture is based on taking basic WAF and creating a **feedback loop** to take data, **identify** actionable intelligence and then **automate** changes based on that intelligence.

**Web Access Control Lists (WEBACL)**
- WEBACL Default Action (**ALLOW** or **BLOCK**) - Non matching
	- Which one of these you pick depends on if you're using WAF to explicitly protect against certain exploits or if you want to only allow known good traffic through to your Web resources.
- Resource Type - **CloudFront** or **Regional Service**
	- **ALB**, **API GW**, **AppSync** .. **pick region**
- Add Rule Groups or Rules .. processed in order
	- Web ACLs on their own don't do anything. You have to add Rule Groups or Rules. Order can be changed. You can move Rules & Rule Groups around.
- Web ACL Capacity Units (**WCU**) - Default max 1500
	- Rules have a certain compute requirement based on their complexity. Limited.
	- Not to be confused with DynamoDB WCUs - Write Capacity Units
	- WCUs are an indication of the complexity of rules
	- 1500 max can be increased via **support ticket**
- WEBACL's are associated with resources (this can take time)
	- // such as a CF distribution; CF needs to update the distribution and then push this out to edge locations.
	- **adjusting** a WEBACL takes **less time** than associating one

Importantly, the relationship is currently that a **resource** can have **one Web ACL**, but **one Web ACL** can be associated with **many resources**. Because of the global nature of CloudFront, you can't associate a CloudFront Web ACL with a regional resource or vice versa. Web ACLs currently can't be used with AWS outposts.

**Rule Groups**
- **Rule Groups** contain **rules**
	- Allow grouped admin of rules
- They **don't** have default actions ... that's defined when **groups** or **rules** are added to WEBACLs
- **Managed** (AWS or Marketplace), **Yours**, **Service** Owned (i.e Shield & Firewall Manager)
	- AWS managed rule groups are mostly available for free for AWS WAF customers. The AWS WAF Bot Control and Fraud Control Account Takeover Protection rule groups do have additional fees. Any rule groups obtained via the marketplace also generally have a subscription attached to them.
- **Rule groups** can be referenced by **multiple WEBACL**
- Have a WCU capacity (defined **upfront**, max 1500*)

- **Type**, **Statement**, **Action**
	- Type - determines how it works
	- Statement - consists of one or more things which match traffic or not
	- Action - what WAF does if a match occurs
- Type : **Regular** or **Rate-based**
	- Regular - match if something occurs
		- Ex: allow SSH connections from a certain IP address
	- Rate-based - match if something occurs at a certain rate
		- Ex: do something connect via SSH 5000 times in a 5 minute period (suggests brute force attack)
- Statement : (**WHAT** to match) or (**COUNT** ALL) or (**WHAT** & **COUNT**)
	- Ex: incoming TCP port 80 or incoming SSH; requests with certain HTTP header.
	- Rate based - slightly different - a rate limit on the number of connections for a source IP address. Or, you're going to be applying a rate limit to connections which come from an IP address which also match certain criteria (eg. 5000 connections in 5 minutes or 5000 connections to SSH in 5 minutes).
	- .. origin country, IP, label, header, cookies, query parameter, URI path, query string, body (**first 8192 bytes ONLY**) (**exam**), HTTP method
	- Example match criteria: exact match, starts with, ends with, contains, RegEx, etc.
- **Single**, AND OR, NOT
	- Rules can have a single statement or multiple. If you do have multiple, you can choose whether to use AND, OR, NOT conditions to define evaluations.
- Action : **Allow***, **Block**, **Count**, **Captcha** .... Custom **Response** (x-amzn-waf-), **Label**
	- regular rules - can allow, block, count or run a captcha
	- rate based rules - you can block, count or run a captcha
		- it makes sense that **allow** is **not valid** for **rate based** rules - if a rate is above a certain value it doesn't make sense that that something is allow
	- custom responses - optional extra
		- block - can be a custom response or a custom header
		- allows, counts, and captcha - can be a custom header only. Means your app can react to traffic which has been matched. custom headers are prefixed with "x-amzn-waf-".
	- labels - optional. Internal to WAF. Allows **multi stage flows**.
		- One rule can add a label; whether another rule runs can be based on the label being present or not.
		- Referenced later in the same Web ACL. Using labels relies on WAF not stopping processing.
	- **ALLOW** & **BLOCK** stop processing; Count/Captcha actions, processing continues

## CloudHSM
Similar to KMS in terms of the functionality which it provides, in that it's an appliance which creates, manages, and secures cryptographic material, or keys. You need to know key differences.

**CloudHSM**
- With KMS .. AWS Manage .. Shared but separated
	- Encryption within AWS
	- Integrates with other AWS products
	- Generates keys. Manages keys.
	- Has one security **concern** (if you operate in a really demanding security environment) - it's a **shared** service
		- While your part of KMS is isolated, under the covers you're using a service which other accounts within AWS also use.
		- While the permissions within AWS are strict, **AWS** do have a certain level of **access** to the KMS product - They manage the hardware and the software of the systems, which provide the KMS product to you as a customer.
- (**exam**) True "Single Tenant" Hardware Security Module (**HSM**)
	- Behind the scenes, KMS uses HSM (Hardware Security Module), industry standard pieces of hardware designed to manage keys and perform cryptographic operations. You can actually run your own HSM on premise.
		- If you hear the term HSM mentioned, it could refer to both Cloud HSM, or an on-premise HSM device
- **AWS provisioned** ... **fully customer managed**
	- They're responsible for hardware maintenance, but they have no access to the part of the unit where the keys are stored and managed. It's a physically tamper resistant piece of hardware. Generally, if you as the customer lose access to a HSM, that's it, game over. You can reprovision them, but there's no easy way to recover data.
		- Now there's actually a well-known standard for these cryptographic modules. It's called the Federal Information Processing Standard Publication 140-2. You can easily determine the capability of any HSM modules based on their compliance with this standard.
			- More info: [FIPS 140-2 - Wikipedia](https://en.wikipedia.org/wiki/FIPS_140-2)
- (**exam**) Fully **FIPS 140-2 Level 3** (KMS is **L2** Overall, **some L3**)
	- (**exam**) If you see an exam question, or if you're in a real-world production situation which requires **140-2 Level 3** overall, then you have to use Cloud HSM or your own on-premises HSM device.
- (**exam**) Industry Standard APIs - **PKCS#11**, Java Cryptography Extensions (**JCE**), Microsoft **CryptoNG** (CNG) libraries
	- With KMS, all operations are performed with AWS standard APIs, and all permissions are also controlled with IAM permissions. Cloud HSM isn't so integrated with AWS, and this is by design. With Cloud HSM, you access it with industry standard APIs such as PKCS11, the JCE extensions, or the Crypto NG extensions.
	- If you see these highlighted keywords (PKCS#11, JCE, CryptoNG), you know you need a HSM appliance, either on-premise or Cloud HSM hosted by AWS.
- KMS can use **CloudHSM** as a **custom key store**, CloudHSM integration with KMS

To summarize: remember the 3 highlighted (**exam**) powerups above to determine whether to use KMS or CloudHSM.

**CloudHSM**
![[CloudHSM.png]]
Cloud HSMs are not actually deployed inside a VPC that you control. They're deployed into an AWS-managed Cloud HSM VPC which you have no visibility of.

**HSM**, by default, is **not** a **HA** device. In the Cloud HSM VPC, **to achieve HA**, you need to deploy **multiple HSMs** and configure them as a **cluster**. Once HSM devices are configured to be in a cluster, then they **replicate** any keys, any policies, or any other important configuration between all of the HSM devices in that cluster. That's managed by default by the devices themselves (not something you need to configure).

The HSMs **operate** from this **AWS**-managed **VPC**, but they're **injected** into your **customer**-managed **VPC** via **ENIs**. You get **one ENI** for **every HSM** in the cluster. **Services** in your **VPC** can utilize the HSM cluster by using these **ENIs**. If you want to achieve **true HA**, instances will need to be configured to **load balance** across all of the **different interfaces**. To utilize the cloud HSM devices, a client (the **cloud HSM client**) needs to be installed on the EC2 instances - a background process. Then, you can use **industry standard APIs** such as PKCS#11, JCE, CNG to access the HSM cluster.

Distinguishing factor between CloudHSM and KMS - while AWS provision HSM, but have access to the area of the HSM appliances (tamper resistant) which store the keys. AWS can perform things like software updates and other maintenance tasks, but these don't take place on the area of the HSM which is used to perform cryptographic operations. Only you (or delegated admins) have access to the secure area of the HSM.

**CloudHSM Use Cases**
- (**exam**) No Native AWS integration .. e.g. no S3 SSE
	- Cloud HSM is not accessed using AWS standard APIs, at least by default, and so you can't integrate it directly with any AWS services. You could, for example, use cloud HSM to perform client-side encryption. So if you've got an encryption library on a particular local machine and you want to encrypt objects before you upload them to S3, then you can use it to perform that encryption on the object before you upload it to the S3 service. But this is not integrated with S3.
- (**exam**) Offload the SSL/TLS Processing for Web Servers
	- Web servers benefit from not having to perform cryptographic operations.
	- But also the cloud HSM is a custom designed piece of hardware that accelerates those processes. More economical than doing it on general purpose EC2 instance.
	- That's something that a cloud HSM can do for you, but KMS natively cannot.
- (**exam**) Enable Transparent Data Encryption (TDE) for Oracle Databases
	- Other products which are able to interact using these industry standard APIs that you might use inside AWS can also benefit from cloud HSM - like Oracle databases
	- CloudHSM is ideal product for strict regulatory environment where you really need to use strong encryption and verify exactly who has the ability to perform encryption operations.
- (**exam**) Protect the Private Keys for an Issuing Certificate Authority (CA)
	- If you're running your own CA, you can utilize CloudHSM to manage the private keys.

The **overall theme** is that for anything which **isn't specific to AWS** - anything which expects to have access to a **HSM** using **industry standard** APIs - the ideal product is CloudHSM. For anything which does require AWS integration, then natively, CloudHSM isn't suitable. If **FIPS 140-2 level 3** is mentioned, it's CloudHSM. If **integration** with **AWS** is mentioned, then it's probably going to be **KMS**. If you need to utilize industry standard encryption APIs, then it's likely to be CloudHSM.

- **Continuous** security monitoring service
- Analyses **supported Data Sources**
- plus **AI**/**ML**, plus threat intelligence feeds
- Identifies **unexpected** and **unauthorized** activity
	- GuardDuty is doing this in an intelligent way (using threat intelligence feeds), so you aren't having to identify things you usually do or define what normal activity is. You can influence this - whitelisting IPs, influencing OK behavior, but on the whole, it learns patterns on its own of what happens normally within any managed accounts
- **notify** or **event-driven** protection/remediation
	- might be a Lambda function performing some kind of remediation, or an event-driven workflow, via CloudWatch events
	- can be part of an automatic event-driven security response
- Supports multiple accounts (**MASTER** and **MEMBER**)
	- When you enable GuardDuty, you're essentially making the account that you enable it in the **master** GuardDuty account. Then you can invite other AWS accounts (**member**)

**Amazon GuardDuty**
![[Amazon GuardDuty.png]]
GuardDuty receives logs. Ingested together with various threat intelligent feeds. Used to generate findings. Findings can be sent to CloudWatch events, now known as EventBridge. Can be used to handle event-driven notification and automatic remediation - SNS, invoke Lambda (ex: Add an explicit deny rule to a NACL if there's a potential intrusion)
