## Border Gateway Protocol 101
BGP is a routing protocol. Used to control how data flows from point A through points B and C and arrives at the destination point D. AWS products such as Direct Connect and Dynamic VPNs both utilize BGP.

- Autonomous System (**AS**) - Routers controlled by one entity ... a network in BGP.
	- BGP as a system is made up of lots of self-managing networks known as Autonomous Systems. an AS could be a large network - a collection of routers - they're controlled by one single entity. From a BGP perspective it's viewed as a **black box** - an abstraction away from the detail which BGP doesn't need. You might have an enterprise network with lots of routers and complex internal routing but all BGP needs to be aware of is your network as a whole.
- **ASN** are unique and allocated by [[IANA]] (0-65535) 64512 - 65534 are private
	- Generally ASNs are 16 bits in length and range from 0 through to 65,535
		- // 32 Bit ASNs do exist
		- Most of that range are public ASNs which are directly allocated by IANA, however the range from 64,512 to 65,534 are private and can be utilized within private peering arrangements without being officially allocated.
		- ASNs are the way that BGP identifies different entities within the network. It's the way that BGP can distinguish between your network (your ASN) and my network.
- BGP Operates over **tcp/179** - Its **reliable**
	- It includes error correction & flow control to ensure all parties can communicate reliably.
- **Not automatic** - peering is **manually configured** (between two different AS)
	- Then, the two AS can communicate what they know about network topology.
	- A given Autonomous System will learn about networks from any of the peering relationships that it has. And anything that it learns, it will communicate out to any of its other peers. So, you rapidly build up a larger BGP network where each individual Autonomous System is able to communicate with its peers. That's how the internet functions from a routing perspective. All of the major core networks are busy exchanging routing and topology information between each other.
- BGP is a **path-vector** protocol. It exchanges the **best path** to a **destination** between peers ... the path is called the **ASPATH** (autonomous system path).
	- BGP doesn't take into account link speed or condition. It focuses on paths.
	- For example, can we get from A to D using A, B, C and D? Or is there a direct link between A and D? It's BGP's responsibility to build up this network topology network.
- **iBGP** = Internal BGP - Routing **within** an AS
- **eBGP** = External BGP - Routing **between** AS'S
	- Used most often with AWS

![[Border Gateway Protocol (BGP).png]]

0.0.0.0 means it's locally connected.
The ASPATH shows the way to get from one AS to another. The i means it's the origin (this network).
AS's advertise the shortest route that they're aware of to any other AS's.
(Blue = indirect route. Not preferred, because it isn't the shortest path). BGP always uses the shorter path as the preferred one.

Ideally, we only ever use the satellite connection because, 1) it's slow, 2 )It will suffer from significantly higher latencies. BGP doesn't take into account performance or condition, so the satellite connection will always be preferred. But you are able to use a technique called **ASPath prepending** which means that you can configure BGP at Alice Springs to make the satellite link look worse than it actually is. You do this by adding additional AS numbers to the path.

## IPSec VPN Fundamentals
- IPSEC is a group of protocols ...
- It sets up **secure tunnels** across **insecure networks**
	- between **two peers** (**local** and **remote**)
		- (peer = router)
- Provides **Authentication**
	- and **encryption**
		- data being caried by IPsec is ciphertext

![[IPSEC VPN Fundamentals.png]]

- Interesting traffic = traffic which matches certain rules.
	- could be based on network prefixes or match more complex traffic types
	- If data matches any of those rules, it's classified as interesting traffic, and a VPN tunnel is created to carry traffic through to its destination. If there's no interesting traffic, then tunnels are eventually torn down, only to be re-established when the system next detects interesting traffic.
The key thing to understand is that even though those **tunnels** use the **public internet** for transit, any data within the tunnels is **encrypted** while **transiting** over that insecure network. It's protected.

- Remember - **Symmetric Encryption** is fast
	- but it's a challenge to exchange keys securely
- **Asymmetric Encryption** is slow
	- but you can easily exchange public keys (because different keys are used for encryption and decryption public to encrypt, private to decrypt)
	- // the aim of most protocols which handle the encryption of data over the internet is to start with asymmetric encryption, use this to securely exchange symmetric keys, and then use those for ongoing encryption
- IPSEC has **two** main phases
- **IKE Phase 1** (Slow & heavy)
	- Authenticate - Pre-shared key (password) / Certificate
	- Using Asymmetric encryption to agree on, and create a shared Symmetric key
	- IKE SA (Security Association) Created (phase 1 tunnel)
		- // At the end of phase 1, you have a phase 1 tunnel
- **IKE Phase 2** (Fast & Agile)
	- Uses the keys agreed in phase 1
	- Agree encryption method, and keys used for bulk data transfer
	- Create IPSEC SA ... phase 2 tunnel (architecturally running over phase 1)
It's possible for phase one to be established, then a phase two tunnel created, used, and then torn down when no more interesting traffic occurs, but the phase one tunnel stays. It means that establishing a new phase two tunnel is much faster and less work.

**IKE Phase 1**
![[IPSEC VPN Fundamentals - IKE PHASE 1.png]]
- 1) about confirming identity (not encryption)
- 2) **Diffie-Hellman** (**DH**) key exchange. // (exam) try to remember **Diffie-Hellman**
	- Each side **creates** a DH **private** key - used to decrypt data and to sign things. Each side uses that private key & ...
- 3) ... **derives** a corresponding **public** key - used to encrypt data only that private key can decrypt. At this point each side has a private key as well as a corresponding public key.
- 4) 
- 5) // fancy math involved
- 6) This part you can think of as a negotiation. The result: each side uses their uses DH key + the exchanged key material to generate a ...
- 7) ...  final Phase 1 **symmetrical** key
	- This key is used to encrypt anything passing through the **Phase 1 tunnel**, known as the **IKE Security Association**
This process seems slow and heavy - both complex & simplistically elegant at the same time - both sides have the same symmetric key without that ever having been passed between them.

**IKE Phase 2**
![[IPSEC VPN Fundamentals - IKE PHASE 2.png]]
- In phase two, we have a few things - 
	- a **DH key** on both sides
	- the same phase 1 **symmetric** key on both sides
	- the established Phase 1 Tunnel (IKE Security Association)
Phase 1 was about allowing the peers to communicate. Phase 2 is about both of the peers are wanting to agree how the VPN itself will be constructed. Getting the VPN up and running. Being in a position to encrypt data. Agreeing how, when and what.
- 1) one peer is informing the other about the range of cipher suites that it supports (encryption methods which it can perform).
- 2) The other peer (in this example, the right one) pick the "best" "shared" method which it also supports & lets the left peer know.
- 3) IPSEC Key is designed for large-scale data transfer.
	- It's an efficient and secure algorithm. The specific one is based on the negotiation which happened above in steps one and two of this phase.
- 4) IPSEC Key is used for the encryption and decryption of Interesting Traffic across the VPN tunnel
- Across each phase one tunnel you actually have a pair of security associations - one from right to left, one from left to right. These are the Security Associations which are used to transfer the data between networks at either side of a VPN.

There are two different types of VPN which you need to understand: Policy-based VPNs and Route-Based VPNs. The difference is how they match Interesting Traffic.
- **Policy-based VPNs**
	- **rule sets** match traffic => a pair of SAs
	- different rules/security settings (for different types of traffic)
		- something which is great for more rigorous security environments
- **Route-based VPNs**
	- target matching (prefix)
		- Ex: send traffic for 192.168.0.0/24 over this VPN.
	- matches a single pair of SAs
		- // With this type of VPN, you have a single pair of security associations for each network prefix. This means all traffic types between those networks use the same pair of security associations. This provides less functionality, but it is much simpler to set up.

**Route Vs Policy Based VPN**
![[IPSEC VPN - Route vs Policy Based.png]]
**Route-Based VPN**
The phase 1 tunnel is established using a phase 1 tunnel key.
A single pair of security associations will be created & used to set up the route-based VPN - one in each direction using a single IPSEC key. This means that we have a pair of security associations, essentially a single phase 2 tunnel, running over the phase 1 tunnel. That phase 2 (or, IPSEC tunnel) can be dropped when there is no more interesting traffic and recreated again on top of the same phase 1 tunnel when new traffic is detected.

The key thing to understand is that there's one phase one tunnel running one phase two tunnel based on routes.

**Policy Based VPN**
Running a policy-based VPN is different.
We still have the same phase one tunnel, but over the top of this, each policy match uses an SA pair with a unique IPsec key. this allows us to have, for the same network, different security settings for different types of traffic. In this example, infrastructure at the top, CCTV in the middle, and financial systems at the bottom.

Policy-based VPNs are more difficult to configure, but do provide much more flexibility when it comes to using different security settings for different types of traffic.

## AWS Site-to-Site VPN
VPNs offer the quickest way to create a network link between an AWS environment and something that's not AWS - on prem, another cloud, data center.

- A logical connection between a VPC and on-premises network encrypted (in transit) using IPsec, running over the **public internet**\*
	- * (in most cases); exception: when running over the top of a Direct Connect
- (exam) Full HA - if you design and implement it correctly
	- // There are a few points of failure within the VPN architecture. You need to understand them all.
- Quick to provision ... **less than an hour**
	- // in contrast to the physical connections like Direct Connect
- // VPNs connect **VPCs** and private on-premise networks.
- Virtual Private Gateway (**VGW**)
	- Type of logical gateway object which can be the target on route tables. Something that you create and associate with a single VPC, and it's the target on one or more route tables.
- Customer Gateway (**CGW**)
	- Can refer to two different things
		- the **logical** piece of configuration within AWS, and...
		- the **physical** on-premises router which the VPN connects to.
- VPN Connection between the **VGW** and **CGW**

![[AWS Site-to-Site VPN1.png]]

The **VGW** is a logical gateway object, so it can be the **target** of **routes**. Customer on prem router will have an external ip address. For this router, we create a **CGW** object within AWS. This is a logical configuration entity that represents this physical device on our customer premises. In this case, we need to define its **public IP address** so that the logical CGW entity **matches** the physical **router**.

Behind the scenes, the **VGW** is actually a **HA** gateway object. Create the gateway and associate it with a VPC. Behind the scenes a VGW has physical endpoints - devices in different AZs, each with public IPv4 addresses. This means that the VGW is HA by design. If an AZ fails, the other device still functions. But this **doesn't mean the whole thing** is HA.

Next, create a **VPN** connection inside AWS. There are different types - static & dynamic. For now, we're going to create a **static** one. We need to **link** the **VPN** to a **VGW** to use the **endpoints** which that VGW provides; and, you need to specify a customer gateway to use. When you specify a specify a customer gateway to use, two VPN **tunnels** are created (blue lines) - one between each endpoint and the physical on-premises router.

// A VPN tunnel is an encrypted channel through which data can flow between the VPC and on-prem network & vice versa. As long as at least one of these VPN tunnels are active, then the two networks are connected. In this case, we have one VPN connection that's using the two endpoints of the VGW and both of those are connected back to our one CGW. So, we have a **partially HA** design. One AZ on the AWS side can fail & at least one of the tunnels will still be active. There is still one single point of failure - customer on-premises router. Because all of the tunnels terminate into the same single point of failure, this is known as partial high availability - HA on the AWS side, but single point of failure on the customer side.

Because this is a static VPN, we have to statically configure the VPN connection with IP addressing information. We have to tell the AWS side about the network range that's in use within the on-premises network. And, we have to configure the on-premises side so that it knows the IP address range that the AWS side uses. this means that traffic can flow from the VPC via the VPC router through the VGW over the tunnels to the on-premises network and back again.

![[AWS Site-to-Site VPN2.png]]To resolve the **partial high availability problem**, we can add **another** on-premises customer **router** using a **second internet connection** and ideally doing all of this in a separate building.

Once you have this second resilient connectivity method, then you can create an **additional VPN connection** at the AWS side (red line). Behind the scenes, this creates two more physical endpoints, which are managed by the VGW. Each of those has their own public IP addressing. This new VPN connection would be linked to the same VGW at the AWS side, but to the new customer gateway (Gateway 2). Architecturally, **the VGW is now HA** - it's HA as a logical entity; it's using endpoints which are located in different AZs (so it can withstand physical failure); at the customer side, we're now using multiple pieces of hardware, multiple internet connections (ideally, in separate buildings). It's got 2 VPN tunnels connecting each customer premises router to two VPC endpoints in separate AZs. And then that configuration is repeated again with a second customer gateway. Either of the customer gateways can fail & either AZ can fail & the VPC & on prem network will have connectivity.

**Static vs Dynamic VPN**
![[Static vs Dynamic VPN (BGP).png]]
A dynamic VPN uses BGP (a protocol). That's important because if your customer router doesn't support BGP then you can't use dynamic VPNs.

The architecture between static & dynamic VPNs is the same. The difference is how routes are communicated.
Static VPN uses static networking configuration - Static routes are added to the route tables, and static networks have to be identified on the VPN connection.
The **benefits** of **static** VPNs: It's **simple**. It only uses **IPSec**, so it **works almost anywhere** - with a combination of routers.

But they are restricted on things like, **load balancing** & **multi-connection failover**. So, if you need any advanced high availability, if you need to use multiple connections, if the VPNs need to work with Direct Connect, then you do need to be using **dynamic** VPNs.

**Dynamic** VPNs use BGP, which lets routers exchange networking information. **VGW** and the **CGW** can **exchange information** on which networks are at the AWS side and which are at the customer side. They can **communicate the state of links** and adjust routing on the fly. That allows for **multiple links** to be used at once between the same locations. This is why dynamic VPNs are able to use **high-end**, **highly available** VPN architectures. 

With dynamic VPNs, routes can still be added to the route table statically, or you can make the entire solution fully dynamic by enabling a feature called **route propagation** on the route tables in the VPC. Route Propagation: While any VPNs are active, any networks that these VPNs become aware of are **automatically added** as dynamically learned **routes** on the **route tables** (learned from the VGW).

- (exam) Speed Limitations - **1.25Gbps**
	- This is an AWS limit. You also need to check **speed** supported by **customer router**. because VPNs use encryption, there's a processing overhead on encrypting and decrypting data. At high speeds, this overhead can be significant.
	- (exam) If you need more than 1.25Gbps, then you can't use VPNs
	- There is a cap for the VGW as a whole - also 1.25Gbps
- (exam) Latency Considerations - **inconsistent**, **public internet**
	- The VPN connection transits over the public internet, and depending on the quality of your internet connection, there may be many hops between you and the AWS VPN endpoints. More hops = more latency & variability.
	- If you care about these as a priority (ex: running highly latency sensitive app), you might want to look at something else, like Direct Connect.
	- (exam) latency is often a selection criteria to pick between VPNs and something else in the exam
- Cost - AWS hourly cost, GB out cost, data cap (on premises internet connection)
- (exam) Speed of setup - **hours** .. all software configuration
	- IPsec is supported on pretty much all hardware at this point, even consumer grade routers
	- Remember, BGP support is much less common
	- When comparing VPNs to anything else, VPNs are almost always faster to set up versus other private connection technologies
- Can be used as a backup for Direct Connect (**DX**)
- Can be used with Direct Connect (**DX**)
	- You can use VPNs initially while DX is being setup. DX can take weeks or months to set up.
VPNs can also be used over the top of Direct Connect to add a layer of encryption.

## Direct Connect (DX) Concepts
- A physical connection (1, 10, or 100 Gbps)
- Business Premises => DX Location => AWS Region
- **Port Allocation** at a DX Location
	- When you order a DX connection what you're actually ordering is a network port at the DX location. That's it. It's just a physical port. It's up to you to connect to this directly or arrange the connection to be extended via a third party comms provider.
- Port Hourly Cost & Outbound Data transfer
	- Inbound data transfer is free
- Provisioning time ... physical cables & no resilience
	- AWS will take time to allocate a port. And then once allocated you will need to arrange connection into that port at the DX location
	- If you want to connect the DX location to your business network & need to physically lay cables, keep in mind that can take weeks or months.
	- Because it's a physical cable there's no built in resilience. If the cable is cut, the cable is cut. You can design in resilience by using multiple Direct Connects, but that's something that you have to layer on top.
- Low & consistent latency + High Speeds
	- Data isn't transiting across the public internet, like with say a VPN.
	- The best way to achieve the highest speeds for hybrid networking within AWS. You're very likely to achieve the maximum possible speed of that port (1, 10, or 100Gbps).
- AWS **Private** Services (**VPCs**) and AWS **Public** Services -  **NO INTERNET**
	- It cannot be used to access the public internet unless you add a proxy or other networking appliance to do that on your behalf.

**DX location**
![[Direct Connect (DX) Concepts.png]]
Not owned by AWS.
**AWS Direct Connect Cage** - Contains one or more DX routers - the end points of the DX service.
**Customer or Comms Partner Cage** - Often you'll also rent space at this DX location. Large orgs might rent this space directly. It might have some of your other infrastructure together with a router. This is known as the **Customer Cage**.
If you're a smaller organization then this cage might belong to a communications partner. This is known as the **comms** or **communications partner cage**. The communications partner extend any connections from this DX location into your business premises.

The key thing to understand about Direct Connect is that it's a **port allocation**. This needs to be connected physically with a fiber optic cable to another port in the DX location - either your router in **your cage** at the DX location or a **communication partners** router.

Between these to ports, you're going to order a **cross connect** - a connection (physical cable) between the Direct Connect port within the AWS cage in the DX location and **either** a **port** on **your** router or a **communications partner** also in the DX location. If you are using a communications partner, this link can be further extended through to your customer premises.

The **AWS region** is AWS owned infrastructure. It might be running from the same physical facilities as the DX location or it might be different but in either case it's connected with **multiple** resilient high-speed **network connections**. Just think about it as something which is always connected with one or more local DX locations.

Logically we have to configure **virtual interfaces** (**VIFs**) over this single physical connection.

There are three types of **VIFs** -
- **Transit VIFs** (specific use case)
- **Public VIFs** - used to access the AWS public space services
	- Being a virtual interface, it runs over the end-to-end **direct connect** from your **customer router** through to the **customer DX router** into the **AWS DX router** and then into the **public part** of the **AWS region**.
- **Private VIFs** - run over the Direct Connect, but connect into VGWs which are attached to a VPC
	- These provide access to **private** AWS services (private IPs only)

## Direct Connect (DX) Resilience
As an architect, you need to understand the impacts of failures at various points within the DX architecture and the way that it integrates with your on-premises networks.

**DX Architecture - No Resilience**
![[Direct Connect Resilience - NONE.png]]
Let's review an architecture which is not resilient. worryingly, this is actually the way I've seen most people provision DX.

To summarize, the AWS region is linked in a highly available way to one or more DX locations. The DX location houses the AWS DX routers in addition to your or a provider's DX router and you cross connect from the AWS DX router into your DX router with a physical cable and then all of this is extended to your on-premises environment.

There are actually **seven** single **points** of **failure** on this diagram.
- The entire **DX location** could fail - power failures, buildings can and often do collapse
- The AWS **DX router** could fail - either in isolation or along with the building
- The **cross connect** cable can fail
- **Your DX** router could fail
	- What if you don't have an on-site spare?
- The **extension** from the DX location to your on-premises environment **cable** can fail
	- It probably goes under the road or across above ground cables and any engineering works can potentially be a risk to the stability of that cable.
- You might also have a failure of your actual **customer premises environment**
- Your **customer premises router** within that environment could also have a hardware failure

DX as a product is not resilient in any way by default. It's a product which is based on lots of physical components which each depend on each other. But, it's also a product that's designed to be flexible so it can actually be made into a super resilient service.

**DX Architecture - OK**
![[Direct Connect Resilience - OK.png]]
We can improve the resilience of the architecture by provisioning multiple DX ports by ordering two DX's. This architecture has two AWS DX routers, two customer DX routers, and two customer premises routers.

The architecture can tolerate a failure of a router in either of those two paths, or a failure of one of the extensions, and still continue operating.

The design does have some problems though, we have **two** single points of failure - The two **locations** that are involved in this private networking:
- The **DX location** itself fails
- A single **customer location**
We also have a potentially hidden single point of failure with this architecture - the **extensions** between the DX location and the single customer premises location could, in theory, travel via the **same physical cable route**.

**DX Architecture - BETTER**
![[DX Architecture - BETTER.png]]
Now, we have **two** independent **customer premises** (two buildings; ideally, spread out geographically). In addition, we have **two** different **DX locations**.

In each DX location, we're going to provision one DX port that's cross-connected into one customer DX router, and each of these is going to be extended into a different customer router in a different customer premises.

This architecture offers better resilience.

This architecture can tolerate the failure of:
- One DX location
- Hardware and location failure at the customer side
(example) If both DX Loc 1 & Customer Prem 1 failed, this solution would still provide connectivity. This solution would only fail if all of that failed plus either: DX Loc 2 or Customer Prem 2.

Risk of outage if:
- An entire location fails + the hardware in the remaining (other) path also fails

**DX Architecture - GREAT**
![[DX Architecture - GREAT.png]]
This time, we have **two DX ports** on **separate equipment**. In **each location** (DX Location & Customer Prem), we also have **two customer DX routers**.

This is relatively complex network architecture. The thing that I want you to take away from this lesson, from an exam perspective, and if you intend to use Direct Connect in real world projects, is that Direct Connect is a physical technology, and so it is not resilient in any way, unless you architect it that way. If you need HA, you should definitely review all of these HA architectures, rather than provisioning a simple single DX.

You can also use site-to-site VPN as a backup for DX.

## Direct Connect (DX) - Public VIF + VPN (Encryption)
How you can use DX, Public VIFs, and IPsec VPNs to provide end-to-end encrypted access to private VPC networks across DX.

**Public VIF + VPN**
- Encrypted & Authenticated tunnel
	- Using a VPN gives you an encrypted and authenticated tunnel whether you use the public internet or run a VPN over DX.
- Over DX (**Iow latency** & **consistent** latency)
	- By running a VPN over DX though, you get great performance and security
- Uses a **Public VIF** + **VGW**/**TGW** **public** endpoints
	- Many students get confused by this because it provides access to a private VPC. So, why not use a private VIF? **Private VIFs** only give access to **private IPs**. A **public** VIF gives access to public zones, meaning **public IP addresses** owned by AWS. With a VPN, you're connecting to public IPs which belong to a VGW or Transit Gateway. So, you need a public VIF.
- Transit Agnostic (**DX** / **Public internet**)
	- You can connect using a VPN to a Virtual Private Gateway or a Transit Gateway over the public internet or over a public VIF. The VPN configuration is the same, it's just the transit which differs - public internet or public VIF.
- End-2-End .. CGW <=> TGW/VGW - MACsec is single hop based
	- A **VPN** is **end-to-end encryption** from a **customer gateway** through to a **transit** or **virtual private gateway**. Compare this to MACsec which is single hop based between the **AWS DX router** and whatever your **cross connect** is terminated into. VPN and MACsec are not competitors - they do different things. A **MACsec** connection is between **two hops** in the **same layer 2** local area network.
- Wider vendor support
	- Getting a router which supports IPsec VPN is easier than getting a switch which supports MACsec (Although, this will change over time).
- VPN has more **CRYPTOGRAPHIC overhead** vs MACsec ... **limits speeds**
	- MACSEC is much faster and designed for terabit or above network speeds
- Can be used while **DX is being provisioned** and/or as a **DX backup**
	- You can start with a VPN, get your traffic flows working over that, then add a DX later, either leaving the VPN in place to encrypt primary traffic over the DX or using it as a backup to the DX, or both.
	- A common form of **resilience** in many of my clients is to have a normal internet connection. Over this, you also run an **IPSec VPN** into AWS. Then you have a **DX** also running **another IPSec VPN** tunnel. This way, traffic is always encrypted. The DX is the **primary** (giving good performance) & you have a **backup** in the form of a completely separate network connection and a completely separate IPSec tunnel.

The architecture of using a VPN and DX looks like this:
**Public VIF + VPN**
![[Public VIF + VPN.png]]

// The DX location in the image is in ap-southeast-2
When using a VPN with AWS (with VGW, in this case), what actually happens is that **two VPN endpoints** are created within the AWS public zone in that region (one in each of two AZs). These endpoints have public addressing.

This means that you can **either** connect from the customer site to these endpoints using the **public internet** for transit, (which means lots of hops as well as a fairly varied latency), **or** you can create the **IPSec VPN** across the **public VIF**, (which means you'll benefit from DX's low and consistent latency).  In both cases, it's the same encrypted tunnel between the customer on-premises gateway and the AWS VPN endpoint.

You can even connect to VPN gateways in other AWS regions using the same public VIF across the AWS global network. And this is often a great way to provide global encrypted transit between VPCs and your business network.

What I want you to take away from this lesson is: **IPSec** running over a DX doesn't compete with **MACsec**. **VPN** is for when you need **e2e encryption** of data from AWS to on-premises networks, using something which can work equally as well over the public internet and a public VIF. It also means that you can connect to **VPCs** in **remote regions** using the same grade of equipment.
Focus on understanding why we're using a **public VIF** with this architecture, because we're connecting from the **customer gateway** to a **public IP** or public IPs, which are provided by the **VGW** or **TGW**. Because we're connecting to public IPs, we need to use a public VIF.

## Transit Gateway
- **Network Transit** Hub to connect VPCs to on premises networks
	- Connects VPCs to each other and to on-premises networks using site-to-site VPNs and DX
- Significantly **reduces** network complexity
- Single network object - HA and Scalable
- **Attachments** to other network types
	- How Transit Gateway connects to other network objects within AWS, and it's how it connects to on-premises networks. Currently, valid attachments include VPC attachments, site-to-site VPN attachments, and Direct Connect gateway attachments
- **VPC**, **Site-to-Site VPN** & **Direct Connect Gateway**

![[Without Transit Gateway (TGW).png]]

Suppose the Animals for Life network has 4 VPCs - A, B, C, & D.
We can use VPC **peering connections** to connect the four VPCs, and these are already highly available and scalable. But, they **don**'t support **transitive** routing, and so we need to create a **full mesh** between all VPCs. So rather than four peering connections, we'd need to have **six**.

We need the corporate office to be connected to all of the VPCs. Because VPN **routing** isn't **transitive**, we need a **full mesh** here as well. This means a **CGW** on the customer side, and VPN connections between the VPCs and that CGW (red lines) - total of 8 tunnels. This ensures high availability at the AWS side.

We need this architecture to be fully, highly available. And we currently have a single **point of failure** - the CGW on the customer side. We have multiple availability zones at the AWS side, all connecting back to the customer. So, we **another CGW** on the **customer premises** (ideally, on a separate internet connection & in a separate premises entirely). And then have that CGW connected back to all four of these VPCs - **another 8 tunnel** connections (blue lines).

A full mesh network is complex - lots of admin overhead. Scales poorly. This is where the transit gateway is useful.

![[With Transit Gateway (TGW).png]]
This time, we have a **TGW** using a **site-to-site VPN attachment**. It becomes the AWS side **termination point** for the VPN. So rather than having to have connections between the corporate office and **every VPC** terminated on a **VGW**, each **CGW** only has to be connected to the **TGW**. We have the same level of HA. We still have the four tunnels connected from different AZs connected to CGWs, but we reduce the number of VPN tunnels that are required.

TGWs can create attachments to VPCs; like **VPC interface endpoints**, (// [[15.0 ADVANCED VPC Networking#VPC Endpoints (Interface)]]), you need to specify a **subnet** in each AZ inside the VPCs that you want to use the TGW with. When you do that, it acts as a HA inter VPC router.  One single TGW can route traffic between lots of different VPCs. This is a **transitive** routing capable device. So, we only need attachments from the TGW to VPC A, B, C, and D, then they can all talk to each other through the TGW. Because we have the VPN attachment, all the VPCs can communicate with the on-prem environment & the on-prem environment can communicate with all of the individual VPCs.

You can **peer** TGWs with **different regions** in the same or cross accounts. Any cross region data uses the AWS global network, and so benefits from the more predictable latency rather than using the public internet.

You can also **attach** a TGW to **DX gateways** if your business uses DX for use with physical private networking connections into your business premises.

TGWs come with the **default route table** which is how traffic is routed between attachments but you can create a complex routing topology by using multiple route tables.

- Supports **transitive routing**
	- Don't need to create full mesh topology
	- Single TGW with multiple attachments will orchestrate the routing of traffic between all attachments as long as appropriate routing is in place.
- Can be used to create global networks
- Share **between accounts** using **AWS RAM**
- Peer with **different regions** ... same or cross account
- **Less complexity** vs without TGW

## Storage Gateway - Volume
The key to exam success when it comes to Storage Gateway is to understand when you would use each of the modes because each of them has their own specific situation when it should and shouldn't be used.

This lesson covers **Storage Gateway** running in **Volume Stored Mode** and **Volume Cached Mode**.

- **Virtual machine** (or hardware appliance)
	- acts as a bridge between on-prem and AWS
- Presents storage using **iSCI**, **NFS**, or **SMB**
	- iSCI - SAN & NAS protocol
	- NFS - linux
	- SMB - windows
- Integrates with **EBS**, **S3**, and **Glacier** within AWS
- (exam) **Migrations**, **Extensions**, **Storage Tiering**, **DR**, and Replacement of **backups systems**
- (exam) For the exam ... **picking the right mode** (for given scenarios)

A Storage Gateway is generally something which is run as a virtual appliance on-premises. You might have attached on-prem NAS or SAN - being used by on-prem servers.

This is a traditional architecture that you'll see in many businesses. Small businesses often have little, if any, funds for backups or effective disaster recovery. They're often looking at AWS as a solution to rising operational costs or as an alternative to running their own data centers.

**Volume Stored Mode**
![[Storage Gateway - Volume Stored.png]]
The virtual appliance presents **raw disk** volumes over **iSCSI** to servers running on-premises. Servers can create **file systems** on top of these volumes, just as they can with the volumes presented by the NAS or SAN devices.

In **stored mode**, these volumes **consume capacity on-premises**. The Storage Gateway has **local storage** and this local storage is the primary storage location for all of the volumes that Storage Gateway presents out over iSCSI.

Storage Gateway in this mode also has a separate area of storage called the **upload buffer**. Any data which is written to any of the volumes in the local storage is also **written** to this **buffer** temporarily and then it's **copied asynchronously** into AWS and this is via the Storage Gateway endpoint which is a public endpoint. This can occur over your normal internet connection or a public VIF running on a DX. This data is being copied into S3 in the form of **EBS snapshots** of the volumes running on-premises and this occurs **constantly** in the background.

- Great for doing **full disk backup** of servers
	- excellent RPO and RTO values - snapshots can be **quickly restored** without much in the way of lost data
- Great for **disaster recovery**
	- because the EBS snapshots which are created can themselves be used to create new EBS volumes. In theory you can provision a **full copy** of an **on-premises server** within AWS by just using these EBS snapshots.
- (exam) What this mode **doesn't allow** is **extending** your data center capacity, because the primary location for data is **on-prem**. This mode won't help you if you have **capacity issues**.

(don't need to remember these for exam): You can have 32 volumes per gateway, 16 TB per volume - that represents 512 TB per gateway in Volume Stored Mode.

**Volume Cached Mode**
![[Storage Gateway - Volume Cached.png]]
You still have the Storage Gateway running as a virtual appliance, or in some cases physical.

The difference starts is that the main location for the **data** is **no longer on-premises**. Instead, the **primary location** for the data is in AWS, specifically **S3**, and it's cached locally.

When I'm talking about the primary data being stored in S3, it's actually an **AWS-managed area** of S3. This is only **visible** from the **Storage Gateway console**. You can't just open a bucket and look at the data. The data being stored is raw block storage. It's not files or objects. It's raw data from a volume. You can still use it to create EBS snapshots.

The only thing that's stored **locally** is the **frequently accessed data**. It means that we could potentially have hundreds of terabytes of data managed by the Storage Gateway and presented to servers and only consume a fraction of that locally in the form of cached storage. This allows for an architecture known as **data center extension**.

**Volume Stored** only really provides **backup**, **DR**, and **migration** capabilities. Doesn't allow for capacity **extension**. Data is accessible locally at local area network speeds.
With **Volume Cached**, frequently accessed data is cached locally in the cache storage, so it too is accessible with local area network speeds. Anything that isn't frequently accessed doesn't get cached and is slower to access. But, you can extend capacity.
A single gateway can handle 32 volumes, 32TB per volume, for a total of 1PB per gateway.

## Storage Gateway - Tape (VTL)
Storage Gateway running in Tape Mode (VTL = Virtual Tape Library).
Large enterprise backups tend to run in one of three ways: Backup to Tape, Backup to Disk, or Off-Site Backup to a remote facility over a network link. This lesson is focused on Tape backup.

- Large Backups => **TAPE**
- e.g. LTO-9 Media can hold **24TB** Raw Data
	- LTO = Linear Tape Open
	- up to **60TB Compressed**
- **1 Tape Drive** can use **1 tape** at a time
	- can read from the tape or write to the tape, sequentially. It's not random access like disk or SSD.
	- to find data, you need to seek through the entire tape, locate the data, and then read it.
	- can't be easily updated. can't modify. has to be overwritten. write as a whole or read as a whole.
- **Loaders** (Robots) can swap tapes
	- Imagine a robot arm
- A **Library** is 1+ **drive(s)**, 1+ **loader(s)** and **slots**
	- A library fits in a rack. Slots store tapes not in the drive.
- Components: **Drive** ... **library** ... **shelf** (stores tapes)
	- (if you see a shelf mentioned, it's **anywhere but the library**)

![[Traditional Tape Backup.png]]
Media Changer - another name for a tape loader / tape robot.
Enterprise-grade backup architecture is expensive. Storage Gateway running in VTL fixes many of these problems.

![[Storage Gateway Tape (VTL).png]]

Instead of the on-premises tape library, we use Storage Gateway in tape or VTL mode.

The Storage Gateway pretends to be an iSCSI Tape Library, an iSCSI Changer, and an iSCSI Drive. It uses a combination of S3 and Glacier / Glacier Deep Archive to support the backup and restore functionality of a physical tape library.

The backup server doesn't know the difference between this and the previous physical tape library.
The Storage Gateway presents a **media changer** and the **tape drives** which looks like a normal physical tape library, but it's not - Essentially, they're virtual tapes. It has an **upload buffer** and a **local cache**, much like Volume Gateway running in cached mode. Used to store data which is being actively used. The **Storage Gateway** communicates with the **Storage Gateway endpoint** within AWS.

The **Storage Gateway endpoint** then presents **two** main **capabilities**: **VTL**, backed by S3, and the **VTS**, backed by glacier.
VTL = AWS-hosted version of a tape library. VTS = for virtual tapes which have been logically moved out of that VTL.

Backups occur at LAN speeds to the local storage that the Storage Gateway uses. The on-premises Storage Gateway caches stuff locally and uploads in the background to the VTL. A VTL can be from 100GB to 5TB (also the max size for an S3 object).

Storage Gateway can handle a total of 1PB of data across 1500 Virtual Tapes within the VTL (the part which uses S3).

When Virtual Tapes aren't being used, they can be exported within the backup software. This marks them as not being within the Library. Then, it archives into VTS (S3 -> Glacier). The limit of this Storage Gateway appliance is only for Tapes that are stored in the VTL. Anything which you archive into the Virtual Tape Shelf benefits from unlimited amounts of capacity.

Glacier is generally used for archival when there's an expectation that at some point you will need access to data - infrequently accessed. Glacier Deep Archive is used to archive data and is used for longer-term data retention, where you might never need to access the data again, but you do need to keep it, maybe for legal reasons. In either case, if you need to access the data again, then it can be retrieved from the VTS into the VTL, then accessed again by the Storage Gateway.

Capabilities this gives:
- **maintain** your existing **backup** system, but **replace** much of the **expensive** parts with economical AWS storage.
- **extend** an additional backup system by using capacity within AWS
- **migration**
	- Ex: migrate tape backups onto Storage Gateway (VTL), decommission your physical tape hardware, then even run the Storage Gateway appliance and the backup server from within AWS for any data retrieval needs

## Storage Gateway - File
Running in file mode, Storage Gateway manages files.

(**exam**) For any Storage Gateway questions in the exam, if you see **volumes** mentioned then you should default to **Volume Gateway**. If you see **tapes** mentioned, default to **VTL mode**. If you see **files** mentioned, then default to **File mode**. Only move away if you see something that eliminates any of those options

- Bridges on-premises **file** storage and S3
- Mount Points (shares) available via **NFS** or **SMB**
	- // NFS for Linux, SMB for Windows
	- (exam) These are keywords which will help you distinguish between Volume Gateway, Tape Gateway, and File Gateway
- Map directly onto an **S3 bucket**
- **Files stored** into a **mount point**, are **visible as objects** in an **S3 bucket**.
	- When you store files onto a mount point over SMB or NFS, they appear in the S3 bucket as objects. If you store objects into an S3 bucket, they're visible on the corresponding mount point on-premises.
	- This is essentially the key benefit of using Storage Gateway running in File Mode - It translates between on-premises files and AWS-based S3 objects
- **Read** and **Write** **Caching** ensure **LAN-like** performance
	- Like the other Storage Gateways, it typically runs on-premises
![[Storage Gateway - File.png]]
File Gateway runs as a virtual appliance in most cases and it has local storage that it uses as a read and write cache. This gives whatever data is managed by the Storage Gateway near local area network performance.

On the Storage Gateway end (on prem), we create file shares. Each of these **file shares** are **linked** with a **single** **S3 bucket** running in your account. This link is known as a **bucket share**. can be accessed from any local servers using NFS (Linux) or SMB (Windows). A windows share can use Active Directory authentication.

The reason why File Gateway is awesome is because the **file shares** and the **buckets** are **linked** together - S3 objects are visible in the file share and vice versa. Direct mapping. The **structure** of on-premise file shares is **preserved** by building that structure into the **object name** within S3. this is much like how S3 emulates a nested file system structure within what is a flat object storage system by building it into the object name.

You can have **10** of these **bucket shares** per **storage gateway**. Crucially, the **primary data** is **held on S3**. So the only thing that's stored **locally** is within the local **cache**. This holds data written or read from the storage gateway and is designed to improve **performance** to near those achieved from any other resources running on a **local area network**.

S3 Integration. You can use S3 events and Lambda as well as other AWS services such as Athena.

If you see the keyword **file** in the **exam**, maybe with the keyword **extension**, then a possible answer is going to be the storage gateway running in file mode.

It enables some really cool **hybrid architectures**. The architecture that's on screen now is a simple **two-site** hybrid architecture with on-premises on the left and then AWS on the right. But storage gateway in file mode can be used to implement a true **multi-site** architecture.

**Storage Gateway - Multiple Contributors**
![[Storage Gateway - Multiple Contributors.png]]
We can add another on-premises environment at the bottom.
There are some concerns to keep in mind.
First, when you **update** a file on a local storage gateway, that **update** is **copied** into S3. That's automatic. But to save on resource use, and avoid unnecessary S3 **listings**, there's **no** automatic **version** of that in reverse. When you **list** the file share on-premises, you're listing the **most recent** copy of the S3 bucket that the gateway is aware of.

 If you **added** a new cat picture to the top storage gateway, that would create a new object immediately in the S3 bucket. But if you then **listed** the file share in the bottom on-premises environment, it **wouldn't show** until you **initiated a listing**. There's a feature of storage gateway called **notify when uploaded** which sends an event using **CloudWatch events** which can inform the other storage gateways when an update has occurred. But this needs to be **designed** into your solution. It doesn't occur by default.
 // [NotifyWhenUploaded - Storage Gateway](https://docs.aws.amazon.com/storagegateway/latest/APIReference/API_NotifyWhenUploaded.html)

File gateway doesn't support any form of **object locking**. If **two users** **both write** to the same file, there isn't any form of checking or control over this access. This can result in data loss where one update overwrites another. Either make sure that one of the shares is R/W and everything else is read, or implement some form of control on who accesses files and when.

Another powerful architecture is **replication**.
![[Multiple Contributors and Replication.png]]
We have two customer sites linked to the S3 bucket in US East 1. We create another bucket in say US West 1, then configure **cross region replication** of that data between those two buckets. This gives us a nice way to implement multi-region DR without any significant changes to infrastructure or much in the way of additional costs.

We can also use file gateway and S3 **lifecycle management** together.
![[Storage Gateway - File - Lifecycle Management.png]]
Using file gateway means that the files and objects remain in **sync**. Because it's using S3, there are **different storage classes** available for objects. And three examples are S3 standard, S3 standard in frequent access, and S3 glacier. When you create a file share, you specify the default storage class to use (usually S3 standard).

But over the top of this default, you can create **lifecycle policies** which run within an S3 bucket. Maybe you configure them to move objects from standard to standard IA after 30 days. And behind the scenes, objects are moved automatically between these two different classes. Multiple steps are allowed. You could also have a 90-day move to glacier. This process happens in the background automatically, which means it's cost effective. Because the primary copy of all data is in S3, any on-premises locations automatically benefit from this cost effective storage system.

For the **exam**, make sure that you're familiar with when you'd use each **type** of storage gateway - Volume stored, volume cached, VTL, File Gateway.

## Directory Service
Provides a managed directory, a store of users, objects, and other configuration. Delivered as a managed service.

	- Tree structure referred to as a domain

	- Microsoft Active Directory Domain Services (**AD DS**)

**Directory Service**
- **AWS Managed** implementation (of a Directory)

	- Using it means you have no **admin overhead** of running your own directory service. And that admin overhead is often significant.
- Runs within a **VPC** (it's a private service)
	- To use it for services, those services either need to be within that VPC. Or you need to configure private connectivity to that VPC.

	- Amazon Workspaces = virtual desktop product. Like Citrix. It needs a directory registered with AWS. It needs a directory service product.

- Can be **isolated** ..
- .. or **integrated** with existing **on-premises system**
- Or act as a '**proxy**' back to on-premises
	- allows you to use your existing on-premises directory with AWS services which require a registered directory service

## FSx for Windows Servers
One of the topics you only need high level overview for the exam.

FSx for Windows File Server. FSx is a shared file system product, but it handles the implementation in a very different way than, say, EFS. FSx for Windows File Server is one of the core components of the range of services that AWS provide to support Windows environments in AWS.

- Fully managed **native windows** file servers/shares
	- You're provided with file shares as your unit of consumption. The servers are hidden. Similar to RDS.
- Designed for **integration** with **windows environments**
	- It's a native Windows file system. It's not an emulated file server.
- Integrates with **Directory Service** or **Self-Managed AD**
	- This is a critical feature for enterprises who already have their own Active Directory provision

	- It's a resilient and HA system
	- Picking between the two controls the network interfaces which are available and are used to access the product - Uses ENIs in the VPC
	- The backend, even in single AZ mode, uses replication within that AZ to ensure that it's resilient to hardware failure. If you pick multi-AZ, then you get a fully multi-AZ, highly available solution
- **On-demand** and **Scheduled** Backups
- Accessible using **VPC**, **Peering**, **VPN**, **Direct Connect**

In the **exam**, when you're faced with any questions which talk about shared file systems, you need to be looking to identify any **Windows related keywords** - native Windows file systems, Active Directory, Directory Service integration. Your job in the exam needs to be to pick when to use **FSX versus EFS**. Generally, **EFS** tends to be used for **shared file systems**, for **Linux EC2** instances, as well as **Linux on-premises** servers, whereas FSX is dedicated for Windows environments.

![[FSx for Windows File Server.png]]
FSX **uses AD** for its **user store**. Needs to be connected to some form of directory for its user store. Once deployed, you can create a **network share** using FSX, and this can be accessed in the normal way, using the double backslash DNS name and share notation that you'll be familiar with if you use Windows Environment (e.g. \\\fs-xxx123.animaIs41ife.org\catpics).

This access path can be accessed from other AWS services which use Windows-based storage, such as WorkSpaces (VDI like Citrix). when you deploy WorkSpaces, into a VPC, not only does it require a directory service to function, but for any shared file system needs, it can also use FSX.

The most important thing to remember about FSX is that it is a native Windows file system. It supports things like de-duplication, the distributed file system, or DFS, which is a way Windows can group file shares together and scale out for a more managed file share structure at scale, it supports at-rest encryption using KMS, and it also lets you enforce encryption in transit.

Shares are accessed using SMB protocol, which is standard in Windows environments, and FSX even allows for volume shadow copies, which in this context are a way that users can see multiple file versions and initiate restores from the client side. You can right-click on a file or folder, view previous versions, and initiate file level restores without having to use AWS or engage with a system administrator - that's something that's provided along with the FSX product.

From a performance perspective, FSX is highly performant. The performance that's delivered can range from anywhere from 8 MB per second to 2 GB per second, it can deliver hundreds of thousands of IOPS, and it delivers less than a 1 millisecond latency. So it can scale up to whatever performance requirements your organization has.

## FSx For Lustre
Designed for various high-performance computing workloads.

You won't need to know about Lustre in detail. It's one of those relatively niche products, but you'll need to distinguish between scenarios when you might use products such as FSX for Windows versus FSX for Lustre.

FSx for Windows is a Windows native file system which is accessed over SMB. It's used for Windows native environments within AWS

**FSx for Lustre**
- Managed **Lustre** - Designed for **HPC** - **LINUX** Clients (POSIX)
	- FSX for Lustre is a managed implementation of the Lustre file system, which is a file system designed specifically for HPC. It supports Linux-based instances running in AWS and as a keyword to track for the exam, it also supports POSIX-style permissions for file systems.
- **Machine Learning**, **Big Data**, **Financial Modelling**
- **100's GB/s** throughput & **sub millisecond** latency
- Deployment types - **Persistent** or **Scratch**

	- but doesn't provide much resilience or HA
- Persistent - **longer term**, **HA** (**in one AZ**), **self-healing**
- Accessible over **VPN** or **Direct Connect**
	- You'll need substantial bandwidth

![[FSx for Lustre.png]]
The product focuses around a **managed file** system which you create, it's accessible from within a **VPC**, and anything connected to that VPC via **private networking**. Connectivity wise, it's much like EFS or FSx for Windows (in that sense in that you can access it from the VPC or anything connected to it with private networking).

The file system is where the data lives - while being analyzed or processed by your applications. When you create a file system, you can associate it with a repository. In this case, an S3 bucket. If you do this when the file system is created, the objects within the S3 bucket are **visible** in the file system. But, crucially at this stage they're **not actually stored** within the Lustre file system. When they're **first accessed** by any clients connected to the Lustre file system, the data is **lazy loaded** into the file system from the S3 repository. Then they're present in the file system. There isn't actually any built-in synchronization. It can just use an S3 repository as a foundation. You can actually **sync** any **changes** made in the file system **back** to the **S3** repository using the **hsm_archive** command.

What I want you to understand conceptually is that the Lustre file system is completely **separate**. It can be configured to lazy load data from S3 and to write it back, but it's not automatically in sync.

Lustre splits data up when it's storing it to disks. There are a number of different types or elements to data that are stored within the file system.
- Metadata stored on Metadata Targets (**MST**)
	- Metadata: ex: file names, timestamps, permissions
- Objects are stored on called object storage targets (**OSTs**) (**1.17TiB**)
	- data is split over OSTs to achieve performance
- **Baseline** performance based on **size**
- Size - min **1.2TiB** then increments of **2.4TiB**
- For **Scratch** - Base **200 MB/s** per **TiB** of storage TiB of storage
- **Persistent** - offers three baseline performance levels - **50MB/s**, **100MB/s**, and **200 MB/s** per TiB of storage
- Both types can **Burst** up to **1,300 MB/s** per TiB (Credit System) 
	- You earn credits when you're using a performance level below your baseline. You consume these credits when you burst above the baseline. Shares many of the characteristics of EBS volumes, but at higher scale and with more parallel architecture.

![[FSx for Lustre2.png]]
Any FSX architecture uses a **client-managed VPC**. Inside this client-managed VPC are some clients (generally Linux **EC2 instances** with the **Lustre software** installed).

Other side of architecture: you create a **Lustre file system** and optionally an **S3 repository** for that file system. Depending on the size of storage that you configure within Lustre, the product deploys a number of **storage servers**. These servers **handle** the **storage requests** placed against the file system, and each of them also provides an **in-memory cache**, which allows faster access to **frequently used data**. This performance is delivered into your VPC using a single **ENI**. Lustre runs from **one AZ**.

Any **writes** to Lustre will go via the ENI and they'll be written directly to disk. That will be dependent on the disk throughput and I/O characteristics. **Read** from disk - performance based on disk characteristics. But frequently accessed data is cached in-memory. In that case, performance is based on networking characteristics.

- **Scratch** is designed for **pure performance**
- **Short term** or **temp** workloads
- NO HA .. NO REPLICATION
	- Hardware failure = data loss
- **Larger file systems** means **more servers**, **more disks** and **more chance of failure**
- Persistent has **replication** within ONE AZ only
	- Protects you against hardware failure, but not full AZ failure.
- **Auto-heals** when hardware failure occurs
- You can **backup to S3** with **both** !! (Manual or Automatic 0-35 day retention)

FSX for Lustre is similar to FSX for Windows and similar to EFS in terms of how it's architected. Uses ENIs injected to a VPC. Can be accessed via private networking.

(exam), if you see **Windows** mentioned or **SMB** mentioned then it's going to be FSX for Windows and not FSX for Lustre. If you see any mention of Lustre, any mention of really high end performance requirements, any mention of POSIX, high performance computing, machine learning, big data, SageMaker, or any of those type of scenarios, then it's going to be FSX for Lustre.

## AWS Transfer Family
- Managed file transfer service - Supports transferring TO or FROM **S3** and **EFS**
- Provides managed "**servers**" which support **protocols**
	- allows you to upload and download data to and from EFS and S3 using protocols other than those two native protocols
- File Transfer Protocol (**FTP**) - Unencrypted file transfer.
	- Legacy protocol. Relatively niche.
- File Transfer Protocol Secure (**FTPS**) - File transfer with TLS encryption
- Secure Shell (SSH) File Transfer Protocol (**SFTP**) - File transfer over SSH
- Applicability Statement 2 (**AS2**) - Structured B2B Data
	- Relatively niche. Relatively common in certain industries. Compliance. Data security. Supply chain. Payment workflow. CRM.
- Identities - **Service** Managed, Directory Service, Custom (**Lambda**/**APIGW**)
- Managed File Transfer Workflows (**MFTW**) - serverless file workflow engine
	- When files are uploaded, you can define a workflow as to what happens to that file as it gets uploaded. Notification or tagging.
You get access to all of these different file transfer protocols via a TransferFamily server, within AWS without the need to manage any server infrastructure. So if you need to **interact** with **S3** or **EFS** using existing workflows where you **can't change your applications**, then you can use TransferFamily.

![[AWS Transfer Family - Architecture.png]]
We want to grant access to S3 or EFS to an external user. Suppose it's a medical user who wants to use the SFTP protocol. Configure TransferFamily to communicate with backend storage resources using **IAM roles** in order to get permissions. Once this is configured, our user can access these resources potentially using a custom DNS name, using a protocol which they support and not the native S3 or EFS access methods. TransferFamily supports a range of **authentication** methods including built-in identities, directory service within AWS, or a custom identity store.

![[AWS Transfer Family - Endpoint Type.png]]
Within TransferFamily, you create **servers** which you can think of as the front end **access points** to your storage. They present the supporting backend storage, so S3 and EFS, via one or more supported **protocols** (SFTP, FTP-S, FTP and AS2).

3 options to **configure** the **service endpoints**: Public, VPC with internet access, and VPC internal only.

**Public** - the endpoint is running in the AWS public zone. Accessible from the public internet. Nothing to configure.
Shortcomings:
- SFTP only.
- The endpoint has a dynamic IP which can change (managed by AWS), so, you should generally use DNS to access it.
- You can't control who can access it with features like NACLs or SGs.

**VPC-Internet** - can use SFTP and FTP-S endpoints. And also AS2 (niche).
**VPC-Internal** - can use SFTP, FTP-S, and FTP. And also AS2.
- Both - can be **accessed** from **connected** business **networks** (DX, VPNs).
	- Anything which has connectivity into the VPC can access this service as though it was inside the VPC.
- Both - Transfer Family provides static IPs
- Both - secured with NACLs or SGs
The main **difference** is that the **VPC internet** type is allocated with an **elastic IP**. This is static.  Allows it to be **accessible** over the **public** internet in addition to within the VPC and from corporate networks.

- Multi-AZ - Resilient and Scalable
- Provisioned **Server per hour $** + **data transferred $**
	- no upfront costs
- **FTP** and **FTPS** - **Directory Service** or Custom IDP only
- **FTP** - **VPC only** (cannot be public)
- AS2 VPC Internet/internal Only
- If you need to **access S3/EFS**, but with **existing protocols**
	- integrating **with existing workflows**
	- or using **MFTW** (managed file transfer workflow) to create new ones.
