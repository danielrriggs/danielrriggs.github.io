## Object Versioning & MFA Delete
Object Versioning  is controlled at a bucket level.
It starts disabled & can be enabled. **ONCE OBJECT VERSIONING IS ENABLED, YOU CAN NEVER DISABLE IT EVER AGAIN**. There will probably be trick question on this. An enabled bucket can never be disabled again.
![[Object Versioning1.png]]
You can, however, suspend it. Suspended buckets can be re-enabled.

Without versioning enabled on a bucket, each object is identified solely by the object key (its name - unique inside the bucket). If you modify an object, the original version of that object is replaced. 

When versioning on a bucket is disabled, the ID of the objects in that bucket are set to null. That's what versioning being off on a bucket means. All of the objects have an ID of null. When you turn on versioning, S3 allocates an id to that object.
![[Object Versioning2.png]]
S3 always returns the **current version** (the newest version). You can provide the ID to request a specific version.

![[Object Versioning3.png]]
When we delete on a version enabled bucket, S3 adds a special object known as a **delete marker** (a special object) which **hides** all previous versions of that object (S3 doesn't actually delete anything - it's just hidden). You can delete the delete marker, which essentially **undeletes** the object.

Now even with versioning enabled, you **can** actually **fully delete** the object. And that actually really deletes it. To do that, you just need to delete an object and **specify** the particular **version ID** that you want to remove. And if you are deleting a particular version of an object and the version that you're deleting is the most recent version, so the current version, then the next most recent version of that object then becomes the current version.

Important Points to remember on Object Versioning:
- **cannot be switched** off - only suspended
- Space is consumed by ALL versions
- You are billed for ALL versions
- Only way to 0 costs - is to delete the bucket
	- And re-upload all the stuff again to a new bucket without versioning enabled. This is why it's important to remember that you **can't disable** versioning - only suspend it.

(**exam**) **MFA Delete**
- Enabled in **versioning configuration** on a bucket
- MFA is required to change bucket **versioning state**
- MFA is required to **delete versions**
	- To fully delete any versions, you need this MFA token
- Serial number (MFA) + Code passed with API CALLS

**Summary From S3 Versioning Demo**
When you're operating with **objects** it's always creating **new versions** (for objects w/ the same name) or adding **delete markers**. But when you're working with particular **versions** rather than objects, any operations are **permanent**.

## S3 Performance Optimization
- Single data stream to S3
	- // By default, when you upload an object to S3, it's uploaded (via the PUT object API) as a single blob of data in a single stream.
- Stream fails - upload fails
	- // This method has its problems. While it is simple, it means that if a stream fails, the whole upload fails
- Requires full restart
	- // The only recovery from it is a full restart of the entire upload.
- Speed & reliability = limit of 1 stream
	- // If you download stuff online, oftentimes, it uses multiple streams behind the scenes.
	- Single stream data transfer protocols will be bottlenecked by the lowest speed of the two points.
	- Single stream data transfer is slow and unreliable.
- Any upload up to **5GB**
![[Multipart Upload.png]]
Solution: **multi-part upload**.
- Breaks uploads into parts.
	- It improves speed & reliability.
- The minimum size for using multi-part upload is **100 MB**.
	- // Recommendation is to start using this feature as soon as you can. There are almost no situations where a single stream upload is worth it once you're uploading a > 100 MB file. The benefits of multi part upload are too extensive and valuable.
- **10,000** max parts, **5MB** -> **5GB**
	- An upload can be split into a maximum of 10 MB. So you can upload up to 10,000 parts.
	- Each part can range in size between 5 MB and 5 GB.
- The **last part** is left over, so it **can be smaller** than 5 MB if needed.
- Parts can fail, and be restarted
	- // Each individual part can **fail** in isolation and be **restarted** in isolation, rather than needing to restart the whole thing.
- Transfer rate = speeds of all parts
	- // It's faster & more reliable. The transfer rate is the sum of the parts. If you have any **stream limitations** on your **ISP**, or any network inefficiencies, by uploading multiple different streams of data, then you more **effectively** use the **internet bandwidth** between you and the S3 endpoint.

Public **networking paths** may **not** be **performance optimal**. Routers and ISPs are picking this path based on what they think is best, and potentially commercially viable. So using the public internet for data transit is never an optimal way to get data from source. The solution: **S3 Transfer Acceleration**.
Transfer Acceleration uses the network of **AWS edge** locations, which are located in lots of convenient locations globally.

An S3 bucket needs to be enabled for **Transfer Acceleration**.
The default is that it's switched off, and there are some restrictions for enabling it.
The bucket name **cannot contain periods**.
It needs to be **DNS compatible** in its naming.

Once enabled, data being uploaded enters the closest, best performing AWS edge location. This does occur over the public internet, but geographically, it's close, and it transits through fewer normal networks.

The internet is not designed primarily for speed, it's designed for flexibility and resilience. The AWS network is much faster, and with lower consistent latency. The improvements can vary, but the benefits achieved by using transfer acceleration improve the larger the distance between the upload location and the location of the S3 bucket. The worse the initial connection, the better the benefit by using transfer acceleration.

AWS Accelerated Transfer Tool : [http://s3-accelerate-speedtest.s3-accelerate.amazonaws.com/en/accelerate-speed-comparsion.html](http://s3-accelerate-speedtest.s3-accelerate.amazonaws.com/en/accelerate-speed-comparsion.html)

## Key Management Service (KMS)
- Regional & Public Service
- Create, Store and Manage Keys
	- These keys are used to convert plain text to ciphertext and vice versa.
- KMS is capable of handling **Symmetric** and **Asymmetric** Keys
	- You should understand what that means - Where symmetric keys are used, where public asymmetric are used, as well as private asymmetric. Know that KMS is capable of operating with all of these different key architectures.
- KMS is also capable of performing Cryptographic operations (**encrypt**, **decrypt**, & ... )
- **Keys never leave KMS** - Provides FIPS 140-2 (**L2**)
	- (**exam** - **MEMORIZE**) **FIPS 140-2 (L2)**.
		- It's a US security standard. The level 2 part matters. It's often a key point of distinction between using KMS versus using something like Cloud HSM. Some of KMS's features have achieved level 3 compliance. But overall, it's level 2.

*From here on, assume we're talking about symmetric keys unless otherwise indicated*.

The main type of key that KMS manages are KMS keys. You might see these referred to as CMKs or Customer Master Keys. But that naming scheme has been superseded. So they're now called KMS keys.

- KMS Keys
	- Used by KMS within the AWS system.
	- Used within cryptographic operations
		- You can use them, applications can use them, and other AWS services can use them
- KMS Keys are **logical**
	- The data that makes up the key: ID, date, policy, desc, & state
	- Think of them as a container for the actual physical key material.
	- Backed by **physical** key material
- Generated or Imported
- KMS Keys can be used for up to **4KB of data**

![[Keys KMS and KMS.png]]
**Ashley KMS interaction example:**
- Ashley picks region. Creates a KMS key.
	- Key is backed by physical material.
	- Key is stored in KMS in encrypted form.
- Ashley makes **encrypt** call to encrypt some data - specifies the key to use & data to encrypt.
	- KMS decrypts the KMS key & uses that key to encrypt Ashley's plain text data. Returns the data to Ashley.
	- KMS performs the cryptographic operations internally
- Ashley makes decrypt call, supplying ciphertext.
	- KMS doesn't need to be told which KMS key to use for the decrypt operation. It's encoded into the ciphertext.
	- Permissions to decrypt are separate from the permissions to encrypt and are also separate from the generation of keys.
- KMS keys never leave the KMS product, or stored on disk in plain text.
- At each step Ashley needs **permissions** to perform the **operations**.
	- KMS is very **granular** with **permissions**. You need individual permissions for various **operations** including encrypt and decrypt. 
		- You need **permissions** on given KMS **keys** in order to use those keys. 
		- Ashley could have permissions to **generate** keys. And to use keys to **encrypt** and **decrypt** (or just one of those permissions).
		- She might have permissions to manage KMS **creating** keys and **setting** permissions. But **not** permissions to **use** keys to encrypt or decrypt data. This process is called **role separation**.

- KMS key can only operate cryptographically on data which is a maximum of **4 KB** in size. Let's look at how KMS gets around this:
- Data Encryption Keys (**DEKs**) are another type of key which KMS can generate **using** a **KMS key** using the **generate data key** operation.
	- // This generates a **DEK** which can be used to **encrypt** and **decrypt** data which is **more than 4 KB**.
- DEKs are **linked** to the **KMS key** which **created** them, so KMS can tell that a specific DEK was created using a specific KMS key.
	- (Most important thing about KMS and DEKs) - **KMS doesn't store the DEK** in any way.
		- It **provides** it to you or the service using KMS and then it **discards** it. The reason it discards it is that **KMS doesn't** actually **do** the **encryption or decryption** of data using DEKs. **You do** or the **service using** KMS performs those operations. So let's look at how this works.

When a DEK is generated, KMS provides you with **two versions** of that DEK.
- GenerateDataKey - works on **> 4KB**
- **Plaintext** Version
	- First, a plain text version of that key. Something which can be used immediately to perform cryptographic operations.
- **Ciphertext** Version
	- And second, a ciphertext or encrypted version of that same DEK. The DEK is encrypted using the KMS key that generated it. And in future, this encrypted DEK can be given back to KMS for it to be decrypted.
- **Encrypt** data using **plaintext** key
- **Discard**
- **Store encrypted key** with data

Now the architecture is that you would **generate** a DEK **immediately before** you wanted to encrypt something.
You would **encrypt** the data using the **plain text** version of the DEK, and then once finished with that process, **discard** the plain text version of that DEK. That would leave you with the encrypted data. And you would then **store** the **encrypted DEK** along with that **encrypted data**.

KMS doesn't actually do the encryption or decryption on data larger than 4KB using DEKs. You do, or the service using KMS does. KMS doesn't track the usage of DEKs. That's also you or the service using KMS. Now you could use the **same** DEK to encrypt a hundred or a million files. Or you could request **a new** DEK for each of those million files. How you decide to do this is based on your exact requirements. By storing the encrypted DEK on disk with the encrypted data, you always have the correct DEK to use. But both the DEK and the data are encrypted. So administration is easy and security is maintained.

Decription:
You pass the encrypted DEK back to KMS and ask for it to decrypt it using the same KMS key used to generate it. Then you use the decrypted DEK to decrypt the data, then you discard the decrypted DEK.

Services such as S3, when using KMS, generate a DEK for every single object. They encrypt the object and then discard the plain text version.

**Key Concepts**
- KMS Keys are isolated to a **region** & never leave.
	- Any interactions with a KMS key are done using the APIs available from KMS.
	- // Multi-region keys discussed (if required) in a different video
	- Within KMS as a product, keys are either **AWS** owned or **customer** owned
		- We're going to be dealing mainly with customer owned keys
		- **AWS owned** keys are a collection of KMS keys that an AWS service owns and manages for use in multiple AWS accounts. They **operate in the background** and you largely don't need to worry about them.
	- When dealing with **customer owned** keys, there are two types. AWS **managed** and customer **managed**
		- **AWS managed** keys are created automatically by AWS when you use a service such as S3 which integrated with KMS.
		- **Customer managed** keys are created explicitly by the customer to use directly in an application or within an AWS service. Customer managed keys are **more configurable**. For example, you can edit the key policy, which means you could allow cross-account access so that other AWS accounts can use your keys. AWS managed keys can't really be customized in this way.
- KMS Keys support rotation
	- Rotation is where physical backing material, so the data used to actually do cryptographic operations, is changed. With AWS managed keys, this can't be disabled. It's set to rotate approximately once per year. 
	- With customer managed keys, rotation is optional. It's enabled by default and happens approximately once every year.
- **Backing Key** (and **previous** backing keys)
- Aliases (shortcuts to keys - so they can be rotated)
	- But, they're still per region. Neither aliases nor keys are global by default.

Key Policies and Security
![[Key Policies and Security.png]]
- Key Policies (Resource)
	- (verbose) Many services will always trust the account that they're containing. 
		- Meaning if you grant access via an **identity policy**, that access will be allowed unless there's an explicit deny. KMS is different. This account trust is explicitly added on a **key policy** or not.
		- The starting point for KMS security is the **key policy**. This key policy is a type of resource policy, like a bucket policy only on a key. Every KMS key has one. And for customer managed keys, it's a key policy. If you want to change the key policy, you can change it. To reiterate this, the reason the key policy is so important is that unlike other AWS services, **KMS has to explicitly be told that keys trust the AWS account that they're contained within.** You always need this type of key policy in place if you want to be able to grant access to a key using identity policies. But in high security environments, you might want to remove this account trust and insist on any key permissions being added inside the key policy.
		- ^ **Summary**: All KMS keys have a key policy. KMS Keys' **key policy** need to explicitly trust an AWS account in order to use **identity policies**. Otherwise, you'd have explicitly add any permissions on the key policy itself.

## S3 Object Encryption CSE/SSE
You don't define encryption at the bucket level. You define encryption at the **object level**, and each object in a bucket might be using different encryption settings.

There's something called bucket default encryption, but that's different, and I'll cover that elsewhere in the course.

Encryption in transit vs at rest.

**Client** Side Encryption - you encrypt data (you control the encryption **keys, process, and tooling**) before uploading to s3. AWS only receives cyphertext.
**Server**-Side Encryption (SSE) - you ship plain text (via HTTPS, so it's encrypted in transit). AWS performs some of the encryption process - this means you have to trust AWS with parts of your data. AWS has recently made server-side encryption **mandatory**.

Three types of Server Side Encryption for S3 Objects:
They trade-off between these usual factors: trust, overhead, resource consumption, and more.
- Server-Side Encryption with Customer-Provided Keys (**SSE-C**)
- Server-Side Encryption with Amazon S3-Managed Keys (**SSE-S3**) (this is the default)
- Server-Side Encryption with KMS KEYS Stored in AWS Key Management Service (SSE-KMS)
The difference between all of these methods is what parts of the process you trust S3 with and how the encryption process and key management is handled.

There are two components to SSE:
1) The encryption and decryption process.
	1) Encryption: You take plain text, a key, and an algorithm and generate ciphertext.
	2) Decryption: You take ciphertext, a key & algorithm, and generate plain text.
		1) This is symmetrical encryption where the same key is used for both encryption and decryption.
2) The generation and management of the cryptographic keys which are used as part of the encryption and decryption processes.

Remember, SSE is now mandatory on S3 objects.

SSE-C - The customer is responsible for keys. S3 Manages encryption & decryption operations. This might sound like a small thing, but if you're dealing with millions of objects and a high number of transactions, then the CPU capability required to do encryption can really add up. So you're essentially offloading the CPU requirements of this process to AWS.
The customer provides the plain text object and an encryption key (encrypted in transit by HTTPS).
When it arrives at S3, the object is encrypted and a hash of the key is tagged to the object and the key is destroyed. Now this hash is one-way. If a key is provided during decryption, the hash can identify if that specific key was used or not. The object and this one-way hash are stored on disk persistently. To decrypt, you need to provide S3 with the request and the key used to encrypt the object. S3 decrypts the object, discards the key and returns the plain text.

**S3 SSE-C**
![[S3 SSE-C.png]]
**SSE-C Tradeoffs:**
You have to manage your keys.
You also save on the CPU requirements versus client-side encryption (good for smaller devices - they don't need to consume resources for cryptographic operations).
You need to trust that S3 will discard the keys after use.
You choose SSE-C when you absolutely need to manage your own keys, but are happy to allow S3 to perform the encryption and decryption processes.

You would choose client-side encryption when you need to manage the keys and also the encryption and decryption processes.

**SSE-S3**
AWS handles both the encryption processes as well as the key generation and management. You just provide the plain text data. When an object is uploaded to S3 using SSE-S3, it's encrypted by a (generated) key which is **unique for every object.** 
For extra safety, S3 **has a key which it manages** as part of the service.
You can't change any options on this key, nor do you get to pick it. It's handled end-to-end by AWS.  It's not visible anywhere in the user interface. It's rotated internally by S3 out of your visibility and control. This key is used to encrypt the **per-object** key, and then the original key is discarded.
What we're left with is a ciphertext object and a ciphertext key. Both of these are persistently stored on disk.

**S3 SSE-S3**
![[S3 SSE-S3.png]]
Pros:
Less admin overhead.

Cons:
Little control over keys used.

For most situations, SSE-S3 is a good default.
It uses a strong algorithm, AES-256

3 major problems:
Not suitable for strongly **regulated** environments where you need to control keys used.
If you need to control **rotation**, this isn't suitable
If you need **role separation**, this isn't suitable.
	Role Separation: a full S3 administrator, can also decrypt and view data. You can't stop an S3 full administrator from viewing data when using this type of server-side encryption. In certain industry areas, such as financial and medical, you might have requirements like: a business group can view data only, & a sysadmin group can manage infra only.

 **SSE-KMS**
 We're now involving KMS.
 You create a KMS key, or you can use the service default one, but the real power and flexibility comes from creating a customer-managed KMS key. If you choose a customer-managed KMS key, it means this is created by you within KMS, it's managed by you, and it has isolated permissions. The key is fully configurable.
 When S3 wants to encrypt an object using SSE-KMS, it has to liaise with KMS and request a new DEK to be generated using the chosen KMS key. KMS delivers two versions of the same DEK - a plaintext version and an encrypted or ciphertext version. S3 then takes the plaintext object and the plaintext DEK and creates an encrypted or ciphertext object, and then it immediately discards the plaintext key, leaving only the ciphertext version of that key, and both of these are stored on S3 storage. KMS keys can only encrypt objects up to 4 KB in size, so the KMS key is used to generate DEK which don't have those limitations. It's important to understand that KMS doesn't store the DEKs, it only generates them and gives them to S3. But you do have control over the KMS key, the same control as you would with any other customer-managed KMS key.

**S3 SSE-KMS**
![[S3 SSE-KMS.png]]
So in regulated industries this alone is enough reason to consider SSE-KMS because it gives fine-grained control over the KMS key being used, as well as its rotation. You also have logging and auditing on the KMS key itself, and with CloudTrail you'll be able to see any calls made against that key. But probably the best benefit provided by SSE-KMS is the **role separation**.

To decrypt an object encrypted using SSE-KMS, you need access to the KMS key which was originally used. That KMS key is used to decrypt the encrypted copy of the DEK for that object which is stored along with that object. If you don't have access to KMS, you can't decrypt the DEK, so you can't decrypt the object, and so it follows that you can't access the object.

So, for example, a sysadmin (Phil) can have full control over an s3 bucket, but without access to the KMS key which was used to encrypt, he can't read the stored objects (because he can't decrypt the DEK using the KMS key - because he has no permissions on that KMS key).

![[S3 CSE - SSE Summary.png]]

Don't confuse CSE with SSE. Client-side encryption isn't really anything to do with S3. You can use CSE and SSE together. SSE-S3 uses **AES-256**. This might be on the test.

## S3 Bucket Keys
Bucket Keys are a way to help S3 scale and reduce costs when using KMS encryption.

![[S3 without Bucket Keys.png]]
KMS has a **cost**. It means that using SSE-KMS carries an ever-increasing cost, which goes up based on the number of objects that you put into an S3 bucket. And perhaps more of a problem is that there are **throttling issues**. The generate DEK operation can only be run either 5500, 10,000, or 50,000 times per second. And this is shared across regions. Now this exact number depends on which regions you use. But this effectively places a limit on how often a single KMS key, can be used to generate DEKs, which limits the amount of puts that you can do to S3 every second.

With bucket keys, the architecture changes a little. Instead of the KMS key being used to generate each individual DEK, instead, it's used to generate a time-limited bucket key. Conceptually, this is given to the bucket. This is then used for a period of time to generate any DEKs within the bucket for individual object encryption operations. This essentially offloads the work from KMS to S3. It reduces the number of KMS API calls, so reduces the cost and increases scalability.

**S3 with Bucket Keys**
![[S3 with Bucket Keys.png]]
Things to keep in mind when you're using S3 bucket keys:
- CloudTrail KMS events now show the **bucket** ARN, not the object ARN.
	- Because you're offloading a lot of the work from KMS to S3, you're going to see fewer CloudTrail events for KMS in those logs. You're going to see the bucket in the logs, **not the object**.
- Works with **replication** (both same region replication and cross region). The object encryption is maintained
- If replicating plaintext to a bucket using bucket keys the object is encrypted at the destination side (**ETAG changes**)

## S3 Object Storage Classes PARTs 1 - 2
**Storage Classes - S3 Standard**
![[Storage Classes - S3 Standard.png]]
**S3 Standard**
- s3 standard - default - objects are **replicated** across at least 3 AZs.
- s3 standard provides 11 nines of **durability**. 
	- If you store 10 million objects within an S3 bucket, then on average you might lose one object every 10,000 years. The replication uses Content-MD5 checksums together with Cyclic Redundancy Checks (**CRCs**) to detect and resolve any data issues.
(**exam**) When objects which were uploaded to S3 have been stored durably, S3 responds with a **HTTP 1.1 200 OK** status..

With S3 standard, you are billed:
- A GB/month fee for data stored.
- A $ per GB charge for transfer OUT (IN is free)
- A price per 1,000 requests. 
No specific **retrieval fee**, no **minimum duration**, no **minimum size**.

S3 standard has a first byte latency of milliseconds.
Objects can be made publicly available.

This is either using S3 permissions, or if you enable static website hosting and make all of the contents of the bucket available to the public internet.

S3 standard should be used for frequently accessed data which is important and non-replaceable.
It should be your default, and you should only investigate moving to other storage classes when you have a specific reason to do so.

**S3 Storage Classes - S3 Standard-IA**
![[S3 Storage Classes - S3 Standard-IA.png]]
**S3 Standard-IA** (infrequent access)
So standard infrequent access shares most of the architecture and characteristics of S3 standard.

- Data is still **replicated** over at least three AZs in the region.
- The **durability** is the same
- The availability is the same
- The first byte latency is the same
- Objects can still be made publicly available.
- You also have the same basic cost model starting with a **storage cost**, but the storage costs for this class are much cheaper than S3 standard, about **half of the price** of the standard.
- You have a per request charge
- You have a data **transfer out** cost, which is the same as S3 standard, and like other AWS services, data transfer in is free of charge.

Compromises for the lower storage cost:
 - A retrieval fee - $ per GB to retrieve. This is in addition to the transfer fee.

 - There is a minimum duration charge for objects using this class
	 - However **long** you store objects, you're billed for a minimum duration of **30 days**.
	 - However **small** the objects that you store within this class, you're billed a minimum of **128 KB** in size per object

 The costs of storage for this class are much less than S3 standard, that cost efficacy is reduced the more that you access the data. This class is cost effective for data as long as you don't **access** the data **very often**, or you don't need to store it **short term**, or **lots of tiny objects**. Also, don't use it for data which isn't important, or which can be easily replaced, because there's a better, cheaper option for that - S3 One Zone-IA.

**Storage Classes - S3 One Zone-IA**
![[Storage Classes - S3 One Zone-IA.png]]
**S3 One Zone-IA**
Cheaper than S3 standard or S3 infrequent access.
- Retrieval fee
- 30 day billed storage duration
- 128 KB min capacity charge per object.

Big difference: data stored is only in one AZ. It doesn't have the replication across at least 3 AZs. You get cheaper access to storage, but you take on additional risk of data loss if the AZ that the data is stored in fails.

Oddly enough, you do get the same level of durability - 11 9's.

This class should be used for data which is:
- Long lived (because of size & duration minimums)
- Infrequently Accessed (because of retrieval fee)
- Non-critical data
	- Things like replica copies.
	- If you're using same or cross-region replication.
	- Intermediate data which you can afford to lose.

**S3 Storage Classes - S3 Glacier - Instant**
![[S3 Storage Classes - S3 Glacier - Instant.png]]
**S3 Glacier Instant Retrieval**
Like S3 Standard Infrequent Access, except it offers cheaper storage, more expensive retrieval costs, and longer minimums.
Standard IA is designed for when you need data instantly, but not very often, say once a month.
Glacier Instant Retrieval extends this, so data where you still want instant retrieval, but where you might only access it, say once every quarter.
Minimum storage duration charge of 90 days, versus the 30 days of Standard Infrequent Access.
This class is the next step along the path. As the access frequency of objects decrease, you can move them gradually from Standard, then to Standard Infrequent Access, and then to Glacier Instant Retrieval.
The important thing to remember about this specific S3 Glacier class is that you still have instant access to your data.
There's no retrieval process required, you can still use it like S3 Standard and S3 Standard Infrequent Access.

**S3 Storage Classes - S3 Glacier - Flexible**
![[S3 Storage Classes - S3 Glacier - Flexible.png]]
**S3 Glacier Flexible Retrieval** (formerly known as S3 Glacier)
It has the same three availability zone architecture as S3 Standard and S3 Standard Infrequent Access. And at the time of creating this lesson, S3 Glacier Flexible Retrieval has a storage cost which is about one-sixth of the cost of S3 Standard.

- It has the same **durability** characteristics, so 11 nines.
- **Replication** over **3 AZ's** & **Content-MD5 Checksums** & Cyclic Redundancy Checks (**CRCs**) are used to detect and fix any data corruption.

Conceptually, think of the stored objects as cold objects - because they're cold, they aren't immediately available.

You can retrieve them permanently by changing the class back to one of the S3s. But this is a different process.

S3 Glacier Flexible Retrieval Limits:
- 40 KB minimum size
- 90 day minimum duration
- Objects **can't be made public** (either in the bucket or using static website hosting).
	- While you can see these objects within an S3 bucket, they're now just a pointer to that object. To get access to them, you need to perform a **retrieval process**.

**Retrieval jobs** come in three different types:
Data in Glacier Flexible is retrieved to S3 Standard-IA temporarily.
Expedited (1-5 minutes)
Standard (3-5 hours)
bulk (5-12 hours)
Faster = More Expensive

(**exam**) Glacier Flexible Retrieval is for situations where you need to store archival data where frequent or real-time access isn't needed.

**Storage Classes - S3 Glacier Deep Archive**
![[Storage Classes - S3 Glacier Deep Archive.png]]
**S3 Glacier Deep Archive**
S3 Glacier Deep Archive is much cheaper than S3 Glacier Flexible Retrieval, but there are even more restrictions which you need to be able to tolerate.
Conceptually, data in S3 Glacier Flexible is in a chilled state, where data in S3 Glacier Deep Archive is in a frozen state.
S3 Glacier Deep Archive Limits:
- 40 KB minimum size
- 180 day minimum duration

**Retrieval jobs**:
Just like S3 Glacier Flexible Retrieval, Data in S3 Glacier Deep Archive is retrieved to S3 Standard-IA temporarily, but the retrieval jobs take longer.
Standard (12 hours)
Bulk (up to 48 hours)
That's the compromise you agree to - the storage is a lot cheaper in exchange for longer restore times.

Glacier deep archive should be used for data which is archival, which rarely, if ever, needs to be accessed, and where hours or days is tolerable for the retrieval process.
	So it's not really suited to primary system backups because of this restore time. It's more suited for secondary long-term archival backups, or data which comes under legal or regulatory requirements in terms of retention length.

**S3 Intelligent Tiering**
![[S3 Intelligent Tiering.png]]
**S3 Intelligent Tiering**
This storage class is different from the other storage classes.
Contains 5 storage tiers.
- Frequent Access - you can think of like S3 Standard
- Infrequent Access - you can think of like S3 Standard-IA
- Archive Instant Access - same price & performance as S3 Glacier Instant Retrieval
- Archive Access - same price & performance as S3 Glacier Flexible Retrieval
- Deep Archive - same price & performance as S3 Glacier Deep Archive

Unlike the other S3 storage classes, you don't have to worry about the fact that you can store objects in the same storage class. You don't have to worry about moving objects between tiers. With intelligent tiering, the intelligent tiering system does this for you.
When the object is in regular use, it stays in the Frequent Access tier which has the same costs as S3 standard. If the object isn't accessed for 30 days, then it would be moved automatically into the Infrequent Access Tier, where it would be stored at a lower rate.
	At this stage you can also add configuration, so based on a bucket, prefix or object tag, any objects which are accessed less frequently can be moved into the three archive tiers. There's a 90 day minimum for Archive Instant Access.

When objects are moved into Archive Access or Deep Access there's a **retrieval time** to bring them back. So, only use these tiers when your application can tolerate **asynchronous access patterns**. Archive Instant Access requires no application or system changes (data can still be instantly accessed if you need) - it's just another tier for less frequently accessed objects with a lower cost.

If an object stays in Infrequent Access or Archive Instant Access & then they suddenly become super viral, they'll automatically be moved back to Frequent Access with no retrieval charges.

Intelligent Tiering has a **monitoring and automation cost per 1,000 objects**. The frequent access tier costs the same as S3 Standard, the infrequent the same as Standard-IA. Archive Instant, Archive and Deep Archive are comparable to their S3 glacier equivalents.

S3 Intelligent -Tiering should be used for **long-lived data**, with **changing** or **unknown** patterns.

Intelligent tiering is only good if you have data where the pattern changes or you don't know it.

## S3 Lifecycle Configuration
Lifecycle configurations offer a way to automate the **deletion** of objects or object versions or **change the storage class** of objects to optimize costs over time. 

- A Lifecycle configuration is a **set of rules**
	- Rules consist of **actions** which apply based on criteria (do X if Y is true)
	- These rules can apply to a whole bucket or they can apply to **groups of objects** in that bucket. Defined by prefix or tags.
- The actions applied are one of two types
	- **Transition** actions - change the storage class of whichever object or objects are affected.
		- Ex: You could transition objects from S3 standard to say S3-IA after 30 days. You could then maybe transition the object from S3-IA to S3 Glacier Deep Archive after 90 days.
	- **Expiration** actions - can delete whatever object or objects or object versions are affected.
Both of these can work on versions if you have a version enabled bucket, but it can get complicated.
You **can't** move objects between classes based on how **frequently** they're **accessed**. Intelligent Tiering can do that.

![[S3 Lifecycle Configuration - Transitions.png]]

S3 One Zone-IA can transition into S3 Glacier - Flexible Retrieval or S3 Glacier Deep Archive, but NOT into S3 Glacier - Instant Retrieval. This is one of the exceptions to be aware of.

Transition can't happen in an upward direction. Only down.

Restrictions to be aware of:
- Smaller objects can (minimum size) cost more.
	- Be careful when transitioning smaller objects from Standard through to S3-IA, Intelligent tearing, or S3 One Zone-IA. This is because of the minimums on those classes.
- (**exam**) There's a **30 day minimum** period where an object needs to remain on S3 Standard before then moving into S3-IA or S3 One Zone-IA.
	- You can always directly adjust the storage class of an object from the CLI or console UI, but when you're using lifecycle configuration, an object needs to be in S3 standard for 30 days before transitioning to S3-IA or S3 One Zone-IA.
- A **single rule** cannot transition to S3-IA or One Zone-IA and THEN to **glacier classes** .. within 30 days (duration minimums).

## S3 Replication
There are two types of replication supported by S3
- Cross-Region Replication (**CRR**)
	- Allows the replication of objects from a **source** bucket to one or more **destination** buckets in different AWS regions
- Same-Region Replication (**SRR**)
	- The **source** and **destination** buckets are in the same AWS region.

 - A replication configuration (which configures S3 to replicate from this source bucket to a destination bucket) is applied to the source bucket. It specifies:
	 - Destination bucket
	 - IAM Role
		 - The role is configured to allow the S3 service to assume it. That's defined in its trust policy.
		 - The roles' permissions policy gives it the permission to read objects on the source bucket, and permissions to replicate those objects to the destination bucket.

**S3 Replication**
![[S3 Replication.png]]

For the **same** account, that means that the IAM **role** automatically has access to the source and the destination buckets, as long as the role's permission policy grants that access.
If you're configuring replication between **different** AWS accounts, the destination bucket doesn't **trust** the source account or the **role** that's used to replicate the bucket contents - there's also a requirement to add a **bucket policy** (which is a resource policy) on the destination bucket which allows the role in the source account to replicate objects into it.

Replication Configuration Options:
- (default) **All objects** or a **subset**
	- An entire source bucket to a destination bucket - all objects, all prefixes, and all tags.
	- If you want a subset -  you can create a rule that filters objects by prefix, tags or a combination of both.
- Which **Storage Class** (in the destination bucket) the objects will use - default is to maintain.
- **Ownership** - default is the source account
	- However, if the buckets are in different accounts, then by default, the objects inside the destination bucket will be owned by the source bucket account. And that could mean you end up in the situation where the destination account can't read those objects because they're owned by a different AWS account. With this option, you can override that and you can set it so that anything created in the destination bucket is owned by the destination account.
- Replication Time Control (**RTC**)
	- Has additional cost
	- Without this, it's a best efforts process, but RTC adds this SLA for a guaranteed level of predictability. It even adds additional monitoring so you can see which objects are queued for replication.
		- This is something that you would tend to only use if you've got a really strict set of requirements from your business to make sure that the destination bucket and source buckets are in sync as closely as possible. If you don't require this, if this is just performing backups, or it's just for a personal project, or if the source and destination buckets aren't required to always be in sync within this 15-minute window, then it's probably not worth adding this feature.
			- (**exam**) If you do see any questions that mention **15 minutes for replication**, then you know that you need this **Replication Time Control**.

(**exam**) Exam considerations:
- By Default* **Not retroactive** & **Versioning** needs to be **ON**.
	- Objects will be replicated only after you turn on replication. If you enable replication on a bucket which already has objects, those preexisting objects will not be replicated.
	- In order to enable replication on a bucket, both the source and destination bucket need to have **versioning** enabled. A bucket cannot be enabled for replication without versioning.
- You can use S3 **batch replication** to replicate **preexisting** objects
	- But this is something that you need to specifically configure. If you don't, just remember by default, replication is not retroactive.
- Be default, replication is **one-way** - Source to Destination
	- If you add objects manually in the destination, they will not be replicated back to the source
	- More recently, AWS added bi-directional replication, but this is something you need to configure.
- What gets replicated? Unencrypted, SSE-S3 & SSE-KMS (**with extra config**), SSE-C
- Source bucket owner needs permissions to objects
- NO **system events**, **Glacier** or **Glacier Deep Archive** storage classes
- NO DELETES (But this can be added -DeleteMarkerRepIication)
	- By default, for versioned buckets, delete markers aren't replicated. You can enable it, though.

Why use replication?
- SRR (same region replication) - Log Aggregation
- SRR - PROD and TEST sync
- SRR - Resilience with strict sovereignty
- CRR (cross region replication) - Global Resilience Improvements

## S3 PreSigned URLs
Pre-signed URLs are a way that you can give another person or application access to an object inside an S3 bucket using your credentials in a safe and secure way.

For an S3 bucket which doesn't have any public access configured (it's still in a default private configuration) an IAM user such as IAM admin would have to authenticate to AWS and be authorized to access the resource. IAM admin would send credentials along with the access request, AWS would validate them at the time that the request is made, and only then would they be able to access the resource.

![[Presigned URL1.png]]

Now if giving the mystery user access to S3 is an essential requirement for the business, then there are three common solutions at this point, and none of them are ideal.
1) give the mystery user an AWS identity
	1) If the user only needs short-term access to the bucket and objects, the effort of supplying an identity seems excessive
2) give the mystery user some AWS credentials to use
3) make the bucket or the object public

![[Presigned URL2.png]]

IAM Admin is an AWS identity with some access rights granted via a permissions policy. So IAM Admin can make a request to S3 to generate, and it will create a pre-signed URL. She would need to provide her security credentials, specify a bucket name, an object key, and an expiry date and time, as well as indicate how the object would be accessed. And S3 will create a pre-signed URL and return it. This URL will have encoded inside it the details that IAM Admin provided. So which bucket it's for, which object it's for. It will be encoded with the fact that the IAM Admin user generated it. It will be configured to expire at a certain date & time as requested by the IAM Admin user. The URL could then be passed to our mystery user, and he or she could use it to access the specific object in the specific S3 bucket, up until the point at which it expires. When the pre-signed URL is used, the holder of that URL is actually interacting with S3 as the person who generated it. So for that specific object, in that specific bucket, until the timer expires, our masked man is actually IAM Admin. Pre-signed URLs can be used for both downloads from S3, so GET operations, or uploads to S3, known as PUT operations.

Example: serve large video file from s3 bucket in an app. Application service accounts are a common scenario where **IAM users** are used (for procuring pre-signed URLs).

![[Presigned URL3.png]]

Pre-signed URLs are often used when you offload media into S3, or as part of serverless architectures, where access to a private S3 bucket needs to be controlled, and you don't want to run thick application servers to broker that access.

Exam Power Ups:
- You can create a URL for an object you have **no access to**
	- The only requirement for generating a pre-signed URL is that you specify a particular object and an expiry date and time.
		- Which also, because it's linked to you, will have no access to that object - So there aren't many use cases where this is applicable, but you do need to be aware that it is possible to generate a pre-signed URL when you don't have any access.
- When using the URL, the permissions match the **identity which generated it**
	- Access denied could mean the generating ID **never had access** or **doesn't now**.
- **Don't generate with a role**. URL stops working when temporary credentials expire.
	- Remember, IAM Roles give you temporary credentials. It's possible to generate a presigned url with an IAM Role, but don't. A pre-signed URL can have a much longer validity period than those temporary credentials. Generally you would create an IAM user for the application, and this IAM user would have fairly static permissions.

## S3 Access Logs
![[S3 Access Logs.png]]

We want to understand what types of accesses are occurring to this source bucket. The target bucket is where we want the logging to go.
To use the feature, we have to enable logging on the source bucket (via the console UI or using a put bucket logging operation using the CLI or the API).
Logging is managed by a system known as the S3 log delivery group, which reads the logging configuration which you set on the source bucket.
This is a best efforts process - it can take a few hours.
You also need to give the log delivery group access to the target bucket. And this is done using an ACL on the target bucket.
You add the S3 log delivery group, giving it write access. This is how it can deliver the logs through to the target bucket.

Logs are delivered as log files. Each file consists of a number of log records. These are newline delimited. Each record consists of attributes such as date and time, the requester, the operation, status codes, error codes, and much more. Attributes are space delimited.

A single target bucket can be used for many source buckets. You can separate these easily using prefixes in the target bucket. This is configured within the logging configuration that's set on the source bucket.

Access logging provides detailed information about the requests which are made to a source bucket. Common uses: security functions and any access audits; understand the access patterns of your customer base; understand any charges on your s3 bill.

if you do use this feature then you need to personally manage the lifecycle or deletion of any of the log files - it isn't built into the product. You need to manage either the movement of these log files to different storage classes or deleting them after a certain amount of time.

## S3 Object Lock
S3 object lock is a group of related features.

- (5/25/2025 Update) Object Lock can now be enabled on existing buckets.
	- Once enabled, **versioning** is also enabled on that bucket.
		- Versioning (required for Object Lock) cannot be suspended or disabled once Object Lock is enabled on the bucket.
	- Once enabled, Object Lock cannot be disabled. You can still manage and configure object lock settings (retention periods, legal holds).
- Write-Once-Read-Many (**WORM**) - **No Delete**, **No Overwrite**
	- Object versions, once created, can't be overwritten or deleted
- Requires versioning - **individual object versions** are locked
- Retention is managed 2 ways:
	- Retention Periods
	- Legal Hold
	- An object can have **both**, **either**, or **none** of these.
		- // Think of S3 Object Lock Retention and Legal Hold as 2 different things.
- Can be defined on individual **object** versions, or you can define **bucket** defaults for all of the object lock features.
	- // Just like with bucket default encryption settings
- A Bucket can have **default Object Lock Settings**

**S3 Object Lock Retention Period** (style of object locking)
- When you create the object lock, you specify a retention period of **Days** & **Years**
- 2 Modes of Retention Period lock - **this is very important** you get this right. If you get it wrong, it will cause a world of pain.
	- **Compliance** mode - An object version **can't** be **adjusted**, **deleted**, **overwritten**.
		- An object version cannot be deleted or overwritten for the duration of the retention period AND it means the retention period itself cannot be reduced or adjusted during the retention period - **even by the account root user**. This is serious business. It's the most strict form of object lock. Don't set this unless you really want that object version to stay around in its current form until the retention period expires. You'd use this, as the name suggests, for compliance reasons. Ex: medical / financial data.
	- **Governance** mode - special **permissions** can be granted **allowing lock settings to be adjusted**.
		- **s3:BypassGovernanceRetention** + **x-amz-bypass-governance-retention:true** (console default) to override the governance mode of retention.
		- Governance mode is useful for:
			- preventing accidental deletion
			- you have process reasons or governance reasons to keep object versions
			- you might use it as a test of settings before picking the compliance mode

**S3 Object Legal Hold**
- Set an object version **ON** or **OFF**
	- You don't set a retention period
- **NO Deletes** or **Changes** until removed
- **s3:PutObjectLegalHoId** is required to add or remove
- Prevent accidental deletion of critical object versions
