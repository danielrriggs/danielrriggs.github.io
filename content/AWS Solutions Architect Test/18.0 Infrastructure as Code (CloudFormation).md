## CloudFormation Physical & Logical Resources
Automates infrastructure. IaaC.

- CloudFormation **Template** - YAML or JSON
	- contains **logical resources** - the "WHAT"
- Templates are used to create **Stacks**
	- 1 stack, 100 stacks, 20.. stacks in each region
	- stacks create **physical resources** from the **logical**
		- For every logical resource in a template when a stack is created a physical resource is also created
- If a stacks **template** is changed - **physical** resources are changed
- If a stack is **deleted**, normally, the **physical** resources are deleted

![[Physical and Logical Resources.png]]
CFN Template is used to create 1 or many stacks. The stack will react to template updates & add or delete physical resources as required. CFN keeps the physical and logical resources in sync.

CFN can also be used as part of change management. Store templates in code repos, add changes, get approvals. Or, they can be used to spin up one-off deployments.

## CloudFormation Intrinsic Functions
Intrinsic functions allow you to gain access to data at runtime. Makes it easier to design portable templates.

- **Ref** & Fn::**GetAtt** 
	- Both allow you to reference a value from one logical resource or parameter
	- Ex: VPC references a subnet
- Fn::**Join** & Fn::**Split**
	- Ex: You create an EC2 instance which is given a public IPv4 DNS name; you can use the Join Fn to create a webUrl which anyone can use to access that resource.
- FN::**GetAZs** & FN::**Select**
	- GetAZs - gets a list of AZs for a region
	- Select - allows you to select one element from a list
- Conditions (Fn::**IF**, **And**, **Equals**, **Not** & **OR**)
	- Ex: If someParam=prod, deploy big instances. If someParam=dev, deploy small instances.
- Fn::**Base64** & Fn::**Sub**
	- base64 function accepts non-encoded text, and it outputs base64 encoded
	- Ex: if providing userData to EC2 with some user data for automated builds, you need to provide this using base64.
	- Sub - substitute things within text based on runtime information
		- Ex: you might be passing build information into EC2, and you want to provide a value from the template parameters
- Fn::**Cidr**
- Later ... Fn::lmportValue, Fn::FindlnMap, Fn::Transform

![[Ref and Fn-GetAtt.png]]
Every parameter and logical resource within CloudFormation has a main value which it returns. For example, the main value returned by an EC2 instance is its physical resource ID. The main value for a parameter is its value. The ref function can be used to reference this main value of a parameter or a logical resource. ! Ref LatestAmiId is a parameter.

When an EC2 instance is created, once it reaches a create complete state, it makes available a range of data. The primary value (its physical ID), can be accessed using the ref intrinsic function. The **getAtt** function can access **secondary** values. With this function, you provide the logical resource name and the name of an attribute. GetAtt is used in almost all CloudFormation templates to access **logical** resource attributes, **template parameters**, pseudo parameters, and much more.

![[Fn-GetAZs and Fn-Select.png]]
There is a little nuance here - !GetAZs "us-east-I" or (current region) returns a list of all AZs within that region where the default VPC has subnets in that AZ. If you have a default VPC where you've deleted subnets, then the list returned will not have all available AZs. If you don't have a default VPC, it will return a list of all AZs for that region.

## CloudFormation DependsOn
Establish formal dependencies between resources within CloudFormation templates.

- CloudFormation tries to be efficient
- .. does things in parallel (create, update, & delete)
- .. tries to determine a **dependency order** (VPC => SUBNET => EC2)
	- in most cases the built-in dependency mapping will work and you won't encounter any issues
- .. **references** or **functions** create these
- **DependsOn** lets you **explicitly** define these
- .. lf Resources **B** and **C** depend on **A**
- .. both wait for **A** to **complete** before starting

![[CloudFormation DependsOn.png]]
There's no explicit dependency between a VPC and an IGW. But, what if we had an IGW Attachment? It depends on both the VPC and the IGW. It's an **implicit dependency** (assumed by CFN - because the IGW Attachment references the two - we can't have a value for a reference which doesn't yet exist). This implicit dependency feature works in most cases. But, there are some exceptions:
(**exam**) If we wanted to create an **Elastic IP**. If you're creating an **EIP** and you want to associate it with a **VPC** (a **subnet**) that you're creating in the same template then it actually **requires** an attached **IGW**. Otherwise you'll encounter issues. You might find that when creating stacks using templates sometimes it works or sometimes it doesn't. You might find when deleting stacks sometimes it works or sometimes it doesn't. Without formally declaring this relationship, whether you can create an EIP depends on the random order that CloudFormation creates these resources.

To explicitly define a dependency, you can use DependsOn.

## CloudFormation Wait Conditions & cfn-signal
- **Logical** Resources in the **template**
- ..Used to create a **Stack**
- .. creates **physical** resources in AWS
- Logical Resource CREATE_COMPLETE = All OK? 
	- We don't actually know. CFN has no further access to any other information beyond the fact that EC2 is telling it that that resource has completed its provisioning process.
Creation policies, wait conditions, and CFN signal provide a few ways that we can get around this default limitation and allow systems to provide more detailed signals on completion or not to CloudFormation.

Enhanced signaling is done is via the CFN signal command, which is included in the AWS CFN bootstrap package

- Configure CloudFormation to **hold** (more on this soon..)
- Wait for 'X' number of **success** signals
- Wait for **Timeout H:M:S** for those signals (**12 hour max**)
- If **success signals** received .. **CREATE_COMPLETE**
- If **failure** signal received .. **creation fails**
- If **timeout** is reached (without the required # of success signals) .. **creation fails**
	- CFN views this as an implicit failure. The resource being created fails, then the stack fails the entire process.
- .. **CreationPolicy** or  **WaitCondition**

![[CloudFormation - CreationPolicy.png]]
Because I'm using a **creation policy** here, a few things happen which are different to how CloudFormation normally functions. First, the creation policy here **adds** a **signal requirement** and **timeout** to the **stack**. In this case, the stack needs three signals, and it has a timeout of 15 minutes to receive them. So the EC2 instances are provisioned, but because of the **creation policy**, the **ASG doesn't move** into a **create complete** state as normal. It waits. It **can't complete** until the **creation policy** directive is **fulfilled**. The user data for the EC2 instances contains some bootstrapping, and then the CFN signal statement at the bottom. So once the **bootstrapping** process **completes**, (let's say that it's installing the CataGram application), the **CFN** signal tool **signals** the resource (the ASG) that it's completed the build. This causes each instance to signal once. The ASG requires 3 of these signals in 15 minutes.

Creation policies are generally used for EC2 instances or for ASGs.



**Wait conditions** operate in a similar way to creation policies. A wait condition is a **specific logical resource**, not something defined in an existing resource.  A wait condition can depend on other resources, and other resources can also depend on a wait condition. So, it can be used as a more general **progress gate** within a template, a point which can't be passed until those signals are received. A wait condition will not **proceed** to create complete until it gets its **signals** or the **timeout** configured on that wait condition expires. A wait condition relies on a **wait handle** - another logical resource whose sole job is to generate a pre-signed URL which can be used to send signals to. It's pre-signed so that whatever using it doesn't need to use any AWS credentials.

Let's say that we have an EC2 instance or external server responsible for performing a **process** - maybe some final detailed configuration, or maybe they assign licensing. Something which has to happen **after** a part of the template but **before** the other part. These generate a **JSON document** which contains some **information** about the **event** from the external system. What's awesome about this is that not only does this signal allow resource creation to be paused and then continued when this event has occurred, but the data which is passed back can also be **accessed elsewhere** in the template. We can use the **getAt** function to query for the **data attribute** of the **wait condition** and get access to the details on the signal. This allows a small amount of **data exchange** and processing between whatever is signaling and the CloudFormation stack

Wait conditions in many ways are just like creation policies - not allowing progress, until signaling is received; only, wait conditions are a separate resource and can use some more advanced data flow features. AWS recommend creation policies for most situations because they're simpler to manage, but as you create more complex templates, you might well have need to use wait conditions as well.

## CloudFormation Nested Stacks
Resources in a single stack **share a lifecycle**.

![[CFN Stack.png]]
 A CloudFormation stack is isolated, meaning it contains all of the AWS resources that the project needs. Designing a monolithic CFN stack is fine as long as you don't hit any limits:
 - There's a limit of 500 resources per stack.
Another issue with isolated stacks is that you can't easily **reuse** resources.

At the professional level (or for complex projects), you'll tend to use multi-stack architectures. Two ways to architect a multi-stack project - **Nested stacks** and **cross-stack references**.


**Nested Stacks**
![[CFN Nested Stacks.png]]

You start with one stack, which is referred to as the **root stack**. In this example, this stack is both the **root** and the **parent** stack. A root stack is the stack which gets created **first** - either **manually** through the **console UI** or the **command line**, or using some form of **automation**. The root stack is the only component of a nested stack which gets created manually by an entity (either a human or a software process).\

A **parent stack** is the parent of any stacks which it immediately creates. Complex nested stack structures can have multiple levels. A **root stack** can create **several nested stacks**. Each of those can in turn create additional nested stacks. A **parent stack** is just a way that we can refer to anything which **has its own nested stacks**. So in this case, this stack is going to be a root stack and a parent stack.

A root stack can have parameters just like a normal stack. And also have outputs also just like a normal stack. That's because a root stack is just a normal stack. There's nothing special about nested stacks. Inside all stacks you have logical resources (ex: S3 buckets, VPC, DynamoDb table). You have to give the nested stack a **URL** to the **CFN template** which will be used to create it.

In this case, the yaml file that's used for VPCSTACK has three parameters - param one, two, and three - when we're creating it as a nested stack, we need to supply values for those parameters (exception: if it has default values). In this case, the **root stack** has **one logical resource**, the **VPCSTACK**. This creates a **nested stack resource**. We pass in the 3 parameter values. When the VPCSTACK nested stack finishes creating, then the logical VPCSTACK resource within the root stack moves into a create complete status. Any **outputs** of that nested stack are **returned** to the root stack. These can be **referenced** using the **logical resource name** of the nested stack (**VPCSTACK**.Outputs.xxx). You can only reference **outputs** when using nested stacks. You **can**'t directly reference **logical resources** created in any of the nested stacks.

We might also have **other nested stacks** contained within the root stack. Because these are also **logical resources**, they too would be created; but, they might have **dependencies** - Either ones which **CFN calculates** or one where we use the depends on directive to **explicitly** inform CFN that there is a dependency between different stacks. Ex: ADSTACK **DependsOn** VPCSTACK. (Whether it's a self-managed active directory or one provided by directory service, it will need to run from a VPC). The root stack can take the **outputs** from one nested stack and give them as **parameters** to another. Ex: VPC ID or the subnet IDs of the resources created inside the VPCSTACK.

As each of the **nested stacks** finish provisioning, the resource in the root stack will be marked as create **complete**. And once all of the logical resources for the nested stacks are complete, then the **root stack** itself will be marked as create **complete**.

By breaking up solutions into **modular templates**, it means that these templates can be **reused**. In this example, we have VPC stack, which is probably something that can be used again and again for different deployments. If you **upload** the template somewhere, then many nested stack architectures can use that template. And crucially, this is reusing the **code** (**the template**) for a stack. You can reuse each of these templates to form part of a single solution, which is lifecycle linked.

Nested stacks are generally used when all of the infrastructure that you're creating is forming part of the same solution - when it's lifecycle linked. Ex: App needs AD, which needs VPC. It's likely that these will all be created together, operate together, and maybe someday be deleted together.

Nested Stack Benefits:
- Overcome the **500 Resource Limit** of one stack
- **Modular** templates ... **code reuse**
- Make the **installation process easier** ...
- .. nested stacks created by the root stack
- **Use only when everything is lifecycle linked**
	- If you're anticipating needing one part long-term but not others, then nested stacks are the wrong choice.
	- If you imagine needing to use the same actual VPC across multiple implementations, then **cross-stack references** are probably better suited
	- If you want to make frequent changes to one part of an application and not others, then it's probably better to have individual non-nested stacks, and utilize cross-stack references

## CloudFormation Cross-Stack References
The **limitation** of **nested stacks** was that if you reused a particular template, say the VPC template, you would only **reuse** the **code**, not the actual VPC that it creates. In some cases we want to consume a shared component, for example the VPC, for lots of different implementations. The issue is that stacks are, by design, self-contained and isolated. There's a logical boundary around each stack. Things in one stack can't be by default referenced in another.

![[CF Cross-Stack References.png]]
In this example, if we were deploying EC2 instances into AppStack 1 and AppStack 2, they couldn't natively reference the subnets created by the shared VPC stack. This is where cross-stack references come in handy - if you want one stack to be able to reference the resources created in another, in order to reuse those actual resources.

- Outputs are normally **not visible** from other stacks
	- // Can't use ref to reference anything from one stack in another (exception: root stacks can reference outputs of nested stacks. But this links their lifecycle).
- **Nested stacks** can reference them ...
Imagine you work for a software development company. Each time a new **version** of your application is **committed** to a GitHub **repository**, you want to use CloudFormation to create a VPC, **run** the application in the VPC, and operate a set of **tests** before **tearing** it all down. Now, you could create an isolated VPC each time using a nested stack architecture. But if you wanted to save costs, you could use the **same** shared **VPC**, the same set of **NAT GWs**, and the same set of **subnets**. To do this, outputs of a template can be exported.
- (exam) Outputs can be **exported** .. **making them visible from other stacks**
- (exam) Exports must have a **unique name** in the **region**
Ex of things you might export for a shared VPC design: VPC ID, subnet IDs, CIDR ranges, SG Ids - anything which you could expect to use elsewhere.
- (exam) **Fn::ImportVaIue** can be used instead of **Ref**

![[CF Cross-Stack References2.png]]
Make sure that anything you want to use is added as an **output**. For example, the VPC ID. This means that this output will be visible from the **command line** or the **console UI**, but to **use this value** in any other stack in this region of the account, we need to use the **export directive** to export that value to a list within one region of your account. The **exports list** operates **per region**, **per account**. Name must be unique. Once a value is in the exports list, it can be referenced in other stacks using the **import value function**. This only works in the same region as a stack is being applied in. Cross region or cross account isn't supported.

The process:
1) create an **output** in one stack
2) **export** the value for that output into the exports list
3) use the import value function to **import** that exported value into each stack that you want to use it in

Situations where you would choose to use cross stack references:
- When you're implementing **service-oriented** architectures.
	- when you need to provide services from one stack to another
- You have a churn of short-lived applications which all consume from a shared services VPC
	- If you have things which have different values. Life cycles, long versus short, then you want to separate them into different stacks and use cross stack references
- If you want to reuse a stack

For the **exam**, be clear that a **template** is **not a stack** or vice versa. A template is used to create **one or more stacks**. Each stack is unique.

If you want to **reuse a template**, then you can choose to use **nested stacks** which allow you to use the same template that you've created once in many distinct architectures. A VPC template, for example, might be used as part of an email system, a financial system, or for the implementation of hundreds of different isolated client environments. Each time you reuse that template, it creates its own distinct infrastructure.

If you want to **reuse** an actual stack (the **resources** inside a stack), as with this example of a shared VPC, then you should use **cross stack references**.
