## DynamoDB - Architecture
- NoSQL **Public** Database-as-a-Service (**DBaaS**) - **Key**/**VaIue** & **Document** 
	- wide-column, key-value database
- **No** **self-managed servers** or infrastructure
	- not like RDS or Aurora or Aurora Serverless, which are database server-as-a-service products. With DynamoDB you get the database itself delivered as a service.
- **Manual** / **Automatic** provisioned performance IN/OUT or **On-Demand**
	- range of scaling options
	- you can configure a table with **provisioned** capacity or **on-demand** **capacity**
		- capacity is an odd term - in DynamoDB, capacity means **speed** (performance)
	- on-demand capacity model - You just pay for the operations against the DynamoDB table (cost per operation)
	- provisioned capacity - you explicitly set the capacity values on a per-table basis
	- WCU = Write Capacity Unit
		- 1 WCU means you can write 1KB per second on that table
	- RCU = Read Capacity Unit
		- 1 WCU means you can read 4KB per second on that table
		- // Eventually consistent reads are half price
- Highly Resilient ... across **AZs** and optionally **global**
- **Really fast** .. **single-digit milliseconds** (SSD based)
- Backups, point-in-time recovery, encryption at rest
- Event-Driven integration ... do things when data changes
![[DynamoDB Tables.png]]
**Tables** are actually the base entity inside the DynamoDB product. DynamoDB shouldn't really be described as a database-as-a-service product. It's more like a database table-as-a-service product. A table within DynamoDB is a grouping of items which all **share** the same **primary key**. Items within a table are how you manage your data within that table. Think of an item like a row in a traditional database product. A table can have an **infinite** number of items within it.

When you create a table within DynamoDB, you have to pick its **primary key**. It can either be a **simple primary key**, which is just the **partition key**, known as a PK, or it can be a **composite primary** key, which is a combination of the **partition key and the sort key**, which is known as the SK. Items can have other bits of data aside from the primary key called **attributes**. But every item can be different as long as it has the same primary key. An item itself can be a maximum of 400 kilobytes in size.

![[DynamoDB On-Demand Backups.png]]
**Backups** - similar to manual RDS snapshots. they're a full backup of the table **retained** until you **manually remove** that backup. Can restore data and configuration - either to the same region or cross-region (so, they can be used for migrations). You can use a backup to restore a table with or without **indexes**, and you also have the ability to adjust **encryption** settings as part of the restore. The **key thing** to remember is that **you're responsible** for **performing** the backup and **removing** the older backups as needed when they're no longer required.

![[Point-in-time Recovery (PITR).png]]
**point-in-time recovery** - disabled by default. Need to enable on a table-by-table basis. In an entire 35 day window, you can restore to a new table with a one-second granularity.

## DynamoDB - Operations, Consistency and Performance-PART1
Pick between two different capacity modes when you create a table (with some restriction, you can switch between modes, even after data's added) - **on-demand** and **provisioned**.

- **On-Demand** - unknown, unpredictable, low admin
- On-Demand - price **per million** R or W units.
	- Can be as much as 5x more than provisioned.
- **Provisioned** ... **RCU** and **WCU** set on a per table basis
- (exam) Every operation consumes at least 1 **RCU**/**WCU**(\*)
- (exam) 1 RCU is **1 x 4KB** read operation per second (\*)
	- Reads always rounds up to the next whole RCU value.
	- It can be more.
	- If you perform an operation and it only uses one kilobyte to read an item, you still consume one RCU.
	- // Eventually consistent reads are half price
- 1 WCU is **1 x 1KB** write operation per second
- Every table has a RCIJ and WCU burst pool (**300 seconds**)
	- // try to dip into the burst pool as infrequently as possible. Because other table modification tasks can use this pool as well. Relying on it too much is pretty dangerous. If you ever deplete the pool and have insufficient capacity set on a table, then you will receive a provisioned throughput exceeded exception error. And you'll be throttled. The solution is to wait and retry or increase the capacity settings.

**Query**

Operations you can perform on a DynamoDB table: **query** and **scan**.
There is an architectural benefit with the platform to minimizing the size of an item as much as possible. Because if you have to perform queries which operate on single items, as a minimum, you are going to consume the capacity that that whole item uses.

**Scan**

## DynamoDB - Operations, Consistency and Performance-PART2
Consistency **modes** for **read** operations: **eventually** consistent, or **strongly** (immediately) consistent.
**DynamoDB Consistency Model**
![[DynamoDB Consistency Model.png]]
With DynamoDB, every piece of data is replicated multiple times in separate availability zones, and each one of these points is called a **storage node**. One of them is elected as the **leader**. This is a dynamic process, so if the leader ever fails, the election will happen again, and a new one will be created. Writes are always directed at the leader node. The leader node, the item will be manipulated; at this point, the leader node is known as **consistent**. It begins **replicating**.

Eventually consistent reads don't guarantee the latest data. Eventually consistent reads are half price. Strongly consistent reads always use the leader node. It's less scalable & more expensive.
![[WCU Calculation.png]]
**How to calculate the WCU / RCU setting you should set per table**
You need to understand the **average size** of an item that's being written to DynamoDB and how many **items per second** will be written.
// Some cases **exam** questions might try to trick you and say that 60 items will be written per minute. You need to calculate how many per second.
**WCU** per item = avg **Item Size / Size of a WCU (1 KB)**, then round up to highest whole number. **\* # per second** = **WCU required setting for the table**.
![[RCU Calculation.png]]
RCU per item = avg **Item Size / Size of a RCU (4 KB)**, round up; **\* # per second** = **Strongly Consistent RCU Required** (50% of Strongly Consistent RCU for Eventually Consistent RCU Required).

## DynamoDB - Streams & Lambda Triggers
**Stream Concepts**
- Time ordered list of ITEM CHANGES in a table
	- // every time a change occurs to an item in a table, a change is recorded chronologically within a DynamoDB stream
- **24-Hour** rolling window
	- // Behind the scenes, uses Kinesis streams.
- Enabled on a **per table** basis
- Records **INSERTS**, **UPDATES**, and **DELETES**
- Different **view types** influence what is in the stream
**DynamoDB Streams**
![[DynamoDB Streams.png]]
Scenario: Suppose the 4th attribute (dark orange) is removed.
There are 4 view types a stream can be configured with.
Given this scenario, these view types have the following differences:
- KEYS_ONLY - the stream will only record the **partition key**, and optionally, any applicable **sort key** value for the item which has changed.
	- It would be up to whatever is interrogating the stream to determine exactly what has changed, and that would probably require a database read.
	- So in this example, where we've removed the fourth attribute, the one in dark orange, the only information that we get using keys only is that the partition key is blue, and the sort key is green. We don't see exactly how this item has been manipulated.
- NEW_IMAGE - stores the **entire item** with the **state** as it was **after** the **change**.
	- Ex use: a business process which operated on the new updated data
	- If you wanted to know exactly what had changed, then you couldn't determine that using this view type.
- OLD_IMAGE - you have a copy of the data as it was before the change.
	- If you wanted to know what changed, then one option would be to use the old image type; by comparing the old image item inside the stream to the item in the database table, you could **calculate** exactly what had **changed**.
- NEW_AND_OLD_IMAGES - stores both the pre-change and the post-change.
	- Another option to be able to determine exactly what has changed. You can determine the difference without having to consult the database table itself.
	- If you have a business process which needs complete visibility of the change, and have this visibility independent of the actual table.

The real power of database streams: They're the foundation for an architecture called database triggers. Event driven architecture. Respond to changes in a table. Dbs have supported these for years, but with DynamoDB, they can be implemented in a serverless way.

**Trigger Concepts**
- ITEM **changes** generate an **event**
- That event **contains the data** which changed
	- // The data depends on the view type
- An **action is taken** using that data
	- // When an event is generated
- AWS = **Streams + Lambda**
	- // The way action is implemented within AWS
- **Reporting** & **Analytics**
	- // ex: item stock
- **Aggregation**, **Messaging**, **Notifications**
	- // ex: aggregation in app which records votes
	- // ex: messaging app w/ group chat. DynamoDb stores chat items, streams and triggers send push notifications to members (rather than having to poll databases, which consumes compute resources even if nothing happens).

For SAA **exam**, you just need to know that you use streams and Lambda together to implement a trigger architecture for DynamoDB.
**DynamoDB Triggers**
![[DynamoDB Triggers.png]]
Enable streams on a table, configure a Lambda function, & you've got a really cost effective and powerful serverless implementation of a trigger architecture.

## DynamoDB - Global Tables
- Global tables provides **multi-master cross-region** replication
	- // All tables are the same (no master / replica). R/W replication between all tables.
- Tables are created in multiple regions and added to the same global table (becoming replica tables)
	- // You create tables in multiple AWS regions, and then on one of the tables, it doesn't matter which, you configure the links between all of the tables. 
	- // Tables become table replicas of a global table. Think of a global table as an entity by itself with supporting DynamoDB tables in different AWS regions, configured for multi-master replication.
- **Last writer wins** (most recent) is used for conflict resolution
- **Reads** and **Writes** can occur to any region
- Generally **sub-second** replication between regions
- Strongly consistent reads **ONLY** in the same region as writes
	- For anything else, always eventual consistency; the replication is asynchronous.
![[DynamoDB Global Tables.png]]
To use global tables, you first need to select the AWS **regions**, which will be part of that global table. In each of those regions, you'd create a **DynamoDB** table. Select one, doesn't matter which; from that table, **add** all of the tables into the **global table configuration**. This would establish the **multi-master replication** between all three tables.

For the **exam**, you don't need to know implementation details, just architecture. Know the stuff in the picture above.

It's simple & highly effective. If your application can tolerate last writer wins conflict resolution & eventual consistency, then you can use the feature to support a global data layer for your application.

## DynamoDB - Accelerator (DAX)
DynamoDB Accelerator. In-memory cache for DynamoDB which substantially improves performance. Unlike other caches, it's directly integrated with the product itself, so it's really easy for an architect to implement without lots of additional planning work.
![[Traditional Caches vs DAX.png]]
Top: Traditional cache (Cache Miss > Load Data > Cache Hit).
The **problem** with this architecture is the **lack** of **integration** between the cache and the database.
Bottom: DAX. There's extra software involved - the DAX SDK. Now, DAX and DynamoDB, are one and the same from the application's perspective.
Advantage: It's one set of API calls using one Software Development Kit. DAX is designed for DyanmoDB & tightly integrated with it. Makes it easy to implement caching into your app.

![[DAX Architecture.png]]
DAX operates from within a VPC, and it's designed to be deployed into multiple availability zones in that VPC. Like many VPC-based compute services, you need to **deploy** it **across AZs** to ensure that it's **highly available**.

There's a **primary node**, which is the **read** and **write** node, and this replicates out to other nodes, which are the **replica nodes**, and these function as **read replicas**.

DAX maintains **two** different **caches**.
1) The **item cache** - caches individual items which are retrieved via the **GetItem** or **Batch GetItem** operations. These operate on **single items** - you need to specify an item's **partition key**, and if present, its **sort key**.
2) The **query cache** - stores **collection** of items retrieved via **query** or **scan** operations, but crucially, it also stores the **parameters** used in that original query or scan.
	1) It means that whole query or scan operations can be rerun and return the same cached data.

DAX is accessed architecturally much like RDS. Every DAX cluster has an **endpoint** which is used to **load balance** across the cluster.

Writing data to DynamoDB DAX can use **write-through caching** - the data is written into DAX, at the same time as being written into the database.

Architecturally, **DAX** is an efficient way to interact with DynamoDB because it **abstracts** away DynamoDB.

**DAX Considerations**
- **Primary** NODE (**Writes**) and **Replicas** (**Read**)
	- DAX is a cluster
- Nodes are **HA** .. Primary failure = election
	- If you implement multiple nodes and the primary fails, it'll have an election to re-elect a different primary node.
- In-Memory cache - Scaling .. **Much faster reads, reduced costs**
	- Designed to reduce response time for read operations by an order of magnitude.
- Scale **UP** and Scale **OUT** (**Bigger** or **More**)
- Supports **write-through**
	- You can write it using the DAX SDK - DAX will write it to DynamoDB & store it in cache simultaneously.
- DAX Deployed **WITHIN a vpc**
	- So, any application which is using DAX will also need to be deployed into that VPC.

**Choosing** between DAX and a generic in-memory cache comes down to how much admin **overhead** you want to manage. DAX is integrated with DynamoDB. It supports this single SDK for accessing the cache and DynamoDB (both as an abstract entity). If you've got **read-heavy** or **bursty** workloads, then DAX provides increased throughput and potentially significant cost reductions. If you find yourself having to apply **large RCU** values onto a table, these can get expensive really quickly, and you might be better implementing DAX.

Situations where DAX is **not ideal**, are any applications that require **strongly consistent reads**. If your application cannot tolerate **eventual consistency**, then DAX is not going to be suitable. If you **don't have** an application that is **latency sensitive**, if you **don't need** these really **low response times**, again, DAX might not be the right solution. If your application is **write-heavy**, DAX is probably not the right solution.

On the **exam**, if you see a **caching** requirement with **DynamoDB**, by default, assume it's DAX, and only move away if you see significant evidence to suggest something else.

## DynamoDB - TTL
Time to Live.

![[Dynamo TTL.png]]
2 partitions - 1 dark blue; 1 light blue.
On a table, pick an attribute to be used for the TTL processes. TTL is specified in seconds since the epoch (the 1st of January 1970). Do that for all items you want to be effected by the TTL processes.

Process 1) Scans partitions and when the TTL attribute is less than the current date and time, that item is set to **expired**. They **aren't deleted** yet.

Process 2) Finds expired items and removes them from the table, indexes, and any streams configured on the table. these delete operations are system events running in the background. They don't cause any performance issues, nor do they have a charge.

You can also **configure a stream** on the **TTL processes**. This creates a 24-hour window of any deletions which are caused by the TTL processes. Useful for housekeeping processes. Table auditing.

## Amazon Athena
- **Serverless** Interactive Querying Service
- Ad-hoc queries on data - pay only **data consumed**
	- On S3 data
- **Schema-on-read** - table-like translation
	- // What's special about Athena is how it handles the structured, semi-structured, and even unstructured data that it uses.
	- Like a window or a lens through which you see the data in a certain way
- Original data **never changed** - **remains on S3** **!!!!!!!!!!**
- Schema translates data => relational-like when read
	- The schema which you define in advance modifies data in flight as it's read through the schema.
	- The translation only happens within the product during the querying process.
	- No ETL
![[Amazon Athena.png]]
Unlike a traditional database, where a table is the final structure, in Athena you're defining a way to take the original data, and present it in a way that you want, which allows you to run queries against these tables. Like a recipe. A method to get from the source data to the structure that you want to be able to query.

These **tables** within Athena don't actually contain data like a traditional database product. They **contain information directives** on how to **convert** the source data to be able to query on it. This schema is used at the time of querying when data is read. This is why it's called **schema on read**.

Just pay for amount of data consumed by the query. You can even optimize the original data set to reduce the amount of data that has to be used for individual queries.

The key thing to understand about Athena going into the **exam** is that it has **no input**. No infrastructure. No setup. No need to premeditate data manipulation or loading data.

	- // ^ native support; (exam keywords)

	- Athena now has the capability to query **non-S3 data sources**

## Redshift Architecture
- **Petabyte**-scale **Data warehouse**
	- // A location where many different operational databases from across your business can pump data into for long-term analysis and trending. OLAP database (reporting and analytics). Rather than OLTP (transactions).
- **OLAP** (**Column** based) not OLTP (row/transaction)
	- Reporting and analytics; Aggregated data.
	- // RDS is OLTP (row based; interact with specific records.)
	- // column-based - reporting style queries more efficient (ex: avg. of all ages, read all names, etc.)
- Pay as you use ... similar structure to RDS
	- Delivered as a service just like RDS
	- Pretty quick to provision; you can provision it, load data, use it for something, and then tear it down when you've finished
	- Generally, data is loaded into Redshift before being worked on
- Direct Query S3 using **Redshift Spectrum**
	- Allows for querying of data on S3 without loading it into Redshift in advance. Great for larger data sets. Still need a Redshift cluster, but saves on the time-consuming exercise of loading data into the platform.
- Direct Query other DBs using **federated query**
	- Allows you to directly query data that's stored in remote data sources. You can integrate Redshift with other databases, foreign or remote databases, and query their data directly.
- Integrates with AWS tooling such as Quicksight
	- Quicksight - for visualization
- SQL-like interface **JDBC/ODBC** connections

**Redshift Architecture**
- **Server** based (**not serverless**)
	- Provisioned product. Not serverless, like Athena.
	- Not used on an ad-hoc basis, like Athena. Faster than on-premise data warehouse, but does have provisioning time.
- **One AZ** in a VPC - network cost/performance
	- Uses a cluster architecture. The cluster is actually a private network. You can't access most of the cluster directly. Redshift runs with multiple nodes and high-speed networking between those nodes. Because of this, it runs in one AZ. **Not HA** by design.
- **Leader Node** - Query input, planning and aggregation
	- The leader node manages communications with client programs and all communications with the compute nodes. It develops execution plans to carry out complex queries.
- **Compute Node** - performing queries of data.
	- They store the data loaded into the system
	- A compute node is partitioned into **slices**.
		- Each slice is allocated a portion of the node's **memory** and **disk** space where it processes a **portion** of the **workload** assigned to that node.
		- The leader node manages distributing data to the slices and apportions the workload for any queries or other operations onto the slices.
		- The slices then work in parallel to complete the operation.
		- A node might have 2, 4, 16 or 32 slices. It depends on the resource capacity of that node.
- VPC Security, **IAM** Permissions, **KMS** at rest Encryption, **CW** Monitoring
- (exam) Redshift **Enhanced VPC Routing** - **VPC Networking**
	- By default, Redshift uses public routes for traffic when communicating with external services or any AWS services such as S3 when it's loading in data. If you enable enhanced VPC routing, then traffic is routed based on your VPC networking configuration. This means it can be controlled by SGs, NACLs, can use custom DNS, and it will require the use of any VPC GWs (IGWs, NAT GWs, or any other VPC endpoint) that any other type of traffic requires to reach AWS and external services.
	- (**exam**) If you want **advanced networking control**, then you need to **enable enhanced VPC routing**.
