**Amazon Workspaces**
![[Amazon Workspaces.png]]
WorkSpaces run within the AWS ecosystem. They don't run directly within customer-managed VPCs. (example: 2 AZs, a public & a private subnet per AZ).

Something else that also runs within this AWS-managed VPC: WorkSpace-related shared components - **authentication** and **streaming** **gateways**. (**exam**) WorkSpaces are **not highly available** by design. They're just virtual desktops running on a host within an AZ injected into your VPC in one specific subnet. And so they're susceptible to AZ failure. Now there is **recovery**, and you can **utilize multiple AZs** and distribute your WorkSpaces across different availability zones to minimize the impact of a failure. But just be aware that WorkSpaces in isolation are impacted by any AZ failures within the region that they operate.

## Directory Service Deep Dive (AD Connector)
- A **Pair** of directory endpoints running in AWS (**ENIs** in a **VPC**)
	- like other modes, injects ENIs into two subnets within a VPC.
- Supports directory-aware AWS products
	- // Once created to any AWS products which are capable of using a Directory, AD Connector appears as a native Directory.
	- // supports services such as WorkSpaces, WorkDocs, WorkMail, and many others.
- **Redirects requests** to **existing directory servers**
- **No directory data** stored in AWS ... **all redirected**
- Use **existing on-premises AD** with **directory compatible AWS Services** - without any identity data in AWS
	- AD Connector mode allows you to use AWS services which require a Directory (such as WorkSpaces), and use these with an on-premises Directory infrastructure. Using this mode means you don't need to deploy additional Directory infrastructure into AWS. Products within AWS can see your on-premises Active Directory as though it was an AWS supported Directory.
- **Proof of concepts**, where you need to use existing identities.
	- Remember it just relays any requests to your existing on-premises Directory. It doesn't by itself perform any authentication or other Directory related workloads.
- Two sizes .. **small** and **large**.. no explicit limits
	- .. controls the amount of compute allocated (throughput)
- Multiple AD Connectors can be used to spread load
	- // these factors are things that you need to test during any testing or proof of concept phase as part of your project implementation.
- Requires **2 subnets** within a VPC .. **different AZS**
- Connector requires 1 or more directory server(s) to be configured
	- // Normally two
	- You need to provide account information for the connector to authenticate with the on prem AD platform. All of this information is configured when setting up the AD Connector. Once done, AWS services can use it as though it was a full directory service implementation. They can use it for both authentication and authorization as part of those services.
- **REQUIRES** a **working network** connection
	- // between the AWS VPC and those directory servers you configured when setting it up
	- Without a working network connection, it can't function, because there's no caching or data held locally inside AWS
- Network connectivity via **Direct Connect** or **VPN**

(**exam**)
- If you need a directory service implementation inside AWS, to use AWS services which need a directory, logically, you're going to use the directory service.
- But, if you want to do that quickly for **proof of concepts**, where you want as **little admin overhead** as possible, then you can use the **AD connector**.
- If you're prevented from having any directory data in AWS, maybe for legal reasons, then you can use the AD connector.
- But, if you do decide to use the AD connector, you need working network connectivity between AWS and your on-premises environment.

**Directory Service - AD Connector**
![[Directory Service - AD Connector.png]]
When setting up the AD connector, you enter the IP addresses of directory servers in the corporate office, and the connector instances use these to **relay** any authentication or authorization requests through to these on-premise directory servers. This occurs over the VPN or direct connect. Any AWS services which need a directory can utilize the AD connector as this directory. But, just to keep reaffirming this, it is only a redirect. Nothing is stored locally in AWS.

Generally, in the **exam**, you would only answer AD connector when there is a compelling reason to do so, in a given specific scenario that suits this product:
- Proof of concept.
- Business which only has a small amount of infrastructure within AWS, but it does need directory capability so that it can use compatible AWS services.
- Business might have legal or compliance reasons not to have any directory information within AWS.
- Just be aware, always, that by using the AD connector, you're adding a reliance on the network connectivity. Without working connectivity between AWS and the on-premises environment, the AD connector won't work.
	- // For smaller AWS deployments and proof of concepts, AD Connector can be great, but for anything larger, especially if there's only a single network connection, then I would have significant concerns. For larger projects, certainly ones where you only have one network connection, then you do need to give significant thought to if AD connector is the right product.
