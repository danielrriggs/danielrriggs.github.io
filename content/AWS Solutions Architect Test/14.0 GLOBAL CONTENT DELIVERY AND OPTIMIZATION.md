## Cloudfront Architecture
CloudFront is a CDN. Improves delivery of content by caching and by using an efficient global network.
This is a refresher. See [[12.0 HA & SCALING#Regional and Global AWS Architecture]]

![[CloudFront Architecture1.png]]

- **Origin** - The source location of your content.
- **S3 Origin** or **Custom Origin** - anything else which runs a web server and has a publicly routable IPv4 address. For every Cloudfront configuration, you'll have 1 or more origins.
- **Distribution** - The **configuration** unit of CloudFront
	- To use CloudFront you create a distribution and this distribution gets deployed out to the CloudFront network. Almost everything is configured within a distribution, directly or indirectly. Multi origins are configured in a distribution, but indirectly.
- **Edge Location** - Local cache of your data
- **Regional Edge Cache** - Larger version of an edge location. Provides another layer of caching.
	- There are fewer of these than edge locations. They're designed to hold more data to cache things which are accessed less frequently, but where there's still a performance benefit for caching your data closer to your customers than your origins. Provide a real benefit when it comes to larger more global deployments of CloudFront.

![[CloudFront Architecture2.png]]

One of the things which is created along with the distribution is a **domain name** for that distribution. It always **ends in CloudFront.net**. Unique to every distribution. You can also take your own domain name and configure the distribution to use that alternate domain name (animalsforlife.org). When you deploy a distribution to the CloudFront network, it's pushed to chosen edge locations.

Cache hit is delivered from edge. Cache miss checks Regional Edge Cache. If not there, it does an **origin fetch**, which stores the object on the Regional Edge Cache. The Regional Edge Cache pushes the object to the Edge which originally requested it. It's now on the Edge.

CloudFront integrates with ACM - the AWS certificate manager. So, you can use SSL certificates with CloudFront. CloudFront is for **download** style operations **only**. Uploads go direct to the origin for processing - **no R/W caching**.

![[CloudFront Architecture3.png]]
**Origins** are linked to **Distributions** which are linked to **Behaviors**. A CloudFront distribution always has at least one behavior. Behaviors pattern match - default(\*) - wildcard - used for low security things.

We can define a second Behavior - private(img/\*) - matching a more specific pattern. This allows us to have different configurations within a distribution - Origins, Origin Groups, TTL, Protocol Policies, restricted access - these are configured via Behaviors.

## CloudFront - TTL and Invalidations
CloudFront TTL & Invalidations can be used to influence how long objects are stored at edge locations and when they're ejected.

![[TTL and Invalidations.png]]

On the edge location, we replaced the pic of Whiskers crying with a cuter Whiskers pic. In step 4, the middle user received an old version of the object even though a newer version was stored in the origin.

- More frequent **cache HITS** = **lower origin load**
- Default TTL (**behavior**) = **24 hours** (validity period)
- You can set **Minimum TTL** and **Maximum TTL** values
	- These are limiters for any per object settings that are defined using these cache control headers
- Origin Header : **Cache-Control max-age** (seconds)
- Origin Header : **Cache-Control s-maxage** (seconds)
	- ^ These two headers (**Cache-Control max-age** & **Cache-Control s-maxage**) do the same thing.
- Origin Header : **Expires** (Date & Time)
- Custom Origin or S3 (Via **object metadata** - set via API, CLI, UI)
	- Custom Origin can be injected by your app or the web server

- Cache Invalidation ... performed on a **distribution**
	- applies to all edge locations ... **takes time**
	- immediately expires any objects, regardless of their TTL
- Examples:
	- /images/whiskersl .jpg
	- /images/whiskers*
	- /images/*
	- /*
		- Everything on every edge location is invalidated
- **Versioned file names** ... whiskers1_ v1.jpg // \_v2.jpg // \_v3.jpg
	- There is a cost to perform cache invalidations. That cost is the same regardless of the # of objects which are matched by the pattern. Invalidation should only really be thought of as a way to correct errors. If you are regularly having to update or invalidate files, consider using versioned file names instead.
	- **Versioned file names** comes up in the exam all the time. Bersioned file names are better for a few reasons:
		- 1) different name for the object - even if those objects are cached in a customers browser, it won't be used, because you're changing the object name.
		- 2) logging is more effective because nothing has the same name.
		- 3) you keep all versions of all objects
		- 4) less expensive - because you don't need to use continued cache invalidations
		- // don't confuse versioned file names with s3 object versioning. s3 object versioning allows you to have different data for an object - different versions which use the same name. Cloudfront will always use the latest version, by default.

You need to know a little at the associate level; more at the pro level.

- HTTP - Simple and Insecure
	- // Ex: spoof domain name & redirect to fake site

- Data is encrypted **in-transit**
- Certificates **prove identity**
- **Chain of trust** - Signed by a **trusted authority** (SSL/TLS)
	- Since the web client trusts the CA, you trust the cert which it signs, which is why you trust the site - it's harder to spoof. DNS name & cert are tied together.
- ACM lets you run a **public** or **private** Certificate Authority (CA)
	- Private CA has the same architecture as public ; Often used by large corporations
- **Private CA** - Applications need to **trust your private CA**
	- // Something generally done manually by adding this trust into your client laptop and desktop builds or automatically by adding a policy to configure this trust
- **Public CA** - Browsers trust a list of providers, which can trust other providers
- ACM can **generate** or **import** Certificates
	- // To make a cert, you need DNS or email verification to prove you own the domain.
- If **generated** ... it can **automatically renew**
- If **imported** (into ACM from external source) .. **you are responsible for renewal** (with external source)
- Certificates can be deployed out to **supported services**
	- Certificates are always stored encrypted within the product and deployed in a managed and secure way to those supported services.
- (**exam**) **Supported** AWS Services **ONLY** (e.g. CloudFront and ALBs.. **NOT EC2**)
	- // because AWS has no way of securing the transfer and deployment to EC2. If you have root access on an EC2 instance, you'll always have access to access the cert. The whole point of ACM is to secure the storage and deployment of those certificates.
- ACM is a **regional service**
- Certs **cannot leave the region they are generated or imported in**
- (**exam**) To use a cert with an **ALB** in **ap-southeast-2** you need **a cert in ACM** In **ap-southeast-2**
	- For most services (except CloudFront), the certs must be in that region.
- (one exception) Global Services such as CloudFront **operate as though within 'us-east-1**
	- // conceptually, think about the distribution (the unit of configuration for CF) for CloudFront as being in us-east-1 from an ACM perspective. You always use us-east-1 for CloudFront certificates.

## Cloudfront and SSL/TLS
How CloudFront works with SSL.

- CloudFront **Default Domain Name** (CNAME)
	- Each CloudFront distribution receives a default domain name when it's created
- https://dl11111abcdef8.cloudfront.net/
- SSL Supported by default ... \***.cloudfront.net** cert
	- You can enable HTTPS access to your distribution by default as long as you use this address
- **Alternate Domain Names** (CNAMES) e.g. cdn.catagram...
	- Most of the time, you want to use your own custom name with a CloudFront distribution. This is how you do that. Once these are added and active, you can point that custom name at your CloudFront distribution using a DNS provider such as Route 53.
- Verify Ownership (optionally HTTPS) using a matching certificate
	- Whether you want to use HTTPS or not, you need to add a cert to the distribution which matches the ultimate domain name you're trying to add. To do that, you need to generate/import an SSL certificate using ACM.
- Generate or import in ACM .. in us-east-1
	- (// reminder) Normally, you need to add a certificate in the same region as the service that you're using (so, a Load Balancer in ap-southeast-2 would need a cert in ACM in ap-southeast-2). Exceptions to this are global services, such as CloudFront. For these services, the cert must always be created/added in us-east-1.
- 3 CloudFront behavior options: 1) HTTP or HTTPS, 2) HTTP => (redirect to) HTTPS, 3) HTTPS only
	- If you choose to use HTTPS with CloudFront, you have to have the appropriate certificates which match the name that you're using for that distribution.
- Two SSL Connections: Viewer => CloudFront and CloudFront => Origin
	- These are known as the **viewer protocol** and **origin protocol**.
- (**exam**) ^ **Both** Need valid **public** certificates (and intermediate certs)
	- (**exam**) **Self signed certs won't work with CloudFront**! They need to be publicly trusted.

We need to understand how CloudFront is charged. To do that we need to understand how SSL has worked over time.

- Historically, every **SSL enabled** site needed its **own IP** (before 2003)
	- [[SSL]] & [[TLS]] are often used interchangeably. In this context we just mean encryption that happens over a network connection.
- Encryption starts at the **TCP** connection
	- TCP is lower layer protocol than  HTTP - an application protocol.
- **Host headers** happens after that - **Layer 7** / **Application**
	- A single web server can many websites using different names using one single IP address - e.g. Categram and Dogogram. How this works when only using HTTP - your web browser is sends a request to my web server & uses a host header. But this happens at layer 7 - after the connection has been established. TLS, the encrypted part of HTTPS happens before this point. Part of what TLS does is allow a web server to validate its identity. The server can only provide one certificate. this is why historically it wasn't possible to host multiple HTTPS sites on a single IP. The web server had no method of understanding which site you were trying to access to provide the relevant cert. In 2003, an extension was added to TLS called [[SNI]].
- **SNI** is a **TLS extension**, allowing a **host to be included** in the TLS handshake
	- Resulting in **many SSL Certs**/**Hosts** using a **shared IP**
- **Old browsers don't support SNI** ... CF charges extra for dedicated IP (to support older browsers)
	- SNI mode is free. Otherwise, you have to spend $ to use dedicated IPs at the edge location. Currently $600/mo per distribution.

![[CloudFront and SSL-SNI.png]]

(Viewer side) You **cannot use self signed certs**. Only **publicly** trusted certs are able to be applied to CF distributions.
(Origin side) Again, no self-signed certs. Only publicly trusted certs. If your origin is S3, no need to apply certs to S3 buckets. Just point CF distribution (your behavior) at the origin, and it works.

## CloudFront (CF) - Origin Types & Origin Architecture
You need to understand the **types** of **origins**, how they **differ** and the **features** that each of them provides.

Origins are where CloudFront goes to get content. If an edge location receives a request from a customer and that object isn't cached at the edge, then an origin fetch occurs to the relevant origin.
**Origin groups** allow you to add resiliency - if you have two or more origins created within a distribution, you can create an origin group - used by a behavior.
Origins can have: S3 buckets, AWS Media Package channel endpoints, AWS MediaStore container endpoints, then everything else (meaning, web servers). "Everything else" = **custom origin**. Custom origins have different features and restrictions versus S3 buckets.

**S3 Origin**
- Origin Path - by default, would go to top level of bucket. We can specify a particular path inside the bucket.
- Origin access - **restrict** access to an S3 origin so it's **only accessible** via a **CF distribution**.
	- Public
	- Origin **access control** settings (recommended)
	- Legacy **access identities**
Whichever protocol is used between the customer and the edge location (the **viewer protocol**) is also used between CF & S3 (**origin protocol)**. They're matched at both sides (HTTP or HTTPS, for example).
- Add custom headers

**Custom Origin**
- Origin Path
	- If we wanted to point somewhere besides the top level.
- Protocol
	- When using S3, the viewer & origin protocols match. When using a Custom Origin, you can select from: HTTP Only, HTTPS Only, or Match Viewer
	- HTTP/S **port**
		- In case you have different services bound to different ports (default is 80 for HTTP, 443 for HTTPS).
- Minimum SSL protocol
- Custom Headers
	- // Security - If you're **not** using an S3 origin, it means you **don**'t have the ability to use **origin access identities** or **origin access control**. To **secure** custom origins, you can use **custom headers**. You can pass in a custom header that only you're aware of & have have your custom origin check for that header.

## Securing CF and S3 using OAI
How to secure the content delivery path when using CloudFront.

If you use the **static web hosting** feature of S3 with CloudFront, then the S3 bucket is **treated** the same as any **non-S3 origin** (a custom origin).
**OAI** (Origin Access Identity) is only applicable for S3 origins.

- An **OAI** is a type of **identity**
	- Not the same as an IAM user or an IAM role, but some of the characteristics of both.
- It can be **associated** with CloudFront **Distributions**
- CloudFront '**becomes**' that **OAI**
- That **OAI** can be used in **S3 Bucket Policies**
	- The identity can be used within bucket policies. So either explicit allows or denies. 
	- **DENY** all **BUT** one or more **OAI's**
		- Generally, the common pattern is to lock an S3 origin down to only being accessible via CloudFront. This uses the implicit default deny to apply to everything except the origin access identity.

**OAIs (S3 Origins)**
![[Origin Access Identity (OAI).png]]

Access from the edge locations are from the OAI. Access from the edge locations is allowed because the OAI is explicitly allowed via the bucket policy. Direct access would not have the OAI & would be implicitly denied.

OAIs can be created & used on many CF distributions at the same time. Generally though, I find it easier to manage if you create one OAI for use with one CloudFront distribution. This makes it easier to manage permissions in the long term.

**Custom Origins**
![[Securing Custom Origins.png]]

We have 2 ways to prevent people from accessing origins directly.
Configure viewer protocol & origin policies to insist on HTTPS.
1) Use **custom headers**. Custom headers are injected at the edge location.
2) Traditional **IP Blocks**. We can use a traditional **firewall** around the custom origin configured to allow connections in from the edge locations (ip ranges) and deny anything else. (AWS publicizes the IP addresses of all their services).

## CloudFront - Private Distribution & Behaviours
How you can deliver private content from CloudFront using Behaviors. The differences between signed URLs and signed cookies.

CloudFront can run in two security modes - public & private
- **Public** - Open Access to objects
- **Private** ... requests require Signed **Cookie** or **URL**
- 1 Behavior = **Whole Distribution** PUBLIC or PRIVATE
	- Multiple Behavious - each is PUBLIC or PRIVATE
	- Generally though, you're going to have multiple behaviors;
There are two ways to configure private behaviours in CloudFront. The old way, and the new preferred way. In both cases, you require a signer - an entity which can create signed URLs or signed cookies.
- OLD Way - A **CloudFront Key** is created by an Account Root User
	- Tied to an account, rather than an identity within that account.
- OLD Way - THE ACCOUNT is added as a **TRUSTED SIGNER**
	- (exam) Remember the term Trusted Signer. If you see that term, you know a private distribution/behavior is involved.
- NEW - **TRUSTED KEY GROUP(S)** added & assigned as signers
	- Key groups determine which keys can be used to create signed URLs and signed cookies
	- Reasons it's better:
		- No need to use the AWS **account root** user to manage public keys for CloudFront signed URLs and signed cookies
		- You can **manage** these key groups and the configuration using the CloudFront **API**
		- you can associate a **higher number** of public keys with your distribution (specifically, with your behavior) giving you more **flexibility** in how you **use** and **manage** those **keys**
**CloudFront Signed URLs vs Cookies**
- (**exam**) SignedURLs provides access to **one object**
- **Historically** RTMP distributions **couldn't use cookies**
	- // this was a legacy point to pick between signed URLs and cookies, but this isn't really applicable anymore
- Use **URLs** if your client **doesn't support cookies**
- **Cookies** provide access to groups of objects
	- Use for **groups** of files/**all files of a type** - e.g. all cat gifs
- Or if maintaining application URL's is important
	- If you want to present access using a certain format of URL, then you need to use signed cookies

![[Private Distributions.png]]

Within the CloudFront distribution, there are two behaviors. A public behavior (the default) - this handles all non-sensitive application operations. And a private one - handles access to all of the sensitive privateCatGifs.

// Let's assume that the mobile app is using ID Federation, so a Google, Twitter, or Facebook identity for logins.

The **application** communicates with the **default behavior**, uses API Gateway, it logs in, and accesses some images which are private. The **Lambda signer** function checks the application's access to the image, and if everything is good, because we've added trusted key groups on the distribution, specifically the behavior, the Lambda function is able to **generate** a **signed cookie** & it's returned to the mobile application. The mobile application supplies the cookie along with requests for privateCatGifs. The cookie is checked by CloudFront, and assuming everything checks out, an origin fetch occurs. The privateCatGifs are retrieved and returned back to the application.

Private behaviors are an excellent way to secure content, but you need to make sure that the **application** is **secure**, and that the **origin** is also secure. In this case, the S3 origin needs to be configured using an OAI, so that it only accepts connections from the CF distribution - that will avoid the security issue where CF gets bypassed.

## Lambda@Edge
- You can run **lightweight** Lambda at **edge locations**
- **Adjust** data between the **Viewer** & **Origin**
- Currently supports **Node**.js and **Python**
- Run in the **AWS Public Space** (Not VPC)
- **Layers** are not supported
- **Different Limits** vs Normal Lambda Functions

![[Lambda@Edge.png]]

Viewer request function - runs after the CloudFront Edge location receives a request from a viewer.
Origin request function - runs before CloudFront forwards that request onto the origin.
Origin response function - runs after CloudFront receives a reply from the origin.
Viewer response function - runs before the response is forwarded back to the viewer.
- Function Limits
	- Viewer side: 128mb, 5s timeout
	- Origin Side: Normal Lambda (128MB to 10240MB), 30s timeout
		- // [[13.0 SERVERLESS AND APPLICATION SERVICES#AWS Lambda - PART1]]

**Lambda@Edge Use Cases**
- A/B testing - **Viewer Request**
	- Ex: the function views the viewer request and modifies the request URL based on which version of an image you want the viewer to receive.
- Migration Between S3 Origins - **Origin Request**
- Different Objects Based on Device - **Origin Request**
	- Ex: send device with high DPI screen objects which have higher dpi values.
- Content By Country - **Origin Request**

## Global Accelerator
Designed to optimize the flow of data from your users to your AWS infrastructure.

**Global Accelerator - The Problem**
![[Global Accelerator - The Problem.png]]
Generally, fewer hops = better experience. The internet is designed to be distributed, autonomous, and highly resilient; speed being a lower priority.

Global Accelerator's architecture is similar to CloudFront. You'll need to know when to use which service. They both improve performance, but in different ways.

![[Global Accelerator.png]]

Global Accelerator starts with two [[Anycast IP address|Anycast IP addresses]].  **Normal IP** addresses are [[Unicast IP address|Unicast IP addresses]]. Internet routers will route traffic to the device closest to the source.

In this example, both of our Anycast IP addresses map onto three Global Accelerator edge locations (in reality, there are many more). The key thing to understand is that all three of these Global Accelerator edge locations are all using this pair of Anycast IP Addresses. Any traffic that's destined for either one of these Anycast IP addresses, can be serviced by any one of the Global Accelerator edge locations.

The customer to edge connection is still subject to the variability that the public internet can cause but now it's very limited to just the part between the customer and the Global Accelerator edge location. We've moved the AWS network closer to the customer. Global Accelerator accepts the data that arrives at one of its edge locations, and it transits that data from that edge location to the destination (the yellow line). But crucially, this transit occurs over the AWS global network - which AWS controls. It's fast (fiber links).

**When & Where to Use Global Accelerator**
- Moves the AWS network closer to customers
	- CF moves content closer by caching it on edge locations. GA moves the AWS network closer.
- (**exam**) Connections **enter at edge** .. using anycast IPs
- (**exam**) **Transit over AWS backbone** to **1+** locations
- (**exam**) Can be used for **NON HTTP/S (TCP/UDP)**  **Difference from CloudFront**
	- GA's a network product. It doesn't cache anything.
	- If you see questions which mention caching, then CF's probably the right answer; questions which mention TCP or UDP and the requirement for global performance optimization, GA's probably the right answer.
