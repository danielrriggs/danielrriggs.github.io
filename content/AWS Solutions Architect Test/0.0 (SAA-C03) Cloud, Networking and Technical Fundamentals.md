**Layer 1 networking**
- **No device addressing**, all data is processed by all devices
	- L1 is a broadcast medium (fixed by L2)
- If multiple devices transmit at once - a **collision** occurs, rendering all the information useless
	- Only one thing can transmit at once on a shared medium and be legible to everything else
- L1 has **No Media Access Control (MAC)** and **no Collision Detection (CD)**
	- Media Access Control (MAC) - way to control which devices can transmit
	- Likelihood of collisions increases the more L1 devices are on the same L1 network.
	- L1 is physical, not digital. It's dumb.
	- L1 doesn't scale very well.
- Physical **shared** medium
- **Standards** for **transmitting** onto the medium
- **Standards** for **receiving** from the medium
	- All devices which are part of the same layer 1 network need to be using the same layer 1 medium and device standards.
		- Certain network card, certain cable, wi-fi cards w/ certain antennae & frequency ranges
- No access Control
- No uniquely identified devices
- No device => device communications

L2 (datalink) adds intelligence to L1.

## Layer 2 - DataLink - PART1
Important layer. Everything above this point relies on the device-to-device communication which the data link layer provides.
![[Layer 2 - Data link - Frame.png]]
Higher layers build (& depend upon) on lower layers, adding capabilities.
There are different L2 protocols and standards; we're going to focus on ethernet.
L2 introduces the concept of **frames** - a format for sending information over a L2 network.

L2 introduces the concept of a **MAC address**. Not software assigned. The address is attached to a piece of hardware. Formed with 2 parts: the organizationally unique identifier (**OUI**) - assigned to companies who manufacture network devices; & the Network Interface Controller (**NIC**), or, NIC-specific. Together, the MAC address on a card should be globally unique.

An ethernet frame can be transmitted over L1. L2 provides frames, L1 provides physical reception & transmission.

**Frame**
- **Preamble** - frame delimiter. Start of frame.
- Destination MAC Address
	- A frame is sent to a specific device, or you can put all F's to send to every device on the local network - known as a broadcast.
- Source MAC Address (allows to receive replies)
- Ether Type - specifies which L3 protocol is putting its data inside a frame.
	- Common Example: IP (the Internet Protocol)
- These three fields (Destination, Source, ET) = **MAC Header**
- Payload
	- Encapsulation - Example: L3 generates an IP packet and puts it inside an L2 ethernet frame
- Frame Check Sequence - [[cyclic redundancy check|CRC]] check; allows destination to check for corruption

## Layer 3 - Network - PART 1 - 3

L2 moves frames from a local source to a local destination.
To moving data between different local networks is known as inter-networking, (this is where the name internet comes from), we need L3. L3 is a common protocol which can span multiple L2 networks.
![[Building a Common L3 Network.png]]
**IP - Packet Structure**
![[Layer 3 - IP - Packet Structure.png]]
Protocol - The L4 protocol. Examples: ICMP (ping) (1), TCP (6), or UDP (17).
A single packet might exist inside tens of different frames throughout its route to its destination. One for every L2 network or L2 point-to-point link which it moves through.

**IPv4**
![[IP Addressing (v4) - IPv4.png]]
IP addresses are not actually dotted decimal. That's how they're represented for humans. They're actually 4 Octets.
If the network part of the IP address match, they're local; else, they're remote.
DHCP - Dynamic Host Configuration Protocol.
IP addresses need to be unique, (locally, and globally) or bad things happen.

- Subnet masks, IP addresses, & (for most interfaces) a default gateway are configured on L3 interfaces.
- Default Gateway - an IP address on the local network which packets are forwarded to generally if the intended destination is not a local IP address.
- Subnet Masks - what allow an IP device to know if an IP address which it's communicating with is on the same network or not.
	- Influences if the device attempts to communicate directly on the local network or if it needs to use the default gateway.
**Subnet Mask**
![[Subnet Mask.png]]
Along with this IP address, we would generally also configure, either statically or using DHCP, a subnet mask (255.255.0.0, or, /16; same thing).
The /16 is shorthand. It's a prefix. It's the number of '1's starting from the left. /16 means 16 1's, which is the same as 255.255.0.0 when you convert that into binary.

Subnet masks are used to identify which part of an IP address is the network part, and which is the host part.

The starting address of a network is the network component of the IP address (identified with the subnet mask), and then all 0s for the host part of the IP address.
The ending address of the network is the network part of the IP address to start with, and then for the host component, we have all 1s.

As long as the network part for two different IP addresses is the same, then we know that both of those IP addresses are on the same IP network.
![[Route Tables & Routes.png]]
Every router has at least one route table.
/24 means the first 24 bits are for the network and the last 8 bits are for the host; Matches a network with 256 IP addresses.
The more specific route will be selected. The top route (52.217.13.0/24) & middle route (the router's default route, 0.0.0.0/0) contain the range (52.217.13.37). The top route is more specific (because /24 is a more specific prefix).

When our ISP router is forwarding the packet through to the AWS router, it's forwarding it at layer 2. It wraps the packet in a frame. The frame has the AWS router's MAC Address as its destination. That's how the packet gets to the AWS router. But, how do we determine the MAC Address of the AWS router? We use the **Address Resolution Protocol**.
![[Address Resolution Protocol.png]]
- **Address Resolution Protocol** (**ARP**) - gives you the **MAC Address** for a **given IP Address**.
	- Used to encapsulate a L3 packet (w/ dest IP) in a L2 frame, then send that frame to a MAC Address.
	- Process which runs between L2 & L3.
	- Broadcasts on L2
	- (4) Sends an ARP frame to all Fs as a MAC address; Asks: "Who has the IP address 133.33.3.10?".
	- (5) The right laptop is running the ARP software; it responds with its MAC Address.
	- (6) Now, the left laptop can build L2 frames.
**Layer 3 - IP Routing**
![[Layer 3 - IP Routing.png]]
- D1 wants to communicate with D2 (local network)
	- D1 uses its own IP address and subnet mask together with D2's IP address and calculates that they're both on the same local network. So, router R1 is not required.
	- A packet gets created called P1 w/ D2's destination.
		- ARP (L3) is used to get D2's MAC Address. That packet is encapsulated in a frame (L2) with that MAC Address as the destination.
	- Frame is sent to the MAC Address of D2. ... Frame arrives at D2. D2 checks the destination address; sees its the recipient. Strips the frame away. Passes packet to L3. Sees its the destination IP address. Strips the packet away; passes the game data to the game.
- D2 Communicates to D3 (remote networks)
	- (1) The D2 laptop compares its own IP Address to the D3 laptop IP Address & uses its subnet mask to determine that they're on different networks. Creates packet P2 with the D3 laptop as its dest IP address. Wraps this in frame F2.
	- (2) Because D3 is remote, D2 knows it needs to use the Default Gateway as a router (the dest MAC Address for F2 must be R1's Mac Address). D2 uses ARP to get R1's MAC Address (the local router). Packet P2's dest IP address is D3 while Frame F2's dest address is R1's Mac Address.
	- (4) F2 is sent to R1. R1 sees F2 is addressed to itself; strips away the frame, leaving just P2.
		- // If a laptop or a phone got a packet it wasn't destined for, it would just drop it. A router is different. It's designed to handle packets addressed to somewhere else. The router review P2's dest address; it has a route in its route table for that. It knows that R2 should be the next hop.
	- (5) R1 encapsulate P2 in a new frame, F3 w/ R2 as the dest MAC (it gets this using ARP).
	- (6) F3 sent to R2. R2 sees that F3's dest MAC is itself.
	- (7) Strips F2, leaving P2.
	- (8) Router sees that it isn't P2's dest. Sees P2 is addressed to something on the same network. Uses ARP to get the MAC Address of D3. Creates F4 w/ D3's MAC.
	- (9) F4 sent to D3. Receives, strips F4. Strips P2. Gives data to game.

Routers move packets between networks. They review packets, checking route tables for the next hop or target addresses and then add frames to allow the packets to pass through intermediate layer 2 networks. A packet during its life might move through any number of layer 2 networks and be reencapsulated many times during its trip. But normally the packet itself remains unchanged all the way from source to destination. A router is just a device which understands physical networking, it understands data link networking and it understands IP networking.

(Summary)
- L1 - raw bit stream data transmitted to/from physical shared media.
- L2 - adds identifiable devices, switches, and MAC. L2 ends with isolated L2 networks.
- L3 - adds IP address & routing (SRC => DST across interconnected networks).
- L4 - adds 2 new protocols (both run on top of IP):
	- TCP - Transmission Control Protocol
		- Slower; Use when you want reliability, error correction, and ordering of data.
		- Used for most of the important application layer protocols - HTTP, HTTPS, SSH, etc.
		- Connection-oriented protocol - setup bi-directional channel between two devices.
	- UDP - User Datagram Protocol
		- Faster; doesn't have the TCP overhead for the reliable delivery of data.
**TCP Segments**
![[TCP Segments.png]]
- TCP introduces **Segments** (another container for data). Segments are encapsulated in IP Packets.
- Segments have ..
- .. **SRC & DST port**
	- Allow for unique streams of communication - combination of SRC & DST IP + SRC & DST Port - these 4 values identify a single "conversation" / communications channel.
		- // It's why SSH & HTTPS can exist on the same EC2 instance, and why you can have multiple SSH instances open on the same EC2 instance.
- .. **Sequence Number**
	- Unique.
	- Incremented with each segment that's sent.
	- Can be used for:
		- Error correction.
		- Ordering data.
- .. **Acknowledgment**
	- Every segment transmitted needs to be acknowledged.
- .. **FLAGS 'N' THINGS (\*)***
	- Flags component - 9 bits - allows various controls over the TCP segments & the wider connection.
		- Flags are used to:
			- Close the connection
			- Synchronize sequence numbers
			- data offset
			- reserved space
- TCP **Window** - the # of bytes you're willing to receive between acknowledgements.
	- Once reached, the sender will **pause** until you acknowledge that amount of data. And this is how **flow control** is implemented. Lets the receiver control the rate at which the sender sends data.
		- smaller window = more control
		- larger window = more efficient (because the header of a TCP segment takes up an amount of space; smaller window = more headers are involved)
- **Checksum** - used for error checking.
	- TCP can detect errors and can arrange for retransmission of the data as required.
- **Urgent Pointer**
	- Both sides can use this field to prioritize traffic.
		- Ex: Imagine you have a data transfer app where 99% of transferred data is 'data' and 1% is control traffic. Setting this field could prioritize the control traffic data within the communication.
		- Latency sensitive protocols such as FTP and Telnet, can use this field.
- All of these fields ^ are known as the TCP Header.

## Network Address Translation NAT - PART 1 -2
- NAT is designed to overcome **IPv4 shortages**
	- IPv4 addresses are either publicly routable, or they fall within the private address space of IPv4
	- Publicly routable addresses are assigned by a central agency and regional agencies to ISPs which allocate them to business or consumer end-users.
	- Private addresses, such as those in the 10.0.0.0 range can't be routed over the internet. To give internet access to private devices, we need to use NAT.
- .. also provides some **security benefits**
- Translates **Private** IPv4 addresses to **Public**
- **Static NAT** - **1 private** to **1 (fixed) public address** (IGW)
	- Use when certain, specific private IP addresses need access to the internet, using a public IP, and where these IPs need to be consistent
- **Dynamic NAT** - **1 private** to **1st available Public** (from a Pool)
	- Used when you have fewer public IPs than private IPs & you want to be efficient with how they're used
- Port Address Translation (**PAT**) - **many private** to **1 public** (NATGW)
	- Likely what your home internet router does.
	- PAT a.k.a. "overloading"
	- Uses ports to identify individual devices
- **IPv4 only** ... makes no sense with IPv6

## VLANs TRUNKS & QinQ
**Physical Segment**
![[Physical Segment.png]]
**Physical Segments**
![[Physical Segments.png]]
vLANs are valuable because physical LANs don't scale well.

**Frame Tagging (802.1Q & 802.1AD)**
![[Frame Tagging (802.1Q & 802.1AD).png]]
A standard frame doesn't offer us is any way to isolate devices into different parts (different networks).

**802.1Q** (a.k.a "1Q") is a **standard** which changes the Ethernet Frame format by **adding** an additional 32 bit **802.1Q field**. 0 Signifies no vLan. 1 signifies the Management vLan. The other values (in the range 0 - 4096) can be used as desired by the local network admin. Any 1Q frames can be a member of over 4000 VLANs - you can create separate vLAN in the same L2 physical network.

A broadcast frame, so anything that's destined to all Fs, would only reach other devices which are in the same VLAN. Essentially, it creates over 4000 broadcast domains in the same physical network. You might have a VLAN for CCTV, a VLAN for servers, a VLAN for game testing, a VLAN for guests, and many more.

Imagine you're a large business with many locations around the country. You use vLAN 1337, but your comms provider services another client who also uses vLAN 1337. 802.1AD fixes this problem.

**802.1AD** (a.k.a. **QinQ**) / Provider Bridging / Stacked VLANS - adds another space in the frame for another vLAN field. This is known as the S-TAG (service tag). Your service provider uses this tag to distinguish customers. Once the frame reaches another of your sites over the service provider network, then the S tag is removed and the frame is passed back to you as a standard .1Q frame, with your customer VLAN still tagged. Thus, allowing service providers to enable clients to use vLANs over their networks.

QinQ tends to be used for larger, more complex networks; .1Q is used in smaller networks.
![[VLANS.png]]
With 802.1q, ports in switchers are defined as either access ports or trunk ports. An **access port** generally has **one** specific VLAN ID or VID associated with it. A **trunk** conceptually has **all** VLAN IDs associated with it.

**How broadcast frames work**.
The default behavior for switches is to forward the **broadcast** out of all ports, except the one that it was used for. For switches using VLANs this is slightly different. First it forwards to any other access ports on the same VLAN, but the tagging will be removed. This is important because devices connected to access ports won't always understand 802.1Q, so they expect normal untagged frames. In addition, the switch will forward frames over any trunk ports. A **trunk port** is a **connection** between **two .1Q capable devices**. It forwards all frames and it includes the VLAN tagging. Tagged .1Q frames either get their tagging stripped and sent to access ports with the same VLAN, or they get forwarded across trunk ports with the VLAN tagging intact.

Unicast frames (which go to a single MAC address) will be either forwarded to an access port in the same VLAN that the specific device is on, or if the switch isn't aware of the MAC address of that device in the same VLAN, then it will do a broadcast.

VLANs are how certain things within AWS work, such as public VIFs, private VIFs, and Direct Connect (DX).

**VLANS**
- Create separate L2 network segments
- **Isolated** .. traffic isolation
- .. different customers...
- .. different networks (AWS Direct Connect VPCs)
- Separate broadcast domains
- **802.1Q** (**VLANS**) ... **802.1AD** (nested **QinQ** VLANS)
	- If you see any mention of 802.1Q, then you know that that means VLANs.
	- If you see any mention of VLAN stacking, or provider bridging, or 802.1AD, or QinQ, this means nested VLANs.
		- Having a customer tag and a service tag, allowing you to have vLANs in vLANs.
			- Useful if you want to use VLANs on your internal business network, and then use a service provider to provide wide area network connectivity who also uses VLANs.

## SSL and TLS
SSL and TLS do the same thing. TLS is just newer and more secure.

- Privacy and Data Integrity between client server
- **Privacy** - communications are **encrypted**
- ... **asymmetric** and then **symmetric**
	- Asymmetric - server makes its public key available for clients to encrypt (only the server can decrypt using its private key). Asymmetric encryption allows for trustless encryption, where you don't need to arrange for the transfer of keys over a different secure medium. Computationally heavy.
	- As soon as possible, you should aim to move from asymmetric toward symmetric encryption, and use symmetric encryption for any ongoing encryption requirements (because it's computationally easier).
	- Part of the negotiation process which TLS performs is moving from asymmetric to symmetric encryption.
- **Identity** (server or - client server) verified
	- TLS is capable of full two-way encryption; but generally, it's the client verifying the server's identity (using using public key cryptography).
- **Reliable** connection - protect against alteration
**SSL and TLS**
![[SSL and TLS.png]]
First, cipher suites are agreed, authentication happens, and then keys are exchanged.

A **cipher suite** is a set of protocols used by TLS. This includes a key exchange algorithm, a bulk encryption algorithm, and a message authentication algorithm (MAC). There are different versions and types. Certain groups of versions and types are known as a cipher suite. To communicate, the client and server have to agree a cipher suite to use.

## Jumbo Frames & MTU
The maximum Ethernet v2 frame size is 1500 bytes. Anything bigger than this is classified as a jumbo frame. But, when most people refer to jumbo frames, they mean a frame with a maximum size of 9000 bytes.

**Jumbo Frames & MTU**
![[Jumbo Frames & MTU.png]]
Jumbo Frames are more efficient with demanding network applications.

Considerations:
Since Ethernet, which is layer 2, generally carries higher level data inside the frames. If you're communicating between two devices, using IP for example, then you need to make sure that every step supports the same size of jumbo frames. Because if part of your **communication pathway** isn't **compatible** with jumbo frames, you could have fragmentation.

**Where Jumbo Frames are & aren't supported in AWS**
- No - Traffic outside of a single VPC
- No - Traffic over an inter-region VPC peering connection
	- Yes - same region peering
- No - Traffic over VPN connections
- No - Traffic over an internet gateway
- Yes - Direct Connect
- Yes - TGW ... up to 8500

## Encryption 101 - Part 1 & 2
- Encryption Approaches
- Concepts
- Symmetric
- Asymmetric
- Signing
- Steganography
![[Encryption Approaches.png]]
Encryption **At Rest** - designed to protect against physical theft and physical tampering. One entity involved.
Encryption **In Transit** - Multiple Individuals or systems involved.

**Encryption Concepts**
- Plaintext - unencrypted data (not *text*)
	- Document, image, app
- Algorithm
	- Blowfish, AES, RC4, DES, RC5, and RC6
- Key
	- A password
- Ciphertext - encrypted data (not always text)
Encryption: Plaintext + Algorithm + Key = Ciphertext
Decryption: Ciphertext + Key = Plaintext

**Symmetric Encryption**
![[Symmetric Encryption.png]]
Symmetric encryption is great for things like local file encryption or disk encryption on laptops, but not so useful for situations where the data needs to be transferred between two remote parties, because arranging the **transit** of the **key** is the problem.

**Asymmetric Encryption**
![[Asymmetric Encryption.png]]
Used by PGP (a popular email and file encryption system), SSL or TLS, SSH. Computationally more difficult than symmetric. Many processes use asymmetric encryption to communicate a symmetric key, then this symmetric key is used for communication between those two parties from that point onward.

Signing - generally used to verify identity. The Public key can be used to verify that a document was encrypted by the other party's private key. Key signing is generally used for ID verification and certain logon systems.

![[Steganography.png]]
The problem with encryption is that if you use it it's obvious that you've used it. Ex: no deniability in the case government forces you to decrypt something.
Steganography - allows you to embed data in other data. Example: specifically modifya few pixels in an image; embed an encrypted document in the image. The receiving party can use steganography to retrieve the encrypted document if they know the exact pixels.

## Envelope Encryption
You encrypt something with a key, and then you encrypt that key again with another key.

**Envelope Encryption - Encryption**
![[Envelope Encryption - Encryption.png]]
KMS manages KMS keys, which in a general sense are called **key encryption keys** (**KEK**), because they're only used to encrypt data less than 4KB in size, which generally means other encryption keys.

Data encryption keys (**DEKs**) are created by KMS but not managed by KMS. That's the responsibility of the system or person generating them. You get 2 copies of a DEK - a plaintext version, and an encrypted version (a.k.a. a "wrapped" version). The plaintext version can be used to encrypt or decrypt data. The encrypted version is encrypted using the KMS key (the KEK), which was picked when creating it and can only be decrypted using that KEK.

S3 example: Plaintext DEK used to encrypt object. Discarded. Encrypted DEK is stored with the object. Every encrypted object uses a unique key, so if a key is leaked (and somehow decrypted), it only impacts one object.

Generically, key encryption keys, can be asymmetric or symmetric, but in AWS (KMS), the key encryption keys (KMS keys) symmetric, because it's faster. The thing to understand is how using a wrapped key architecture allows us to manage keys at scale. KMS as a service only has 1 KEK to manage. It can be used to generate millions of DEKs, each one used to uniquely encrypt a single object.

Also, the admin of the service can manage the storage of the object and the keys but can't decrypt either without permissions on the KEK (this uses KMS which has its own isolated permissions). The keys managed by KMS never leave KMS.
**Envelope Encryption - Decryption**
![[Envelope Encryption - Decryption.png]]
Envelope Encryption - Considerations
- **Asymmetric** keys are **flexible** (public part is .. public)
	- but they're slow
- **Symmetric** keys are **fast** .. but difficult to securely move
- Envelope encryption can be best of both (if you use Asymmetric KEKs)
- **Symmetric** keys are used for encrypt/decrypt (speed)
	- secured with **Asymmetric** keys (normally) for flexibility
- In either case...**less data** TO/FROM the key storage service (i.e KMS)
- **Unique DEK's** can be used per object
	- limits blast radius of loss or exposure

The devices use **secure enclaves** internally, which makes it almost impossible to gain access to the internal key material through direct physical means. Many smartphones today come with a similar cut-down version of this. It stores your biometric information to keep it isolated from badly behaving software on your smartphone.

Examples of the types of situations where you might use a HSM, and this is a very small subset, there are many others, but you might use it to offload processing for SSL or TLS onto the HSM. So you gain the benefit of secure key management and the performance boost via offloading.

You might also use HSM's for **signing** certificates for a private **PKI** infrastructure that you have within your business. This just provides a way that you can securely manage the key material used to sign your certificates.

## Digital Signatures
You need to understand this to understand areas of IT like DNSSEC or SSL certs.
![[Public Key Cryptography Refresher.png]]

**Digital Signatures**
- Verifies **INTEGRITY** (**WHAT**) & **AUTHENTICITY** (**WHO**)
- **HASH** of the data is taken, original data remains unaltered (**integrity**)
- This allows normal use without worrying about hashing/keys

# DNS & DNSSEC (2.4.x)
## DNS 1 What does DNS do
![[DNS 101 - What it does.png]]
DNS links names to IP addresses. Many large-scale failures on the internet are caused by either failed DNS or badly implemented DNS infrastructure.

## DNS 2 - Why does DNS need a complex architecture?
Why not one server?
- **Risk** problem
- **Scaling** problem
- Data **Volume** problem
	- ~ 341 million domains; each domain = many records.
	- Updates, consistency.
	- A complete DNS dataset is a huge database.
		- It's a huge global scale monolith. 
		- This should be avoided.
		- We need to delegate control over certain parts of the DNS dataset to other organizations so that they can manage it.

**DNS 101 - Key Terms**
- DNS **Zone** .. a database e.g. \*.netflix.com containing records
- **ZoneFile** .. the "**file**" storing the **zone** on disk
- **Name Server (NS)** .. a DNS server which hosts 1 or more **Zones** .. and stores 1 or more **ZoneFiIes**
- **Authoritative** .. contains real/genuine records (boss)
	- There are one or more name servers which can give authoritative answers for www.netflix.com
- Non-Authoritative/**cached** ... copies of records/**zones** stored elsewhere to **speed things up**
	- Your local router or ISP might be able to provide a non-authoritative answer for learn.cantrol.io or youtube.com because you've visited those sites before.
**DNS 101 - Hierarchical Design**
![[DNS 101 - Hierarchical Design.png]]
DNS starts with the **DNS root**. This is a zone like any other part of DNS. This zone is hosted on DNS **name servers** also just like any other part of DNS. The DNS root zone runs on the DNS root servers. The only special element of the root zone is that it's the point that every DNS client knows about and trusts. There are **13 root server** IP addresses which host the **root zone**. These IP addresses are **distributed geographically**, and the **hardware** is managed by independent organizations. The Internet Corporation for Assigned Names and Numbers, or **ICANN**, operates one of the 13 IP addresses which host the root zone. Others include NASA, the University of Maryland, and VeriSign. These organizations manage the hardware for the 13 DNS root server IP addresses. In reality, each of these 13 IP addresses represents many different servers using any cast IP addresses. But from DNS's perspective, there are 13 root server IP addresses.

The **root zone** (a database) is managed by the Internet Assigned Numbers Office (**IANA**). They're responsible for the **contents** of the root zone. Management of the root zone and management of the root servers which host the root zone is different. The root zone doesn't store that much data. What it does store is critical to how DNS functions, but there isn't that much data. The root zone contains high-level information on the **top-level domains**, or **TLDs**. There are **two** types of TLDs, **generic** TLDs such as .com, and **country code-specific** ones such as .uk and .au. IANA delegates the management of these TLDs to other organizations known as **registries**. The job of the root zone is just to point at these TLD registries. IANA delegates management of the .com TLD to VeriSign (the registry). So in the root zone, there's an entry for .com pointing at the name servers which belong to VeriSign. .Com is just one TLD. This process where the root zone points at the name servers hosting the TLD zones, it establishes a **chain of trust** within DNS.

VeriSign will operate some name servers hosting the .com TLD zone. The TLD only contains this high-level information on domains within it, for example, netflix.com. It doesn't contain detailed records within these domains within these domains, for example, www.netflix.com; all the TLD contains is information on the domain itself. For this example, the TLD would have a set of records which point at the **name servers** which host the netflix.com zone (etc for every other domain in the .com zone ... twitter.com, etc.). These name servers, because they're pointed at from the layer above, are **authoritative for the domains** (the zones which they host).

Each layer of DNS from the root, the TLDs, and the domain name servers, they store only a small part of the DNS database. The root zone knows which name servers the .com zone is on. The .com zone knows which name servers netflix.com zone is on and the netflix.com zone contains records for the netflix.com domain and can answer queries.

## DNS 3 - How DNS actually works walking the tree
The job of **DNS** is to help you **locate** and **get a query response** from the **authoritative zone** which hosts the DNS **record(s) you need** (e.g. "What is the IP for netflix.com")
![[DNS 101 - Walking the tree.png]]
A **resolver** is a type of DNS server, often running on a home router or within an internet provider, and it will do the query on our behalf. It also has a local cache. It might be able to return a non-authoritative answer. The only server which can give an authoritative answer is the one which is pointed at for a given domain from the TLD zone of that domain.
![[DNS 101 - Walking the tree - The tech.png]]

## DNS 4 - What happens when a domain is registered

**DNS hosting providers** operate DNS name servers which can host DNS zones. They allow you to manage the content of those zones. ## DNSSEC 1 - Why do we need DNSSEC
DNSSEC is a secure add-on for DNS. It provides additional functionality.

- Data **Origin Authentication**
	- **this data** comes from **this zone**
- Data **Integrity Protection**
	- this data **hasn't been modified in transit**
- DNS CHAIN OF TRUST ... root zone => records
	- Does this in a cryptographically verifiable way.
		- Where DNS has some major security holes, DNSSEC uses public key cryptography to secure itself. In a similar way to how HTTPS and certificates secure the HTTP protocol. It means that at each stage you can trust if a child zone has the trust of a parent zone. And, you can verify that the data contained within that zone hasn't been compromised.

**DNSSEC adds, doesn't replace**
![[DNSSEC adds, doesn't replace.png]]
The DNS only device will only receive DNS results. DNSSEC achieves backward compatibility. A DNSSEC capable device can do more than normal DNS. It still makes queries and gets back DNS results, but it also gets back DNSSEC results. It can use these DNSSEC results to validate the DNS results. DNSSEC doesn't correct anything. It only allows you to validate if something is genuinely from a certain source or not. And if it's been altered or not. It doesn't show you what the result should be.

**DNS Disrupted**
![[DNS Disrupted.png]]
DNS Resolver walks the tree, but a bad actor can poison its cache (spoofing a response from an authoritative NS while the resolver is in the process of walking a tree).

![[DNS.png]]
Without DNSSEC, we can't trust these responses.
![[DNSSEC.png]]
DNSSEC returns both DNS & DNSSEC results. We also have an RRSIG (a DNSSEC resource type) which is basically a digital signature of the record that it corresponds to. Can be used to validate the normal DNS data that's stored within this zone.

## DNSSEC 2 - How DNSSEC Works within a Zone
**DNSSEC - RRSET**
![[DNSSEC - RRSET.png]]
**RRSET** - Resource Record Set. Any records of the same name and the same type.
DNSSEC doesn't validate individual resource records - it validates RR Sets.
**DNSSEC - RRSIG & Zone Signing Key (ZSK)**
![[DNSSEC - RRSIG & Zone Signing Key (ZSK).png]]
A bad actor could change one of the records in the RR Set and (for example,) redirect email. DNSSEC prevents this with two features:
- RRSIG
	- stores a **digital signature** of an **RR Set** using public and private pairs of keys
		- Known as the Zone Signing Key (**ZSK**).
			- The private part of the key is kept offline, outside the zone.
	- RR Set (plain text) + signing process (standard cryptographic process) + ZSK private key = signature
	- If the RRSET changes, the RRSIG has to be regenerated in order to be valid.
		- so, you can tell if anything has changed without the approval of the person controlling the private ZSK
	- Use the public part of the ZSK to verify RSIGs
**DNSSEC - DNSKEY**
![[DNSSEC - DNSKEY.png]]
In a zone, we have the MX RR Set, the MX RR Sig, and the DNSKEY record.
- **DNSKEY records** can store ..
	- .. the **public** key for the **ZSK** (used to verify any RR Sigs in the zone)
	- .. the Key Signing Key (**KSK**)

The DNS resolver can take the RRSET (plain text) + RRSIG and the DNSKEY record, can verify that both the RRSIG matches the RRSET and the signature was generated using the private part of the ZSK. The result of this is that our DNSSEC capable resolver at the bottom can verify the RRSET is valid and hasn't been compromised. This is all assuming that we trust the DNSKEY; specifically, the ZSK - we trust that only the zone admin has the private part of the key & that it's the correct ZSK. Example: a photo ID only proves someone's identity if you trust the photo ID is real and it was created by a genuine authority entity; which is why fake IDs are a problem. This isn't a problem with DNSSEC because we have a **chain** of verifiable **trust** all the way to the DNS root. The DNSKEY record also requires a signature. This means a matching RRSIG record to validate that it hasn't been changed.

The **DNS Key Records** are **signed** with the **KSK** (KSK is used for signing keys - not anything in the zone). The **ZSK** is used for **signing** anything in the **zone** (RRSIG records).

**DNSSEC - 2 Keys?!?! - Key Signing Key (partial)**
![[DNSSEC - 2 Keys - Key Signing Key.png]]
If this was all that we had (just the ZSK), we couldn't trust it. Somebody could swap out the DNSKEY record, putting a new public key in there, use the private part of that fake key to regenerate a fake RRSIG, adjust the RRSET and take over email for this domain.
We need a way of ensuring the ZSK is trusted.
If we didn't have some kind of trust chain, we would need to manually trust every zone within DNS, and that would defeat the purpose of having a globally distributed system.

**DNSSEC - 2 Keys?!?! - Key Signing Key**
![[DNSSEC - 2 Keys - Key Signing Key2.png]]
This zone (icann.org) is cryptographically linked to the parent zone. If we used a single key (the ZSK), that would work, but if we wanted to change the ZSK, we would have to involve the .org parent zone. Best practice is that we want to be cycling keys fairly often, and doing that where it also requires updates up the chain would become inefficient. So, we have this new key pair, the Key Signing Key, or **KSK**. There's a private part and a public part. The private part is used to sign DNS Key Record Sets, which creates an RRSIG of the DNS key.

This makes it easy to change the ZSK used for a zone. We just have to **regenerate**, all of the **RRSIG records**, **update** the **DNS Key Record Set**, and then **regenerate** the **RRSIG** of the **DNS Key Record Set**, using the **private KSK**. All of this is inside our zone only. It doesn't involve the parent zone in any way. We store the public part of the KSK in the DNS Key Record Set. But now we have a new problem, how can we trust the KSK? It's referenced from the parent zone (.org). Remember, the DNS Key Record Set stores both the ZSK and the KSK. This is the main point of trust for the zone. Because the parent zone references our zone's public KSK, we can trust our zone's KSK (assuming we trust the .org parent zone). This KSK signs our ZSK. The ZSK signs all of the RR Sets to create RRSIGs. We have a chain of trust created between 2 different layers of DNS. Specifically, DNSSEC.

By now, you should understand:
- how DNSSEC validates things within a single zone
- How it uses RRSIGs to validate RRSETs
- How it uses the DNS Key records to get the public keys to do that validation using the ZSK
- How a KSK is used to create an RRSIG of the DNS Key, which allows the validation of that DNS Key record
- How the parent domain or parent zone trusts the public KSK of the child domain or zone
	- // we don't know how this trust occurs yet; that's next lesson
- Why two different keys are needed
	- Using a ZSK for signing within a zone and a KSK for signing that key. That allows an admin split. The Key Signing Key can be referenced from the parent zone while the ZSK is used exclusively within the zone. This means a ZSK can be changed without requiring any changes to the parent zone.
So what position does that put us in? With this functionality using DNSSEC, what have we gained in the way of additional security?
- We can now verify the integrity of data within this specific DNS zone
	- So we've eliminated the DNS cache poisoning example
		- Assuming we trust the KSK ..
		- Assuming the KSK hasn't been changed as part of an exploit ..
		- .. then we can trust all of the information contained within a zone

## DNSSEC 3 - DNSSEC Chain of Trust
DS records - delegated signer records. How DNSSEC creates a chain of trust between parent and child.
**DNSSEC - DS Record**
![[DNSSEC - DS Record.png]]
All that matters when we move up a level are the ICANN.org **name servers** for normal DNS, and the **public KSK** for DNSSEC.
We will discuss how the .org zone **delegates** to the ICANN.org zone for ICANN.org, and how **DNSSEC delegates trust** via the **trust chain** to this child zone.

We start with the delegation for DNS - in the form of Name Server **(NS)** Resource **Records** which point at the **name servers** hosting the ICANN.org zone. This just integrates the ICANN.org domain into the DNS infrastructure. It doesn't provide any of the verification which we're looking for from DNSSEC. There's a matching RR SIG for this RR set, which verifies these records, but for the parent to child zone trust, we need more. The .org zone needs to explicitly state that it trusts the ICANN.org child zone. And this is done using a **delegated signer record set** (**DS Record** set). This **stores a hash** of the child domain's public KSK in this record in the parent zone. Since the hash is one way, and since they're unique, adding this record shows that the parent zone trusts the child zone. So at this point, the .org zone is confirming its trust of the ICANN.org KSK via this record set.

Like everything else relating to DNSSEC, we need to provide a mechanism to **validate** this **DS record set**. This means a matching RRSIG DS (a digital signature of the DS RR set) made using the .org zone's private ZSK. At this point, all of the records can be validated within .org, and we can confirm the trust of ICANN.org.

Now we just need to add the records which store the .org zone's public keys. This means a DNS key record set containing the .org public ZSK and KSK. These are used to validate RR SIGs in this zone. This DNS key RR Set needs a matching RR SIG, which is created by signing the DNS key RR SET with the zone's KSK. At this point, if you trust the .org zone's public KSK, then you trust everything in the .org zone, including the trust delegation to the ICANN.org child zone.

How do we trust this? In the same way that the child ICANN.org zone was trusted by the .org zone. Trust is given from the parent zone, which in this case is the root zone. This is the process how a parent zone trusts a child via the DS record set, which contains a hash of the child zone's KSK.

**DNSSEC - Validation Flow**
![[DNSSEC - Validation Flow.png]]
DNSSEC validation flow - how we build this chain of trust between the different levels of the DNS hierarchy.
The **trust** between the levels from child to parent is created via **public KSKs** and the **DS record sets** in the parent zone.
So the **ICANN.org** zone, has a **public KSK**. The **.org** zone **validates** this by having a **DS record** and storing a **hash** of that **KSK** in that record set. The .org zone has its own **KSK** and is trusted because a **hash** of this key is stored in the corresponding **DS record** in the **root** zone.

At the DNS root zone level, we hit a problem because there's no parent zone to provide this trust. The root zone has a public KSK; this and the corresponding private root KSK are **explicitly trusted**. We will later explain the key signing ceremony, but for now, just take it as fact that the root key signing keys are trusted explicitly. They're known as a **trust anchor**. Something that just is. Every DNSSEC capable client or resolver by default trusts these keys. Because we trust the root KSKs, it means that a DNSSEC capable resolver can follow this chain from root through to the DNS record set.

The root zone **KSK** has signed the root zone **ZSK**. This has signed the .org **DS record** in the root zone (this can now be cryptographically validated). This record matches the **public KSK** in the **.org** zone (this can be cryptographically validated). In the .org zone, the **KSK** has signed the **ZSK**, and this has signed **record sets**, including the **DS record** set for icann.org inside the .org zone (this also (signing the DS Record) can be validated). This contains a hash of the public KSK for the ICANN.org zone (lastly, this can be cryptographically validated). This is how you build a chain of trust from the root through to record sets.

We start with the trust anchor that's created during the key signing ceremony. Then, at every level of the DNS hierarchy, by using DS record sets, we create a hash of the KSK of the child domain. This creates the trust from parent to child. We follow that hierarchical trust all of the way down to the actual record sets. This is how we can trust the contents of all of the TLDs. This is how the TLDs trust any domain zones. And this is how we can trust the contents of any record sets within those domain zones. All of this can be cryptographically validated at every step. This is one of the major benefits that DNSSEC provides.

## DNSSEC 4 - DNSSEC Root Signing Ceremony
This ceremony is all about controlling the keys to the internet, more specifically, the trust anchor of the DNS system. It's one of the most important meetings which occur in the technical space. Pretty much everything that you use on the internet is enabled by the technical act which occurs within this ceremony.

**DNSSEC - The TRUST Anchor**
![[DNSSEC - The TRUST Anchor.png]]
How can the root zone be a trust anchor? Locked away within two secure locations, one in California and another in Virginia, is what amounts to the keys of the internet. The private DNS root KSK. It's impossible to overstate how important these set of keys are to the internet. They rarely change and the trust in them is hard coded into all DNSSEC clients. With them, you can define what's valid on the DNSSEC root zone. And because of this, every child top level domain, every child zone inside those, and every DNS record. These are locked away, protected, and never exposed. And they use redundant hardware security modules also redundant across physical locations. Access to the private keys is controlled via the fact that HSMs are used. You can only use the HSMs in tightly controlled ways. The keys never leave those HSMs. Those HSMs never leave those locations. You can only use them within those locations if you have the right group of people. And people can only get into those locations after going through a rigorous, multi-stage ID process.

We all know the public part of this key. It's part of the DNS key record set within the root zone along with the public ZSK. To restate this, every DNSSEC client and resolver on the planet explicitly trusts this KSK. If we have this public root zone KSK, we can verify anything signed by the private key - the one that's locked away within the HSMs. Because the security of the private root key signing key is so tight, it's not practical to use constantly. So, there's another key pair which controls the security of the DNS root zone. This is known as the root zone ZSK.

The whole function of this massively controlled ceremony is to take the root zone ZSK, take this into the ceremony, sign it with the private root zone KSK under these hugely tightly controlled conditions and then produce as an output the root zone RRSIG DNS key. This single record is why DNS is trusted from this level down through the TLDs, into the domain zones - because the root zone is trusted via this signing process.
// Details on the DNSSEC Root Signing Ceremony - // [The DNSSEC Root Signing Ceremony | Cloudflare](https://www.cloudflare.com/learning/dns/dnssec/root-signing-ceremony/). These ceremonies are public and recorded.

**DNSSEC - The Signing Ceremony**
![[DNSSEC - The Signing Ceremony.png]]
The signing ceremony takes place in one of two secure locations. There are a few key sets of people involved - ceremony administrator, an internal witness, the credential safe controller, the hardware safe controller, and then crypto officer 1, crypto officer 2, and crypto officer 3. There are a total of 14 of these crypto officers. 7 of them are affiliated with each of the locations, and at least 3 are required to attend for the process to work. Logistically, dates and times are picked when 4 to 5 are available to ensure some level of resilience. The most important part of the whole process, hardware-wise, is the HSM - the hardware which contains the root zone private KSK. This device is protected, and can only be interacted with via the ceremony laptop, which is connected to the HSM over ethernet. This is only operated by the ceremony administrator. The laptop has no battery and no storage. It's designed to be stateless, and only used to perform the ceremony, and not store any data afterwards. The HSM device can only be used when crypto officers use their allocated cards. What's being signed are the public KSKs and ZSKs (actually, a pack of them to allow for rotation between this ceremony date and the next). The HSM device via the ceremony laptop then outputs the signatures for these keys, which become the DNS key RRSIG records for the DNS root zone. This process happens every 3 months. It's generally broadcast. Notes of the process are available. And it's publicly audited. The level of security procedure which goes into ensuring that groups of human participants can't collude and corrupt the process is extreme.

Take the **Root KSK** that **everything trusts**. **Sign Root ZSKs** which can be used operationally (used to sign individual resource record sets within the root zone).

It's that public and private zone signing key pair which is then used to create the chain of trust, which allows trust in top level domains. And then those top level domains can pass that trust on to domains, and then in domains that trust can be passed to individual resource record sets. And this all has to happen because we have nothing above the root key signing keys in DNS. They're a trust anchor. Nothing makes us trust them other than the trust itself. And this ceremony ensures that it's almost impossible to corrupt that trust.

# Backups & DR (2.6.x)
## Recovery Point Objective (RPO) & Recovery Time Objective (RTO)
RPO - generally expressed in minutes or hours. An RPO of 6 hours means an org can't tolerate more than 6 hours of data loss when recovering from a disaster.

Understanding how data can be lost during disaster recovery scenarios is key to understanding how to implement a given RPO requirement.

**Recovery Point Objective (RPO)**
![[Recovery Point Objective (RPO).png]]
Successful backup are known as **recovery points**. In the case of full backups, each successful backup is one of a recovery point. If you use full backups and incremental backups, It's possible that to restore a single incremental backup, i.e. to use that one recovery point, you'll need the most recent full backup and every incremental backup between that full and the most recent OK incremental backup. So, it's possible a recovery point will need more than 1 backup. As a general rule, you need to make sure that **backups** occur **as often or more often** than the **RPO value**. To cope with random backup failure, generally, you'll want to make sure backups occur more frequently than required.

Lower RPOs - more frequent backups, higher costs (resources and power, media, licensing, management overhead, etc).
**Recovery Time Objective (RTO)**
![[Recovery Time Objective (RTO).png]]
Recovery Time Objective (**RTO**) - the maximum tolerable length of time that a system can be down after a failure or disaster occurs.
Recovery time of a system begins at the moment of the failure. It ends not when the issue is fixed but when the system is handed back to the business in a fully tested state. RTO isn't just about technical things. The biggest impacts on RTOs are things which as a technical person you might not always identify.
Some of the considerations which might impact the ability of this animal rescues operation team to meet this 13 hour RTO directive:
- To recover a system you need to know that that system has failed
	- The ability **to recover** only really starts when you're made **aware** that the system has failed
	- How long until the operations teams knows there's an issue? Is there monitoring? Is it reliable (because too many false positives mean people will ignore outage notifications)? How will the monitoring system notify staff? Will it wake sleeping staff? Will it be the correct staff (those empowered to begin a recovery process)? This often adds lag onto the start of the process.
		- Don't underestimate the importance of effective monitoring and notification systems. Your process must be planned & configured in advance.
		- Waking up a junior operations person who has no ability to make decisions or no ability to wake up senior staff members is useless.
- Step 2: Investigate the issue. Somebody needs time to diagnose the issue and make the final decision to perform a restore if required.
- Assuming that we are going to do a restore ..
	- Who & how will this happen? What backups do we have? Where are they? Are they accessible? Is the process documented? Are the people available, awake, aware?
	- Stressful situations late at night without your team around you is when mistakes happen.
- Step 3: Where are we restoring to?
	- Do we have a spare? Do we need to order another server? Are we using physical or virtual servers? Are we even forced to use a secondary disaster recovery site, because not only is the server on fire, but also is the server room?
	- A badly documented process to restore servers, or a slow notification system, might add additional hours.
	- Having to order new server hardware could add days to a recovery time.
- Step 4: Business **Testing**, User **Testing**, Final **Handover**
	- This must be done before you consider recovery to be complete.
This entire process, end to end, is what recovery is. If a business has a 13-hour RTO, you need to make sure that all of this process, in its entirety, fits into that 13 hours.

- **RPO** - How much data (**MAX TIME**) a business can lose
	- .. worst case = **time between successful backups**
	- .. more **frequent** backups = more **cost** = **lower RPO**
- **RTO** - How long **restore time** a business can tolerate
	- .. end to end from identification through to handover
- Reduce via .. **planning**, **monitoring**, **notification**, process, **spare hardware**, training, more **efficient** systems (virtual or AWS)
- Different **businesses** & **systems** will have different **RPO** & **RTO** values
- Aim for **Goldilocks** ... as close to the **TRUE** business requirements as possible

It's often the case that a business isn't aware of appropriate RPO and RTO values. One of the core duties of a solutions architect is to work with the business and understand which systems are critical and which can tolerate more data loss or recovery outages. By appropriately designing systems to match the true business requirements, you can deliver a system which meets those requirements in a cost-effective way.

# Cloud Computing 101 (2.8.x)
## What is Cloud Computing
A system needs a set of five characteristics to be considered cloud.

Source: The National Institute of Standards and Technology (NIST), (part of the US Department of Commerce). NIST creates standards documents, and one such document is named Special Publication 800-145. 
// [SP 800-145, The NIST Definition of Cloud Computing | CSRC](https://csrc.nist.gov/pubs/sp/800/145/final)
The document defines five essential characteristics, which a system needs to meet in order to be cloud

- On-Demand Self-Service
	- "... can provision capabilities as needed **without requiring human interaction**"
		- VMs, storage, DB, networking - web interface or API (CLI) in self written apps can provision resources without leasing with support team, on demand.
- Broad Network Access
	- "Capabilities are available over the network and accessed through standard mechanisms..."
		- Capabilities are available over a standard network using standard mechanisms (HTTP, HTTPS, SSH, RdP, VPN).
			- If you need to go to a vendor, a site, or need a private network link, it's probably not cloud.
- Resource Pooling
	- "There is a sense of **location independence** .. no **control** or **knowledge** over the exact **location** of the resources"
	- "Resources are **pooled** to serve multiple consumers using a **multi-tenant model**"
	- This characteristic is about abstraction and economies of scale.
	- // IT managers have moved from viewing hardware as being valuable to the business to apps & services as being valuable to the business.
- Rapid Elasticity
	- "Capabilities can be **elastically provisioned** and **released** to scale **rapidly** outward and inward with demand."
	- "To the consumer, the capabilities available for provisioning often **appear** to be **unlimited**"
	- System costs increase & decrease with demand
	- // (opinion) - most important aspect of cloud
- Measured Service
	- "Resource usage can be **monitored**, **controlled**, **reported** ... AND **BILLED**"
	- // Non-cloud: used CAPEX - paid for hardware in advance. In the beginning, you had more capacity than needed (so, $ was wasted). Demand grew over time. Eventually you buy more servers to cope with demand. If you did that too slowly, you had performance issues or failures.

## Public vs Private vs Multi vs Hybrid Cloud
**Public vs Private vs Multi vs Hybrid**
![[Public vs Private vs Multi vs Hybrid.png]]
- **Public Cloud** = using **1** public cloud
- **Multi-cloud** - using **more than 1** public cloud
	- // I would personally stay away from any products or vendors who attempt to provide a so-called single management window ("single plane of glass")
		- It is possible to manage multiple cloud platforms as one single environment, but you're now relying on the lowest common feature set, so you're losing what makes each vendor special and unique. Ex: Provisioning a VM in Azure & AWS - I would need to assume a feature set which is available to both.
	- // Abstraction / 3rd party tools NOT recommended
	- // (opinion) - the best multi-cloud environments use part of your infrastructure in one cloud environment and part in the other.
- **Private Cloud** - using on-premises ***real*** cloud
	- Dedicated to your business
	- AWS Outposts, Azure Stack, Google Anthos
	- There is a massive difference between having on-premises infrastructure, such as VMware, Hyper-V, or Zen Server, versus having a private cloud.
		- A private cloud, still needs to meet the five essential characteristics of cloud computing, which most traditional infrastructure platforms don't.
- **Hybrid Cloud** - using **private** cloud and **public** cloud, cooperating together as a single environment.
	- It's **not** hybrid cloud if you just utilize a public environment such as AWS together with your on-premises equipment.
	- To add confusion, you might hear people use the term **hybrid environment**. And in my experience, people use hybrid environment to refer to the idea of **public cloud** used together with existing **on-premises** infrastructure.
	- With true hybrid cloud, you get to use the same tooling, the same interfaces, the same processes to interact with both the public and private components.

## Cloud Service Models IAAS PAAS SAAS
**Infrastructure Stack**
![[Infrastructure Stack.png]]
When you deploy an application anywhere, it uses what's known as an **infrastructure stack** - a collection of things which that application needs, all stacked onto each other.
- Parts you manage
- Parts managed by the **vendor**
- Units of consumption - what you pay for. What you're responsible for, from that point up the stack.

**On-Premises vs DC Hosted**
![[On-Premises vs DC Hosted.png]]
(pre-cloud) Data Center Hosting - your unit of consumption was rack space. All of the service models we use today are just evolutions of this type of model, where more parts of the stack are handed off to a vendor. The costs, risks, and amount of flexibility you have change.

**On-Prem vs DC Hosted vs IaaS vs PaaS vs SaaS**
![[On-Prem vs DC Hosted vs IaaS vs PaaS vs SaaS.png]]
- **IaaS** - you generally pay a per second, per minute, or per hour fee for the virtual machine. You lose a little flexibility (must consume VM sizes and capabilities the provider allows), but there is substantial cost reduction.
- **PaaS** - your unit of consumption is the runtime or the runtime environment.
- **SaaS** - you consume the application. You have no exposure to anything else
	- Examples: Netflix, Dropbox, Office 365, Flickr, Google Mail
		- Businesses consume SaaS products because they are standard known services. Email is email.
