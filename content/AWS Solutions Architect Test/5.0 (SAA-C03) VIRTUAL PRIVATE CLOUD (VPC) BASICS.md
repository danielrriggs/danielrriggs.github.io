## VPC Sizing and Structure - PART 1 & 2
How to design an IP plan for a business.

When creating a VPC, one of the first things you'll need to decide on is the IP range that the VPC will use - the VPC CIDR. Even if that range is made up of multiple smaller ranges, you need to think about this stuff in advance.
Deciding on an IP plan and VPC structure in advance is one of the most critically important things you will do as a solutions architect, because it's not easy to change later, and it will cause you a world of pain if you don't get it right.

Considerations:
- What **size** should the VPC be?
	- This influences how many services can fit inside the VPC, occupying its space.
- Are there any Networks **we can't use**
	- Overlapping (duplicate) ranges makes network communication difficult.
- Be mindful of ranges used in other VPC's, Clouds, On-premises networks, Partners & Vendors
	- Try to avoid ranges which other parties use which you might need to interact with. When in doubt, assume the worst.
	- Try to predict the **future**
- VPC **Structure** - Tiers & Resiliency (Availability) Zones
	- For a given IP range we allocate to a VPC, it'll need to be broken down further. Every IT network has tiers - web tier, application tier, and database tier are 3 common examples; there are more. Tiers separate application components & allow different security to be applied. Modern IT systems have different resiliency zones, known as Availability Zones in AWS. Networks are often split. Parts of that network are assigned to each of these zones.

There is a limit on VPC sizing in AWS

**How Many AZs?**
So the first decision point that you need to think about is **how many availability zones** your VPCs, will use. This decision impacts **high availability** and **resilience** (some regions have 3 AZs, some have more).
 I always start with **three** as my default. Why? Because it will work in almost any region. But I also always add a **spare** to accommodate growth. This means, as a minimum, **4 AZs**. That means that we have to at least split the VPC into at least four smaller networks. So if we started with a slash 16, we would now have four slash 18s.

**Tiers**
As well as the availability zones inside the VPC. We also have tiers. And tiers are for different types of infrastructure that are running inside that VPC. We might have a **web** tier, an **application** tier, a **database** tier. That makes three. And you should always add **buffer**. So my default is to start with four tiers. Web, application, database, and a spare.
If you only used one availability zone, then each tier would need its own subnet. Meaning four subnets in total. But we also have four AZs. And since we want to take full advantage of the resiliency provided by these AZs, we need the same base networking duplicated in each availability zone. So each tier has its own subnet in each availability zone. Four web subnets, four app subnets, four database subnets, and four spares. For a total of **16 subnets**.

So if we chose a slash 16 for the VPC, that would mean that each of the 16 subnets would need to fit into that slash 16. So a slash 16 VPC split into 16 subnets results in 16 smaller network ranges. Each of which is a subnet. Each of which is a slash 20. Remember, each time the prefix is increased, from 16 to 17 it creates two networks. From 16 to 18 it creates four. From 16 to 19 it creates eight. And from 16 to 20 it creates 16 smaller networks. Now that we know that we need 16 subnets, we could start with a slash 17 VPC. And then each subnet would be a slash 21. Or we could start with a slash 18 VPC. And then each subnet would be a slash 22. And so on. Now that you know the number of subnets, and because of that, the size of the subnets in relation to the VPC prefix size, picking the size of the VPC is all about how much capacity you need. Whatever prefix you pick for the VPC, the subnets will be four steps away.

**Custom VPCs**
- Regional Service - All AZS in the region
	- A VPC is created in a region, and it operates from all of the AZs in that region
- Isolated Network
- Nothing **IN** or **OUT** without explicit configuration
	- It's a network boundary, and it provides an isolated blast radius - if one resource or a set of resources are exploited, the impact is limited to that VPC or anything that you have connected to it.
- Flexible configuration - simple or multi-tier
- Hybrid Networking - allow you to connect to other cloud & on-premises
- **Default** or **Dedicated Tenancy**!
	- This controls whether the resources created inside the VPC are provisioned on shared hardware or dedicated hardware.
	- If you pick default, then you can choose on a per-resource basis later on when you provision resources. If you pick **dedicated** tenancy at a VPC level, then that's locked in. **Be really careful with this option!** Any resources that you create inside that VPC have to be on dedicated hardware. Dedicated tenancy comes at a cost premium. My rule on this is unless you really know that you require dedicated, then pick default
- IPv4 Private CIDR Blocks & Public IPs
	- The private CIDR block is the main method of IP communication for the VPC. By default, everything uses these private addresses.
	- Public IPs are used when you want to make resources public. When you want them to communicate with the public internet or the AWS public zone or you want to allow communication to them from the public internet.
- A VPC is allocated 1 mandatory Primary Private IPv4 CIDR Block - this is configured when you create the VPC
	- This primary block has two main restrictions:
		- Min /28 (16 IP) Max /16 (65,536 IP)
- Optional secondary IPv4 Blocks
	- Currently, the max is 5, but this can be increased with a support ticket.
When thinking conceptually about VPC, imagine it that it's got a pool of private IP version 4 addresses. And optionally, it can use public addresses.
- Optional single **assigned** IPv6 /56 CIDR Block
	- A VPC can be configured to use IP version 6 by assigning a slash 56 IP v6 CIDR to the VPC. This is a feature set which is still being matured. Not everything works with the same level of features as it does for IP version 4, but with the increasing worldwide usage of IP version 6, in most circumstances you should start looking at applying an IP version 6 range as default.
	- An important thing about IP version 6 is that the range is either allocated by AWS - as in you have no choice on which range to use or you can select to use your own IP version 6 addresses which you own. You can't pick a block like you can with IP version 4.
		- IP version 6 IPs don't have the concept of private and public. The range of IP version 6 addresses that AWS uses are all publicly routable by default. But if you do use them, you still have to explicitly allow connectivity to and from the public internet. So don't worry about security concerns. It just removes an admin overhead because you don't need to worry about this distinction between public and private.
- AWS VPCs also have fully featured **DNS**. It's provided by Route 53 and inside the VPC.
	- it's available on the **base** IP address of the VPC **plus 2**. So if the VPC is 10.0.0.0, then the DNS IP will be 10.0.0.2.
- There are two options which are critical for how DNS functions in a VPC:
	- **enableDnsHostnames** - gives instances DNS Names
		- This indicates whether instances with public IP addresses in a VPC are given public DNS host names.
		- **enableDnsSupport** - enables DNS resolution in VPC
	- (**exam**) (or real world) if you have any DNS issues, these are the first 2 things you should check.

## VPC Subnets
Subnets are what services run from inside VPCs, and they're how you add structure, functionality, and resilience to VPCs.

Subnets in VPC start private & take configuration to make public.
- A subnet is an **AZ Resilient** subnetwork of a VPC - **within a particular AZ**
- It's created within **one AZ.** It can never be changed & **can never be in multiple AZs**.
	- 1 AZ can have 0 or lots of subnets
- The subnet by default uses IPv4 networking & is allocated an IPv4 CIDR
	- IPv4 CIDR is a subset of the VPC CIDR block
	- The CIDR a subnet uses cannot overlap with any other subnets in that VPC. They must be **non-overlapping**.
- A subnet can optionally be allocated an IPv6 CIDR block as long as the VPC is also enabled for IPv6.
	- The range that's allocated to individual subnets is a /64 range. The /64 range is a subset of the /56 VPC.
		- A /56 IPv6 range has enough space for 256 /64 ranges which each subnet can use.
- Subnets can communicate with other subnets in the VPC
	- The isolation of a VPC is at the perimeter of the VPC. Internally, there's free communication between subnets by default.

(Reminder): Sizes of networks are based on the prefix.
Ex: a /24 network allows values from 0 to 255 in the fourth octet. That's a possible 256 IPs. But, in a subnet, you don't get to use them all. Some IPs inside every VPC subnet are reserved.

- There are **five IP addresses** within **every VPC subnet** that you can't use.
	- So if a subnet should have 16 IPs, it actually has 11 usable IPs. So keep this in mind, especially when you're creating smaller VPCs and subnets because this can quickly eat up IP addresses.
- Ex: 10.16.16.0/20 (10.16.16.0 => 10.16.31.255)
- **Reserved addresses**:
	- 1) **Network** Address (10.16.16.0)
		- (NOT AWS specific) The first address of any subnet is the one that represents the network, the starting address of the network, and it can't be used. It's the case for any other IP networks as well. Nothing uses the first address on a network.
	- 2) '**Network +1**' (10.16.16.1) - **VPC Router**
		- (AWS specific) Next is what's known as the network plus one address - the first IP after the network address. In AWS this is used by the VPC router - the logical network device which moves data between subnets and in and out of the VPC if it's configured to allow that. The VPC router has a network interface in every subnet.
		- // [[5.0 (SAP) NETWORKING & HYBRID#VPC Router Deep Dive]]
	- 3) '**Network +2**' (10.16.16.2) - Reserved (DNS*)
		- (AWS specific) In a VPC, the second usable address of the VPC range is used for DNS.
			- I've put DNS and an asterisk here because I refer to this reservation as the DNS reservation. But strictly speaking, it's the second address (VPC range plus 2) in a VPC which is used for DNS.
	- 4) '**Network +3**' (10.16.16.3) - Reserved Future Use
		- (AWS specific) This doesn't have a use yet, it's reserved for future requirements.
	- 5) **Broadcast** Address (10.16.31.255) (Last IP in subnet)
		- (NOT AWS specific) Broadcasts are not supported inside a VPC, but the last IP address in every subnet is reserved regardless.

![[VPC Subnets.png]]
A VPC has a configuration object applied to it called a **DHCP option set**. It can't be changed. You can create option sets, but you cannot edit them. Keep that in mind. If you want to change the settings, you need to create a new one and then change the VPC allocation to this new one.

DHCP stands for Dynamic Host Configuration Protocol. It's how computing devices receive IP addresses automatically. There's one DHCP option set applied to a VPC at one time, and this configuration flows through to subnets. It controls things, like DNS servers, NTP servers, NetBIOS servers, and a few other things.

On every subnet, you can also define two important IP allocation options.
The first option controls if resources in a subnet are allocated a public IPv4 address, in addition to their private subnet address automatically.
- This will be covered in the lesson on routing & internet gateway because there's some additional theory that you need to understand about public IPv4 addresses; but, this is one of the steps that you need to do to make a subnet **public** - it's on a **per subnet basis** that you can set **auto assign public IPv4 addresses**.
- Another related option defined at a subnet level is whether resources deployed into that subnet are also given an **IPv6** address. Logically for that to work, the subnet has to have an **allocation** as does the VPC. But both of these options are defined at a subnet level and flow on to any resources inside that subnet.

## VPC Routing, Internet Gateway & Bastion Hosts
How routing works within a VPC.
Internet Gateway - how we can configure a VPC so that data can exit to and enter from the AWS Public Zone and public Internet.
Bastion hosts - also known as jump boxes.

- Every VPC has a VPC Router - Highly Available
	- A VPC router is a HA device which is present in every VPC, both default or custom, which moves traffic from somewhere to somewhere else. It runs in all the AZs the VPC uses - you never need to worry about its availability. It simply works.
- The router has a network interface in **every subnet** in your VPC, the **network plus one** address of the subnet.
	- By **default**, in a custom VPC, without any other configuration, the VPC router simply **routes traffic between subnets** in that VPC.
		- If an EC2 instance in one subnet wants to communicate with something in another, the VPC router is the thing that moves the traffic between the two.
- Controlled by 'route tables' - each subnet has one
	- Route tables (associated with a subnet) defines what the VPC router will do when data leaves that subnet.
- A VPC is created with what's known as a **Main** route table - subnet default
	- If you don't explicitly associate a custom route table with a subnet, it uses the main route table of the VPC. If you do associate a route table that you create with a subnet, then when you associate that, the main route table is disassociated. A subnet can only have one route table associated with it at any one time, but a route table can be associated with many subnets.

![[Route Tables.png]]

And a route table is just a list of routes. When traffic leaves the subnet that this route table is associated with, the VPC router reviews the IP packets. A packet has a source address, a destination address, and some data. The VPC router looks at the destination address of all packets leaving this subnet. When it has that address, it looks at the route table and it identifies all of the routes which match that destination address (checks destination field on a route).

The destination field on a route could match exactly one specific IP address. It could be an IP with a /32 prefix (that means that it matches one single IP). Or, the destination field on a route could also be a network match - matching an entire network of which that IP is part. Or it could be a default route. For IPv4, 0.0.0.0/0 matches all IPv4 IP addresses. That's a default route - a catch all.

In the case where traffic leaving a subnet only matches one route, then that one route is selected. If multiple routes match, so maybe there's a specific slash 32 IP match, maybe there's a slash 60 network match, and maybe there is a 0.0.0.0 slash 0 default match, well then the prefix is used as a priority. The higher the prefix value, the more specific the route is, and the higher priority that that route has (/32 being highest).

Once we get to the point where a single rule in a route table is selected, either the sole route that applies or the one with the highest priority, then the VPC router forwards that traffic through to its destination, which is determined by the target field on the route. The target field will either point at an AWS gateway - or it will say, local. Local means that the destination is in the VPC itself. So, the VPC router can forward the traffic directly.

All route tables have at least one route, the local route. This matches the VPC CIDR range, and it lets the VPC router know that traffic destined for any IP address in the VPC CIDR range is local, and it can be delivered directly. If the VPC is also IPv6 enabled, it will also have another local route matching the IPv6 CIDR for the VPC.

These local routes can never be updated. They're always present, and the local routes always take priority. They're the exception to that previous rule about the more specific the route is, the higher the priority.

(**exam**) Summary:
- Route tables are attached to zero or more subnets.
- A subnet has to have a route table.
	- It's either the main route table of the VPC or a custom one that you've created.
- A route table controls what happens to data as it leaves the subnet or subnets that that route table is associated with.
- Local routes are always there, uneditable, and match the VPC IPv4 or IPv6 CIDR range.
- For anything else, higher prefix values are more specific and they take priority.
- The way that a route works is it matches a destination IP, and for that route, it directs traffic towards a specific target.
- A default route is what happens if nothing else matches.

An internet gateway is one of the most important add - on features available within a VPC.
- It's a **region resilient** gateway attached to a VPC - (this always comes up in the exam).
	- You do not need a gateway per AZ. The IGW is resilient by design. One IGW will cover all the AZs in the region which the VPC is using.
- 1 VPC = 0 or 1 IGW, 1 IGW = 0 or 1 VPC
	- There's a 1:1 relationship between IGWs & the VPC. A VPC can how no IGWs, which makes it entirely private, or it can have 1 IGW. Those are the 2 choices. An IGW can only ever be attached to 1 VPC at a time - at which point it's valid in all the AZs the VPC uses.
- The IGW runs from within the border of the VPC & the AWS Public Zone.
	- It's what allows services inside a VPC which are allocated with public IPv4 addresses or IPv6 addresses to be reached from the internet and to connect to the AWS Public Zone (S3,SQS, SNS, etc) or the internet.
- IGWs are Managed - AWS handles performance. From your perspective, it simply works.

**Using an IGW**
![[Using an IGW.png]]
- First, we create and attach an internet gateway to a VPC. This means that it's available for use inside the VPC. We can use it as a target within route tables.
- Then we create a custom route table & associate it with the web subnet.
- Then we add IPv4 & optionally IPv6 default routes to the route table with the target being the IGW
- Finally, we configure the subnet to allocate IPv4 addresses and optionally IPv6 by default.
Once we've done all that, the subnet is classified as being a public subnet. Any services inside that subnet with public IP addresses can communicate to the internet and vice versa and they can communicate with the AWS public zone as long as there's no other security limitations that are in play.

The exam can have difficult questions around IPv4 addressing works, so we want to clarify exactly how that works - 

![[IPv4 Addresses with a IGW.png]]


Conceptually, this is how an EC2 instance might look if it's using IPv4 to communicate with a software update server of some kind. So we've got the instance on the left with an internet gateway in between. And let's say it's a Linux EC2 instance trying to do some software updates to a Linux update server. That's located somewhere in the public internet zone. So the instance has a private IP address of, let's say, 10.16.16.20. And it also has an IPv4 public address that's assigned to it of 43.250.192.20. 

Only, that's not how it really works. What actually happens with public **IPv4 addresses** is that they **never touch the actual services inside a VPC**.
Instead, when you allocate a public IPv4 address, for example, to this EC2 instance, **a record** is created which the **internet gateway maintains**. It **links** the instance's **private** IP to its allocated **public** IP.
So the instance itself is not configured with that public IP. That's why when you make an EC2 instance and allocate it a public IPv4 address, inside the **operating system**, it **only sees the private IP address**. **Keep this in mind for the exam**. There are questions which will try to trip you up on this one. For IPv4, it is not configured in the OS with the public IP address.

**How the flow of data works:**
When the Linux instance wants to communicate with the Linux software update server, it creates a packet of data. The packet has a source address of the EC2 instance and a destination address of the Linux software update server. So at this point, the packet is not configured with any public addressing. This packet would not be routable across the public internet. It could not reach the Linux update server. That's really important to realize.

![[IPv4 Addresses with a IGW - Packet Out.png]]

Now, the packet leaves the instance. And because we've configured a default route, it arrives at the internet gateway. The internet gateway sees that this packet is from the EC2 instance because it analyzes the source IP address of that packet. And it knows that this instance has an associated public IPv4 address. And so it adjusts the packet. It **changes** the packet's **source** IP address to the **public IP** address that's allocated to that instance. And this IP address, because it's public, is routable across the internet. So the internet gateway then forwards the updated packet onto its destination. So as far as the Linux software update server is concerned, it's receiving a packet from a source IP address of 43.250.192.20. It knows nothing of the private IP address of this EC2 instance.

Now, on the way back, the inverse happens. The Linux software update server wants to send a packet back to our EC2 instance. But as far as it's concerned, it doesn't know about the private address. It just knows about the public address.  So the software update server sends a packet back, addressed to the instance's public IP address with its source address. So it thinks that the real IP address of the instance is this 43.250.192.20 address. Now, this IP address actually belongs to the internet gateway. And so it travels over the public internet. And it arrives at the internet gateway, which then modifies this packet. It changes it. Then it forwards this packet through the VPC network to the original EC2 instance.

Don't fall for any exam questions which try to convince you to assign the public IPv4 address of an EC2 instance directly to the OS. The EC2 instance OS has no knowledge of this public address.

For IPv6, all addresses that AWS uses are natively publicly routable. And so in the case of IP version 6, the operating system does have the IP address version 6 address configured on it. That's the publicly routable address. And all the internet gateway does is pass traffic from an instance to an internet server and then back again. It doesn't do any translation.

## Stateful vs Stateless Firewalls
Stateful vs stateless firewalls.
![[Transmission Control Protocol (TCP).png]]
(refresher) TCP is L4 protocol running on top of IP (it adds error correction & ports).

When you make a connection using TCP, each side is sending IP packets to each other. These IP packets have a source and destination IP and are carried across local networks and the public internet. TCP is a layer 4 protocol which runs on top of IP. It adds **error correction** together with the idea of **ports**. HTTP runs on port 80 and HTTPS runs on TCP port 443.

**How TCP Works**
![[Stateful vs Stateless Firewalls.png]]

**Outbound vs Inbound Depends on Perspective**
![[Stateful vs Stateless Firewalls2.png]]
A stateless firewall means that it doesn't understand the state of connections.

**Stateless Firewalls**
![[Stateless Firewalls.png]]
It sees a request from Bob's laptop & the response as two different parts. You need to think about allowing or denying them as two parts. You need two rules. In this case, one inbound rule (the request) & one outbound rule (the response). This is more management overhead.

Two points about stateless firewalls:
1) For any servers where they accept connections and where they initiate connections (common with web servers where they need to accept connections from clients, but they also need to do software updates) - you'll have to deal with two rules and they will need to be the inverse of each other. Get used to thinking that outbound rules can be both the request and the response; inbound rules can be both the request and the response. Start by determining the direction of the request.
2) The request component will always be to a well known port.
	1) If you're managing the firewall for the Categram application, you'll need to allow connections to TCP port 443. The response is always from the server to a client, but this always uses a random ephemeral port.
		1) Because the firewall is stateless, it has no way of knowing which specific port is used for the **response**. So you'll often have to allow the **full range of ephemeral ports** to any destination. This makes security engineers uneasy. It's also why stateful firewalls are much better.

**Stateful Firewalls**
![[Stateful Firewalls.png]]
With a stateful firewall, you'll generally only have to allow the request or not and the response will be allowed or not automatically. This significantly reduces the admin overhead and the chance for mistakes because you just have to think in terms of the directionality and the IPs and ports of the request. In addition, you don't need to allow the full ephemeral port range.

## Network Access Control Lists (NACLs)
A Network Access Control List can be thought of as a traditional firewall available within AWS VPCs.

**Network Access Control Lists (NACL)**
![[Network Access Control Lists (NACL).png]]
The first thing to understand, and this is core to how NACLs work within AWS, is that they are associated with subnets. Every subnet has an associated network ACL, and this filters data as it crosses the boundary of that subnet. In practice, this means any data coming into the subnet is affected, and data leaving the subnet is affected.

But, and this is super important to remember, connections **between things** within that subnet, such as between instance A and instance B, in this example, are **not affected** by network ACLs.

A request can be either inbound or outbound. Remember that this doesn't always match directly to request or response. A request can be either inbound or outbound as can a response. These inbound and outbound rules are focused only on the direction of traffic, not whether it's request or response.
NACLs are stateless - they don't know whether requests are requests or response. It's all about direction.

Rules match the destination IP or IP range, destination port or port range, together with the protocol. And they can explicitly allow or explicitly deny traffic. Remember this one, **network ACLs** offer both **explicit allows** and **explicit denies**.

Rules are processed in order.
First, a network ACL determines if the inbound or outbound rules apply. Then, it starts from the lowest rule number. It evaluates traffic against each individual rule until it finds a match. Then, that traffic is either allowed or denied based on that rule, and then processing stops.
	This is critical to understand, because it means that if you have a deny rule, and an allow rule, which match the same traffic, but if the deny rule comes first, then the allow rule might never be processed.
There's a catch-all, showed by the asterisk in the rule number, and this is an implicit deny.

Network ACLs are stateless. This means that rules are required for both the request and the response part of every communication. You need individual rules for those, so one inbound and one outbound.

## Security Groups (SG)
Security groups are the second type of security filtering feature commonly used within AWS - other type being network access control lists.

SGs & NACLs share concepts, but operate differently.

**VPC Security Groups (SG)**
- **STATEFUL** - **detect response** traffic **automatically**
	- SG's are stateful. They detect response traffic automatically for a given request.
- **Allowed** (IN or OUT) **request** = **allowed response**
	- If you allow inbound or outbound requests, the response is automatically allowed (they use ephemeral ports) - You don't have to worry about configuring ephemeral ports. (Ex: Web server operating on TCP 443 - you allow inbound SG rule on inbound TCP 443, & the response, which uses ephemeral ports, is automatically allowed).
- **NO EXPLICIT DENY** ... only ALLOW or Implicit DENY
	- SG have a major limitation - no explicit deny. If you don't explicitly allow traffic, you're implicitly denying it..
- .. **can't block specific bad actors**
	- .. This means you can't use SGs to block bad actors (a specific IP address or a specific range). For this, typically you'd use NACLs in conjunction with SGs, where the NACLs are used to add explicit denies.
- Supports IP/CIDR ... and **logical resources**
	- SGs operate above NACLs on the OSI 7 layer stack, which means they have more features - they support IP and CIDR based rules, but they also allow referencing AWS logical resources. This includes other SGs & even itself within rules.

(**exam**) SGs are NOT attached to instances nor are they attached to subnets - **SGs are attached to ENI's (elastic network interfaces)**.

## Network Address Translation (NAT) & NAT Gateway
NAT (Network Address Translation) - a process of giving a private resource outgoing only access to the internet. A NAT Gateway is the AWS implementation which is available within a VPC.

![[What is NAT.png]]

NAT means more than people think it does. In a strict sense, it's a set of different processes which can adjust IP packets by changing their source or destination IP addresses.

The IGW (Internet Gateway) performs a type of NAT known as static NAT. It's how a resource can be allocated with a public IPv4 address. When the packets of data leave those resources & pass through the IGW, it adjusts the source IP address from the private address to the public, and then sends the packet on. When the packet returns, it adjusts the public IP address to the original private address. This is called **static NAT**. This is how the IGW implements public IPv4 addressing.

What most people think of when they think of NAT is a subset of NAT called **IP Masquerading**.  IP masquerading hies a whole CIDR block behind one public IP. Rather than a 1 private IP to 1 public IP process the IGW does, NAT is many private IPs to one single public IP. This technique is popular because the public IPv4 address space is running out. IP Masquerading, which we will from here on call NAT, gives a whole private range of IP addresses **outgoing** only access to the public internet and the AWS public zone.
	Because many private IPs use a single public IP, private devices that use NAT can **initiate outgoing** connections to Internet or AWS public space services and those connections can receive response data. But, you **cannot initiate connections from** the public internet to these private IP addresses when NAT is used. 

AWS has 2 ways to provide NAT services. Historically, you could use an EC2 instance configured to provide NAT. But there's also a managed service - the NAT gateway, which you can provision inside a VPC to provide the same functionality.

![[NAT Architecture.png]]

If we wanted these blue instances (which are private) to perform public networking (such as get software updates), how would we do it?

We could make the subnets public in the same way we've done with the public subnets (the web subnets). However, we might not want to do that architecturally. With this multi tier architecture we're implementing, part of the design logic is to have tiers which aren't public & aren't accessible from the public internet.

We could also host some kind of software update server inside the VPC. Some businesses chose to do that - some businesses run Windows or Linux update servers inside their private network. But that comes with admin overhead. NAT offers us a third option - 

We provision a NAT gateway into a public subnet. Remember, the public subnet allows us to use public IP addresses. The public subnet has a route table attached to it which provides default IPv4 routes pointing at the IGW. Because the NAT Gateway is located in this public web subnet, it has a public IP which is routable across the public internet; so, it's able to send data out & get data back. The private instances route tables could be configured differently than the public one. We point the private subnet's route table to point at the NAT gateway (rather than the public internet).

Example:
source: instance 10.16.32.10, destination: 1.3.3.7 (software update server).
This packet's routed through the NAT Gateway.
The NAT gateway makes a record of the data packet. It stores the destination that the packet is for, the source address of the instance sending it, port, and other details which help it identify the specific communication in future (to uniquely identify it) into a translation table. The NAT gateway maintains something called a translation table which records all of this information.
The NAT gateway changes the source address of this IP packet to be its own source address.
	If this NAT appliance were anywhere but AWS, what it would do right now is adjust the packet with a public routable address. It'd do this directly. But remember, nothing inside a VPC really has directly attached to it a public IPv4 address. That's what the internet gateway does.

The NAT gateway, because it's in the web subnet, it has a default route. And this default route points at the internet gateway. And so the packet is moved from the NAT gateway to the IGW (by the VPC router).

The IGW knows that this packet is from the NAT gateway. It knows that the NAT gateway has a public IPv4 address associated with it. And so it modifies the packet to have a source address of the NAT gateway's public address. And it sends it on its way. The NAT gateway's job is to allow multiple private IP addresses to masquerade behind the IP address.

 If you need to give an instance its own public IPv4 address, then only the internet gateway is required.
 If you want to give private instances outgoing access to the internet and the AWS public zone services (such as s3), then you need both the NAT Gateway (to do the m:1 translation) & the IGW to translate from the IP of the NAT Gateway to a real IPv4 address.

![[NAT Gateways.png]]

To deploy a NAT Gateway, it needs to run from a public subnet because it needs to be able to be assigned a public IPv4 IP address for itself. You need your VPC in a position where it has public subnets and for that you need an IGW, subnets configured to allocate public IPv4 addresses and default routes for those subnets pointing at the IGW.

A NAT Gateway uses a special type of IPv4 address - elastic IPs. These are IPv4 addresses which are static - they don't change. They're allocated to your account in a region and they can be used for whatever you want until you deallocate them. NAT Gateways are one service which use these elastic IPs.

If an AZ entirely fails, the NAT Gateway fails. For region resilience (to mirror the HA of an IGW), you need to deploy one NAT GW in each AZ that you're using in a VPC, then have a route table for private subnets in that AZ pointing at the NAT GW also in that AZ.

NAT GWs aren't very expensive, but they can get costly if you have lots of AZs, which is why it's important think about your VPC design.

You can always deploy multiple NAT GWs & split your subnets across multiple provisioned products - so, if you need more bandwidth, you can always deploy more NAT GWs. For example, you can split heavy consumers across 2 different subnets in the same AZ, have 2 NAT GWs in the same AZ, and just route each of those subnets to a different NAT GW. That would quickly allow you to double your available bandwidth.

With NAT GWs, you're billed based on the # you have - there's a standard hourly charge for running a NAT GW. Subject to change & differs per region. $0.04 per hour. Partial hours are billed as a full hour. There's also a processing charge. ~$0.04 per GB of processed data. Don't focus on the values - just focus on the two charged elements - hourly & per data processed.

![[NAT GW Full Resilience.png]]

To implement a truly resilient architecture for NAT services in a VPC, you need a NAT gateway in a public subnet, inside each AZ that the VPC uses. As a minimum, you need private route tables in each availability zone. In this example, AZA, AZB, and then AZC. Each of these would need to have their own route table, which would have a default IP version for route, which points at the NAT gateway in the same availability zone. That way, if any availability zone fails, the others could continue operating without issues.

Don't let the test fool you into into thinking one NAT gateway is enough. One NAT GW is not regionally resilient. A NAT gateway is highly available in the availability zone that it's in. If hardware fails or it needs to scale to cope with load, it can do so within that AZ, but if the whole AZ fails, there's no failover. You deploy a NAT GW into an AZ - it isn't region resilient by default (like the IGW).

**NAT Instance vs NAT GW**
![[NAT Instance vs NAT GW.png]]
NAT used to be provided by NAT Instances. These are a NAT process running on an EC2 instance. This probably won't feature on the exam - but, if you ever need to use a NAT instance, by default, EC2 filters all traffic it sends or receives. It drops any data that's on its network card when that network card is not either the source or the destination. If an instance is running as a NAT instance, it will be receiving some data which the source address will be of other resources in that VPC, and the destination will be a host on the internet. So it will neither be the source, nor the destination. So by default that traffic will be dropped. And if you need to allow an EC2 instance to function as a NAT instance, then you need to disable a feature called Source and Destination Checks. This can be disabled via the console UI, the CLI, or the API. The only reason I mention this is I have seen this question in the exam before, and if you do implement this in a real world production style scenario, you need to be aware that this feature exists.

At the highest level, architecturally, NAT instances and NAT gateways are kind of the same. They both need a public IP address, they both need to run in a public subnet, and they both need a functional Internet gateway. At this point it's not really preferred to use EC2 running as a NAT instance. It's much easier to use a NAT gateway, and it's recommended by AWS in most situations. But, there are a few key scenarios where you might want to consider using an EC2 based NAT instance:

If you value availability, bandwidth, low levels of maintenance, and high performance, then you should choose NAT gateways. That goes for both real world production usage, as well as being default for answering any exam questions.

A NAT gateway offers high end performance, it scales, it's custom designed to perform network address translation. A NAT instance in comparison is limited by the capabilities of the instance it's running on, and that instance is also general purpose, so won't offer the same level of custom designed performance as a NAT gateway. Now, availability is another important consideration, a NAT instance is a single EC2 instance running inside an availability zone. It will fail if the EC2 hardware fails, it will fail if its storage fails, or if its networking fails, and it will fail if the AZ itself fails entirely. A NAT gateway has some benefits over a NAT instance. So inside one availability zone, it's highly available, so it can automatically recover, it can automatically scale, so it removes almost all of the risks of outage versus a NAT instance, but it will still fail entirely if the AZ fails entirely. You still need to provision multiple NAT gateways spread across all the AZs that you intend to use, if you want to ensure complete availability. For maximum availability, a NAT gateway in every AZ you use. This is critical to remember for the exam.

Now if cost is your primary choice, or if the VPC that you're deploying NAT services into is just a test VPC, or something that's incredibly low volume, then a NAT instance can be cheaper. It can also be significantly cheaper at high volumes of data. You've got a couple of options. You can use a very small EC2 instance, even ones that are free-tier eligible to reduce costs, and the instances can also be fixed in size, meaning they offer predictable costs. A NAT gateway will scale automatically, and you'll build for both the NAT gateway and the amount of data transferred, which increases as the gateway scales. A NAT gateway is also not free-tier eligible. Now this is really important, because when we deploy these in the system, and we're going to do the next demo lesson, it's one of those services that I need to warn you will come at a cost.

You will be charged for a NAT gateway regardless of how small the usage. NAT instances also offer other niche advantages. Because they're just ec2 instances, you can connect to them just like any other ec2 instance & you can multi purpose them - you can use them for things like bastion hosts, port forwarding (maybe port 80 for web or 443 for secure web).

- NAT instances are just EC2 instances, and so you can filter traffic using either network **ACLs** on the **subnet** the instance is in, or **security groups** directly associated with that instance.
- (**exam**) NAT GWs don't support security groups. You can only use **NACLs** with **NAT GWs**.

What about IPv6?
- NAT isn't required for IPv6.
- All IPv6 addresses in AWS are publicly routable
- The Internet Gateway works with ALL IPv6 IPs directly
	- If you choose to make an instance in a private subnet, have a default IP version 6 route to the internet gateway, it will become a public instance. As long as you don't have any NACLs or any security groups, any IP version 6 IP address in AWS, you can communicate directly with the AWS public zone and the public internet. So the internet gateway can work directly with IP version 6.
- NAT gateways **do not work with IP version 6**.
	- If you see any questions which mention IP version 6 and NAT gateways, you can exclude the answer.
- ::/0 Route + IGW for bi-directional connectivity
	- With any subnet inside AWS, which has been configured for IP version 6, if you add the IP version 6 default route, which is ::/0, if you add that route and you point that route at the internet gateway as a target, that will give that instance bidirectional connectivity to the public internet, and it will allow it to reach the AWS public zone and public services.
- ::/0 Route + Egress-Only Internet Gateway - Outbound Only
	- egress-only internet gateways are a specific type of gateway that works only with IPv6. It's used for giving IPv6 instances outgoing-only access to the public internet and the AWS public zone.

Get it really burned into your memory that you do not use NAT & you don't use NAT GWs with IPv6.
