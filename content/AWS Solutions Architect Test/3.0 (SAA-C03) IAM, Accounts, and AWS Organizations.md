## IAM Identity Policies
How AWS handles security.
IAM Policies get attached to identities inside AWS. (Identities are users, groups, and roles).

Understanding policies comes in 3 main stages:
1) (**exam**) Understand their architecture & how they work - this is enough for the exam.
2) Gain the ability to read & understand the policy.
3) Understand how to write your own.

An IAM policy is a **set of security statements** to AWS. It **grants** or **denies** access to AWS products and features to any **identity** which uses that policy. **Identity policies**, also known as **policy documents**, are created using JSON.
A policy document is one or more statements. Inside a statement block, there can be multiple statements. These statements grant or deny permissions to AWS services.
When an identity attempts to access AWS resources, that identity needs to prove **who** it is to AWS. This is **authentication**. Once authenticated, that identity is known as an **authenticated identity**. AWS knows which policies an identity has, and it could be multiple. Each of these policies can have multiple statements in it.
![[IAM Policy Document.png]]
First part of a statement:
**Sid** - (statement id) - **optional** field that allows you to identify what a statement does. (ex: FullAccess, DenyCatBucket). It's best practice to always use Sids.
*Every **interaction** with AWS is a combination of two things - the **resource** you're interacting with and the **action** you're attempting to perform on that resource. A **statement** only **applies** if the interaction you're having **matches** the action AND the resource.*

**Action** format: `[<service>:*]`
	A **wildcard** matches all actions. An action can be a specific action, a wildcard, or a list of actions.
**Resources** is the same, except it matches AWS Resources. When using a list, use the ARN format (amazon resource name) format.
Policies can overlap.
![[IAM Policies1.png]]
**Priority**, or order, in which policy statements are **resolved**:
1) Explicit Deny - explicit deny will overrule everything else.
2) Explicit Allows
3) Default Deny (implicit) - if neither explicit deny or explicit allow is specified, then the default implicit deny is applied. With the exception of the account root user, AWS identities start with **no access** to any AWS resources.
(**exam** - **MEMORIZE**) **Deny - Allow - Deny**
![[IAM Policies2.png]]
Example:
Sally has 2 policies. She's also in a group (AWSDevs) which has a policy. The resource she's trying to access also has a policy. AWS collects all of these policies and evaluates them with the rule discussed above - Deny - Allow - Deny.
![[IAM Policies3.png]]
Example of **inline** policy:
You have 3 devs working on a project. You create 3 policy files - one for each individual dev (3 **isolated** bits of JSON). Changing access rights requires changing all 3 inline policies. This **isn't scalable**.

Another option: use a **managed policy**. Managed policies are created as their own object. First, create the managed policy & **attach** it to **identities**.
Managed policies are good because:
1) They're **reusable**
2) Low **Management** Overhead

Managed policies should be used for the **normal default operational rights** in your business (a set of common access rights you want to give to lots of people).

**Inline** policies are generally used for **exceptions** to the normal access rights.

## IAM Users and ARNs
IAM Users are an identity used for anything requiring **long term** AWS access. E.g. **Humans**, **applications**, or **service accounts**.
![[IAM Users.png]]
IAM starts with a **principal**. This is an **identity** trying to access an AWS account. Principals can be individual **people, computers, services**, or a **group** of any of those things. For a principle to be able to do anything, it needs to be **authenticated** and be **authorized**. A principle is a person or an application who makes requests to IAM to interact with resources. To be able to interact with resources, it needs to **authenticate** **against** an **identity** within **IAM**. An IAM user is an identity which can be used in this way. 

Authentication for IAM is done with either **username** & **password** OR **access keys**. These are both examples of **long term credentials**. Generally, u&p are used if a human is accessing AWS & accessing via the console UI. **Access keys** are used if it's an **application**, or if it's a **human** attempting to use the AWS **CLI**.
Once the principal goes through the authentication process, the principal is now known as an **authenticated identity**.

Then, the process of authorization happens. When the authenticated identity tries to interact with a resource (like upload to an s3 bucket), then IAM checks the **statements** that are applied to the **identity** (authorization) & either allows or denies access.

**ARNs**
Amazon Resource Names - they **uniquely identify resources within any AWS account**.
ARNs allow you to refer to **single resources** or a **group** of resources using **wild cards**.
ARNs are generally used in **policies** (which are **attached** to **identities**).
![[Amazon Resource Name.png]]
arn: aws : s3 : : : catgifs
arn: aws : s3 : : : catgifs/*

The first ARN references the **bucket**. The second references **objects in the bucket**, but not the bucket itself.
This is really important & trip up a lot of people. These 2 ARNs don't overlap.

Some actions operate on the bucket level, which would need something like the top ARN.
Some actions operate on the object level, which would need something like the bottom ARN.

Using a wildcard in the ARN (for a service) isn't the same thing as not specifying a service.

- (**exam** - **MEMORIZE**) You can only have **5000** users in a single IAM **account**.
- IAM User can be a member of **10** groups.
- This has design impacts - if you have a system that requires more than 5000 identities, you can't use one IAM user for each identity. This might be a limit for **internet scale** apps with millions of users. Or it might be a limit for **large orgs** with > 5000 staff. Or when large **orgs merge**.
- We can use IAM **roles** or Identity **Federation** in these scenarios.

## IAM Groups
IAM Groups are **containers** for IAM **Users**. They exist to make organizing large sets of IAM Users easier. You can't login to IAM groups & they have no credentials.
![[IAM Groups.png]]
They're used solely to make **managing** IAM users **easier**. An IAM User can be a member of multiple groups.
Groups can have **policies** attached to them - both **inline** & **managed**. All policies are collected, and then resolved according to DENY - ALLOW - DENY.

There's **no** effective **limit** for the # of **users** in a single IAM **Group** (recall the 5k limit per AWS account - you can have all 5k in one group).
Trick question in **exam**: there **isn't** a built in **All Users group** inside IAM. You could do this, but you'd have to **create & manage** the group **yourself**.
Another limitation with groups: There's **no nesting**. You can't have groups within groups. IAM groups contain users & IAM groups can have **permissions attached**. That's it.

There's a limit of **300 groups per account**, but this can be increased with a support ticket.

Resource policies control access to a specific resource & allow or deny identities to access the resource. It does this by referencing identities, using an ARN. Users, an IAM role, can be referenced this way. Policy resources can reference IAM Users and Roles using an ARN. So, a bucket can give access to one or more users or one or more roles. But, groups **aren't** a **true identity**. They can't be referenced as a **principal** in a **policy**. A resource policy can't grant access to an IAM Group.

## IAM Roles - The Tech
A **Principal** is a physical **person**, **app**, **device**, or **process** which wants to authenticate with AWS.
**Authenticate** - proving to AWS you are **who** you say. If you **authenticate** & then you **authorize**, you can access 1 or more resources.

Logging into a user vs assuming a role - what's the difference - both get access rights.

- An **IAM User** is generally designed for situations where a **single principal** uses that IAM User.
	- If I can imagine a single thing (1 person / all) which uses an identity, then generally we'd use an IAM User.
	- Can have identity **permissions** attached to them - either **inline** or **attached** **managed policies** (allow or deny). Referred to as **permission policies** (attached or managed - doesn't matter).
- **IAM Roles** are identities, but are generally best suited for an **unknown # or multiple principals**.
	- IAM Roles are **assumed ... you become that role**. You **borrow** the role for a short period of time.
	- Real identities. May be referenced within resource policies.
	- 2 types of policies that can be attached.
		- **Trust Policy** - determine **which** identity **can assume** that role.
			- Can **reference** identities in the **same** AWS account (users / roles / services) or **other** AWS accounts.
			- Can even enable **anonymous** usage of that role.
			- And, also to other types of identities, like Facebook, Google, Twitter.
	- **Permissions Policy**
- If a **role** gets **assumed** by something that's allowed to assume it, AWS generates **temporary security credentials**.
	- These are made available to the identity which assumed the role. They're like access keys, but they're time limited. They need to be renewed by the identity re-assuming the role.
- **Roles** are used within **AWS Organizations** to allow us to login to one account within an organization & **access different accounts** without having to login again.
	- They become useful when managing large # of accounts.
- STS (**sts:AssumeRole**) - the secure token service. This is the **operation** that's used to **assume** the role & get the credentials.

## When to use IAM Roles
Common use of **Roles**: for **AWS services** themselves. AWS Services need access rights to perform certain actions.

![[When to use IAM Roles1.png]]
Lambda is a FaaS product. Give it come code & create a lambda function. This code could do things like start & stop ec2 instances, perform backups, or perform real time data processing - it doesn't matter for our purposes. What's important is that a **Lambda function** (as with most AWS things) has **no permissions** by default. A lambda isn't an AWS identity; it's a component of a service. So, it needs some way to get permission when it runs.

They **need access keys**. Better than hard coding access keys into your lambda function: We create an **IAM execution role**.
This **execution role** has a **trust policy** which trusts the Lambda service.
(sts - secure token service) sts:AssumeRole.

- Code runs in a **runtime environment**. Runtime environment **assumes** the role & gets **temporary security credentials**.
	- If we didn't use a role here, we'd have to **hardcode** access codes; this would be **bad**.
		- Is a security risk & the keys can't be easily changed / rotated.
	- Best practice is to always **roles** when possible.
		- Creds are temporary;
		- services are given permission for enough time to complete a task, then the credentials are discarded.

- When a **role** is best:
	- The # of instances is unknown
![[When to use IAM Roles2.png]]
- **Emergency Role**
	- Ex: Help desk guy can assume an **Emergency Role** when he needs to.
		- Ex: Break Glass for Key. The glass is a barrier. Breaking glass requires **intention**.

![[When to use IAM Roles3.png]]
- On Prem **SSO**
	- When you want to reuse your **existing identities** within AWS
		- Ex: You can't use Google / Fb / Twitter identities to directly interact with S3. Allow an IAM role to be assumed. Temporary access creds are generated. 
	- Using a role in this way (giving permissions to an external IdP - Active Directory, in this case) & allowing external identities to assume this role is called **ID Federation**.
		- It means you have a small # of roles to manage & external entities can use these roles to access your AWS resources.
- OR > 5,000 identities
	- (you can't create 5k users. Even if you could, would you want to managed 5k accounts?).
![[When to use IAM Roles4.png]]
Ex: Mobile Ride Sharing App w/ 1,000,000's of users
Web Identity Federation - uses IAM roles.
Most mobile apps let you sign in with a web identity (Google, FB, Twitter) - we can trust these identities and allow them to assume an IAM role. Through this role, we can allow the users to access AWS resources, like DynamoDB.

Advantages of Web **Identity Federation**:
- **No** AWS **Creds** stored on the app. If an app is exploited, there's no chance of creds being leaked.
- Makes use of **existing** customer **logins**
- **Scales** to 100,000,000's of accounts. You don't need to worry about the 5k IAM user limit. Using ID federation (IAM roles) is how you do that.
![[When to use IAM Roles5.png]]
Another example: **Cross account access**. Your partner (different AWS account) gives you a role to access his s3 bucket b/c their admins didn't want to create IAM Users for you.

## Service-linked Roles & PassRole
- A Service Linked role is an IAM role linked to a **specific AWS service**.
- They provide a set of permissions which is **predefined** by a **service**.
	- They provide permissions that a single AWS **service** needs to interact with **other AWS services** on your behalf.
- Service linked roles might **be created** by the service itself, or the service might **allow you** to create the role during the **setup** process of that service, or service linked roles might also get created within IAM.
- Key difference between service linked roles & normal roles: You can't delete the role until it's no longer required - and that means it's no longer used within that AWS service.

- Formats can differ. The names are case sensitive.

![[Service-linked roles - Mgmt - PassRole.png]]
- **iam:PassRole** is a method in AWS which gives you the ability to implement **role separation**. **PassRole** is a permission granted to IAM Users and resources that permits them **to use an IAM Role**.
	- For example, you can assign an IAM Role to a resource (say, "Administrators" role), then use iam:PassRole to grant a user permission to use that role.

Passing a role is an important AWS security architecture.

## AWS Organizations
Allows larger businesses to **manage** multiple AWS accounts in a cost effective way.
Example: Complexity from scale: Lots of users; various payment methods.

- The **management / master** (same thing - it used to be called the master account) account is special for 2 reasons:
	- The management account can **invite** existing AWS accounts into the organization.
		- When standard AWS accounts join an organization, they change from **standard** accounts to being **member** accounts of that organization.
	- Organizations have **1:1** management account & **0:M** member accounts.
- You can create a **structure** of member accounts within an organization.
	- This is useful if you have lots of accounts & need to **group** them (by things like business units, function, or stage of development).
- The **Organization Root** (not the Root IAM user - the admin user of an AWS account) is a **container** within an AWS Organization which can contain AWS accounts. The Org Root is the top level of the hierarchy.
	- The Org Root can **contain other containers** called Organizational Units (**OUs**).
- **Consolidated Billing** - 
	- When member accounts are added to an AWS Organization, the individual billing methods are removed for the member accounts. Instead, they pass their billing through to the management account of the organization. In consolidated billing, you might see this as the Payer Account.
	- Master account, management account, & payer account = same thing.
	- You get **1 bill** per month for all the accounts. This **reduces admin overhead**. This alone makes it worth creating an organization for most large enterprises.
	- For certain services, the **more you spend**, the **more you save**.
		- For some services, you can pay in advance in exchange for cheaper rates. When using Organizations, these **benefits** are **pooled**.

SCPs (service control policies) - a feature of AWS Organizations. More on this later.

With Organizations, you don't need to have IAM Users in every AWS account - IAM roles can be used to allow IAM Users to access other AWS accounts.

- Large orgs will often keep the management account clean & have a separate account dedicated to handle logins.
	- Both of these are fine, but just be aware that the architectural pattern is to have a single AWS account which contains all of the identities which are logged into. Large orgs may have their own ID system & may use Identity Federation so your on prem id's can access the dedicated login account.

From there, we can **role switch** (via the console UI)) onto different member accounts of the Org. Either login directly to the login account (using IAM identities) or use Identity Federation to gain access to the login account, then you role switch into other accounts. Behind the scenes, this assumes a role which is inside these other AWS accounts.

## Service Control Policies (SCPs)
SCPs are a feature of Organizations to restrict AWS accounts.

**SCPs** are a **policy document** (a .json file) & can be attached to:
- The root container - this attaches them to the organization as a whole
- 1:M OUs
- Individual AWS accounts
![[Service Control Policies.png]]
- SCPs inherit down the Org tree.
- SCPs attached to the **root container** affect all the accounts inside the organization
- SCPs attached to an **OU** impact all accounts in the OU as well as all accounts within OUs inside that OU. So if you have nested OUs, then by attaching them to one OU, they affect that OU and **everything below it**.
- SCPs attached to 1 or more accounts affect only those accounts they're attached to.
- The **management account** of an organization is **special**. Even if it has SCPs attached - either directly via an OU or on the root container of the Org itself, then the management account is **never affected by SCPs**. This can be both beneficial and a limitation. As a security practice, because the management account can't be restricted with SCPs, in Prod, I **avoid using the management account for any AWS resources**.

- SCPs are **account permissions boundaries**
- They limit what the account (**including account root user**) can do.
	- Earlier in the course we said that you can't directly restrict what the account root user can do. But, with an SCP, you CAN restrict what the account itself can do - specifically any identities within that account. So, you're indirectly restricting the account root user - because you're reducing the allowed permissions on the account, you're **effectively** reducing the account permissions on the account root user.
- SCPs **don't grant any permissions**. They're just a boundary - they define the **limit** of what is & isn't allowed within the account. You still need to give identities within that identities permissions to AWS resources. SCPs just limit the permissions which can be assigned to individual identities.

Example use for SCPs:
- Prevent usage of an account outside a known region
- Allow only a certain size EC2 instance to be used within the account

SCPs can be used in 2 ways:
- **Allow** list vs **Deny** list
	- Allow list - you can block by default & allow certain services. You have to explicitly allow services.
	- Deny list - you can allow by default & block access to certain services. This is the **default**.

**SCP Deny List Architecture**
![[SCP Deny List Architecture.png]]
When you enable SCPs, AWS applies a default policy - **Full AWS Access** - this is applied to the organization and all OUs within that organization.
- In the default implementation, this **won't have any effect** (since nothing is restricted). Service Control Policies **don't grant permissions**.
	- But when SCPs are enabled, there is an implicit default deny, just like IAM policies.
		- **If you had no initial allow**, then **everything would be denied**. So, the default is this Full Access Policy, which essentially means no restrictions. It has the **effect** of making SCPs a **deny list architecture**.
Remember: Deny (explicit) - Allow (explicit) - Deny (implicit). Explicit deny always wins.

**SCP Allow List Architecture**
![[SCP Allow List Architecture.png]]
- In certain situations, you might need to be **more conscious** about usage in your accounts. And that's where you would use **allow lists**.
	- To implement allow lists, it's a two-part architecture.
		 - One part of it is to **remove** the **AWS full access policy**. This means that only the implicit deny list is in place and active.
		 - Then, you would need to allow any services which you want to allow into a new policy
	 - **More secure**, must explicitly allow services; but, **more admin overhead**

Generally, prefer deny list architectures simply because it's less admin overhead.

![[scp-identity-policy.png]]
Only permissions which are allowed within **identity policies** in the account and are allowed by a service control policy are actually active.
**Effective permissions** for identities within an account **are the overlap** between any **identity policies** and any applicable **SCPs**.

## CloudWatch Logs
- **Public Service** - usable from AWS or on-prem.
	- Regional Service (i.e. us-east-1)
- **Store**, **Monitor** and **access** logging data
	- Logging data: a piece of date + a timestamp - generally year, month, day, hour, minute, second, and time zone.
- **AWS Integrations** - EC2, VPC Flow Logs, Lambda, CloudTrail, R53 and more...
	- Any services which integrate with CloudWatch logs can store data directly inside the product, and the security for this is generally provided by using IAM roles or service roles.
	- For anything else, you can use the **CloudWatch agent**.
	- The third way is to use the development kits for AWS to implement logging into CloudWatch logs directly into your application.
- Can generate **metrics** based on logs - **metric filter**.
	- // A metric filter is taking data and generating metrics from it.
![[CloudWatch Logs.png]]
Example Metric Filter: failed SSH connection. CW takes this data, generates a metric, then can generate an alarm to do things.

- **Log Groups** are are containers for multiple log streams for the same type of logging.
- Log Groups store configuration settings (retention settings, permissions)
	- When we define these settings on a log group, they apply to all log streams inside that log group.
- Metric Filters are defined on Log Groups.
	- Constantly reviewing log events for patterns.
	- When detected, they increment a metric.
	- Metrics can have associated alarms.

## CloudTrail
- Logs API calls/activities as a **CloudTrail Event**.
	- Every logged activity is a CloudTrail event. This activity can be an action taken by a user, a role, or a service.
- 90 days stored by default in **Event History**
- Enabled **by default** - no cost for 90 days of history.
- To customize the service, create 1 or more **Trails**.
- **Management** Events and **Data** Events.
![[CloudTrail Essentials.png]]
A **trail** can be One Region or All Regions. If AWS adds new regions, it'll be automatically updated.

**Global or regional**
- Global services (IAM, STS, CloudFront) always log to **US East 1** (North Virginia).
- Regional services log to their region.
- A trail needs to have this enabled in order to log these events. Enabled by default if you create a trail inside the UI.

- Once you have a trail created, **management events** and **data events** are captured.
	- Data events aren't enabled by default. They must be set when creating a trail.

- CloudTrail logs are stored in json files in s3. You're only charged for the s3 storage.
- CloudTrail can be integrated with CloudWatch Logs.
	- Once in CloudWatch (instead of s3), you can search the data, or apply metric filters.
- CloudTrail can create organizational trails - single management point for all API. Makes managing multi environments easier.

- Enabled by default ... but **90** days ... **no s3** (unless you enable a trail)
- **Trails** are how you configure S3 and CWLogs
- Management events **only** by default
	- Ex Management events: Creating an instance, stopping an instance, terminating an instance, creating or deleting S3 buckets, logins to the console
	- Data events need to be enabled & come at additional cost.
- IAM, STS, CloudFront - Global Service Events. Logged to US East 1.
	- // These type of events are called global service events, and a trail needs to have this enabled in order to log these events.
- **CloudTrail is not real time. There is a delay**.
	- CloudTrail typically delivers log files within 15 minutes of the account activity occurring, and it generally publishes log files multiple times per hour.

## AWS Control Tower 101
You can think of Control Tower as another evolution of AWS Organizations, adding more features, intelligence, & automation.
- Control Tower allows the **quick** & **easy** setup of **multi-account** environments.
- **Orchestrates** other AWS services to provide this functionality
	- For example, it uses AWS Organizations, IAM Identity Center (AWS SSO), CloudFormation, Config, and more...
- **Landing Zone** (LZ) - **multi-account** environment.
	- Like AWS Org, but with superpowers.
	- Provides SSO/ID Federation, Centralized Logging & Auditing (uses a combination of CloudWatch, CloudTrail, AWS Config, and SNS)
*Everything else in Control Tower surrounds Landing Zone*
- **Guard Rails** - **Detect**/**Mandate** rules/standards across all accounts within the LZ.
- **Account Factory** - **Automates** and **Standardizes** new account creation.
- **Dashboard** - single page oversight of the entire environment.

![[control-tower.png]]
Control Tower is like AWS Organizations - something you **create** from within AWS, and this account becomes the **management account** at the **landing zone**. Within the management account, Control Tower orchestrates everything.

We have AWS Organizations, and as you've already experienced, this provides the multi-account structure. So, **OUs** and **SCPs**. And then we have **SSO** provided by the **IAM Identity Center** (historically was known as AWS SSO) - we can use the same set of internal or federated identities to access everything in the landing zone that we have permissions to.

Now, this works in much the same way as AWS SSO worked, but it's all set up and orchestrated by Control Tower. When Control Tower is first set up, it generally creates two OUs. The **foundational** organization is the one that is used to create the organization. The OU, which by default is called **security**, and a custom OU, which by default is named **sandbox**. Inside the foundational or security OU, Control Tower creates two AWS accounts, the **audit** account and the **log archive** account.

The **log archive** account is for users that need access to all logging information for all of your enrolled accounts within the landing zone. Examples of things used within this account are **AWS Config** and **CloudTrail logs**, so they're stored within this account so that they're isolated. You have to explicitly grant access to this account, and it offers a secure, read-only archive account for logging.

Now, the **audit account** is for your users which need access to the **audit information** made available by Control Tower. You can also use this account as a location for any third-party accounts, such as the one that you're currently using. You can also use this account as a location for any **third-party tools** to perform auditing of your environment. So it's in this account that you might use **SNS** for **notifications** of **changes** to governance and security **policies**, and **CloudWatch** for monitoring landing zone-wide metrics.

Now, it's at this point where Control Tower becomes really awesome, because we have the concept of an **account factory**. Think of this as a team of robots who are creating, modifying, or deleting AWS accounts, as your business needs them. And this can be interacted with both from the Control Tower console or via the service catalog. So within the custom OU, Account Factory will **create AWS accounts** in a fully automated way, as many of them as you need. Now, the configuration of these accounts is handled by Account Factory. So from an account and networking perspective, you have a baseline, or cookie-cutter configurations applied. And this ensures a **consistent configuration** across all AWS accounts within your landing zone.

Now, Control Tower **utilizes CloudFormation** under the covers to implement much of this automation. So expect to see **stacks** created by the product within your environment. And Control Tower uses both **AWS Config** and **SCPs** to implement account **guardrails**. And these detect drifts away from governance standards, or prevent those drifts occurring in the first place.


**Landing Zone**
- **Well Architected** multi-account environment - **Home Region**
	- built with AWS **Organizations**, AWS **Config**, **CloudFormation**
- **Security** OU - Log Archive & Audit Accounts (CloudTrail & Config Logs)
- **Sandbox** OU - Test/less rigid security
- You can create other OU's and Accounts
- **IAM Identity Center** (**AWS SSO**) - SSO, multiple-accounts, ID **Federation**
- Monitoring and Notifications - CloudWatch and SNS
- **End User** account **provisioning** vis **Service Catalog**

**Guard Rails**
- **Guardrails** are **rules** - multi-account governance
- **Mandatory**, **Strongly Recommended**, or **Elective**
- **Preventive** - Stop you doing things (AWS ORG SCP)
	- enforced or not enabled
	- i.e allow or deny regions or disallow bucket policy changes
- **Detective** - compliance checks (AWS CONFIG Rules)
	- *clear*, *in violation* or *not enabled*
	- detect CloudTrail enabled or EC2 Public IPv4
**Account Factory**
- **Automated** Account **Provisioning**
	- This can be done by either cloud **admins** or **end users** (with appropriate permissions)
		- This allows you to have a truly self-service automatic process for provisioning AWS accounts. These can be long-running accounts or short-term accounts
- **Guardrails** - **automatically** added
- Account **admin** given to a **named user** (IAM Identity Center)
- Account & network **standard configuration**
- Accounts can be **closed** or **repurposed**
- Can be fully **integrated** with a businesses **SDLC**
