## Introduction to Containers
What we refer to as virtualization should really be called operating system or OS virtualization. It's the process of running multiple operating systems on the same physical hardware.

![[Virtualization Refresher.png]]

Part of this lesson's objectives is to understand the difference between **operating system virtualization** and **containers**.
The important thing to realize about these virtual machines is that each of them is an operating system with associated resources.
An OS can consume much of the allocated disk & RAM.
If you're running many Guest OS's on a hypervisor, it's likely that you're **wasting** system resources on **duplicate** OS's.

What we really want to do with this example is to run applications 1 through to 6 in separate, isolated, protected environments. Do we really need 6 copies of the same operating system taking up disk space and host resources? No.

![[Containerization.png]]

A container is similar to a virtual machine in that it provides an isolated environment which an application can run within.

VMs run a whole OS on top of a hypervisor.
A container runs as a process within the host operating system. It's isolated from all of the other processes, but it can use the host operating system for a lot of things, like networking and file I.O. It has its own file systems, isolated from everything else, and it can run child processors inside it, which are also isolated from everything else.

Because we don't need to run a full operating system for each application, the containers are much **lighter** than the virtual machines. We can run many more containers on the same hardware versus using virtualization. This density is one of the many benefits of containers.

What is an EC2 instance?
An EC2 instance is a running copy of its EBS volumes, its virtual disks. An EC2 instance's boot volume is used and you end up with a running copy of an operating system, running in a virtualized environment.

A container is no different in this regard. A container is a running copy of a Docker image.
Docker images are made up of multiple independent layers.
Docker images are stacks of these layers and not a single monolithic disk image.
Each line in a Docker file is processed one by one, and each line creates a new file system layer inside the Docker image that it creates.
Each layer is **differential**, and so it stores only the changes made against it versus the layers below. Together all stacked up, it creates what the container sees as a file system.

![[Image Anatomy.png]]
*Note that in the image above, the red layer's really the base layer, blue in the middle, and the green layer's really on top. The image is misleading.
All Docker images start off being created either from scratch or they use a base image. This is what this top line controls.

![[Container Anatomy.png]]

A Docker image is how we create a Docker container.  A Docker container is just a running copy of a Docker image with one crucial difference - a Docker container has an additional read-write file system layer. If log files are generated, or if an application generates or reads data, that's all stored in the read-write layer of the container.

We can use a docker image to create many containers. The layers that are shared (red, blue, green) are read-only layers, so there's no potential for overwrites. The **only difference** is the **read-write layer**, which is different in both of these containers. That's what makes the containers separate and keeps things **isolated**.

The reuse architecture that's offered by the way that containers do their disk images scales really well.

The base layers (the operating systems) are generally made available by the operating system vendors via container registries, like Docker Hub.

From container registries, container images can be deployed to Docker hosts, which are just servers running a container engine, in this case Docker.
Docker hosts, can run many containers based on one or more images.
A single image can be used to generate containers on many different Docker hosts.

You can use the Docker Hub to download container images, but also upload your own.

- Dockerfiles are used to build images
- **Portable** - self-contained, always run as expected (**consistency**)
	- Portability and consistency are two of the main benefits of using containerized computing
- Lightweight - Parent OS used, **fs layers are shared**
- Container only runs the application & environment it needsl
- Provides much of the **isolation** VM's do
- Ports are '**exposed**' to the host and beyond...
- Application stacks can be multi-container ...

## ECS - Concepts
ECS allows you to use containers running on infrastructure which AWS fully manage or partially manage. It takes away much of the admin overhead of self-managing your container hosts. ECS is to containers what EC2 is to virtual machines.

ECS uses **clusters** which run in one of two modes:
- EC2 mode - uses EC2 instances as container hosts; just normal EC2 hosts running the ECS software.
- Fargate mode - a serverless way of running Docker containers

**Clusters** are where your containers run from. You create a cluster and then you deploy **tasks** or **services** into that cluster.

![[ECS.png]]

Upload your container images to a container registry - You can use ECR (Elastic Container Registry) (integrated w/ AWS - provides permissions & scalability benefits), or you can use another container registry, like Docker Hub.

A **Container Definition**
- Tells ECS about your container.
- Tells ECS where your container image is.
- Tells ECS which port your container uses (such as 80).

**Container Definition** vs **Task Definition**
*I remember the difference by thinking of the container definition as just a **pointer** to **where** the container is stored and what **port** is exposed. The rest is defined in the task definition*.

**Task Definition**
- A task in ECS represents a self-contained application.
	- It could have **one** container defined inside it or **many**.
		- Maybe a web app container and a database container. A task in ECS represents the application as a whole.
- Store the **resources** used by the task (CPU, memory)
- Store the networking mode that the task uses
- Store the compatibility (whether the task will work on EC2 mode or Fargate)
- Stores the **task role**
	- A task role is an IAM role that a task can assume
		- When the task assumes that role, it gains temporary credentials which can be used within the task to interact with AWS resources. Task roles are the best practice way of giving **containers** within ECS **permissions** to access AWS products and services.
			- **Remember this for the exam ^**
- Don't scale on their own
- Aren't Highly Available

**ECS Service**
- Defined via Service Definition
- A **Service** is how, for ECS, we can define how we want a task to scale. How many copies we'd like to run.
	- It can add capacity and it can add **resilience**. Because we can have **multiple independent copies** of our task running.
		- You can deploy a load balancer in front of a service. So the incoming load is distributed across all of the tasks inside a service.
- You would generally use a service to provide that level of **scalability** and **high availability**
You can run a single copy of a task on its own. But it's the service wrapper that you use if you want to configure scaling and high availability.

It's tasks or services that you deploy into an ECS cluster (whether it's EC2 based or Fargate based).

Summary
- Container Definition - Image & Ports
- Task Definition - Security (Task Role), Container(s), Resources
- Task Role - IAM Role which the TASK assumes
- Service - How many copies, HA, Restarts
	- Generally what you use if it's a business critical application
	- Or something in production that needs to cope with substantial incoming load.

## ECS - Cluster Mode
The two different cluster modes when running containers with ECS are: EC2 mode and Fargate Mode.
Differences:
Admin overhead - which parts you manage vs which parts AWS manages.
Some cost differences.

![[ECS - EC2 Mode.png]]

ECS management components - handle high-level tasks like scheduling, orchestration, cluster management, and the placement engine which handles where to run containers, so which container hosts.

^ These high level components exist in both EC2 mode and Fargate mode.

With EC2 mode, an ECS cluster is created within a VPC inside your AWS account.
Because an EC2 mode cluster runs within a VPC, it benefits from the multiple AZs which are available within this VPC.

When you create the cluster, you specify an initial size. This is handled by an auto-scaling group.

Let's say that we have four container instances. Now these are just EC2 instances. When these are provisioned, you will be paying for them regardless of what containers you have running on them. So with EC2 cluster mode, you are responsible for these EC2 instances that are acting as container hosts. ECS provisions these EC2 container hosts, but there is an expectation that you will manage them, generally through the ECS tooling.

ECS using EC2 mode is not a serverless solution. You need to worry about **capacity** and **availability** for your cluster.

ECS uses container registries (like ECR, Docker Hub), and these are where your container images are stored.

Tasks and services (which direct ECS to run your containers) use images on container registries; via the task and service definitions inside ECS, container images are deployed onto container hosts in the form of containers.

ECS using EC2 mode offers a great middle ground. If you want to use containers in your infrastructure, but you absolutely need to manage the container host capacity and availability, then EC2 mode is for you. If your business has reserved EC2 instances, you can use those. You can use EC2 spot pricing but you need to manage all of this yourself.
With EC2 mode, even if you **aren't running** any tasks or any services on your **EC2 container hosts**, you are still **paying** for them while they're in a running state.
ECS as a product takes away a lot of the management overhead of using containers, in EC2 cluster mode, you keep some of that overhead and some flexibility.

![[ECS - Fargate Mode.png]]

Fargate mode removes more management overhead.
You don't have to manage EC2 instances for use as container hosts.
Fargate is a cluster model, which means you have no servers to manage. Because of this, you aren't paying for EC2 instances, regardless of whether you're using them or not.

- Fargate mode uses the same surrounding technologies - 
	- The Fargate service handling schedule and orchestration, cluster management and placement.
- You still use registries for the container images.
- You still use task and service definitions to define tasks and services.

What differs is how containers are actually hosted.
AWS maintain a shared Fargate infrastructure platform. Much like how EC2 isolates customers from each other, so does Fargate.

Task and service definitions are allocated to the shared Fargate platform. You still have your VPC.

A Fargate deployment still uses a cluster. And a cluster uses a VPC, which operates in availability zones.

Where it starts to differ - from a networking perspective - ECS tasks are injected into your VPC & given an elastic network interface. This has an IP address within the VPC. At that point, they work just like any other VPC resource. And they can be accessed from within that VPC. And from the public internet, if the VPC is configured that way (so, if the VPC is configured to use public subnets, which automatically allocate an IPv4 address; then, tasks & services can be given IPv4 addressing). // Tasks and services are actually running from the shared infrastructure platform. You access ?? through the injected NICs.

With Fargate mode, you only pay for the containers that you're using based on the resources that they consume.

You don't need to manage hosts, provision hosts, or think about capacity and availability.

How to advise when a business or a team should use:
- EC2 (natively - deploying an app as a VM)
- ECS (in **EC2 mode** - a containerized app running in ECS using an EC2 based cluster)
- ECS (in **Fargate mode** - a containerized app running in ECS Fargate mode)

**EC2 vs ECS**
- If you use containers, ... **ECS**
- It's generally a bad idea to run a docker host on an EC2 instance. The normal options are:
	- Run an application inside an operating system inside EC2.
	- Or utilize ECS in one of these two different modes.
		- Containers in general make sense if you're just wanting to isolate your applications. Applications which have low usage levels. Applications which all use the same OS. Applications where you don't need the overhead of virtualization.
- **Large** workload - **price** conscious - **EC2 Mode**
	- Use spot pricing, reserved pricing; make use of reservations you already have. Running your own fleet of EC2 based ECS hosts will probably be cheaper, but only if you can minimize the admin overhead of managing them: scaling, sizing, as well as correcting any faults.
- **Large** workload - **overhead** conscious - **Fargate**
	- Less management overhead versus EC2 mode
	- No exposure to container hosts or their management
- Small / Burst workloads - Fargate
	- Because with Fargate you only pay for the container capacity that you use. 
		- Having a fleet of EC2 based container hosts running constantly for non-consistent workloads is wasteful.
- Batch / Periodic workloads - **Fargate**
	- Fargate means that you pay for what you consume. EC2 mode would mean paying for the container. Instances even when you don't use them.

## Elastic Container Registry (ECR)
- Managed **Container image registry** service (like Docker hub, but for AWS)
- Each **AWS** account has a **public** and **private** registry
- Each **registry** can have many **repositories**
- Each **repository** can contain many **images**
- **Images** can have several **tags**
- Public = public R/O access. R/W requires permissions.
- Private = permissions required for any R/O or R/W (to pull or to push)

- Integrated with **IAM** - **Permissions**
- Image scanning, **basic** and **enhanced** (uses the *inspector* product)
- Near real-time **Metrics** - delivered into **CloudWatch** (auth, push, pull)
- **API Actions** = CloudTrail
- **Events** => **EventBridge**
- Replication ... Cross-Region AND Cross-Account

## Kubernetes 101
Open-source container orchestration system. Use it to automate the deployment, scaling, and management of containerized applications.

![[Kubernetes 101 - Cluster Structure.png]]

The control plane orchestrates containerized applications which run on nodes.

Pods are the smallest unit of computing within Kubernetes. You can have pods which have multiple containers and provide shared storage and networking for those pods. It's very common to see a one-container, one-pod architecture.

When you think about Kubernetes, don't think about containers. Think about pods. Pods are non-permanent things. They're created, do a job, then are disposed. There are other things linked to pods which provide more permanence.

![[Kubernetes 101 - Cluster Detail.png]]

Key Components
- **Cluster** - A deployment of Kubernetes; provides management, orchestration, healing, and service access
- **Node** - provide the compute resources; pods are placed on nodes to run
- **Pod** - a pod is 1 or more containers (often 1 container, 1 pod). Not long lived. The cluster replaces them as required.
- **Service** - Abstraction, service running on 1 or more pods.
	- Services provide an abstraction from pods. The service is typically what you will understand as an application. An application can be containerized across many pods, but the service is the consistent thing (the abstraction).
- **Job** - ad-hoc, creates one or more pods until completion.
	- A job creates one or more pods, runs until it completes, retries if required, and then finishes.
- **Ingress** - Exposes a way into a service (**Ingress** =>**Routing**=>**Service**=>**1+Pods**)
	- Ingress is how something external to the cluster can access a service.
		- External users come into an ingress. That's routed through the cluster to a service. The service points at one or more pods, which provides the actual application.
- **Ingress Controller** - used to provide ingress (e.g. AWS LB ingress Controller which uses Application & Network Load Balancers to allow the ingress)
	- But, there are also other controllers, such as Nginx and others for various cloud platforms.
- **Persistent** Storage (**PV**) - Volume whose lifecycle lives beyond any 1 pod using it.
	- It's best to architect things within Kubernetes to be **stateless** from a pod perspective. Remember, pods are temporary. If your application has any form of long-running **state**, then you need a way to store that state somewhere. State can be session data, but also data in the more traditional sense.
	- Any **storage** in Kubernetes by default is **ephemeral**, provided locally by a node.
		- Thus, if a pod moves between nodes, then that storage is lost. Think of this like instant store volumes running on AWS EC2.
	- You can configure persistent storage known as persistent volumes or PVs, and these are volumes whose lifecycle lives beyond any one single pod.

## Elastic Kubernetes Service (EKS) 101
This is AWS's implementation of Kubernetes as a service. AWS have taken the Kubernetes system and added it as a service within AWS. It's the same Kubernetes that you'll see anywhere else, just extended to work well within AWS.

- **AWS Managed Kubernetes** - open source & **cloud agnostic**
- can be run ... on AWS, Outposts, EKS Anywhere, EKS Distro
- **Control plane scales** and runs on **multiple AZs**
- **Integrates** with **AWS services** ... ECR, ELB, IAM, VPC
- **EKS Cluster** = EKS **Control Plane** & EKS **Nodes**
- **etcd** distributed across **multiple AZs**
- **Nodes** - **Self** Managed, **Managed node groups** or **Fargate** pods
	- Self Managed - EC2 instances which you manage and you're billed for based on normal EC2 pricing.
	- Managed node groups - still EC2, but the product handles the provisioning and lifecycle management.
	- You can run pods on Fargate - you don't have to worry about provisioning, configuring or scaling groups of instances. You don't need to choose the instance type or decide when to scale or optimize cluster packing. Instead, you define Fargate profiles which mean that pods can start on Fargate.
	- Deciding between self-managed, managed node groups or Fargate is based on your requirements
		- If you need windows, GPU, Inferentia, Bottlerocket, Outposts, Local zones ... Check node type
	- **Storage Providers** - include.. EBS, EFS, FSx Lustre, FSx for NetApp ONTAp



- When you think of an EKS deployment, you're going to have two VPCs.
	- The first is an AWS managed VPC. It's here where the EKS control plane will run from across multiple availability zones.
	- The second VPC is a customer managed VPC.
		- In this case, the Animals for Life VPC.
		- If you're going to be using EC2 worker nodes, then these will be deployed into the customer VPC.
		- Normally the **control plane** will **communicate** with these worker nodes via ENIs which are injected into the customer VPC. The **kubelet service** running on the worker nodes connects to the control plane, either using these **ENIs**, which are injected into the VPC, but it can also use a **public control plane endpoint**. Any administration via the control plane can also be done using this public endpoint.
		- Any consumption of the EKS services is via ingress configurations, which start from the customer VPC.
