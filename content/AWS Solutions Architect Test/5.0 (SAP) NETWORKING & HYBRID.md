## DHCP In a VPC
- **DHCP** - Dynamic Host Configuration Protocol
	- .. **auto configuration** for network resources
		- ex: how a laptop / phone gets an ip address.
			- Device has L2 Mac Address (vendor part + device part).
- .. starts with L2 broadcast to get info from DHCP server
	- broadcast allows it to discover a DHCP server on the local network.
	- Once discovered, the device (DHCP client) and the DHCP server communicate using Layer 2 initially (meaning frames containing MAC addresses). The end result is the device obtains Layer 3 networking information and additional pieces of configuration.
- IP address, Subnet Mask & Default Gateway
	- These are the minimum requirements for communication at Layer 3 on the local network and beyond using the default gateway.
- DNS Servers & Domain name
	- DHCP within a VPC, also configures which DNS service to use
	- Typically, these are the Amazon provided DNS within a VPC
	- it also allows a custom domain name to be configured on resources within the VPC
- NTP Servers, NetBios Name Servers & Node type
	- It also configures NTP servers for time synchronization
	- as well as NetBIOS name servers and NetBIOS node types
	- these are only used if you're making use of the NetBIOS protocol
- **AmazonProvidedDNS** & **Custom DNS Domain**
	- When you're setting which DNS service to use within a VPC, you can either explicitly provide values or you can use Amazon provided DNS
	- This always maps onto the Route 53 resolver running within the VPC
	- You're also allocated one or two domain names for any resources provisioned into the VPC
	- For example, with EC2 instances, you're allocated a private DNS name, and the format of this name depends on whether you're using US East 1 or other AWS regions. 
	- You're also given a public DNS name if the instance has a public IP address allocated
	- You might want to give your EC2 instances custom domains, and you can do that as long as you use your own DNS servers. You can add the custom domain name and the custom DNS servers to the DHCP option set

The AWS implementation of DHCP is configured using using DHCP option sets.
**DHCP in a VPC**
![[DHCP in a VPC.png]]
(**exam**) DHCP Option Sets are **immutable**.
Any new settings contained in the new DHCP option set will only affect anything in the VPC once a DHCP renew occurs. The timing of this can vary.
- I mentioned previously that DHCP in general is how a device gets the IP address, subnet mask and default gateway.
	- This is also true for DHCP within a VPC. But you can't configure these values within an option set. 
	- The **IP address** is allocated automatically
	- The **subnet mask** is based on the VPC subnet 
	- The **default gateway** is always the **subnet plus one address** (the address that the VPC router interface uses within that VPC subnet)
- What you can configure within an option set is the **DNS service** to use.
	- By default, this is the **Route 53** resolver, which can be referenced using Amazon provided DNS.
		- This uses the **VPC plus 2** address. The subnet plus 2 address is reserved in every subnet. But since I know that you like precision, it's actually the VPC plus 2 address, which the Route 53 resolver uses for DNS within the VPC.
- You can use option sets to configure which **NTP** service to use if time synchronization within a VPC is important.
- Anything provisioned in the VPC also gets **DNS names** allocated.
	- You always have a **private** one, which takes this form: ip-private-ipv4-address.region.compute.internaI
	- If the instance has an allocated **public** IP, it also gets a public DNS name: ec2-pubIic-ipv4-address.region.compute.amazonaws.com
	- AWS provide these automatically. If you want to **customize** the **DNS names**, you need to supply your own DNS service to use within the DHCP option set.

## VPC Router Deep Dive
**VPC Router** Deep Dive
- **Virtual Router** within a VPC
- **Highly Available** - across **all AZs** in that **region**
	- When you create a VPC, the VPC router is created along with it and it operates in all of the AZs in the region which the VPC runs from.
	- The multi AZ provisioning is automatic.
- **Scalable** - no performance management required
	- It delivers whatever performance the resources within the VPC provide.
- **Routes** traffic **between subnets**
	- Remember, subnets can be in different availability zones, so potentially in different underlying physical facilities
	- The VPC router ensures that data gets from one subnet to another
- ... **FROM EXTERNAL** networks **INTO** the **VPC**
	- External networks in this context can mean other VPCs, on-premises networks, other cloud platforms and even the public internet. Other networking gateways are required for these connections to be active, such as the IGW for Internet Connectivity, but it's the VPC router which controls the routing within the VPC to or from these other networks.
- ... **FROM** the **VPC** into **external networks**
- Interface in every subnet ... "**subnet+1**" address (default GW via DHCP Option Set)
	- First IP address in each subnet after the network address itself. This is provided to resources in the VPC as the default gateway, via the DHCP option set associated with that VPC.
		- // See [[5.0 (SAA-C03) VIRTUAL PRIVATE CLOUD (VPC) BASICS#VPC Subnets]] for more on reserved VPC ip addresses.
- Controlled using **route tables**
	- which are associated with subnets in the VPC

**VPC Router Deep Dive**
![[VPC Router Deep Dive.png]]
From a networking perspective though, each subnet has an interface for the VPC router inside that subnet. Those interfaces use the subnets + 1 address. Any services running inside the subnets have this plus one address as their default gateway. Any packets which are destined for outside of that local subnet use the plus one address as the default gateway, and the VPC router controls where the data goes from that point forward.

The decisions that the VPC router makes are controlled via **route tables** - associated with subnets within the VPC.

It's the VPC router configured with route tables together with other gateway objects which can direct traffic entering and leaving the VPC.
(on-prem example) - The VPC Router will generally use a network gateway object such as the **Transit Gateway** or **Virtual Private Gateway (VGW)**.

- Every **VPC** is created with a **Main route table** (RT)
- .. **default** for **every subnet** in the VPC
- **Custom route tables** can be created and associated with subnets in the VPC - **removing the Main RT**
	- If you create a custom route table, you can associate that custom route table with any subnets within that VPC. Once you do associate it, the main route table is disassociated. If you disassociate the custom route table, the main route table is associated again with those subnets.
	- The main route table in general should be left blank.
	- Any **routes** that you want to create should be added to a **custom route table**, and these custom route tables can be explicitly associated with VPC subnets.
		- Why? If you disassociate a custom route table, the subnet is re-associated with the main route table. From a network security perspective, you don't want this **automatic association** to add any **unintended routes**.
- (**exam**) **Subnets** are **associated** with **ONE RT** (Main or Custom)
- Route tables contain **routes** - **most specific** routes **first**
	- /32 being most specific - one ip address.
	- 0.0.0.0/0 being the least specific (default IPv4 address)
	- // for SAA & SAP level, this is enough knowledge, but the Advanced Network Specialty course needs additional detail ..
		- // .. what happens if there are two routes which are equally as specific, but are learned from different things
- RTs **can be associated with gateways** (more on this later)
	- In addition to associating route tables with subnets, you can perform what's known as an **edge association**. This is where you associate a route table with a network gateway.

**VPC Router Deep Dive2**
![[VPC Router Deep Dive2.png]]
Now a route table is just a list of routes. When traffic is leaving the subnet, the VPC router reviews the IP packet; determines which routes match based on SRC & DST addresses. When a route's been selected, traffic is forwarded to its destination (the route target).

All route tables have at least one route, the local route, and this matches the entire VPC CIDR range, and it lets the VPC router know that traffic destined for any IP address within the VPC CIDR is local & can be delivered directly. If the VPC is IPv6 enabled, it also can have IPv6 routes, and there is also going to be a local IPv6 route which matches the IPv6 CIDR for the VPC.

These local routes can never be updated. They're always present, and the local routes always take priority. They're the exception to the previous rule.

(**exam**) Remember, route tables are associated to zero or more subnets. It is possible to create a route table and not associate it with any subnets, but a subnet has to have an associated route table. Either the main route table or a custom one that you create.

(summary)
A route table controls what happens to data as it leaves the subnet or subnets that that route table is associated with. Local routes are always there, uneditable, and match the VPC, IPv4 and IPv6 CIDR ranges. For anything else, higher prefix values are more specific and take priority. A default route is what happens if nothing else matches. This is generally used to direct any unmatched traffic through to a suitable gateway (e.g. the IGW).

## Transit Gateway Deep Dive
**Transit Gateway - Typical Architecture**
![[Transit Gateway - Typical Architecture.png]]
- Networking Object
- Hub and spoke architecture.
- Attach to other networking objects and types.
	- VPC (via VPC attachments)
	- On Prem (via VPN attachments)
		- used as a termination point for the VPN tunnels rather than a VGW
		- Can integrate with Direct Connect directly
			- A Transit VIF is created rather than a private VIF on a Direct Connect. This goes via a DX Gateway, and this DX Gateway can attach to the Transit Gateway. 
				- One DX Gateway can be attached to three Transit Gateways in this way, and provide the DX connection access to all of the things connected to all of those Transit Gateways.
- The Transit Gateway for all of these attachments has a default route table, which is populated with any routes learned from the attachments.
	- For the VPCs, the CIDR ranges of those VPCs
	- For the VPNs, the routes learned using BGP over the VPN
	- For the DX gateway and Transit Gateway attachment, you define the networks within the attachment configured at the DX Gateway side.
	- .. this default route table has, by default, all routes which the Transit Gateway learns about
	- .. by default, the route table is used by all of the attachments of the Transit Gateway
- You can **peer** Transit Gateways with other Transit Gateways in different regions
	- up to 50 per TGW

(summary) **Transit Gateway** Deep Dive
- A TGW by default has one RT
- .. all attachments use this RT for routing decisions
- .. all attachments propagate (add) routes to it
	- (^ exception) * Peering Attachments (more on this in a second)
- All attachments can route to all attachments
**Transit Gateway - Peering**
![[Transit Gateway - Peering.png]]
(**exam**) No route propagation over peering attachments. Routes aren't shared (the Transit Gateway on the left isn't passing routes that it knows about to the Transit Gateway on the right). You need to use **static routes** to allow this peering to function. And that's much the same as you use when configuring VPC peering.

(**exam**) Use unique ASNs for future route propagation features.

The resolution of public DNS to private addressing, for example with EC2, isn't supported over inter-region peers. So remember how with a VPC, if you attempt to resolve the public DNS of an EC2 instance from within the same VPC, it will resolve to the private address. This doesn't currently work over Transit Gateway peering attachments. And this is more to do with the cross-region nature rather than a Transit Gateway limitation.

Much like VPC peering, the data transfer over the peer is encrypted over the global AWS network.

**Transit Gateway Deep Dive**
- Up to 50 peering attachments per TGW
- Different regions & accounts
- No route learning/propagation across peer
- .. static routes are required
	- .. to allow each TGW to be aware of the networks of the other side of the peer
- Data is encrypted (just like with VPC peering)
- .. expect updates ... choose unique ASNs for the TGWs
**Transit Gateway - Isolated Routing**
![[Transit Gateway - Isolated Routing.png]]
In the default mode of Transit Gateway, You have one route table, and all attachments are associated with the same route table, which means when traffic leaves that attachment destined for somewhere else, the attached route table is used to decide where that traffic goes to. In addition, it's also the default that all attachments propagate to this same single route table, which means that all attachments are aware of all other attachments, and each of them can route to every other attachment.

The transit gateway knows how to route traffic from every connected attachment to all of the others. Now, you might not want this...

(summary points)
- Attachments can only be Associated with 1 RT
- RT's can be associated with many attachments
- Attachments can propagate to many RT's
- .. even those they are not associated with

These two mechanics are what allows us to create some fairly advanced isolated routing. You can create hub-and-spoke networks, multiple of them, inside a single transit gateway for routing isolation.

**Transit Gateway - Isolated Routing2**
![[Transit Gateway - Isolated Routing2.png]]
Route table **associations** are used when data is exiting an attachment (how the transit gateway decides where to route traffic to). **Propagation** is the configuration which controls which route tables will be populated with routes known by the attachments. Propagation controls which route tables learn about routes from which attachments. the default is this single route table which all attachments will use, and all attachments are configured to propagate into that route table.

But what if you want to isolate networks? In this example, what if you wanted the VPCs to be able to access the on-premises networks, but not each other? You want VPC1 to be able to communicate with the 10.18 and 10.20, and 10.19 networks, but you don't want VPC1 to be able to communicate with VPC2, or vice versa.

Generally, when configuring route tables inside Transit Gateway, any attachments, or any networks which need to freely communicate, will generally use the same route table, and all of them will propagate to that route table. For isolated networks, you'll want to isolate the route tables and the propagations.

So, we create a route table (tgw-rt-7007), and we configure all attachments to propagate to this route table. Then, we associate this with only the VPN and Direct Connect Gateway attachments. This means that the on-premises networks, and the on-premises networks, can talk to each other, and it means they can talk to the VPCs. What we don't want to do, though, is associate the VPC attachments with this route table, because if we did, they too could communicate with each other, as well as all of the on-premises networks. What we need to do is refine what routes they have available, and to do that, we create another route table, route table (tgw-rt-1337). Then, we set the on-premises attachments, to propagate their routes to this route table, which means that it contains the 10.18 and 10.19 CIDR ranges, and then we associate this route table with the VPC attachments. This means that the VPCs can route to the on-premises networks, because those attachments are propagating their routes to this route table, but the VPCs can't reach each other, because they're not propagating their routes to this route table. In effect, it creates two items, and these two are isolated routing domains.

(**exam**) this is really, really critical to understand for the exam, and especially so for real-world usage. You need to understand the difference between association and propagation, and how we've architected this solution, so the VPC attachments use a separate route table, which they don't propagate their CIDR ranges into. Remember, route tables are used for outgoing traffic

**VPC Routing - Basics**
![[VPC Routing - Basics.png]]
If you have **multiple routes** which could apply and they all have the same prefix length, the next step of priority is that **statically** added routes **take priority** over propagated ones. The logic to this is that if you've added something explicitly to a route table, then it is important and it should be there and it should be preferenced versus anything which is dynamically learned from other entities in AWS. If you have a route table which has a static route to one destination and a VGW which learns that same route with that same prefix and you have route propagation enabled on that route table, you will have two routes to the same destination with the same prefix. And in this case, the static route will be selected as the higher priority and that one will be used.

There are situations where you might have multiple routes, both using the same prefix length and both dynamically learned via route propagation. There's another level of prioritization. For any routes learned via a VGW, the next priority order is:
- First - The routes learned from a **Direct Connect**
- Second - then routes learned via a **static VPN**
- Third - routes learned via a **BGP based VPN**
- Fourth - **ASPath** is used
	- if you still have multiple valid routes at this point, so routes that are both learned via propagation, both learned via BGP, and both with the same prefix length
	- ASPath - BGP term used to represent two different ASNs within BGP. Represents the distance between two different autonomous systems. Routes with a shorter ASPath would be preferenced versus those with a longer ASPath
	- // [[16.0 (SAA-C03) HYBRID ENVIRONMENTS AND MIGRATION#Border Gateway Protocol 101]]

## Accelerated Site-to-Site VPN
// [[16.0 (SAA-C03) HYBRID ENVIRONMENTS AND MIGRATION#AWS Site-to-Site VPN]]
Accelerated Site-to-Site is a performance enhancement to the normal site-to-site VPN product, which uses the AWS Global Network.

**Accelerated Site-to-Site VPN**
- S-2-S VPN - 2 Resilient **Public Space** Endpoints
	- (refresher) Historically, site-to-site VPNs have used a VGW attached to a VPC. They also use a Customer Gateway (CGW) object, which represents your customer router. between these two gateway objects, a VPN connection is created. this allocates two resilient public space endpoints, which are hosted in separate AZs.
- 2 IPSEC Tunnels
	- // These endpoints are used to establish two IPsec tunnels between your customer gateway and the AWS VPN infrastructure.
- **Transit** over the **Public Internet**
- **Variable** performance, Latency & consistency
	- ...or a Direct Connect (DX) Public VIF
- **Better performance** - but costly for many businesses
	- //  is where Accelerated Site-to-Site VPN improves things
**Site-to-site VPN - VGW**
![[Site-to-site VPN - VGW.png]]
(left) VPC w/ **VGW**; (right) VPC w/ CGW attached.
By using the public internet as transit, you open yourself to lots of different points, which can impact the performance of the connection between AWS VPCs and your on-premises environments.

**Site-to-Site VPN - TGW**
![[Site-to-Site VPN - TGW.png]]
Another way that you can potentially implement site-to-site VPNs is by using the **Transit Gateway**. Significantly simplifies VPN and multi-VPC architectures. But, the transit of data is still moving across the public internet meaning it suffers from variable latency and inconsistent speeds.

**Accelerated Site-to-Site VPN**
![[Accelerated Site-to-Site VPN1.png]]
With Accelerated Site-to-Site VPN, the architecture is slightly different. When using accelerated mode, instead of connecting to a VGW or TGW, the AWS Global Network is used (edge locations) for entry to the AWS network. When you create a VPN connection, you get two IP addresses, and each of those IP addresses are allocated to all of the edge locations, and data is routed to the **closest edge location** to the customer gateway. This means that the public internet is only used for a minimal amount of time, just to get to the closest edge location. Results in **lower latency**, **higher throughput**, and **less jitter** (jitter = variance in latency). Essentially, the quality of the connection is better because it's using the public internet less.

Important factors to be aware of:
- (**exam**) Acceleration can be enabled when creating a TGW VPN attachment only (not compatible with VPNs using a VGW)
- When you do enable this feature, there is a **fixed accelerator fee** and a data **transit fee**.

**Accelerated Site-to-Site VPN**
![[Accelerated Site-to-Site VPN2.png]]
We're combining three different products: the site-to-site VPN, the transit gateway, and the global accelerator. The result is that your data gets to the closest edge location, and from that point onward, it's using a high-performing and efficient global network to transit through to its final destination. This is simply just an option that you need to enable on a VPN connection as long as you're using transit gateway. Offers significant reductions to the variance in latency known as jitter, lower overall latency, and improvements to transit speeds.

For any real-world applications, my recommendation is to use this feature by default, and this will mean that for any VPN deployments, you should, where possible, **prefer using the transit gateway** and attaching the VPN to that transit gateway versus using a VGW. VGW-based VPNs are going to start missing out on more and more advanced features that are released by AWS because transit gateways should now be the preferred product. Remember that for the **exam** and for real-world usage. If you're deploying site-to-site VPNs, where possible, use the transit gateway and make sure you enable accelerated site-to-site VPN

## AWS Client VPN
So far, I've talked about site-to-site VPNs, which is how you connect one or more business premises to AWS. Client VPN is similar, but instead of sites connecting to AWS, it's clients which connect. 

**Client VPN**
- Managed implementation of "**OpenVPN**"
	- Nothing prevents you from building your own OpenVPN server running on an EC2 instance, in the same way that nothing prevents you from installing your own database on EC2. Client VPN is the same for OpenVPN as RDS is for databases. It's an AWS-managed implementation.
- .. any client with OpenVPN software is supported
	- // because OpenVPN is an open standard, pretty much every operating system and consumer-grade router can support it
- Connect to a **Client VPN endpoint**
- .. associated to **ONE VPC**
- .. **1+** Target Networks (**high availability**)
- .. **billed** based on **network associations**
	- You're charged based on two elements.
		- First, a flat rate based on the **number of subnets** that you configure as **target networks**, and you can do **one or more** for high availability.
			- // The reason for the subnet billing architecture is that for every subnet you configure as a target network, an interface is placed into that subnet, which is used for traffic flowing between the target networks and the client devices. And those interfaces have a cost, just like any other interface endpoints do within a VPC.
		- Second, an **hourly fee** **per** client **VPN connection**.
**Client VPN**
![[Client VPN.png]]
To get started, we create a **client VPN endpoint**, and we **associate** this with a **VPC** and one or more **subnets** within that VPC. This creates an interface within that subnet. You can only pick one subnet per AZ, and you should view this as a method to ensure HA of the solution.

Client VPNs can use various methods of **authentication**:
- Certificates
- Federated identities
- AWS directory service

- Integrates with CloudWatch
	- Connection logs are stored in CloudWatch logs
	- Metrics stored within CloudWatch

You define a **route table** with the client VPN endpoint. By default that route table is pushed to any clients which connect to the client VPN endpoint. By default this replaces any existing route table on the client machines. The route table contains any of the target networks by default (in this case, the subnet on the left of VPC-A), but you can add other routes to this route table manually.

For example, if you want to allow connections from the clients to the public internet, then you could add a default route for the public internet, and logically you'd also need a NAT GW and an IGW, because the connections are coming from the client VPN interface within a private subnet.

You could also allow connections to instances in VPC-B. To do that, you'd need to create a VPC peer and configure routing as usual for that, and then add a route to the client VPN endpoint route table, allowing connectivity to the peered VPC.

What's important to understand is that you treat any client devices as normal things running within the VPC. They need the same networking gateways, in this case a peering connection, a NAT GW, and an IGW, to access resources just as a normal VPC interface would need.

Additionally, the default behavior is that the client VPN route table replaces any local routes on the client. It means the client devices can't access anything locally on their local network. Any communications between clients (in this case, Client 1 and Client 2) occur over the client VPN, which is actually a suboptimal path for client local communications.

**Client VPN - Split Tunnel**
![[Client VPN - Split Tunnel.png]]
You also have the option of using what's called split tunnel VPN. So as a reminder, by default, all traffic is routed via the client VPN endpoint. If you enable split tunnel, it means that any routes from the client VPN endpoint are added to client machine route tables. They don't replace anything that the clients already have. This means is that connections to the public internet will go directly through the client machine's normal default route. And connections between clients, or from clients to other devices on the local network, will not use the client VPN. This represents an optimal path.

(**exam**) - Split tunnel is not the default.

## Direct Connect (DX) - Security (MACSec)
MACSEC is a security feature which improves or at least partially improves a long-standing problem with Direct Connect which is the lack of built-in encryption.

**MACSec - 101**
- Frame **encryption** - **layer 2** - IEEE 802.1AE-2018
	- // MACSEC is a standard which allows frames on a network to be encrypted.
		- // [[0.0 (SAA-C03) Cloud, Networking and Technical Fundamentals#Layer 2 - DataLink - PART1]]
	- // MACSEC is a standard which extends standard Ethernet IEEE 802.1 AE
- **Hop by Hop** .. between two switches/routers.
	- // MACSEC provides a hop-by-hop encryption architecture.
	- // This means that two devices need to be next to each other at layer 2 in order to use MACSEC. This is referred to as layer 2 adjacency.
- **Confidentiality**
	- // MACSEC provides strong encryption at layer 2 by encrypting the frame's Ether type and payload so it becomes completely opaque to anyone observing it from the outside.
- **Data Integrity**
	- // MACSEC adds additional fields to ensure that data cannot be modified in transit without both parties being able to detect that modification.
- **Data origin authenticity**
	- // This ensures that both parties can see that frames have been sent by the other trusted peer in a MACSEC relationship.
- **Replay protection**
- **Not end-2-end** - does NOT replace IPSEC over DX
	- // it doesn't replace IPSec over Direct Connect because it's not end to end. It's a hop-to-hop, layer-2, adjacent encryption standard. It's used to encrypt a small part of the flow of data through the Direct Connect architecture.
- Designed to allow for super high speed ... terabit networks
- **Secure Channel** - unidirectional (**1 IN**, **1 OUT**)
	- // Each MACSEC participant creates a secure channel that's used to send traffic to the other participant. These channels are unidirectional.
- .. Secure Channel Identifier (**SCI**)
	- // uniquely identifies a secure channel.
- **Secure Associations** - **sessions** on SC, generally **1** exists at a time
	- // Communication that occurs on each secure channel takes place as a series of transient sessions called secure associations. This means that over the lifetime of a MACSEC relationship, then you're going to have multiple secure associations take place on every secure channel. Each secure channel generally only has one secure association which is running at one time. So generally only one of these exists.
- ... except for when they are being **replaced**
	- // The exception to this (generally, 1 SC existing at a time) is when these secure associations are being replaced because a new secure association will be created before the old one is torn down.
- MACsec encapsulation - 16 bytes **MACsec tag** & 16 bytes Integrity Check Value (**ICV**)
	- // MACSEC modifies Ethernet frames by inserting a 16 byte MACSEC tag (a.k.a. SEC Tag or Secure Tag). This occurs just before the Ether type.
	- It also adds a 16 byte integrity check value at the end of the frame
- MACSec Key Agreement - **discovery**, **authentication** & key **generation**
	- // MACSEC handles keys using the MACSEC Key Agreement Protocol or MKA.
	- // the Key Agreement Protocol manages peer discovery, authentication and the generation of encryption keys.
- **Cipher Suite** - **how** data is **encrypted** ... packets per key, rotation ....
	- // The type of algorithm that's used, the number of packets per key, key rotation.
	- // Like other Cipher Suites in AWS, this controls the how of the encryption and decryption process.

**Direct Connect - NO MACsec**
![[Direct Connect - NO MACsec.png]]
Problem: Private VIFs are not encrypted.

We have **Plaintext 802.1Q** frames being moved across the cross connect between the DX port and our port on a customer or provider router. This data center isn't owned by AWS, so, we've introduced another entity that we have to trust or manage **risk** for into the chain of communications.

If we've **extended** the cross connect or any of the VIFs through to our business premises, then that's another party that we have to trust and another portion of the communication which requires risk management.

The only option that we've had available historically as a network architect or specialist is to use a public VIF with an IPSec VPN running on top to provide secure and private access. An IPSec VPN provides end-to-end encryption, but comes at the cost of speed (because of the computation requirements). MACsec is a different model.

**MACsec - 101**
![[MACsec - 101.png]]
This is a standard 802.1q frame. The VLAN tag field (802.1Q field) allows it to be used to create multiple virtual LANs in the same layer 2 space. But, it's plaintext (unless the payload was encrypted higher up the OSI stack).

With MACsec we take the same basic frame but we add a few additional elements:
- MACsec header (security tag)
	- Channel
	- Secure Association
	- Packet Number
- Integrity check value field
These frames allow MACsec to function. It means two things:
- (1) The original frame components (ET, 802.1Q, and payload fields) are **encapsulated & encrypted**.
	- // To any network devices not directly involved in the hop to hop MACsec link, this portion of the frame is encrypted.
- (2) The entire frame is **authenticated** and **integrity protected**
	- // MACsec devices authenticate frames received from the other and can detect any alteration to those frames.
	- // This combined with the encryption means that at least for a single hop, frame payloads are protected from eavesdropping and from alteration.

**Direct Connect - with MACsec**
![[Direct Connect - with MACsec.png]]
This architecture shows the MACsec link between the AWS Direct Connect router in the AWS cage and a customer router in the customer cage. Both of these are at the DX location.

MACsec is something which is defined on either a **DX connection** or a link aggregation group (**LAG**). In both cases you need to create and assign a **CAK / CKN pair** onto the interface or the LAG. Think of this like an **encryption key**.
	You don't need to understand the whole architecture for the exam, but this is something which is configured on both the DX connection or the LAG and on the customer side.

Once this is done, **secure channels** are established one in each direction. Over which **secure associations** can be created (remember normally this is one at a time, but two will be used when changing associations). They have a lifetime and they need to be refreshed. Once secure associations are active, frames will be **encrypted** and their **integrity** will be verified.

**Direct Connect - with MACsec**
![[Direct Connect - with MACsec2.png]]
It's possible to **extend** this. This requires a dedicated physical extension of the cross connect. This type of extension requires **layer 2 adjacency**. Because the customer device and the AWS DX router need to be able to communicate with each other using layer 2 frames. You need to be careful when using a comms provider for this. The cable will have to be dedicated and capable of extending this layer 2 adjacency outside of the DX location. This is something very specific that you need to check with the communications provider and confirm if any extensions that they provide are capable of this layer 2 adjacency.

**MACsec** is a great feature which allows you to **protect** the **data path** between your **customer equipment** and the **AWS DX router**. Since that link goes through a non-AWS owned data center and is potentially extended by a coms provider, it allows you to secure that link at layer 2. It is **not** however a **substitute** for **IPSec VPN** running over a **public VIF** as that provides **end to end encryption** and also allows you to **configure connections to VPCs outside** of the local DX region.

- ... over the layer 2 direct connect (DX)
- Interfaces - **BGP Peering Session** + **VLAN**
	- // A VIF is simply a BGP peering session - something which exchanges prefixes which allow traffic to be routed from one point to the other.
- **VLAN Isolates**, **BGP** exchanges **routes** & **authenticates**
	- // the VLAN isolates the different Layer 3 networks using 802.1Q (VLAN tagging)
		- // [[0.0 (SAA-C03) Cloud, Networking and Technical Fundamentals#VLANs TRUNKS & QinQ]]
	- // BGP exchanges prefixes so that each end knows which networks are at each side.
	- // BGP MD5 authentication means that only authenticated data will be accepted by either side.

- Public, Private, & Transit
- Public - used to connect to public zone services (services which don't run within a VPC, or services which do run in a VPC but have public IP addressing).
- Private - used to connect to AWS private networks (VPCs). Anything communicating between your corporate network and AWS VPCs using private addressing.
- Transit - allow integration between Direct Connect and Transit Gateways.
- **50** **+ 1** Virtual Interfaces on a Direct Connect - Dedicated
	- // A single dedicated DX connection can have a total of 50 public and private VIFs, as well as one transit VIFs.
	- // For hosted connections, this is just one VIF
- BGP is between the **Customer DX router** ...
	- ... and the **AWS DX Router**
	- ... can be extended to customer premises

**DX VIFs - BGP Session + VLAN**
![[DX VIFs - BGP Session + VLAN.png]]
Between the customer router in the DX location and the AWS DX router is the physical cross connect. This is a Layer 2 connection, and it's known as having Layer 2 adjacency. This means that the customer DX router and the AWS DX router can communicate directly using frames (L2 data units).

We run multiple L3 networks (VLANs) over the top. This allows for multiple isolated L3 connections. Using these VLANs we create VIFs. VIFs use a specific VLAN and a BGP session together.

VLAN 100 = private VIF to VPC1; VLAN 300 = private VIF to VPC3; VLAN 200 = public VIF to AWS public zone.

Each VIF has IP version 4 or IP version 6 BGP peering configured, which is how prefixes are exchanged, so that the AWS side knows the private network ranges of the customer side & vice versa.

These BGP sessions use authentication so that only valid data is available (MD5).

The VLANs and thus the VIFs can be extended to the business premises using Q-in-Q encapsulation.
// [[0.0 (SAA-C03) Cloud, Networking and Technical Fundamentals#VLANs TRUNKS & QinQ]]

That, architecturally, is how **VIFs** work - It's a **VLAN** to isolate traffic. It's **BGP** to exchange prefixes so that each side knows the other side's networks. And it's **MD5** authorization.

**Private VIFs**

	- // Private VIFs are created on a Direct Connect connection. They're used to access one AWS VPC, specifically the resources within one AWS VPC using private IP addresses.
		- // If you have EC2 instances in a VPC, and you're trying to access the instance via its private IPv4 address, a private VIF will work. If you're trying to access the same EC2 instance using a public IPv4 or Elastic IP, then private VIFs cannot be used for this.
	- \* You can work around this limitation by using Transit Gateways and Direct Connect Gateways

- .. **in the same region** as the DX location your connection terminates in
	- // A private VIF, by default, attaches to a VPC via a VGW in the same region only
- (**exam**) 1 private VIF = 1 VGW\* = 1 VPC\*
	- // This is the architecture to remember. There are workarounds, but remember this.
- **No encryption on private VIFs** ... apps can layer on encryption (e.g **HTTPS**)
	- // If you have a private IP on your corporate network, and a private IP in a VPC, and these are communicating using a **non-encrypted** protocol, then the data will transit in **plain text** form between the two networks. Direct Connect isn't adding encryption, and neither is the private VIF.
		- // There are ways around this, but start with the default assumption that there is no encryption added by Direct Connect.
- MTU of **1500** or **9001** (Jumbo Frames)
	- // [[0.0 (SAA-C03) Cloud, Networking and Technical Fundamentals#Jumbo Frames & MTU]]
	- But, you need to make sure that everything in the communications chain supports it, including any EC2 instances that you're communicating with.
- Using VGW = Route Propagation enabled by default !
	- // A private VIF which terminates into a VGW can also use route propagation. This allows routes to automatically be added onto route tables, which are learned from the remote side of the VIF.
	- // It's a useful feature, but it means you need to terminate your private VIF into a VGW. There are other ways that you can terminate a VGW and these don't offer the same type of route propagation.

	- // You'll have to choose a VLAN ID (using 802.1Q). This VLAN ID needs to match the configuration at the customer side.

## Direct Connect Link Aggregation Groups (LAG)
**DX Link Aggregation Groups (LAG)**
- **Multiple** Physical Connections **act as one** - **Speed * n**
	- // While LAGs do in certain ways provide resilience benefits, AWS don't market them as a feature that improves resilience. They help protect against the failure of smaller components such as cables or fiber optical interfaces, but do nothing to provide any resilience against hardware failure or the failure of an entire location.
	- // (**exam**) AWS doesn't market LAGs as a feature that improves resilience. For exam questions which mention LAGs, focus on them being a **speed** feature and an **admin overhead** feature rather than one which is related to resilience.
- **Active** / **Active** Architecture
	- // All members of the LAG are used at the same time.
- Maximum of 4 Connections per LAG
	- // Either two 100 gig ports or four less than 100 gig ports - you can create a LAG with a maximum speed of 200 gig.
- All connections need to be the **same speed**
	- // You can't mix 1 gig & 10 gig connections.
- .. and terminate at the **same** DX **location**
	- // creating a LAG with direct connects in different DX locations isn't possible.
Just to reiterate, LAGs are about speed, not resilience. In theory, a LAG can protect against a switch port failing, or the actual cross connect itself, but you often have to assume that these things share switching equipment. And so LAGs are definitely more about improving speed and manageability.
- A LAG has a '**minimumLinks**' attribute - the LAG is active as long as **this value** or **MORE** connections are active
	- // If you set this value to say 2, then if the number of direct connects inside a LAG (remember, a LAG can have 4 max), and the number of working direct connects within a LAG falls below this number, the LAG is also viewed as in a failed state. This is designed to avoid the oversaturation of any remaining operational links within a lag if you have failures.
		- // Trying to force four Direct Connects worth of traffic through one operational member of a lag is not going to be ideal.

**DX Link Aggregation Groups (LAG)**
![[DX Link Aggregation Groups (LAG).png]]
This is the type of architecture that you can expect with a LAG - where you combine two Direct Connects into one logical connection capable of higher speeds. The speed that a lag is capable of delivering is a combination of all of the individual speeds of the individual links that are part of that LAG.

You can move existing Direct Connects into a LAG, or you can create a LAG with the Direct Connects already inside. You can create a lag with one Direct Connect as a starting point, but you need to be careful because members of a lag are allocated to the same DX router chassis. You could be in a situation where there's no additional port capacity in that chassis if you don't allocate all of the members of the lag at the same time. It's always **best practice** to **allocate** the **Direct Connects** at the same time as you're **creating** the LAG. That way the ports are pre-allocated, and you will always have the capacity as required for the lag.

Now an architecture which uses link aggregation groups still has many single points of failure. The AWS DX routers, the DX locations, the customer DX routers, customer routers, and customer premises are all potentially single points of failure. Lags do add some resilience benefits to the cables, the cross-connects, and the fiber optical components used to interface the cables with the equipment, but when you think about LAG, think about speed as a primary consideration.

(**exam**) Key Facts
- A LAG is capable of having two 100 gig ports, or four ports if using less - 200 gig max performance.
- LAGs need to use the same speed of connection
- They need to go in to the same DX location

## AWS PrivateLink
AWS PrivateLink is the tech stack which supports VPC interface endpoints. AWS PrivateLink enables you to connect to services in a secure way which are hosted by other AWS accounts. These are called endpoint services. You can connect to these directly or you can utilize AWS Marketplace partner services. in both cases, these services are presented into your VPC via private IP addresses and ENIs. They work in the same way as normal VPC interface endpoints.

**AWS PrivateLink**
![[AWS PrivateLink.png]]
A typical situation where PrivateLink might be used: you have an application that you want to securely provide to another AWS account. Or, you want to consume a service provided by a service provider.

Because we're going to be working across accounts, we need to work with availability zone IDs (because what's US East 1A in one account might be US East 1C in another - // [[3.0 (SAP) ADVANCED PERMISSIONS & ACCOUNTS#AWS Resource Access Manager (RAM)]]). AZ ID's allow us to be consistent across accounts.

Service provider - the VPC from where the service is provided from
VPC Service Consumers - VPCs which consume a service.

Let's assume there's demand to access this application from the consumer VPC from workspaces running inside two subnets in this VPC accessed via the workspaces client that's running on user devices.

The cat images application is private.

To allow that we need to create an endpoint service within the provider VPC; to ensure that the application performs well and is resilient we use a network load balancer. This creates network load balancer nodes in each availability zone within the provider VPC. The provider needs to make sure that the NLB is configured for cross zone load balancing so that each of the nodes can balance connections to instances in other AZs. This makes sure that the load is distributed and the solution is resilient.

Once the endpoint service has been created then access can be granted to other entities. This can be individual IAM users, it can be roles, it can be AWS accounts or even open access. Once access is granted consumer VPCs can deploy endpoints into subnets within a VPC and these can be protected by using VPC security constructs such as SGs and NACLs.

Interface endpoints provide access to resources outside of the security boundary of the VPC in a secure way which doesn't leave the private AWS security zone.

Interface endpoints are delivered as ENIs within a VPC and so they're accessible via IPv4 in that VPC as though the service itself is located within the consumer VPC.

The data flows through the interface endpoints through to the service provider VPC, it hits the network load balancer via the load balancer nodes and then the connections are distributed to the compute resources providing the application services. The end result: the application is accessible via the consumer VPC in a secure way.

AWS Privatelink outside of its common usage as the technical basis for interface endpoints, is generally used to provide secure access to services delivered by service providers. A service provider either directly or via the marketplace provides a service that's consumed by service consumers using AWS Privatelink. This is a feature that's very often used within larger AWS deployments that you may have to design as well as business that has to operate within strict security guidelines. You may need to consume a service that's provided by a service provider, but do so in a way where the data doesn't transit over the public internet. AWS PrivateLink is one way that you can do this.

In the case of this example, it's a CAT application, but imagine that it's SNS, SQS, or any other AWS service. It's the same technology behind anything which uses interface endpoints. Those services are delivered from provider networks which AWS manage and injected into your VPC using normal interface endpoints.

(**exam**) Key Points
**AWS PrivateLink**
- (**exam**) Highly-Available via **multiple endpoints**
	- // for HA, one endpoint within every AZ inside VPC that you need to consume that service from
- (**exam**) **IPv4** & **TCP** only (**IPv6 isn't supported**)
- **Private DNS is supported** (verified domains)
	- // I could have my CAT application that's available on the public internet using the DNS name of app.awscats.com. I provide this service as well using PrivateLink, then any of my consumers can use private DNS and override the default public DNS with one which points at the interface endpoint for the PrivateLink service. In the same way that you use private DNS to override the default service endpoint for interface endpoints, you can do the same with PrivateLink. This means applications can use services provided by PrivateLink without requiring any code changes. They can maintain the usage of the existing DNS endpoint addresses and use private DNS to override those to point at the PrivateLink endpoints. This is exactly the same architecture that interface endpoints use within a VPC,
- (**exam**) **Direct Connect**, **Site-to-Site VPN** and **VPC Peering** are supported.

## Advanced VPC DNS & DNS Endpoints
Associate Level Coverage: [[5.0 (SAA-C03) VIRTUAL PRIVATE CLOUD (VPC) BASICS#Custom VPCs]].

- DNS via the **VPC .2** Address 10.16.0.**2** (A4L)
	- // In every VPC, there's an IP address that's reserved for the VPC DNS - VPC + 2. This is the address which all VPC-based resources can use for DNS.
- **.2** is reserved in **every subnet**
	- // Additionally, in every subnet, the .2 or plus 2 address is also reserved.
- Now called the Route53 Resolver
	- // This .2 address is now referred to as the Route 53 resolver.
- Provides **R53 Public** & **Associated Private** Zones
	- // It's via this address that VPC resources can access Route 53 public hosted zones, and any associated private hosted zones.
	- // You can deploy your own DNS infrastructure within a VPC, but by default, Route 53 handles this functionality.
- **Only accessible** from within a VPC
	- // The Route 53 resolver is only accessible from within the VPC. You can't access it over site-to-site VPNs or via Direct Connect.
- Hybrid network integration is **problematic** - **IN** and **OUT**
	- // DNS plays a huge part of how most applications work. And if you can't easily integrate your AWS and on-premises DNS infrastructures, then you will experience problems. At best, this means significantly more admin and technical overhead.
	- // Ideally, when dealing with hybrid networking, you want a joined-up DNS platform. You want your AWS resources to be able to discover and resolve on-premise services, and you want your on-premise services to work well with AWS products and services. You don't always want DNS records for private applications being available publicly, because that's often a way that systems are audited before a network attack.
	- // .. The problem we have is how to effectively integrate the often separate DNS systems that exist inside AWS and on-premises.

**Isolated DNS Environments**
![[Isolated DNS Environments.png]]
Historical problem with R53 resolver: disjointedness, because the R53 resolver couldn't forward queries (for any on prem DNS Zones to on prem DNS servers) onto on-premises resolvers. There was no conditional forwarding functionality. Which meant the AWS side resources had no internal visibility of the on prem resources from a DNS perspective.

On prem, the DNS resolver would handle wany local zones; it too would forward anything it didn't know about to the public DNS system. Because: the R53 resolver isn't accessible outside the VPC. So, on prem resources couldn't resolve any non-public DNS records within AWS. Their ability to resolve and discover VPC-based private services is impacted.

This has the overall effect of creating a DNS boundary between the two systems. Neither on prem or AWS side are capable of doing private DNS resolution between.

Solutions to this problem: a VPC-based DNS forwarder running on EC2.

**BEFORE R53 ENDPOINTS**
![[Before R53 Resolver.png]]
We add a DNS forwarder and configure it with DHCP Option Sets inside the VPC. So, this DNS forwarder server is set as the DNS server for any resources inside the VPC.
// [[5.0 (SAA-C03) VIRTUAL PRIVATE CLOUD (VPC) BASICS#VPC Subnets]]
When the forwarder receives any queries, it identifies if they're for corporate DNS zones; if so, it forwards them to the on-prem resolver. Otherwise, the default is to forward them to the R53 resolver, where they're dealt with in the normal way.

The effect of this is that the AWS resources can still use the functionality provided by the AWS Route 53 resolver, but can also fully integrate with the on-premises DNS.

The on-prem resolver can forward on any queries for for non local zones to the DNS Forwarder in AWS - which communicates with the R53 resolver.

Until the release of Route 53 endpoints, this was one example of best practice architecture for hybrid DNS, and this is something you might still find implemented within your clients. To understand why Route 53 endpoints provide a significantly better architecture, it was necessary to understand how things work before Route 53 endpoints.

**Route53 Endpoints**
- VPC interfaces (**ENIs**) - **Accessible** over **VPN** or **DX**
	- // They're accessible outside the VPC they're located in.
	- // They're integrated with the R53 resolver.
- **Inbound** and **Outbound**
- **Inbound** = On-premises can forward to the R53 Resolver
	- // They work just like the EC2 forwarder we just stepped through. But, delivered as a service by AWS.
	- // When you provision them, you select two different subnets. You get two different IP addresses.
	- // On prem DNS infrastructure can be configured to forward any queries that are not for locally hosted DNS zones to these inbound endpoint IP addresses.
- **Outbound** = Conditional Forwarders, R53 to On-premises
	- // Presented in a similar way - interfaces in multiple subnets
	- // Used to contact your on-premises DNS.
- **Rules** control what **requests** are **forwarded**
	- // Rules are associated with an outbound endpoint.
- corp.animals41ife.org => On-premises DNS Nameservers
	- // When you're setting up these outbound endpoints, you have to specify the details of your on-premises DNS infrastructure. Based on these rules, when any queries are occurring for a particular DNS zone these outbound endpoints are used and the queries are forwarded on to your on-premises DNS infrastructure.
	- // Because these outbound endpoints have unique IP addresses, you can whitelist them on-premises as needed.
		- // If you need these IP addresses to be able to bypass any filtering or corporate firewalls, you can do that because you directly control their IP addresses when you're provisioning them within your VPC.
Using a combination of inbound and outbound endpoints allows you to configure a hybrid DNS platform using AWS and on-premises environments.

**Route53 Endpoints**
![[Route53 Endpoints.png]]
Between the two environments is a dedicated private connection in the form of a direct connect between the AWS environment and the Animals for Life on-premises data center

The first step to implementing a hybrid DNS architecture using Route 53 endpoints starts at the AWS side
We create two inbound Route 53 endpoints within the VPC. These are just network interfaces which are part of the Route 53 resolver. These are accessible from the on-premises network. The on-premises DNS servers can be set to forward queries for any non-locally hosted DNS zones to these endpoints. And this occurs over the direct connect and also over a site-to-site VPN for organizations who can't justify the investment of a direct connect.

The inbound endpoints then allow access to the Route 53 resolver, which means that the on-premises side can now fully communicate with AWS and perform DNS resolution for any AWS hosted zones.

We can also integrate in the other direction by creating Route 53 outbound endpoints. These are also interfaces within the VPC. They're configured to point at the DNS servers which run within the on-premises environment. We can attach rules to these endpoints, which configure forwarding for specific domains. This means that when a VPC-based resource queries for any records within this domain (when it matches one of the rules) then it's forwarded via the outbound endpoints across the DX or VPN, and into DNS servers within the on-prem environment. This means the AWS resources can now resolve the on-prem DNS zones. The result is a fully integrated DNS environment which spans both AWS and on-premises environments.

Route 53 endpoints are delivered as a service. They're highly available, and they scale automatically based on load. They can handle around 10,000 queries per second per endpoint.

## IPv6 Capability in VPCs - PARTs 1 - 2
**IPv4 Address Space**
![[IPv4 Address Space.png]]
This is a representation of the IPv4 address space.

All of these IP addresses, except a few exceptions, are **publicly routable**, meaning if you have one of them configured on a device, you can communicate with another device which also uses a public IPv4 address over the public internet, assuming that there's no security in the way.

Parts of this address space are designated as **private addresses** (networks like 10.0.0.0/8 -  If you have one of these, the public internet won't route your data. They're only used internally, but you're free to allocate them however you like. These internal ranges are commonly used within AWS VPCs). See [[0.0 (SAA-C03) Cloud, Networking and Technical Fundamentals#IP Address Space Subnetting - PART 1-2]] for more.

There are 4,294,967,296 IP addresses in the IPv4 address space. They're a scarce resource. There are a lot of IPv6 addresses. They aren't a scarce resource. When designing IPv6 networks, you don't have to do any of the usual micro-level IP management.

**IPv4 VPC Structure**
![[IPv4 VPC Structure.png]]
(refresher) How IPv4 works in AWS. You create a VPC in an AWS region. When you create this VPC, it's allocated a range of private IP addresses. Crucially, these IP addresses are not publicly routable.
inside the VPC, you create subnets - they're either public or private. Public subnets are created with a default IPv4 route which point at an IGW, meaning any instances instances or services in the public subnet can be allocated with a public IPv4 address and use this to communicate with the public IPv4 internet using IPv4. Remember, only public IPv4 addresses are routable on the public IPv4 internet.

Because IPv4 address space is limited, AWS resources are not automatically given public addressing. AWS also has the concept of **private** addressing for VPCs, and so we have the concept of private subnets, which also operate within VPCs. these subnets are private because they only use private addressing. Instances or services that are provisioned into a private subnet, have no allocated public addressing. They can't directly communicate with the internet, and so instead they use a process called **NAT**, or Network Address Translation, and in a best practice way this is delivered by using a NAT gateway within AWS. A NAT gateway is a device which accepts communications from lots of private only resources, and translates their packets to have a public address. The same public address is used for many private services. This means that a private resource can access the internet indirectly, using a default IPv4 route pointing at the NAT gateway, which is running in a public subnet, and use that to access the internet. So the traffic goes to the NAT gateway as the default gateway for those services. The NAT gateway translates the packets to have a public address, and sends them on through to the public IPv4 internet using the IGW.

Two things to remember:
- Public and private IPv4 addresses are completely different
	- **Private** addresses **can't communicate** freely over the public IPv4 internet. They can only be used in private networks such as a VPC. Public addressing can be used to communicate externally to AWS.
- **Private** addressing (RFC 1918) is translated into public addressing using a **NAT gateway**. That's outbound only communication.
	- Private instances can use a NAT gateway to **initiate** communications to a public IPv4 IP address, and receive responses, but public IPv4 IP addresses on the public internet cannot communicate with private instances inside AWS.

You will never see a public IPv4 IP address configured within the operating system of an EC2 instance. You will only ever see the version 4 private address. Any public addressing is dealt with by gateway appliances outside of EC2. It's never the right answer to any technical problem you encounter, or any exam question to configure a public address within the operating system of an EC2 instance. That never happens. Even for public instances, when using IPv4, you never have the public address configured on the instance operating system.

**Part 2**
**IPv6 VPC Structure**
![[IPv6 VPC Structure.png]]
Every IPv6 address in use within AWS is classed as publicly routable. Conceptually, there isn't the concept of public or private subnets within AWS for IPv6. Because of this, NAT isn't used for IPv6. NAT gateways don't support IPv6 because IPv6 has no need for NAT as a process. NAT allows services which use private IP addresses to access public internet services by translating packets that are sent by those instances, changing the source address into a publicly routable address. Because all IPv6 addresses are already publicly routable, NAT as a process and NAT gateway as a product isn't needed for IPv6, and so it's not supported.

To use IPv6 within AWS, the first step is that it needs to be enabled on a VPC. There are a few ways that this can be done. You can use your own range of IPv6 addresses using the bring your own IP feature, or you can utilize an AWS provided range, which is the most common approach. When using this approach, AWS will allocate you a unique slash 56 IPv6 range to use for that VPC. This range will be entirely unique for this VPC, and all addresses in that range will be publicly routable.

See how the VPC IPv6 range that I'm using in this example ends in 2200. Every subnet that you have inside a VPC, if you choose to allocate an IPv6 range to that subnet, it gets allocated inside the VPC range. It uses a hex pair to make it unique in that range. So for this example, the subnet on the left gets 00 at the end, and then the subnet on the right gets 01 at the end

Now because it uses a hex pair for these last two digits, and this hex pair can range from 00 to FF, that means that there is space for 256 unique values. This means 256 /64 networks, each of which could be allocated to one subnet - that gives each subnet a total of 18 quintillion addresses (many orders of magnitude > the IPv4 address space) - just to illustrate the point that you don't need to engage in low level ip planning within a subnet or a VPC. With IPv6, IP addresses are no longer valuable like they are for IPv4.

Routing for IPv4 and IPv6 is handled separately within AWS. We have the same route tables and the same internet gateway, but we have different routes. We have IPv4 routes and IPv6 routes.

With this route table applied, instances in both subnets, can communicate using the internet gateway, both IPv4 and IPv6 in a **bidirectional** way. There are situations when you want to allow IPv6 resources to have outbound communication, but not allow inbound. Remember, **IPv4** provided the concept of the **NAT gateway**, which allows outbound only access, while protecting instances against inbound communications. NAT doesn't work with IPv6, because, again, all addresses are publicly routable. The equivalent using IPv6 is to deploy an **egress-only internet gateway**. Then, we point the route at the egress-only internet gateway instead of the IGW.

![[IPv6 VPC Structure2.png]]
This would allow bidirectional IPv4 traffic, but only allow outbound IPv6.

You can only have 1 IGW associated with a VPC, but an EO-IGW is a different object; you can have both. Because IPv4 and IPv6 traffic is dealt with differently, you can have different gateways and deal with v4 & v6 traffic differently.

**IPv6 Considerations**
- IPv6 can be added **while creating** a VPC/Subnets
- Or addressing **can be migrated** to IPv6
- Add **VPC Range**, Add **subnet range(s)**
- Add **routes** & appropriate **gateway(s)**
- Configure **IPv6 on Services**
- Be aware of which services **support IPv6** vs **NOT**
	- // PrivateLink & Interface Endpoints don't support IPv6 in the same way as IPv4

		- // 3 possibilities: (1) Supports IPv6 entirely; (2) not at all (ex: NAT GW); or, (3) it does support IPv6, but not the same as IPv4 (ex - product limitations).

## Advanced VPC Structure - Subnets Tiers - PART1
**Subnets & Tiers**
![[Subnets & Tiers.png]]
Don't mimic legacy N-tier architecture in AWS. AWS provide security functionality and networking features, which mean this type of tiered approach, specifically using multiple subnets for each tier, is no longer required within AWS.

There are some situations where you do need multiple subnets to deliver a specific set of functionality. You need to know when that required vs when it's not. You need to be aware of all the different decision points that affect how HA, cost-effective, performant, and secure your application is when using single subnets versus multi-subnets.


**Subnets & Tiers2**
![[Subnets & Tiers2.png]]
1 Subnet isn't HA (1 subnet is always in 1 AZ) because we're only using 1 AZ.

Another limitation: if there's only 1 subnet, we can only have 1 NACL associated with it - either the VPC default NACL or a custom one. This means the NACL can't be used to filter traffic between the instances because it only filters traffic when it enters or exits a subnet. It's one common reason to split things into different subnets - so they can benefit from the granular filtering provided by NACLs. This includes explicit denies.

If you have any requirements to explicitly deny traffic flow, maybe you've allowed open access to a set of web servers, but you need to block one network range or one specific IP, then NACLs are required. They're the security construct in AWS which can explicitly deny particular IP addresses or ranges of IP. If network ACLs are required, then these are placed at the subnet boundary. This might influence how many subnets you have for the application.

**Subnets & Tiers4**
![[Subnets & Tiers4.png]]
These EC2 instances have public and private addressing.

One of the common reasons that solutions architects begin thinking about using additional application tiers is when databases are involved. Putting them in the public subnets along with the application instances puts them at risk, right?
Any resources placed into any AWS subnets are given private addressing. It's logical to assume that given that these are public subnets, they'd also be given public addressing. If this were true, it would put these database instances at risk, and that would be a reason to consider adding another tier to our infrastructure.
But there are two things which AWS provide which mitigate this risk:
- (1) You can just **not give public IP addresses** to the database resources.
	- // Public subnets can be configured to allocate public IPv4 addresses by default, or you can have it set to not allocate by default and then explicitly allocate them to appropriate resources on a per-resource basis. In either case, you can always explicitly decide to not allocate public addressing to resources, even if they're located in a public subnet. This requirement alone is not a reason to have multiple tiers for your application. Without a public IP, no public entity could access these database resources.
- (2) Security Groups - use SGs to **not** explicitly allow access.
	- SGs are allocated onto network interfaces or resources. These provide the ability to control security on a much more granular level. SGs can't explicitly deny anything. In this example, the SGs which are attached to the db can be configured to only allow connectivity from the web servers and nowhere else. This would mean that any bad actors can't directly access these database instances from the public internet, even if they had public addressing.

This alone is not enough reason to justify a separate application tier. So what is? You might be given it as a requirement. Being told db instances can't share subnets with other resource types. You might get asked this in a real world situation for security reasons, or it might be a requirement on an exam question.  If you know that you can't have database instances sharing subnets with any other infrastructure, then logically the databases need their own subnets, and this is a separate tier.

**Subnets & Tiers6**
![[Subnets & Tiers6.png]]
- Another reason to create additional subnets or tiers: **Route Tables**
	- Associated with a subnet
	- Route tables matter when you want to control the destination for data flows within an application within AWS or wider hybrid networks.

You can't have NAT gateways in the same subnets as the private instances that they support because the NAT gateway, in order to have internet, needs a default route pointing at the IGW, but, the private IPv4 instances need to have a default route pointing at the NAT gateway. You can't have two different default IPv4 routes on the same route table. You can't have two different route tables on the same subnet. In order to support NAT gateways or NAT instances, you need to separate the gateway into one subnet and the instances which use it into another.

Different subnets, assuming you want HA running in different AZs means different tiers. This is another very common requirement for additional subnets within a VPC - (**exam**) - One of the most common reasons for having different tiers or multiple subnets is to support **different routing decisions**.

**How to calculate the # of subnets an app requirement has**
- **Ignore HA** to start with (thats the only time I'll type this!!)
- How many **subnets** does your app need
- **Public** & **Private** addressing, and security can be controlled with **one subnet**
	- // The only exception: you want to filter traffic with a NACL - then, you need the two things to be in different subnets.
- Different **Routing** - multiple subnets
- **Internet-facing** ALBs **can** communicate with **private instances**
	- // (exam) - common trick question - introducing load balancers. Whether an instance has only private addressing or both private and public addressing doesn't influence whether the ALB can connect to them.
	- // The only restriction is that an **internet facing load balancer** needs to run from **public subnets**.
- Number of **APP subnets** * **AZS** = **number of subnets needed**

A public subnet is capable of having both public and private instances, whereas a private subnet can only do private instances.

You don't need to have separate subnets for a load balancer. A load balancer can inhabit public subnets in addition to the instances, so that can be one tier. Some of those instances can also not be allocated public addressing (private instances). That solution can still be delivered with one subnet per AZ (one tier).

Generally, the only reason to have multiple tiers is if you need different routing, if you need certain security, or if the real world requirements or the exam question dictate that a specific set of services can't be located in the same subnets as anything else (ex: database services which need to be in their own subnets).
