## Regional and Global AWS Architecture
(Opinion) There are 3 main types of architectures:
1) Small-scale architectures - only ever exist in one region or country
2) Small-scale architectures + DR - systems which also exist in one region or country, but where there's a DR requirement. So if that region fails for some reason, then it fails over to a secondary region.
3) Multi region architectures - and need to operate through failure in one or more of those regions.

A few major architectural components:
- Global **Service Location** & **Discovery**
	- When you type netflix.com into your browser, how does your machine discover where to point to?
- Content Delivery (**CDN**) and optimization
	- Are there pockets of storage distributed globally, or is it pulled from a central location?
- Global **health checks** & **Failover**
	- Detecting if infrastructure in one location is healthy or not, and moving customers to another country as required.
- Regional **entry point**
- **Scaling** & **Resilience**
- Application services and **components**

**Global AWS Architecture**
![[Global AWS Architecture.png]]
Route53 is the AWS implementation for DNS. It has health checks. Can direct Netflix clients to US-East 1 (let's suppose this is primary & Australia is a secondary) or Australia if US-East 1 is down. It can also be configured to direct traffic in other ways, such as nearest location.

Regardless of where infrastructure is located, a CDN can be used at the global level. CDNs (distributed globally) cache content & pull from origin locations as required.

The function of architecture at the **global** level:
- Get customers through to a suitable infrastructure location
- Ensure regional failures are isolated & sessions are moved to alternative locations
- Attempts to direct customers to a local region (if the business has multiple locations)
- Attempts to improve caching using a CDN, such as CloudFront

Think about systems architecture is a collection of regions making up a whole. Most AWS products are regional, & many of those regions make up AWS.

Architecture is concerned with:
- how things work
- how things integrate
- what features products provide

**Regional AWS Architecture**
![[Regional AWS Architecture.png]]

**Tiers** - groupings of functionality or different zones.

Generally, the **web tier**'s purpose is to function as an **entry point** for regional-based applications or application components (ex: application load balancer or API gateway). It abstracts customers away from underlying infrastructure, meaning underlying infrastructure can fail, scale, or change without impacting them.

Web tier uses **compute tier** - stuff like EC2, Lambda, containers using ECS.

Compute tier consumes **storage services** - stuff like EBS, EFS, S3. Many global architectures use CloudFront (CDN) which can use S3 for media (origin).

In addition to file storage, most environments require **data storage** - stuff like RDS, Aurora, DynamoDb, RedShift (for data warehousing).

To improve performance, most apps don't directly access the DB. They go through a **caching** layer - stuff like Elastic Cache (for general caching), DynamoDB Accelerator (a.k.a DAX; when using DynamoDb). Caching is generally in memory; it's cheap and fast. Databases tend to be expensive (based on data volume required). Where possible, offload reads to the DB to cache to improve performance reduce costs.

**Application services** - functionality to applications - email, notifications, etc. - stuff like Kinesis, Step Functions, SQS, and SNS. This stuff can change an application's architecture. For example, using queues to decouple components.

## Evolution of the Elastic Load Balancer
![[Evolution of the Elastic Load Balancer lolz.png]]

- 3 Types of load balancers (**ELB**) available within AWS
- Split between **v1** (**avoid / migrate**) and **v2** (**prefer**)
	- At this point, there are no scenarios where you should choose to use a v1 load balancer.
- Classic Load Balancer (**CLB**) - v1 - Introduced in 2009
	- Can load balance HTTP & HTTPS as well as lower level protocols, but they **aren't** really **layer 7** devices. They don't really understand HTTP & don't really make decisions based on HTTP protocol features. Lacking features. Only support **1 SSL cert per CLB**. Which means you need a ton of them for larger scale deployments. This can be consolidated down to a single v2 Load Balancer.
- Application Load Balancer (**ALB**) - v2 - HTTP/S/WebSocket
- Network Load Balancer (**NLB**) - v2 - TCP, TLS (a secure form of TCP) & UDP
	- Generally, you'd use this if you wanted to wanted to Load Balance stuff that isn't HTTP/HTTPs - email servers, SSH servers, games using custom protocols, etc.

## Elastic Load Balancer Architecture - PART1
Load Balancers accept connections from customers & distribute those connections across any registered back-end compute, which means the user is abstracted away from the physical infrastructure - meaning infrastructure can fail, scale, or change without impacting them.

![[ELB Architecture.png]]

When you provision a load balancer, you have to decide on a few important configuration items:

1) IPv4 only or dual stack (dual stack just means using IPv4 & IPv6).
2) The **AZs** the Load Balancer will use. Specifically, one (and only one) **subnet** in two or more AZs.
	1) What you see as a single Load Balancer object is actually made up of multiple **nodes**, (which live in the subnet you picked per AZ). These nodes scale with the AZ; so, they're **HA**. If one node fails, it's replaced. If load to the LB increases, additional nodes are provisioned inside each subnet the LB is configured to use.
When a Load Balancer gets created, it gets created with a single DNS "A" record. This points at all the ELB nodes which get created with the product.
3) Whether the load balancer should be **internet facing** or **internal**.
	1) Controls the nodes **IP addressing**.
		1) **Internet facing** - given public & private IPs.
		2) **Internal** - given private IPs.
4) Listener configuration
	1) Controls what **protocols** and **ports** will be accepted. Route to **targets** on a port & protocol.
An **internet facing** Load Balancer can connect to **BOTH** public & private EC2 instances (or whatever other service). Load balancers **don't care**.

LBs need **8** or more free IP addresses in the subnets they're deployed into. This means a /28 subnet (which provides a total of 16 IP addresses), but minus the 5 reserved by AWS, leaving 11 per subnet. However, AWS recommends a **/27** (or larger) subnet so that it can **scale**. Strictly speaking, /28 & /27 are both correct in their own ways to represent the minimum subnet size for a LB. AWS docs say you need a /27, but they also say you need a minimum of eight free IP addresses. To leave room to deploy a LB & backend instances, for most cases, I try to remember /27 as the correct min value for a LB. If you see any questions that show a /28, but don't show a /27 answer, then /28 is probably the right answer.

**Internal** LBs are generally used to separate different **tiers** of apps. Allows for independent scaling.

## Elastic Load Balancer Architecture - PART2
**ELB Architecture**
![[ELB Architecture-2.png]]
Without load balancers, everything would be tied to everything else. Bob would communicate with a specific instance in the web tier. If this failed or scaled, then Bob's experience would be disrupted. The instance that Bob is connected to would itself connect to a specific instance in the application tier. And if that instance failed or scaled, then again, Bob's experience would be disrupted.

To improve this architecture, put load balancers between the application tiers. This abstraction (LBs) decouple tiers & allow them to scale independently.

**Cross-Zone LB**
![[Cross-Zone LB.png]]
Originally, LB's would balance load across AZ's, so if you had 4 instances in AZ A & 1 instance in AZ B, each instance in AZ A would receive 12.5% of total load % the instance in instance B would receive 50%. **Cross-zone load balancing** fixes this problem by allowing all LB nodes to distribute any connections it receives across registered instances in all AZs (such that each instance would receive 20% load, in this example). Originally, this wasn't enabled by default; nowdays, it's enabled by default for app LB's, but, you need to be aware of it for the exam. For the exam, you can get problems posed as unequal distribution of load & and you need to be aware of this feature to fix the problem.

ELB Summary
- ELB is a **DNS A** Record pointing at **1+** Nodes per AZ
- Nodes (in one subnet per AZ) can scale
- **Internet-facing** means nodes have **public IPv4 IPs**
	- **Internal** is private **only IPs**
- (**exam**) EC2 **doesn't need to be public** to work with a LB. Internet facing LB can route traffic to both public & private EC2 instances.
- **Listener** Configuration controls **WHAT** the LB does
- **8+** Free IPs per subnet, and **/27** subnet to allow scaling

## Application Load balancing (ALB) vs Network Load Balancing (NLB)
**Load Balancer Consolidation**
![[Load Balancer Consolidation.png]]
CLBs don't scale because they don't support [[SNI]]. Every unique app would require its own CLB.

v2 Load Balancers support **listener based rules**. Each listener based rules can have an SSL cert handing HTTPS for both domains. Then, we can have **host based rules** which direct incoming connections at multiple **target groups** (which can forward traffic on to multiple ASGs).

**Application Load Balancer (ALB)**
- **Layer 7** Load balancer. Listens on **HTTP** and/or **HTTPS**
	- But, **no other layer 7 protocols** (SMTP, SSG, gaming, etc.)
	- Must listen using HTTP / HTTPS listeners. Can't directly listen using TCP/UDP/TLS listeners.
- Can understand L7 content
	- content type, cookies, custom headers, user location and app behavior; can make inspect & make decisions based on this info. NLBs can't do this. It has to be an L7 LB to understand these components.
- HTTP HTTPS (SSL/TLS) always **terminated** on the ALB - **no e2e unbroken SSL** chain from client to instances
	- **a new connection** is made to the application
	- This might be important to security teams in strict regulatory environments. May prohibit using an ALB.
- ALBs **MUST** have **SSL** certs if **HTTPS** is used
- ALBs are **slower** than **NLB** . . more levels of the network stack to process
	- For exam questions strict on performance, you might want to look at NLBs rather than ALBs.
- Health checks **evaluate application health** ... at layer 7.

**ALB Rules**
- Rules direct connections which **arrive** at a **listener**
- Processed in **priority order**
- Default rule = catchall
- **Rule Conditions**: host-header, http-header, http-request-method, path-pattern, query-string & source-ip
	- Allows rules to take different decisions
- **Actions** : forward, redirect, fixed-response, authenticate-oidc & authenticate-cognito

![[ALB Rules.png]]

Here, we have an **ALB** with 1 **host** based **rule** with an attached SSL certificate. The rule is using *host header* as a condition, and *forward* as an action. So, it's forwarding catagram.io requests to the target group for the Categram application (target group 1 - an ASG).

If we wanted to present users of Bowtie Incorporated who use the 1.3.3.7 IP address with an alternative version of the application, we can do that with a listener rule. Condition: source IP (1.3.3.7) forwards traffic at a separate target group (target group 2 - separate ASG).
- It's a different shade of purple because ... it's a layer 7 device ... the connection from the load balancer to the instances for target group 2 will be a *separate set of connections*. There's no option to pass through the encrypted connection to the instances. It has to be terminated. This might not matter but it's something that you need to know for the exam.
	- If you have to **forward encrypted** connections through to the instances **without terminating** them on the load balancer then you need to use a **network load balancer**.

An example of using an ALB to work on layer 7 elements of the HTTP protocol would be to redirect Dogogram.io to CataGram.io.

**Network Load Balancer (NLB)**
- Layer 4 load balancer ... can interpret TCP, TLS, UDP, TCP_UDP
- No visibility or understanding of **HTTP** or **HTTPS**
	- No headers, no cookies, no session stickiness
- Really Really Really Fast (millions of rps, 25% of ALB latency)
	- (because they don't have to deal with computationally heavy upper stack)
	- So, they're ideal to deal with any non-HTTP/S protocols - SMTP, SSH, Game Servers, financial apps
- Health checks **JUST** check ICMP / TCP Handshake .. **Not app aware**
	- can't do detailed health checking
- NLB's can have **static IP's** - useful for whitelisting (corporate clients)
- Can **forward TCP** to instances - **unbroken encryption**
	- (**exam**) NLBs + TCP listeners is how you can do unbroken e2e encryption.
	- (Because layers that are built on top of TCP are not terminated on the load balancer)
- (**exam**) Used with PrivateLink to provide services to other VPCs

**ALB vs NLB**
- Unbroken encryption ... NLB
- Static IP for whitelisting ... NLB
- The fastest performance ... NLB (millions rps)
- Protocols not HTTP or HTTPS ... NLB
- PrivateLink ... NLB
- Otherwise ... ALB

## Auto-Scaling Groups
Autoscaling groups are generally used together with elastic load balancers and launch templates to deliver elastic architectures.

- **Automatic Scaling** and **Self-Healing** for EC2
- Launch Templates Uses or Configurations
	- An ASG uses 1 LC or 1 version of an LT. You can change which is associated with it, but it's one of them at a time.
- Has a **Minimum**, **Desired**, and **Maximum** Size (e.g 1 :2:4)
- Keep running instances at the **Desired capacity** by **provisioning** or **terminating** instances
	- Desired capacity is >= the min & <= the max.
- **Scaling Policies** automate based on metrics (like cpu load)

**Auto Scaling Groups**
![[Auto Scaling Groups.png]]

**Auto Scaling Groups Architecture**
![[Auto Scaling Groups Architecture.png]]
ASGs define where instances are launched. They're linked to a VPC, and subnets within that VPC are configured on the autoscaling group. Whatever subnets are configured will be used to provision instances into. When instances are provisioned, there's an attempt to keep the number of instances within each availability zone even (but this isn't always the case - the ASG tries to level capacity where available).

###### Scaling Policies
Scaling policies are rules you define which can adjust the values of an ASG. There are 3 ways you can scale an ASG:
- 1) **Manual** Scaling - Manually adjust the desired capacity. Useful in testing or urgent situations (or for cost control)
- 2) **Scheduled** Scaling - Time based adjustment - e.g. Sales..
	- (**exam**) If you have known periods of usage, then scheduled scaling is going to be a great potential answer.
- 3) **Dynamic** Scaling - they are rules which react to something and change the values on an autoscaling group. There are three subtypes:
	- 3.1) **Simple** - "CPU above 50% +1", "CPU Below 50-1"
		- // if CPU utilization >50%, add 1 to desired capacity; if CPU utilization < 50%, remove 1 from desired capacity.
		- Triggers could also be stuff like memory usage, disk I/O, length of SQS queue, or a custom performance metric within your app, such as response time.
	- 3.2) **Stepped** Scaling - Bigger +/- based on difference
		- Similar to Simple, but you define more detailed rules. Allows you to act depending on how out of normal the metric value is. Allows you to act faster the more extreme the change in conditions. You can define upper & lower bounds.
			- Ex: if CPU > 50%, +1; if CPU > 80%, +3 (for if we have a sudden spike of load). Same in reverse.
		- Stepped scaling is almost always preferred to Simple (because it allows you to adjust better to changing load patterns), except when you're priority is simplicity. 
	- 3.3) **Target** Tracking - Desired Aggregate CPU = 40% ... ASG handle it
		- Not all metrics work for target tracking. Current ones that work: CPU, Avg. network in. Avg. network out, Request count per target (relevant for Application Load Balancers)
- **Cooldown Periods**
	- Value in seconds
	- How long to wait at the end of a scaling action before doing another.
	- Allows ASGs to wait and review chaotic changes to a metric & can avoid costs associated with constantly added or removing instances.
		- Because remember, there is a minimum billable period - you're billed for at least the minimum time every time an instance is provisioned regardless of how long you use it for.

###### ASG Health
**ASG Health**
![[ASG Health.png]]
ASGs monitor the health instances that they provision & will self heal (detect failure, terminate, & re-provision). The same would happen if we terminate an instance manually - the ASG would replace it.

Here's a cheap, simple, and effective way to get High Availability:
Create an LT (which can automatically build an instance). Create an ASG (using that LT), set the ASG to use multiple subnets in different AZs. Set the ASG to use 1:1:1 (min 1, desired 1, max 1), then you have simple instance recovery. The instance will recover if it's terminated or fails & because ASGs work across AZs, the instance can be re-provisioned in another AZ if an AZ fails.

**ASG + Load Balancers**
![[ASG + Load Balancers.png]]
ASGs real power comes from their ability to integrate with Load Balancers.
- Instead of statically adding instances (or other resources) to the target group, you can use an ASG configured to integrate with the target group to get **elasticity** (using load to adjust # of instances to fluidly adjust capacity). The ASG abstracts instances away from the LB.
	- Also, the ASG can be configured to use the **LB health checks** rather than EC2 status checks. ASG health checks are richer. They can monitor the state of HTTP/S requests (because of this, they're application aware). Simple EC2 status checks are not.
		- However, you have to be **careful** when it comes to setting up **health checks**:
			- If your application has some complex logic within it, and you're only testing a static HTML page, then the health check could respond as okay, even though the application might be in a failed state.
			- If your application uses databases, you can use a database access requirement to check the page. If the database fails, then all of your health checks could fail, meaning all of your EC2 instances will be terminated and re-provisioned when the problem is with the database, not the instances.

**Scaling Processes**
- **Launch** and **Terminate** - SUSPEND and RESUME
	- if launch is set to suspend, then the auto-scaling group won't scale out if any alarms or schedule actions take place
	- if terminate is set to suspend, then the auto-scaling group will not terminate any instances
- **AddToLoadBaIancer** - add to LB on launch
- **AlarmNotification** - accept notification from CW
- **AZRebalance** - Balances instances evenly across all of the AZS
- **HealthCheck** - instance health checks on/off
- **ReplaceUnhealthy** - Terminate unhealthy and replace
- **ScheduledActions** - Scheduled on/off
	- Controls whether the ASG will perform any scheduled actions
- **Standby** - use this for instances 'lnService vs Standby'
	- Allows you to suspend any activities of the ASG on a specific instance
	- (Useful for performing maintenance on ec2 instances)

**Final Points (for exam)**
- ASGs are free
- Only the resources created are billed ...
- Use cool downs to avoid rapid scaling
- Think about **more**, **smaller** instances - **granularity**
	- If you have 2 larger instances, adding 1 more would cost more than if you have 20 smaller instances & only need to add 1.
- Use with ALB's for elasticity - **abstraction**
- ASG defines **WHEN** and **WHERE**, LT defines **WHAT**

## ASG HealthCheck Comparison - EC2 vs ELB
3 types of health checks on an ASG:
- **EC2** (Default), **ELB** (Can be enabled), & **Custom**
- **EC2** - Stopping, Stopped, Terminated, Shutting Down, or Impaired (not 2/2 status) = **UNHEALTHY**

## SSL Offload & Session Stickiness
You need to know the theory & architecture for the exam, not the implementation details.

There are 3 ways a load balancer can handle secure connections: bridging, pass-through, & offload.

**SSL Offload**
![[SSL Offload.png]]
- Bridging mode (the default) - decrypt & re-encrypt @ LB.
	- Cons:
		- **Admin** overhead to manage 2 SSL certs (1 on LB, 1 on instances)
		- SSL cert is stored on LB - risk
			- AWS has some degree of access to SSL cert on LB. Could be prohibitive if you have strong security frameworks to stay inside of.
		- **Computation** @ LB & EC2 instances for crypto operations. Could be bad for high volume scenarios. Overhead can be significant.
	- Pros:
		- ALB in bridging mode can see the HTTP traffic & take actions based on content. This is why it's the default mode for the ALB.
- Pass-through - one encrypted tunnel all the way through.
	- // Because listener is configured for TCP, it can see source and destination ip & make some basic decisions.
	- Cons:
		- Can't load balance based on the HTTP part because it's never exposed to the load balancer.
		- EC2 instances need SSL cert
		- EC2 instances use compute for crypto operations.
- Offload - Decrypt @ LB & NOT re-encrypted.
	- Pros:
		- EC2 instances DONT need compute for crypto operations
	- Cons:
		- Data is in plain text across AWS's network
			- If this isn't a problem for you, then Offload might be an effective solution.

**Connection Stickiness**
![[Connection Stickiness.png]]
If we have no session stickiness, customer sessions are distributed fairly (usually, equally) across all backend instances. But, if the **state** is stored **on a particular server**, then it's problematic to load balance across different servers. There's an option on ELBs for **session stickiness**. ALBs enable it on the target group. If enabled, the first time that a user makes a request, the load balancer generates a **cookie** called **AWS ALB** with a duration which you define (1-7 days). The cookie is used to send this session to the same backend instance. This will happen until one of two things happen:
 1) Server failure
	 1) The user will be moved to a different instance
 2) Cookie expiration
	 1) The process repeats. Customer gets a new cookie & is allocated a new backend instance.


**Session stickiness** is designed to allow an application to function using a load balancer if the **state** of the user session is stored **on an individual server**.
- Problem with this method: can cause **uneven load** on backend servers.

Where possible, apps should be designed to use **stateless** servers. Apps need to be designed to handle state **externally** (using things like DynamoDB, for example). Store sessions/state somewhere else; not on the EC2 instance. This way we can load balance without cookies.

## Gateway Load Balancer
![[Gateway Loadbalancer - Why.png]]

- Help you **run** and **scale** 3rd party appliances
	- things like **firewalls**, **intrusion detection**, and **prevention** systems
	- **Inbound** and **Outbound** traffic (**transparent** inspection and protection)
- GWLBs have 2 major components:
	- 1) **GWLB endpoints** ... traffic enters/leaves via these endpoints
		- These are kind of like the VPC interface endpoints, but with one major difference:
			- A GWLBE can be added to a **route table** as the **next hop**. This allows it to be part of traffic flows controlled by that route table.
	- 2) The GWLB itself - it **balances** across **multiple backend appliances**
- Traffic and metadata is tunneled using **GENEVE** protocol
	- Original packets remain unaltered. Encapsulated through to appliances & back.
		- Packets have the same source/destination IP, source/destination port, & contents as when they were created & sent.
			- This facilitates horizontally scaling (security) appliances
- The GWLB manages flow stickiness
	- One flow of data will always use one appliance. This is useful, because it allows that appliance, to monitor the state of flows, through a system. It provides abstraction.
	- It means you can use multiple security appliances to provide resilience - if one fails, then packets are moved over to another available security appliance.

![[GWLB 101 - How it works.png]]

Transparent in-line network security done in a scalable, resilient, and abstracted way:

![[GWLB Architecture.png]]

Traffic flow through this architecture (to demonstrate GWLB architecture & demonstrate scaling a security platform):
- 0) Client accesses catagram.io
- 1) Traffic arrives at IGW
	- 1.1) IGW is configured with a route table
	- 1.2) IGW first translates the destination (public IP), onto the corresponding private IP (of the ALB) - 10.16.96.0/20
		- 1.2.1) The third route is used because it's the most specific route for the 10.16.96.0/20 range
- 2) Traffic is sent at the GWLB endpoint (in the right AZ (10.16.112.0/20))
	- 2.1) Remember, GWLBEs are like interface endpoints, but they can be the targets within routes.
- 3) GWLBE receives packets. Sends to the GWLB. Packets still have the original IP addressing (SRC & DST).
- 4) Packets are encapsulated using GENEVE protocol & sent through to the security appliance chosen by the GWLB, unaltered.
- 5) 3rd-party security apps do their thing. Packets are returned, encapsulated, to the GWLB.
	- 5.1) The encapsulation is stripped by the GWLB
- 6) Packets are returned to the GWLB.
	- 6.1) Since the original IP addressing is maintained, the route table on the top public subnet is used, which has a local route for the VPC CIDR range.
- 7) Packets flow to the ALB. ALB decides which instance to flow traffic to.
- 8) Traffic flows to app instance.
- 9) Data returns to ALB
	- 9.1) The ALB has a local route, but the default route (0.0.0.0) goes towards the GWLB endpoint in the same AZ (10.16.112.0/20).
		- 9.2) // Since traffic is going back to the client device who originally accessed the application, it will have a public IPv4 destination address, so the default route will be used.
- 10) Packets flow back to the GWLBE
- 11) Packets flow to GWLB
- 12) Packets are encapsulated (GENEVE), sent to security appliance.
- 13) 3rd-party security apps do their thing. Packets are returned, encapsulated, to the GWLB
	- 13.1) Encapsulation is stripped by GWLB
- 14) Packets passed back to GWLBE
	- 14.1) The subnet the GWLBE is in has the IGW as the default route. This is used.
- 15) Traffic flows to IGW. Packets SRC IP will be changed to the corresponding public one of the ALB
- 16) Packets are returned to the client device.

GWLBs share many elements with network and ALBs, but they have a very specific purpose - Network security at scale.
