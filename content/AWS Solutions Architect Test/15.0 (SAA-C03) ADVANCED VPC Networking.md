## VPC Flow Logs
- VPC Flow Logs only capture **metadata** (NOT CONTENTS)
	- source IP, the destination IP, the source and destination ports, packet size, and so on - anything which conceptually you could observe from outside.
Flow logs work by attaching virtual monitors within a VPC, and these can be applied at three different levels:
- Attached to a **VPC** - monitors **All ENIs** in that **VPC**
- Attached to a **Subnet** - monitors all ENIs in that **Subnet**
- Attached to **ENIs directly**
- Flow Logs are **NOT realtime**
- Log Destinations ... **S3** or **CloudWatch Logs**
	- it's a preference thing If you use S3, you're able to access the log files directly and can integrate that with either a third-party monitoring solution or something that you design yourself. If you use CloudWatch logs, then you can integrate that with other products, stream that data into different locations, and you can access it either pragmatically or using the CloudWatch logs console.
	- Athena can query flow logs stored in S3 (using SQL like methods)
		- Athena is an ad hoc querying engine (uses schema on read architecture)
		- Only pay for amount of data read.

![[VPC Flow Logs1.png]]

![[VPC Flow Logs2.png]]

Bob sends an ICMP ping to confirm connectivity and to assess the latency. This is what the flow logs look like.

ACTION - ACCEPT/REJECT indicates if it was blocked or not by an SG or NACL. If it's a SG, only one line will show in the flow logs (remember, SGs are stateful, so if the request is allowed, the response is automatically allowed in return).

If you have an EC2 instance inside a subnet where the instance has a SG allowing pings from an external IP address, then the response will be automatically allowed. Buy, if you have a NACL on that instance's subnet which allows the ping inbound, but doesn't allow it outbound, then it can cause a second VPC flow log line - a reject. On the exam, if you see an ACCEPT and then a REJECT & these look to be for the same flow of traffic, then you're going to be able to tell that both the SG and a NACL are used and are potentially restricting the traffic between the source and the destination. Flow logs show the results of traffic flows as they're evaluated. SGs are stateful, and so they only evaluate the conversation itself, which includes the request and the response. Network ACLs are stateless, so they consider traffic flows as two separate parts, request and response, and both of these are evaluated separately, so you might see two log entries within VPC flow logs.

VPC flow logs don't log all types of traffic. Some things are excluded, such as the metadata service ([[6.0 (SAA-C03) ELASTIC COMPUTE CLOUD (EC2) BASICS#Instance Metadata]]), time server requests, DHCP requests which are running inside the VPC, and any communications with the Amazon Windows license server (win EC2 instances).

## Egress-Only Internet gateway
An internet gateway which only allows connections to be initiated from inside a VPC to outside. It's just like a normal IGW, except it's designed for IPv6 traffic & it only allows outgoing traffic & their response.

- With IPv4 addresses are **private** or **public**
	- Private instances cannot directly communicate with the public internet or public AWS services
	- Public instances have a publicly routable IP address which works in both directions. Can communicate to and from public internet (without any security filtering).
- **NAT** allows **private IPs** to access **public networks**
	- **without allowing** externally initiated connections (**IN**)
		- NAT as a process allows private EC2 instances to connect out to the public internet and receive responses back, but doesn't allow the public internet to connect into that private instance.
- With **IPv6** all IPs are **public**
	- NAT exists because of the limitations of IPv4. It doesn't work with IPv6.
- Internet Gateway (IPv6) allows all IPs **IN** and **OUT**
- Egress-Only is **outbound-only** for IPv6

![[Egress-Only Internet Gateway.png]]

The architecture is the same as a normal IGW. It scales based on the traffic flowing through it. Attach it to the VPC. Then, add a default IPv6 route (::/0) & use the egress-only GW as a target to allow traffic to flow to the egress only internet gateway via the VPC router & beyond.

## VPC Endpoints (Gateway)
Two types of VPC endpoints - gateway endpoints & interface endpoints. They're used the same way, but for different AWS services, and, they achieve this functionally differently.

**Gateway Endpoints**
- Provide **private access** to **S3** and **DynamoDB**
	- Private in this context means: they allow a private-only resource inside a VPC, or any resource inside a private-only VPC to access S3 and DynamoDB (remember, both of these are public services). Normally when you want to access AWS public services from within a VPC, you need infrastructure & configuration. Usually an IGW attached to the VPC; grant resources inside that VPC a public IPv4 address, IPv6 address; or you need to implement 1 or more NAT GWs which allow instances with private addresses to access these public services. A gateway endpoint allows you to provide access to these services without implementing that public infrastructure.
- **Prefix List** added to **route table** => **Gateway Endpoint**
	- You create a gateway endpoint **per service**, **per region** (ex: S3 in us-east-1) and you **associate** it with one or more **subnets** in a particular VPC.
	- Gateway endpoints **don't go in VPC subnets**. When you allocate the gateway endpoint to particular subnets, a **prefix list** is **added** to the **route tables** for those subnets (by AWS on your behalf). This prefix list uses the **gateway endpoint** as a **target**.
		- (verbose) A prefix list is a logical entity (it's a VPC gateway object) on a route which represents these services. So, it represents S3 or DynamoDb. Imagine this is a list of IP addresses that those services use, but the list is kept updated by AWS. This prefix list is added to the route table, is used as the destination, and the target is the gateway endpoint. Any traffic destined for S3 as it exits these subnets goes via the gateway endpoint rather than the internet gateway.
- Highly Available (**HA**) across all AZS in a region by default
- Endpoint policy is used to control what it can access
	- Ex: You want to grant resources inside that VPC access to certain S3 buckets, but not the entire S3 service.
- Regional ... **can't access cross-region** services
(Use Case 1 Summary) Private VPC to access public resources (S3 (eg. software/app updates stored in S3)  / DynamoDb)) without allowing public access.

(Use Case 2):
- **Prevent Leaky Buckets** - **S3 Buckets** can be set to **private only** by allowing access ONLY from a gateway endpoint
	- Configure a bucket policy to only allow accept operations coming from a specific gateway endpoint. Because S3 is private by default, the implicit deny would apply. Resulting in a private only S3 bucket.

One limitation of gateway endpoints that you should be aware of for the exam is that they're **only accessible** from **inside** that **specific VPC**. (They're a logical gateway object and you can only access logical gateways created inside a VPC from that VPC).

**Without Gateway Endpoints**
![[Without Gateway Endpoints.png]]
Blue = private subnet; Green = public subnet.
Resources in the **public** subnets on the right can be given public IPv4 addresses and so access public space resources using those addresses through the **VPC router** via the **IGW** into the public space and then through to the public resource, S3 in this example.

**Private** instances can't do this They still go via the **VPC router**, but they need to use a **NAT GW** which provides them with a NATed public IPv4 address to use. This public address that's owned by the NAT GW is used via the **IGW** and finally through to the public resource, again S3.

The problem with this architecture is that the resources have public internet access, either directly for public resources or via the NAT gateway for private only EC2 instances. If you want instances inside the VPC to be able to access S3, but not the public internet then it's problematic. If you work in a heavily regulated industry and you need to create VPCs which are private only, with no internet connectivity, then that is almost impossible to do without using gateway endpoints.

**With Gateway Endpoints**
![[With Gateway Endpoints.png]]

Create a gateway endpoint inside a VPC. Associate it with one or more subnets. Prefix list is added to the route table for those subnets. Any traffic which leaves the private instances inside those subnets now has a route to the public service (via the gateway endpoint - and they won't need public addresses to talk to that service).

Note how this VPC has no IGW and no NAT GW. The private instance has no access to anything else outside the VPC, only S3. And that's only because we've created the gateway endpoint. We could even go one step further, using a bucket policy on the S3 bucket, and denying any access which doesn't come via the gateway endpoint.

## VPC Endpoints (Interface)
These do a similar job to gateway endpoints, but the way that they accomplish it is very different and you need to be aware of the difference.

- Provide **private access** to AWS Public Services
	- Private instances or instances which are in fully private VPCs
- historically.... anything **NOT S3** and **DDB**.. but S3 is now supported
	- // Currently, DynamoDb is only available using Gateway Endpoints.
- Added to specific subnets - an **ENI** - **not HA**
	- One subnet means one AZ. If that AZ fails, the functionality provided by the interface endpoint also fails.
- For HA .. add **one endpoint**, to **one subnet**, **per AZ** used in the VPC
- Network access controlled via **Security Groups**
- **Endpoint Policies** - restrict what can be done with the endpoint
- **TCP** and **IPv4** ONLY
- Uses **[[PrivateLink]]**
	- This is especially useful if you're in a heavily regulated industry, but you want to provide access to third-party services inside private VPCs.

Gateway endpoints used a prefix list - a logical representation of a service - added to route tables. That's how traffic flows to the gateway endpoint from VPC subnets.

Interface endpoints primarily use DNS. Interface endpoints adjust network interfaces inside your VPC. They have a private IP within the range which the subnet uses that they're placed inside.
- Endpoint provides a NEW service endpoint DNS name
	- that name can be used to directly access the service via the interface endpoint
- e.g. vpce-123-xyz.sns.us-east-1.vpce.amazonaws.com
	- example of a DNS name you might get for the SNS service inside the US East 1 region.
	- this name resolves to the private IP address of the interface endpoint
	- if you can update your applications to use this endpoint-specific DNS name, then you can directly use it to access the service via the interface endpoint and not require public IP addressing
Interface endpoints are actually given a number of DNS names.
- Endpoint **Regional DNS**
	- one single DNS name that works whatever AZ you're using to access the interface endpoint
	- good for simplicity and for high availability
- Endpoint **Zonal DNS**
	- each interface in each AZ gets a zonal DNS which resolves to that one specific interface in that one specific AZ
- Applications can optionally use these, or ...
- **PrivateDNS** **overrides** the **default DNS** for services
	- PrivateDNS associates a Route 53 private hosted zone with your VPC. This private hosted zone carries a replacement DNS record for the default service endpoint DNS name. It essentially overrides the default service DNS with a new version that points at your interface endpoint.
	- This option, which is now enabled by default, means that your applications can use interface endpoints without being modified.

Without using interface endpoints, accessing a service like SNS from within a VPC would work like this:
![[Without Interface Endpoints.png]]
The **instance** using SNS would **resolve** the default service endpoint (sns.us-east-1.amazonaws.com) to a public space IP address, and the traffic would be routed via the **VPC router**, then the **IGW**, out to the service.

Private instances would also attempt to do the same, but without having access to a public IP address, they wouldn't be able to get their traffic flow past the IGW, so it would fail.

If we add an interface endpoint:
![[With Interface Endpoint & PrivateDNS.png]]
If PrivateDNS isn't used, then services which continue to use the service default DNS would leave the VPC via the **IGW** and connect with the service in the normal way.

For services which choose to use the endpoint-specific DNS name, they would resolve that name to the interface endpoint's private IP address. The endpoint is a private interface to the service that it's configured for (In this case, SNS). So, the traffic could then flow via the interface endpoint to the service without requiring any public addressing. It's as though SNS has been injected into the VPC. It's being accessed in a more secure way.

If we utilize **PrivateDNS**, it makes it even easier. PrivateDNS **replaces** the service's **default DNS**. Even clients which haven't been reconfigured to use the endpoint specific DNS (so, they keep using the service default DNS name), will now go via the interface endpoint. So in this example, using PrivateDNS overrides the default SNS service endpoint name (sns.us-east-1.amazonaws.com). When you use PrivateDNS, rather than that resolving to a public IP address belonging to the SNS service, it's overridden & now resolves to the private IP address of the interface endpoint.

(summary) For the exam, remember:
- Gateway endpoints use prefix lists and route tables, so they never require changes to apps. Apps think they're communicating directly with S3 / DynamoDb & all we're doing by using a Gateway endpoint is influencing the route that that traffic flow uses. Instead of going via the internet gateway and requiring public IP addresses, it goes via a gateway endpoint and can use private IP addressing.
	- Gateway endpoints, because they're a VPC logical gateway object, they're highly available by design.
- Interface endpoint uses DNS and a private IP address for the interface endpoint. You have the option of either using the endpoint specific DNS names or you can enable private DNS which overrides the default and allows unmodified applications to access the services using the interface endpoint. Interface endpoints don't use routing, they use DNS. The DNS name is resolved, it resolves to the private IP address of the interface endpoint and that is used for connectivity with the service.
	- Interface endpoints, because they use normal VPC network interfaces, are not highly available. If you're utilizing multiple AZs, you need to put interface endpoints in every AZ you use in that VPC.

## VPC Peering
VPC Peering is a service that lets you create a private and encrypted network link between two VPCs.

- (**exam**) Direct encrypted network link between **two VPCs**
	- Two and only two VPCs. No more.
- Works **same**/**cross-region** and **same**/**cross-account**
- (**optional**) **Public Hostnames** resolve to **private IPs**
	- This means that you can use the same DNS names to locate services, whether they're in peered VPCs or not. If a VPC peer exists between one VPC and another, and this option is enabled, then if you attempt to resolve the public DNS hostname of an EC2 instance, it will resolve to the private IP address of that EC2 instance.
- **Same region SG's** can reference **peer SG's**
	- So, you can do the same efficient referencing and nesting of security groups that you can do if you're inside the same VPC. In different regions, you can still utilize security groups, but you'll need to reference IP addresses or IP ranges. If the VPC peers are in the same region, then you can do the logical referencing of an entire security group, and that massively improves the efficiency of the security of VPC peers.
- (**exam**) VPC Peering does **NOT** support **transitive peering**
	- If you have VPC **A** peered to VPC **B**, and VPC **B** peered to VPC **C**, that does not mean there's a connection between A & C.
		-  If you want VPC A, B, and C to all communicate with each other then you need a total of three peers: A->B, B->C, A->C.
- **Routing** Configuration is needed, **SGs** & **NACLs** can filter
	- When you create a VPC peering connection between two VPCs, you're creating a logical gateway object inside of both of those VPCs. To fully configure connectivity between those VPCs you need to configure routing.
		- **Route tables** with routes on them pointing at the **remote** VPC **IP address range**, using the VPC peering connection **gateway object** as the **target**.
		- You also need to make sure that traffic is allowed to flow between the two VPCs by configuring any **SG's** or **NACLs** as appropriate.

![[VPC Peering.png]]

When you create a VPC peering connection between two VPCs, you're creating a logical gateway object inside of both of those VPCs. We need to configure routing tables within each VPC and associate these with subnets. The remote VPC CIDR is the target. This would mean that the VPC router in VPC A would know to send traffic destined for the IP range of VPC B toward the VPC peering logical gateway object. That configuration would be needed on all subnets at both sides of all peering connections assuming we wanted to allow completely open communications.

(**exam**) The **IP address ranges** of the VPCs (the VPC **CIDRs**) **cannot overlap** if you want to create VPC peering connections.

You need 1 peering connection between each VPC which you want to communicate. Communications aren't transitive across multiple peering connections.

With VPC peering, any data that's transferred between VPCs is encrypted. If you're utilizing a cross region VPC peer, data transits over AWS's global secure network. You get secure transit and gain performance from using the global AWS transit network versus the public internet.

First, test lack of connectivity. Connect to EC2 instance A (using session manager). Ping EC2 B's ip address. See that it fails.
VPC > Peering Connections.

**Create VPCA-VPCB Peering Connection**
Create a peering connection (name = VPCA-VPCB; Requestor VPC ID = VPC A; Acceptor VPC ID = VPC B)).
Then, go to VPC A's Route Table (VPC > Route Tables) & add a route - Destination: VPC B's CIDR range, Target: VPCA-VPCB peering connection. Thee peering connection is created in Pending Acceptance status. Accept the peering connection.
**Configure Routing**
Needs to happen on both sides.
Go to VPC A's Route Table. Add route, Destination: VPC B's CIDR range, Target: VPCA-VPCB peering connection.
Go to VPC B's Route Table. Add route, Destination: VPC A's CIDR range, Target: VPCA-VPCB peering connection.

Ping from EC2 A to EC2 B is still failing. This is because security infrastructure is filtering the ping. by default, nACLs that are created generally don't filter any traffic unless you've configured them that way. Any filtering that applies is done by a security group.
**Configure Security Groups**
Check VPC A & VPC B's inbound & outbound rules. Remember, SG's are stateful (they remember the state of traffic). We need to update VPC B's SG inbound rules to allow ping traffic from VPC A. Because we're using VPC peers in the same region, we can logically reference SGs. We can use VPC A's SG's id. In VPC B SG's, create a new inbound rule to allow all ICMP IPv4 traffic, referencing VPC A's SG id. This apply to any instances which have this SG attached to them. Ping now works.

**Configure Security Groups** - use the same steps as above, but for B & C.

We can put SG A's CIDR range. From EC2 A instance, try to ping EC2 C. It fails.
